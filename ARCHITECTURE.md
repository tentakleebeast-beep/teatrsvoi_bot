## 1. Границы MVP

Входит:

| Модуль | Содержание |
|---|---|
| Идентификация | Регистрация по инвайт-коду, роли, личный кабинет |
| Заметки и файлы | Личная папка на едином Google-аккаунте театра, изоляция на уровне бота |
| Бюджет | Захват транзакций из свободного текста по регламенту, чтение/запись Google Sheets, учёт ручных правок |
| Занятость | Сбор занятости из чата в файл, сводное расписание, поиск окон |
| Календарь | Создание событий в общем Google Calendar (по подтверждению) |
| Уведомления | Напоминания о репетициях и взносах, дайджест орг.составу |
| Аудит | Append-only журнал всех изменений |

Не входит: групповые чаты, платёжные интеграции, парсинг банковских выписок, ONYX/DMX, билетные сервисы, субаренда, ПД/согласия (по решению заказчика — доверительная модель внутри труппы).

### Разделение ответственности

| Слой | Отвечает за | Не имеет права |
|---|---|---|
| `tg-gateway` | Telegram-транспорт, сессии, авторизация, кнопки, файлы | принимать решения о данных, писать в Google |
| `tool-api` | единственная точка чтения/записи данных, проверка прав, идемпотентность, аудит | вести диалог, вызывать LLM |
| `tool-api: router/agent` | разбор намерения, вызов LLM, композиция ответа — `services/tool-api/app/router_llm.py` | ходить в Google в обход своих инструментов, доверять LLM как источнику фактов |
| `scheduler` | отложенные задачи, реконсиляция, деградация | изменять данные в обход `tool-api` |
| Google | источник истины по деньгам и занятости (люди правят руками) | — |

Причина такого разреза: данных и прав касается только `tool-api`, поэтому визуально больше ничего не правится; LLM-слой `router_llm.py` меняется чаще контракта `tool-api`, поэтому живёт отдельным модулем, но внутри одного сервиса.

## 3. Поток обработки сообщения

1. `tg-gateway` получает update → нормализует в `message_event` (`chat_id`, `message_id`, `text`, `attachments`, `ts`).
2. Проверка: `participant.status = active`? роль для требуемого действия?
   - Нет → `/start`-сценарий (регистрация) либо вежливый отказ. Дальше ничего не идёт.
3. Идемпотентность: `(chat_id, message_id)` уже обработан → выход (защита от ретраев Telegram).
4. Вызов роутера в `tool-api`: `POST /tools/route` (каскад разбора) либо `POST /tools/agent/ask` (агентный режим) с контекстом:
   `{participant: {id, role, display_name}, session_id, text, allowed_tools[], correlation_id}`.
5. `tool-api`: роутер намерения → LLM (tool-calling) → вызовы своих инструментов → результат. Ответ роутера — `intent`, `category`, `answer`; пустой ответ означает «роутер не ответил», дальше работает ассистент.
6. `tool-api` на каждый вызов: проверка scope роли, запись в `tool_call_log` + `audit_event`, ответ с `source` (файл/лист/строка/дата).
7. Роутер возвращает боту **план действий**, а не готовый HTML:
   `{reply_text, buttons[], actions[]}` — бот исполняет (send, edit, ask_confirm).
8. Ответ уходит пользователю. Факты в тексте — только из `tool`-ответов (см. §5, ADR-4).

Таймауты gateway — 50 с на `router_ask`, 20 с на `agent_ask`, 25 с на `api` по умолчанию
(`services/tg-gateway/app/core.py:17,108,117`). Не уложились → пустой ответ роутера, работает ассистент и кнопки.

## 4. Стек и развёртывание

| Компонент | Выбор | Почему |
|---|---|---|
| Bot | Python 3.12, aiogram 3.x, webhook | зрелая экосистема, файлы/кнопки из коробки |
| API | FastAPI + pydantic v2 | контракт как код, OpenAPI для роутера, Mini App и внешних контуров |

| LLM | OpenRouter, модель с tool-calling | смена модели без правки кода |
| Google | service account + доступ к папке театра | без domain-wide delegation |
| Файлы | Google Drive (единый аккаунт) + локальный кэш на диске | по решению заказчика |
| Деплой | docker compose на одном VPS | MVP на 20 человек не требует большего |

## 5. Ключевые решения (ADR-lite)

**ADR-1. Единый Google-аккаунт, изоляция на уровне бота.**
Все папки `TG_<chat_id>` живут под одним аккаунтом театра. «Изоляция» — свойство `tool-api`: любой путь к файлу вычисляется как `folder_id(participant)`, никогда не принимается от LLM или пользователя. LLM не видит чужих `file_id`. Плюс: не нужен Workspace и OAuth на каждого. Минус: доступ к Drive у персонала театра = доступ ко всему → выдать отдельную учётку без прав на корень либо ограничить правами папки.

**ADR-2. `tool-api` — единственный вход к данным.**
Посредников между ботом и данными нет: в Postgres и Sheets пишет только `tool-api`, LLM-слой живёт внутри него. Иначе права и аудит можно обойти, а сценарии станут непроверяемыми.

**ADR-3. Google Sheets = источник истины по деньгам и занятости; Postgres = индекс, аудит, состояние.**
Люди правят файлы руками, поэтому зеркало в БД вторично. Всегда «прочитать перед записью», сопоставление по `tx_id`, а не по номеру строки. Ночная реконсиляция.

**ADR-4. Факт существует, только если он есть в tool-ответе.**
Каждый tool возвращает `{value, source: {file, sheet, row, fetched_at}}`. Пост-валидатор в `tool-api` проверяет: числа, даты и имена в ответе должны присутствовать в tool-результатах, иначе ответ переписывается в «нет проверенных данных» (см. `docs/architecture/05` §4). Требование «не галлюцинировать» реализуется кодом, не промптом.

**ADR-5. Запись бюджета — append-only + подтверждение для неоднозначного.**
Транзакции не редактируются на месте: изменение = новая строка `rev` + ссылка `replaces`. Отмена — компенсирующая запись.

**ADR-6. Детерминированные вычисления — в Python, не в LLM.**
Поиск окон, суммы, задолженности, дедупликация — код. LLM формулирует и уточняет, но не считает.

**ADR-7. Сессия = `chat_id` (личный чат), память — в БД, окно N последних сообщений.**

## 6. Отказоустойчивость и деградация

| Отказ | Поведение |
|---|---|
| LLM/роутер недоступен | роутер возвращает пустой ответ — работает ассистент и кнопки; интент-независимые команды работают: `/notes`, `/schedule`, `/balance` (только чтение), регистрация |
| LLM недоступен / лимит | тот же режим; в `dead_letter` кладётся задача с текстом, при восстановлении — предложение «повторить» |
| Google API 429/5xx | ретрай с backoff (3 попытки), затем «данные временно недоступны», ничего не пишем |
| Google-файл изменён вручную во время записи | повторное чтение, проверка хэша листа, при конфликте — отказ + уведомление админу |
| Двойной ретрай Telegram | идемпотентность по `(chat_id, message_id)` и по `idempotency_key` в `tool-api` |
| Процесс упал посреди записи | запись в Sheets идёт после фиксации `pending` в БД → при старте worker доигрывает по журналу |

Минимальный набор «простых сценариев» без LLM (по требованию заказчика) — только команды из таблицы выше, без парсинга свободного текста.

## 7. Безопасность

- Whitelist: неактивный `chat_id` не получает ничего, кроме `/start`.
- Инвайт-коды: одноразовые, TTL 7 дней, привязаны к роли, выпуск — только admin, логируются.
- Сервисный токен `tool-api`: бот и другие контуры ходят только с заголовком `Authorization` (токен из `.env`).
- Секреты — в `.env` / docker secrets, не в коде и не в манифестах в открытом виде.
- Доступ к бюджету: персональные долги видит только сам участник и орг.состав; сводные цифры — орг.состав.
- Аудит неизменяем (только INSERT, доступ на чтение — admin).

## 8.1 Дополнения v1.1 (после уточнений заказчика)

**ADR-1 (доп.). Общие папки — единственный экземпляр данных.**
Помимо личных `TG_<chat_id>` существует корень `_shared`:

```
_shared/
  budget/        ← файл бюджета (источник истины по деньгам)
  schedule/      ← файл занятости (источник истины по доступности)
  media/         ← фото/видео, афиши, реквизит
  notes/         ← общие заметки труппы
```

Правила:
- Данные **не дублируются** в личные папки. Личная папка — только личное (свои заметки, свои файлы ролей).
- Чтение `_shared` — все роли (troupe, student видят пьесы, расписание площадки, медиа).
- Запись в `_shared/budget` и `_shared/schedule` — только `org`/`admin`; в `_shared/notes` — `org` (личные заметки остаются личными).
- В БД хранится только индекс (`file_object.drive_file_id`, `scope='shared'`), содержимое не копируется. Один экземпляр файла — ноль расхождений.
- Пути вычисляются из `SHARED_ROOT_ID`, а не принимаются от пользователя или LLM.

**ADR-3 (доп.). Проверка свежести индекса перед ответом.**
Ночной реконсиляции недостаточно: человек может поправить бюджет в 12:00, а вопрос придёт в 12:01. Поэтому **read-through**:

1. Перед любым ответом, основанным на файле, `tool-api` запрашивает метаданные (`files.get` с `fields=modifiedTime`, для Sheets — `properties.lastEditTime`).
2. Сравнивает с `budget_sync_state.last_read_at`.
3. Файл новее → **перечитывает лист, обновляет индекс**, и только потом отвечает.
4. Файл не новее → отвечает из индекса (быстрый путь).
5. Расхождение структуры (заголовки) → отказ от ответа с пометкой «данные в файле изменились, нужна проверка» и алерт админу.

Стоимость: один лёгкий вызов метаданных на запрос (не полное чтение). Кэш метаданных — 30 секунд, чтобы не бить API при серии вопросов.

**ADR-8. Транспорт Telegram — aiogram, не Telegram Trigger в n8n.**
Подробно: `docs/infrastructure/08-infrastructure.md`. Кратко: long polling и локально, и на VPS (публичный HTTPS не нужен); webhook — задача после релиза. n8n-воркфлоу при переезде не меняются. Telegram Trigger отклонён: падение внешнего оркестратора убивало бота целиком, логика вне git, FSM и файлы в нодах неудобны.

Историческая пометка: n8n выведен из контура (V-026, 01.11.2026), история — `docs/archive/29-n8n-scenarios.md`.

**ADR-9. Postgres с первого дня, один контур разработки и эксплуатации.**
SQLite в скелете был компромиссом ради 5-минутного smoke-теста; для проекта это лишний шаг миграции. Принято: `postgres:16` в docker с самого начала, схема из `docs/architecture/01-data-model.md` применяется как есть. Dev и prod отличаются хостом и содержимым `.env` — не движком БД.

**ADR-10. Один бот, одно дерево Drive, созданное с нуля.**
Боевой bot token используется и в разработке (бот зарегистрирован, поллеров на токене нет). Данных, которые можно испортить, нет: папки `SVOI/_shared/*`, таблицы бюджета и занятости, календарь `SVOI` создаются пустыми под проект (`docs/infrastructure/09-google-setup.md`). Поэтому отдельный dev-бот и dev-копии файлов не нужны — нужен только аккуратный смоук-тест перед выкладкой. При появлении реальных данных правило меняется: dev получает копию файлов.

**Зафиксированные параметры (v1.1):**

| Параметр | Значение |
|---|---|
| Часовой пояс | Самара, UTC+4 (`TZ_OFFSET_HOURS=4`, Europe/Samara) |
| Тихие часы | 20:00 → 08:00 следующего дня |
| Регистрация орг.состава | свой инвайт-код с ролью `org`, доступ проверяется по RBAC |
| Наполнение таблицы участников | автоматически ботом при регистрации по коду |

Порога «второе подтверждение траты» нет: решение 30.10.2026 — расход и доход пишутся сразу,
любой суммы, второго подтверждающего не существует (`docs/architecture/25` §4).

## 9. Открытые вопросы (нужны до старта P2/P3)

1. Реальный состав файла занятости (колонки, формат дат, кто такой «участник») — нужен образец, чтобы написать адаптер.
2. Структура файла бюджета: листы, есть ли `Свод` на формулах, есть ли id у строк.
3. Справочник категорий расходов и правило, что считать взносом/пожертвованием.
4. Порог суммы, выше которого запись требует второго подтверждения — снят 30.10.2026: порога нет, крупные суммы пишутся сразу (`docs/architecture/25` §4).
5. Соответствие ФИО в файлах ↔ Telegram-аккаунт (нужна таблица алиасов + кто её ведёт).
6. Кто входит в орг.состав (для матрицы прав) и нужен ли им доступ к аудиту.
