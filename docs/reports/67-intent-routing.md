# 67. Разбор намерения: почему бюджет перехватывал назначение и что с этим делать

Дата: 28.10.2026. Повод: фраза «назначь репетицию с Витей в четверг в 20» приводила к
«Вижу сумму 20 ₽. Это расход или доход?».

---

## 1. Причина (найдена в коде, не гипотеза)

`services/tg-gateway/app/routing.py`, функция `candidates()`:

```python
names = [name for name, rx in _COMPILED if rx.search(low)]
if DIGIT_RE.search(low) and "budget" not in names:
    names.insert(1, "budget")      # ← любая цифра = деньги
```

и порядок правил, где `budget` стоял **раньше** `assign`:

```python
("availability", AVAIL_WORDS), ("budget", BUDGET_WORDS), ... ("assign", ASSIGN_Q)
```

То есть «20» в конце фразы превращало назначение в трату 20 ₽, и до правила `assign`
дело не доходило. Вторая точка той же ошибки — `on_text`: ветка
`if re.search(BUDGET_WORDS) or re.search(r"\d")` срабатывала раньше вызова роутера.

Это не «модель не поняла». Это две строки эвристики: цифра считалась признаком денег,
а «назначь» не имело приоритета.

## 2. Что исправлено сейчас (детерминированно)

1. `assign` стоит в списке правил **перед** `budget`.
2. Цифра включает бюджет только если это не время и не назначение:
   `TIME_LIKE = в 20 / 20:00 / после 20`, плюс проверка `assign`.
3. В `on_text` фраза с глаголом назначения не заходит в бюджетную ветку вообще.
4. Тесты: «назначь репетицию с Витей в четверг в 20» → `assign`, `budget` отсутствует;
   «3000 на реквизит» и «потратили 12000» → по-прежнему бюджет.

Проверено: unit + integration зелёные, ruff чист.

## 3. Стоит ли отдавать первичный разбор намерения модели

Коротко: **да, но не вместо правил, а как арбитр для спорных фраз.** Аргументы по фактам
этого проекта.

### За
- Правила живут регулярками: `BUDGET_WORDS`, `ASSIGN_Q`, `SLOTS_Q`, `SCHEDULE_Q`. Каждое
  новое слово («перенеси», «отмени», «подбери») — правка кода и релиз. Модель с закрытым
  списком намерений покрывает формулировки без правок.
- Уже есть WF-01 (`n8n/workflows/wf-01-router.json`) и `router_ask()` в гейтвее: инфраструктура
  для «спросить модель про интент» существует, её не надо строить.
- Спорных фраз немного. По логам `intent_log` видно, что большинство сообщений однозначны;
  модель нужна на пересечениях (цифра + действие, «занят» + дата, «окна» + имена).

### Против (и как это учесть)
- **Задержка.** Вызов n8n → OpenRouter — это 0.6–2 с. На каждое сообщение unacceptable,
  на спорное — нормально.
- **Деньги и квоты.** В проекте есть `llm_usage` и лимит; при исчерпании бот обязан
  работать дальше на правилах (это уже заявлено в `docs/development/21`).
- **Детерминизм.** Категории бюджета нельзя выбирать «на глаз»: каскад уже требует
  закрытого списка и порога 0.7. Для интентов правило то же: модель выбирает **только**
  из `[budget, availability, assign, slots, schedule, money, list_people, about_me, howto, dues, feedback]`.

### Предлагаемый контракт (следующий шаг)

```
POST /webhook/router
{ "text": "...", "user": {...}, "intents": ["budget", "assign", ...] }
→ { "ok": true, "intent": "assign", "confidence": 0.86, "slots": {"who": ["витя"], "when": "четверг", "hour": 20} }
```

Правило вызова: спрашивать модель **только если** `len(candidates(text)) >= 2`
или если правила не дали ни одного кандидата, а текст похож на команду.
Остальное решают правила — бесплатно и мгновенно.

Порог: `confidence < 0.7` → уточняющий вопрос кнопками («Это расход или назначение?»),
а не догадка. Ответ модели логируется в `intent_log` вместе с тем, что решили правила, —
тогда видно, где модель ошибается, и порог можно двигать по факту, а не по вкусу.

### Что это даст по коду
Уйдут `TIME_LIKE`, часть `BUDGET_WORDS`-эвристик и вторая проверка в `on_text`; останется
один вход «текст → интент» с явным контрактом. Но **не сейчас**: пока нет живой квоты
и логов за неделю, включать модель на все сообщения — значит менять предсказуемость
на неизвестную точность без измерений.

## 4. Итог

Причина была не в модели, а в двух эвристиках; они исправлены и покрыты тестами.
LLM-арбитр для спорных фраз — правильное следующее улучшение, и инфраструктура для него
уже есть; включать его нужно с порогом, закрытым списком и логом решений.
