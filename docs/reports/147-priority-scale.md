# 147. Шкала P0/P1/P2 для требований дополнений 27.10: таблица на утверждение

Дата: 09.11.2026. Карта `t_a01970bf` (V-044). Основание — решение владельца 08.11.2026:
шкалу проставить, но список сначала показать на утверждение. Документ 19 на этом шаге

## 1. Что и зачем

В `docs/development/19-functional-requirements.md` 113 требований. У 89 из них класс
`P0`/`P1`/`P2` стоит в третьей колонке основной таблицы, у 24 — нет: это две таблицы
«Дополнения от 27.10.2026» (стр. 199–237), где третьей колонкой идёт статус, а приоритет
не задан ни классом, ни словом. Из-за этого процентный критерий смоука (`docs/development/143`
§3.2, §7) не может посчитать эти строки: они не попадают ни в один класс.

Слова «высокий», «средний», «низкий» стоят не в документе 19, а в документе
`docs/development/55-requirements-review.md` §2 — ревью, из которого дополнения и выросли.
Оттуда они и взяты в колонку «сейчас словами»; у 12 из 24 требований нет и слова.

## 2. Сколько строк на самом деле: 24, а не 25

V-044 в реестре вопросов и `docs/development/143` §3.2 называют **25** строк. Замер по
действующему файлу даёт **24**. Числа и команда, которой они получены:

```
grep -cE '^\| FR-' docs/development/19-functional-requirements.md          # 113 строк, 113 ID, дублей нет
grep -E '^\| FR-' docs/development/19-functional-requirements.md \
  | awk -F'|' '$4 !~ /^ *P[012] *$/ {c++} END {print c+0}'                 # 24 строки без класса
```

| Факт | Число |
|---|---:|
| Строк требований в документе 19 | 113 |
| Из них с классом `P0`/`P1`/`P2` | 89 (P0 — 48, P1 — 34, P2 — 7) |
| Без класса — попадают в эту таблицу | 24 |
| В `docs/development/143` §3.2 записано с классом | 88 (P0 — 47, P1 — 34, P2 — 7) |
| Отсюда «25» в V-044 и 143 | 113 − 88 |

Расхождение — ровно одна строка P0. Какая именно строка посчитана в 143 иначе, по файлу
не восстановить: история документа в этой ветке — один коммит импорта, сравнивать не с чем.
Поэтому таблица строится по машине (24), а не по прозе (25). Если владелец ждёт 25 —
нужно назвать недостающий ID: вторая шкала на уже размеченное требование не появится
ни при каком ответе (см. §5).

## 3. Правило, по которому предложены классы

Формулировки — из карточки и документа 19:

- **P0** — без этого основной сценарий не работает или даёт неверный результат, а обход
  дороже ошибки (деньги, доступ, сервис целиком).
- **P1** — сценарий выполняется, но с ручным обходом: правка в Google-таблице или календаре,
  SQL, отдельное сообщение человеку. Требование нужно в первые недели.
- **P2** — удобство и оформление: без него результат тот же, обход не нужен.

Класс ставится по последствию отсутствия, а не по статусу в документе 19: «готово» —
это факт реализации, а не мера важности.

1. В двух таблицах дополнений документа 19 появляется колонка «Приоритет» — 24 значения
   из §4, формулировки требований и статусы не правятся.
2. Знаменатели критерия в `docs/development/143` §7 пересчитываются из источника, а не
   переносятся прозой: P0 — 50 из 50, P1 — 49, P2 — 14 (48 + 2, 34 + 15, 7 + 7; сумма 113).

   от знаменателя, иначе следующая правка снова разойдётся с документом 19.
