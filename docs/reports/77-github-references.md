## 2. Что берём по каждому

1. **ravebot** — событие создаётся командой со ссылкой, карточка события обновляется
   по расписанию, новый участник обязан представиться за 90 минут, иначе удаляется.
   Нам полезно: жёсткий вход в сообщество одним правилом и автоподдержка закреплённого
   сообщения. Не берём: автоудаление людей — у нас pending-люди живут до прода без уведомлений.
2. **volunteer-telegram-bot** — испытательный срок новичка (3 участия за 3 месяца),
   автоматический перевод в активные, помесячная обработка статусов, создание события
   мастером из нескольких шагов с задачами. Нам полезно: связка «участие → статус
   участника» считается правилом, а не руками; это прямой аналог наших ролей и взносов.
3. **mitup** — RSVP, лист ожидания, напоминания в часовом поясе каждого участника,
   бот живёт только в личке. Нам полезно: лист ожидания как штатная часть записи на событие
   и персональные напоминания вместо общего «через час».
4. **sport-event-bot** — русскоязычный, мастер создания события с календарём, вступление
   и выход одним нажатием, уведомление автору о вступлении, отметка активных и неактивных
   по истории группы. Нам полезно: тексты и тон кнопок на русском, а также признак
   неактивности — кандидат в «После релиза».
5. **crowd-events-bot** — участник отвечает на пост, бот в личке задаёт три вопроса,
   публикует карточку с голосованием, дайджест пересобирается каждые 10 минут.
   Нам полезно: свободный текст в группе не разбирается, ввод идёт мастером в личке, а
   публикация — отдельный шаг. Это ровно логика Ш-52 «команда для ввода, диалог для анализа».
6. **sola-bot** — платформа эксплуатации группы: бот, Admin API, веб-панель, Mini App,
   воркер, права по модулям, миграции SQL, Docker Compose. Нам полезно: разделение на
   процессы и гранулярные права — подтверждение, что наш контур tool-api + gateway +
   Mini App выбран в ту же сторону, и что права стоит держать по модулям, а не по ролям целиком.
7. **community_bot** — запись на мероприятия с ограниченными местами: сначала те, кого не
   было в прошлый раз, остальные случайно, есть запасной список и автоматический подъём
   из резерва при отказе. Нам полезно: правило «приоритет тому, кто давно не был» — сильный
   кандидат для занятости и спектаклей; у нас пока только «кто первый».
8. **financebot** — расходы по фото чека, PostgreSQL 16, Redis, Docker, лимиты бюджета с
   алертами, выгрузка в Excel. Нам полезно: подтверждение стека (Postgres с первого дня,
   Docker) и формата «лимит по категории + алерт», что близко к нашей панели «Бюджет».
9. **easy-peasy-spendee-bot** — Telegram остаётся быстрым вводом, Google Sheets — источником
   правды: строка пишется только после подтверждения, спорная сумма уходит на проверку,
   есть защита от дублей, правка и удаление пишутся обратно в ту же строку, есть сверка
   листа с вводом. Нам полезно: это наш сценарий «лист ↔ БД» с чужого опыта — подтверждение
   перед записью, дедупликация и обратная правка строки по идентификатору.
10. **aiogram_bot_template** — самый заметный шаблон стека aiogram 3 + PostgreSQL +
   SQLAlchemy + alembic: слои, репозитории, DI, миграции, тесты. Нам полезно как эталон
   структуры проекта; ничего не переносим, у нас своя структура и свои инварианты.

## 3. Выводы для проекта

- **Мастер ввода вместо свободного текста** — общий приём у 2, 4, 5: данные вводятся
  пошагово, а группа и личка используются по назначению. Совпадает с Ш-52.
- **Лист ожидания и приоритет** (3, 7) — единственная механика, которой у нас нет, а для
  занятости она полезна. Записано в «После релиза», не блокер.
- **Права по модулям** (6) — наш `require(...)` уже таков; пересматривать не нужно.
- **Подтверждение и дедупликация при записи в лист** (9) — у нас уже есть в Ш-04/Ш-26,
  референс подтверждает подход.
- Ни один референс не закрывает нашу двустороннюю совместимость целиком: у 9 лист
  первичен, у нас первичны оба, сверка по ID операции — наше отличие, а не отставание.

## 4. Как проверялось

Метаданные — `curl https://api.github.com/repos/<owner>/<repo>` (звёзды, лицензия, язык,
дата push, archived = false у всех десяти). Описания возможностей — README репозиториев.
Репозитории с `archived = true`, без README или без отношения к сообществам в список не
включены.
