# 113. Модели и бюджеты агента: дешёвый классификатор, исполнитель по замеру, лимит на чат

Карта: `t_340bc27b` (A-4). Класс: product + cost. Источник: план агентного режима
01.11.2026, делается по цифрам карты A-0 (`docs/reports/112`).

**Зачем.** Агентный цикл — несколько вызовов модели на одно сообщение. До этой карты
модель выбиралась переменной окружения, цены и лимиты не были записаны нигде, а
повторяющиеся вопросы («какое сегодня число», «кто сегодня занят») каждый раз стоили
токенов. Здесь три вещи становятся измеримыми: какая модель в какой роли, сколько
стоит 1000 сообщений и сколько вправе потратить один чат за сутки.

## 1. Что сделано

| Артефакт | Что это |
|---|---|
| `config/agent-models.yaml` | роли `agent`/`classifier` с обоснованием, дневной бюджет чата, TTL кэша по группам, цены провайдера и курс с источником |
| `services/tool-api/app/agently/models.py` | чтение конфига с кэшем по времени изменения; приоритет «окружение → файл → умолчание»; битый файл не роняет сервис |
| `services/tool-api/app/agently/budget.py` | дневной бюджет чата: шаги и токены из `intent_log`, граница суток по Самаре |
| `services/tool-api/app/agently/cache.py` | кэш повторяющихся ответов с малым TTL, без карточек подтверждения |
| `db/init/052_agent_cache_source.sql` | источник `cache` в `intent_log`: попадание в кэш видно в журнале и не выглядит как ответ модели |
| `scripts/agent_cost.py` | счёт стоимости 1000 сообщений по сохранённому замеру A-0, `--check` сверяет цифры отчёта с прогоном |
| `docs/reports/113-agent-cost.json` | машинные цифры того же счёта: по ним идёт `--check` |
| `services/tool-api/app/api/agent_ask.py` | порядок проверок: кэш → квота человека → бюджет чата → ключ → цикл → деградация |

Настройки меняются в конфиге, без правки кода: роль, модель, лимит шагов, дневной
бюджет, TTL кэша и цены. Файл читается при обращении — правка действует со следующего
запроса, перезапуск не нужен.

## 2. Выбор модели по замеру A-0, а не по цене

Замер (`docs/reports/112`, 30 вопросов × 3 модели × 2 режима, прогон 01.11.2026).
Колонка «цена» здесь пересчитана в рубли по курсу ЦБ 02.11.2026 (см. §3), остальные
цифры — из отчёта A-0.

| модель | режим | адекватно | `tool` | неверно | p95, с | ₽/1000 |
|---|---|---|---|---|---|---|
| openai/gpt-4.1-nano | single | 17% | 0/16 | 20% | 4,3 | 1,49 |
| openai/gpt-4.1-nano | agent | 50% | 8/16 | 33% | 6,5 | 10,16 |
| openai/gpt-4o-mini | single | 13% | 0/16 | 10% | 1,9 | 2,38 |
| **openai/gpt-4o-mini** | **agent** | **57%** | **11/16** | **13%** | **5,5** | **14,59** |
| openai/gpt-4o | single | 13% | 0/16 | 10% | 2,2 | 38,94 |
| openai/gpt-4o | agent | 53% | 10/16 | 23% | 5,3 | 242,92 |

Решение записано в конфиг:

| Роль | Модель | Обоснование цифрами |
|---|---|---|
| `agent` (с инструментами) | `openai/gpt-4o-mini`, лимит 4 шага | лучший класс `tool` (11/16), меньше всех неверных (13%), p95 5,5 с, 14,59 ₽/1000. `gpt-4o` дороже в 16,7 раза и хуже на `tool` (10/16) |
| `classifier` (без инструментов) | `openai/gpt-4.1-nano` | дешёвая: 1,49 ₽/1000 в одиночном вызове против 2,38 ₽ у 4o-mini. Роль — одно слово сценария, инструменты и факты ей не нужны |

Почему не «самая дешёвая везде»: у `gpt-4.1-nano` в цикле 33% неверных ответов против
13% у 4o-mini. Для бота это дороже денег: за выдуманную сумму бюджета отвечает человек
(A-0 §4, п.3). Классификатору же врать негде — он выбирает из четырёх слов.

## 3. Стоимость 1000 сообщений: посчитано, а не оценено

Формула (`scripts/agent_cost.py`):

```
$/сообщение = (токенов_вход × цена_вход + токенов_выход × цена_выход) / 1 000 000
₽/1000      = $/сообщение × 1000 × курс
```

Токены — измеренные провайдером в замере A-0 (`tokens_in`/`tokens_out` у каждого из
30 ответов), средние по всем 30 вопросам, а не по удачному. Цены — OpenRouter на
01.11.2026, курс — ЦБ РФ на 02.11.2026 (80,5573 ₽/$), оба значения лежат в
`config/agent-models.yaml` с источником.

| модель | режим | токенов вход | токенов выход | $/1000 | ₽/1000 |
|---|---|---|---|---|---|
| openai/gpt-4.1-nano | single | 121,5 | 16,0 | 0,0185 | **1,49** |
| openai/gpt-4.1-nano | agent | 1113,1 | 37,1 | 0,1262 | **10,16** |
| openai/gpt-4o-mini | single | 121,5 | 18,9 | 0,0295 | **2,38** |
| openai/gpt-4o-mini | agent | 1043,9 | 40,8 | 0,1811 | **14,59** |
| openai/gpt-4o | single | 121,5 | 18,0 | 0,4834 | **38,94** |
| openai/gpt-4o | agent | 1051,3 | 38,7 | 3,0155 | **242,92** |
| openai/gpt-4.1-nano | assistant | 1203,6 | 40,7 | 0,1367 | **11,01** |
| openai/gpt-4o-mini | assistant | 1134,4 | 44,4 | 0,1916 | **15,44** |
| openai/gpt-4o | assistant | 1141,8 | 42,3 | 3,026 | **243,77** |

Что из этого следует:

* **инструменты стоят в 6 раз дороже одиночного вызова** (14,59 ₽ против 2,38 ₽ у
  4o-mini) — это плата за факты вместо догадок: на классе `tool` одиночный вызов даёт
  0/16, цикл — 11/16;
* **1000 сообщений в боевом режиме — 14,59 ₽**, то есть около 1,5 копейки за сообщение;
  при 300 сообщениях в месяц это ≈ 4,4 ₽; расход никогда не «непредсказуемый» —
  он ограничен бюджетом чата (§4);
* **комбинация «классификатор + исполнитель»** измерена 04.11.2026: классификатор
  (`openai/gpt-4.1-nano`) стоит 0,85 ₽ за 1000 сообщений (90,5 входных / 3,6 выходных
  токена, p95 2,61 с), поэтому режим `assistant` у 4o-mini — 15,44 ₽ против 14,59 ₽
  у чистого `agent`, то есть +0,85 ₽ (+5,8%); строки `assistant` есть для всех трёх
  моделей, а замер лежит в `docs/reports/113-classifier-run-04.11.2026.json`.

## 4. Бюджет чата: шаги и токены в сутки

Считается по журналу разбора `intent_log` (A-5): у каждой агентной сессии там
`agent_status`, `step_count` и `tokens`. Отдельной таблицы нет намеренно — второй
счётчик неизбежно разошёлся бы с первым.

| Предел | Значение | Откуда цифра |
|---|---|---|
| токенов в сутки на чат | 60 000 | 1085 токенов на сообщение в замере → ≈ 55 сообщений |
| шагов в сутки на чат | 100 | 1,9 шага на сообщение в замере → ≈ 52 сообщения |

Оба предела срабатывают почти одновременно, поэтому ни один не маскирует другой;
это проверяется тестом (`tests/unit/test_agent_models.py`). Границы суток — по Самаре,
а не по UTC. Ответы из кэша бюджет не тратят: у них `tokens = 0`, `step_count = 0`.

При исчерпании человек получает **ответ по правилам** (`engine: "rules"`,
`degraded.reason: chat_tokens|chat_steps`, HTTP 200) и одну строку
«Дальше — по кнопкам.» — без ошибки и без «Думаю…». Дата в ответе берётся из
`core.now()`, а не из модели. Gateway (`menu.visible_answer`) для этих двух причин
ничего не дописывает: модель доступна, исчерпан лимит разговора, и внутренний код
человеку не показывается. Пояснение «Модель сейчас недоступна» остаётся только для
настоящих отказов провайдера (`llm_unavailable`, `provider_timeout`, `token_budget`,
`llm_error`).

Если gateway не передал `chat_id`, бюджет считается по человеку; если нет и его —
не применяется (иначе один запрос без области блокировал бы всех).

## 5. Кэш повторяющихся ответов

Кэшируются только вопросы из групп конфига — те, у которых ответ живёт секунды:

| Группа | TTL | Примеры |
|---|---|---|
| `date` | 30 с | «который час», «сколько времени» |
| `availability` | 60 с | «кто сегодня занят», «кто свободен», «занятость на сегодня» |
| всё остальное | не кэшируется | «сколько расходов в октябре», «мои взносы» |

Что до агента не доходит и почему это не потеря:

* **Дата** («какое сегодня число», «какой сегодня день») отвечает gateway из календаря
  проекта до вызова модели (`menu.py::asks_today`). Это не кэш, а ещё дешевле —
  ноль вызовов модели и ноль токенов; кэш для этих формулировок просто не нужен.
  Группа `date` покрывает остальные вопросы о времени («который час»), они идут к агенту.
* **Занятость.** Вопрос «кто сегодня занят» — это вопрос, а не ввод своих данных:
  правило `availability_q` в `routing.py` пропускает его к агенту (инструмент
  `read_availability`), и повтор в течение 60 секунд берётся из кэша. Ввод «занят
  28.10 с 10 до 14» по-прежнему уходит в форму, а не к модели. До исправления
  `AVAIL_WORDS` ловил вопрос раньше агента, и повторный вопрос каждый раз шёл
  к модели — группа `availability` была мёртвой (возврат ревью 02.11.2026).

Почему не «кэш на всё»: бюджет, взносы и расписание меняются, и кэш на минуту
показал бы вчерашнюю цифру как сегодняшнюю. Ответ с карточкой подтверждения
(`propose`) не кэшируется никогда — иначе человек нажал бы кнопку по старому черновику.

Ключ — чат (иначе человек) + нормализованный текст: «Кто сегодня занят?» и
«кто сегодня занят» — один вопрос, а чужой чат ответа не получает. Попадание
пишется в журнал `intent_log` источником `cache`: по журналу видно, сколько ответов
пришло без модели. Экран разбора (`api/admin.py::agent_sessions`) источник пока
не отдаёт — это отдельная карточка Mini App, в этой карте не делалась. Кэш живёт
в памяти процесса: перезапуск его очищает, при нескольких воркерах каждый кэширует
сам — цена этого решения ниже, чем у общего хранилища с блокировками и инвалидацией.

## 6. Деградация

Порядок проверок в `/tools/agent/ask`: кэш → квота человека → бюджет чата →
ключ провайдера → цикл. Если провайдер недоступен, ответил таймаут или кончился
бюджет токенов на запрос — ответ по правилам с причиной в `degraded.reason`
(`llm_unavailable`, `provider_timeout`, `token_budget`, `chat_tokens`, `chat_steps`).
Человек не ждёт «Думаю…»: ответ приходит сразу и без выдуманных чисел.

```
# стоимость 1000 сообщений и сверка с цифрами этого отчёта

    --json docs/reports/113-classifier-run-04.11.2026.json

# тесты карты
env -u PYTHONPATH .venv/bin/python -m pytest -p no:warnings -o addopts="" -q \
    tests/unit/test_agent_models.py tests/unit/test_agent_cache.py \
    tests/unit/test_agent_budget.py tests/unit/test_agent_cost.py \
    tests/integration/test_agent_ask.py
```

Критерии приёмки карты и чем они закрыты:

| Критерий | Чем подтверждён |
|---|---|
| записаны цифры: доля адекватных, p95, цена | §2 (замер A-0 + пересчёт ₽/1000) |
| исчерпан бюджет чата → короткий ответ по правилам, без ошибки | `test_исчерпанный_бюджет_чата_отвечает_по_правилам_с_подсказкой`, `test_исчерпанные_шаги_закрывают_бюджет`, `test_исчерпанный_бюджет_не_даёт_ложной_строки_и_внутреннего_кода`, `test_исчерпанные_шаги_не_дают_ложной_строки` |
| один вопрос дважды в пределах TTL → второй из кэша | `test_повторный_вопрос_идёт_из_кэша`, `test_попадание_в_кэш_видно_в_журнале`; вопрос о занятости доходит до агента — `test_ш52_вопрос_не_включает_ввод_данных` |
| стоимость 1000 сообщений посчитана | §3, `--check`, `test_цифры_отчёта_воспроизводятся_из_замера` |
| провайдер недоступен → деградация к правилам | `test_без_ключа_отвечают_правила_с_датой`, `test_сбой_провайдера_даёт_ответ_по_правилам` |

## 8. Ограничения (честно)

* **Один прогон на вопрос.** Разброс замера A-0 неизвестен (50–63% при повторе);
  цена от разброса не зависит — токены усреднены по 30 ответам.
* **Цена — по тарифу OpenRouter на 01.11.2026.** Смена тарифа меняет только колонку
  ₽/1000, качество — нет; цены лежат в конфиге, а не в коде.
* **Кэш в памяти процесса.** При нескольких воркерах доля попаданий ниже, чем в
  одном процессе, и перезапуск её обнуляет. Это осознанный размен: общий кэш потребовал
  бы хранилища и инвалидации по записи.
* **Бюджет считает только агентные сессии** (`agent_status is not null`). Расход
  старого каскада интентов в него не входит — у него нет ни шагов, ни модели.
* **Кэш не участвует в вопросах о дате**: «какое сегодня число» отвечает gateway
  до агента из календаря, то есть без вызова модели. Это дешевле кэша и потому
  оставлено как есть; экономия на таких вопросах достигается не кэшем, а тем, что
  модель не вызывается вовсе.
