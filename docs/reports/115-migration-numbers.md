Порядок применения — сортировка по имени файла, поэтому пара с одним номером встаёт
в алфавитном порядке на чистой базе (`tests/conftest.py`, `docker-entrypoint-initdb.d`,
`server-deploy.sh db`) и в порядке появления файлов в истории на проде. Пока файлы пары
независимы, расхождение безвредно; как только один ссылается на другой, схемы расходятся
молча, а гейт зелёный. Метрика `migration_duplicates = 2` стояла в
`docs/reports/111-arch-drift-2026-11-02.md` и не краснела нигде: `arch_drift.py` — отчёт,
а не гейт, а проверки уникальности номеров в гейте не было.

## Как учитывается «применено» (до переименования)

Журнала применённых миграций в проекте **нет** — ни `schema_migrations`, ни таблицы с
именами файлов. `migration_marker` (019) — метка разового сброса данных, а не история.

Что есть вместо журнала:

1. `deploy/server-deploy.sh cmd_db` — при `db --migrate` (и при `db` без `--restore`)
   прогоняет **все** `db/init/*.sql` подряд в алфавитном порядке с `ON_ERROR_STOP=1`.
   Повторный прогон — норма: файлы идемпотентны (`create table if not exists`,
   `insert ... where not exists`, `create or replace function`, `drop trigger if exists`).
2. `deploy/check_schema.py` (шаги `verify`/`schema`, выкат `.github/workflows/deploy.yml`)
   выводит «применено ли» **из схемы**: сравнивает `information_schema` с множеством
   `create table if not exists` / `alter table ... add column if not exists` по всем файлам
   `db/init`. Имя файла в отчёте — подсказка, куда смотреть, а не ключ учёта.
3. `tests/conftest.py` — на каждую сессию создаёт `svoi_test_<pid>` и накатывает все файлы
   `sorted(glob)`.

Следствие: переименование файла не может «потерять» применённую миграцию — записей о
применении нет. Проверять надо не историю, а **идемпотентность** (сохранена: содержимое
файлов не менялось) и **порядок** на чистой базе.

## Что сделано

1. **Перенумерованы вторые файлы пар** (второй = появившийся позже):

   | Было | Стало |
   |---|---|
   | `046_income_misc_category.sql` | `053_income_misc_category.sql` |
   | `047_folder_roots.sql` | `054_folder_roots.sql` |

   Содержимое миграций не менялось: только номер в шапке и строка «перенумеровано с …».
   Оба файла уехали **в конец** (053, 054), а не в середину, чтобы не сдвигать порядок
   уже применённых миграций. Номера проверены по всем ветками и worktree
   (`git ls-tree` по `refs/heads` + `refs/remotes`): максимум — 052, поэтому 053 и 054
   свободны и пропусков не появилось.

   Зависимости проверены до переноса: `053` — один `insert into category ... where not
   exists`, зависимостей нет; `054` зависит от `folder` (создана в `046_files_folders.sql`,
   остаётся на месте) и `project` (001), а от `054` не зависит ни один файл 048–052
   (`grep` по `folder`, `ensure_shared_folder`, `project_folder_autocreate` — совпадений
   нет). `do`-блок «уже существующие проекты» теперь отрабатывает последним и накрывает
   всё, что создали предыдущие миграции.

2. **Проверка в гейте** — `scripts/check_registers.py`, функция `check_migrations()`:
   номер в начале имени уникален, имя обязано быть `NNN_имя.sql`, пустой каталог — ошибка.
   Вызывается из `check()`, то есть краснеет в том же прогоне, что и реестры, и в
   `test_настоящие_реестры_чистые` (CI). Пропуски номеров намеренно оставлены в
   `arch_drift.py`: у пропуска бывает задокументированная причина (018), а дубль — дефект
   без исключений.

3. **Тесты** — `tests/unit/test_registers.py`, шесть новых: дубль краснит, уникальные
   проходят, имя без номера ловится, пустой каталог ловится, `check()` включает проверку
   миграций, реальный `db/init` без дублей.

4. **Ссылка в документации**: `docs/development/86-files-and-storage.md` (Ш-6) теперь
   указывает на `db/init/054_folder_roots.sql`.
