# Секреты в индексе и истории: прогон gitleaks

**Дата:** 06.11.2026. **Карта:** `t_16e70a41` (ШАГ Ш-01 плана 129). **Основание:**
`docs/plans/129-public-repo-plan.md` §Ш-01, решения Ш-00 (B — сжатая история, B + C —
обезличивание и удаление дампов).

**Короткий ответ:** реальных секретов нет ни в рабочем дереве, ни в истории. Прогон по
дереву даёт две находки, прогон по истории — четыре, и все они одного корня: маска `***` в
CI-команде и имя ключа миграции в SQL. Две «исторические» — те же совпадения в старых
редакциях файлов (`.github/workflows/tests.yml` правился дважды, `db/init/016…sql` — один
раз), ещё одна появилась от первой редакции этого отчёта, где строка миграции была
процитирована дословно, и осталась в коммите `9f17cdec` (в текущем дереве её нет). Значения
в отчёт не переносятся: сырой JSON gitleaks содержит поля `Match`/`Secret` и потому в
репозиторий не кладётся, здесь только «файл:строка:правило».

## 1. Как проверяли

| Что | Команда | Объём | Находок |
|---|---|---|---|
| Рабочее дерево | `gitleaks dir . --no-banner -f json -r <вне репозитория>` | 18,87 МБ; в индексе 924 файла | 2 |
| История всех веток | `gitleaks git . --log-opts=--all --no-banner -f json -r <вне репозитория>` | 647 коммитов (на момент прогона), 11,84 МБ | 4 |

Числа сняты на ветке карты, сведённой с `main` 06.11.2026 (в `main` уже влиты Ш-03 и Ш-07).
Обе величины — «на момент прогона» и меняются с каждым новым коммитом в `main`; важно не
число, а правило: новых типов совпадений не появляется.

Прогон повторён после того, как цитата SQL в этом отчёте переписана словами: по дереву
находок по-прежнему две, по истории — четыре (третья осталась в коммите с первой редакцией
отчёта, четвёртая — старый вид `tests.yml` из коммита Ш-03). Объём дерева в повторном
прогоне больше первого (8,91 МБ), потому что gitleaks считает и рабочие файлы вне индекса,
а не только отслеживаемые.

Версия инструмента: `gitleaks 8.30.1` (Homebrew bottle, установлен 06.11.2026). Правила —
встроенный набор gitleaks, свой конфиг не применялся. Сырые отчёты лежали в каталоге
scratch вне репозитория и после снятия строк ниже удалены; в git они не попадали.

Прогон по истории сделан потому, что решение B публикует текущее дерево одним коммитом:
если бы в истории что-то было, это всё равно не попало бы в публикацию, но знать факт
нужно до флипа, чтобы закрыть чек-лист Ш-08 честно, а не «по идее».

- Публичное зеркало (решение B — один коммит) содержит два совпадения — №1 и №2 из таблицы.
  Именно их и покажет secret scanning после публикации: это ожидаемо и не утечка. Находки №3
  и №4 остались в истории до публикации (коммиты `9f17cdec` и `d100ad3`) и в публикуемое
  дерево не входят.
- Если алерты мешают шуму, их закрывают файлом `.gitleaksignore` (пути с отпечатками).
  На шаге Ш-01 файлы не правятся — карта не создаёт конфиг; это отдельная работа, если
  владелец решит её завести.
- Проверка перед флипом по-прежнему нужна: `gitleaks` чист по публикуемому дереву
  (решение B — историю не публикуем, по ней проверка справочная).
