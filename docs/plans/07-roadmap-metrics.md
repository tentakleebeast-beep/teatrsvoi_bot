## 1. Фазы

### P0 — фундамент (1–2 недели)
Бот отвечает, регистрация по коду, роли, `participant`/`session`, аудит, `tool-api` скелет, docker compose, n8n локально с WF-00/WF-01/WF-09.
**Готово, когда:** новый человек регистрируется сам, чужой `chat_id` не получает доступа, аудит пишется, все действия видны в `/audit`.

### P1 — заметки и файлы (1 неделя)
Личная папка `TG_<chat_id>`, заметки (.md в Drive), загрузка/чтение/выдача файлов, общая папка `_shared` только на чтение.
**Готово, когда:** актёр сохраняет заметку и файл, другой актёр не может получить к ним доступ ни через бота, ни через подбор `file_id`.

### P2 — бюджет: захват и чтение (2–3 недели) ← **ядро проекта**
Контракт листа, `budget-rules.yaml`, `parse`/`commit`, подтверждение, дедупликация, реконсиляция, `budget/query`, отметка взносов, аудит `before/after`.
**Готово, когда:** 20 реальных сообщений о тратах разобраны без ручных правок (≥95%), ручная правка в файле не ломает бота, ночная сверка даёт 0 ложных расхождений.

### P3 — занятость и окна (2 недели)
Адаптер файла занятости, сбор занятости из чата, сводка, покрытие, детерминированный поиск окон top-3.
**Готово, когда:** орг-состав получает 3 валидных окна на реальный запрос за <10 с, покрытие занятости ≥ 70%.

### P4 — календарь и уведомления (1–2 недели)
Создание событий по подтверждению, напоминания T−24/T−2, `schedule_change`, `payment_due`, дайджест, тихие часы, дедупликация.
**Готово, когда:** ни одного пропущенного или задвоенного напоминания за 2 недели.

### P5 — дальше
Аналитика по категориям/проектам, «сколько стоит спектакль», авто-предложения репетиций, опрос доступности рассылкой, парсинг выписок, платёжные ссылки. Затем Векторы Б (ONYX/DMX) и В (билеты, субаренда).

Порядок неслучаен: P2 даёт деньги (главная боль), P3 — время заказчика. Векторы Б/В — только после 2 месяцев стабильной работы P0–P4.

## 2. Метрики успеха MVP

### Главная (продуктовая)
**Время заказчика на операционную рутину (бюджет + расписание) сокращается на ≥ 50%.**
Измерение: 2 недели «до» (дневник вручную) vs 4 недели «после» (опрос раз в неделю, 3 вопроса).

### Бюджет
| Метрика | Цель |
|---|---|
| Доля транзакций, внесённых через бота (от всех за месяц) | ≥ 80% |
| Точность разбора: сообщения, принятые кнопкой «Записать» без правки полей | ≥ 95% |
| Двойные записи | 0 |
| Ложные категории, обнаруженные при реконсиляции | < 2% строк |
| Задержка «потратил → строка в файле» | < 30 с (медиана) |
| Расхождения зеркала и файла на утро | 0 необъяснённых |

### Расписание
| Метрика | Цель |
|---|---|
| Покрытие занятости (`coverage_pct`, участники с актуальными данными) | ≥ 80% |
| Предложения окон, принятые без пересчёта | ≥ 90% |
| Доля событий, созданных через бота (от всех новых в календаре) | ≥ 90% |
| Запросов «а когда у нас репетиция?» к заказчику в мессенджерах | ↓ 80% |

### Надёжность и доверие
| Метрика | Цель |
|---|---|
| Ответы с непроверенными фактами (факт-валидатор отбросил) | < 1% от всех |
| Жалобы «бот сказал не то про деньги» | 0 |
| Аптайм `tool-api` | ≥ 99% в месяц |
| Пропущенные/задвоенные уведомления | 0 |
| Время реакции на сообщение (медиана / p95) | 3 с / 12 с |

### Стоимость
| Метрика | Цель |
|---|---|
| LLM-расходы на участника в месяц | ≤ 100 ₽ |
| Доля запросов, обслуженных без LLM (простые команды) | ≥ 30% |
| Инфраструктура (VPS + Google) | ≤ 1 500 ₽/мес |

### Адопшн (через месяц после P4)
- ≥ 80% участников хотя бы раз сообщили занятость боту.
- ≥ 70% орг-состава пользуются бюджет-функциями еженедельно.
- ≥ 50% уведомлений получают реакцию (кнопка/ответ).

## 3. Риски

| Риск | Влияние | Смягчение |
|---|---|---|
| Ручные правки ломают контракт листа | Высокое | сверка заголовков при старте, стоп вместо записи, алерт админу |
| Люди не хотят вводить занятость | Высокое | максимально короткие формы, кнопки в напоминаниях, метрика покрытия видна org |
| LLM путает категории | Среднее | детерминированный словарь приоритетнее LLM, подтверждение перед записью |
| Один Google-аккаунт = общий доступ к Drive | Среднее | отдельная учётка без прав на корень, доступ только к папке театра |
| Утечка `chat_id`/пересылка сообщений | Среднее | права проверяются по `participant`, доверительная модель принята заказчиком |
| n8n как точка отказа | Среднее | деградация к простым командам, dead-letter, мониторинг |
| Рост сложности n8n-воркфлоу | Среднее | стабильный контракт `tool-api`, версионирование промптов, тесты контрактов |
| Стоимость LLM при активной труппе | Низкое | лимиты на пользователя/сутки, кэш ответов на типовые вопросы |
| Заказчик — единственный, кто знает «как надо» | Высокое | этот пакет документов как контракт; открытые вопросы закрыть до P2/P3 |
