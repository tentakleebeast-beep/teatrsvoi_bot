## 1. Что решаем

Сейчас развитие идёт заходами: Виктор формулирует задачу → агент делает шаг →
проверки → коммит. Поток ограничен вниманием одного человека и последователен
по построению.

Цель: несколько независимых работ идут параллельно, каждая — в своём рабочем
каталоге, с критериями приёмки, обязательным ревью и следом в базе.

**Чего это не делает:** не увеличивает скорость принятия решений. Узкое место —
ревью-ёмкость владельца, поэтому параллелизм начинается с одной карты и растёт
только по метрикам (раздел 6).

---

## 2. Почему канбан Hermes, а не «команда ботов» Bot Forge

Bot Forge создаёт профили с чатом, рутинами и отдельным launchd-гейтвеем. Для
разработки это неверная абстракция: нет изоляции каталогов, атомарного захвата
задачи, ревью-гейта и следа «кто что делал».

Встроенный `hermes kanban` даёт именно нужное:

| Свойство | Что это значит на практике |
|---|---|
| Durable SQLite | карта переживает перезапуск, история ходов сохраняется |
| Изоляция | `--workspace worktree --branch wt/<id>`: воркер работает в своём worktree |
| Атомарный захват | одна карта не уйдёт двум исполнителям; `max_in_progress_per_profile` |
| Жизненный цикл | `ready → running → review → done / blocked`, плюс `triage` |
| Ревью-гейт | `kanban_request_review` спавнит назначенный профиль с бандл-скиллом `sdlc-review` |
| PR-контракт | `--completion-contract` не даёт закрыть карту без проверок PR |
| Диспетчер | живёт в гейтвее (`kanban.dispatch_in_gateway: true`), отдельных сервисов не нужно |

Bot Forge остаётся для личных ботов (дежурный по проду, разбор почты). Разработка
ведётся доской.

## 3. Доска и роли

**Доска:** `teatrsvoi`, default-workdir — каталог проекта.
`hermes kanban boards switch teatrsvoi` для работы в ней по умолчанию.

| Профиль | Роль | Инструменты | Что запрещено |
|---|---|---|---|
| `orchestrator` | разбирает цель на карты, линкует зависимости, назначает | только `kanban` | кодить (нет terminal/file) |
| `worker-feature` | одна карта = одна фича: код, тесты, PR | terminal, file, code_execution, github, kanban | merge в main |
| `worker-integrity` | рефакторинг, мёртвый код, доки, CI | те же | merge в main |
| `reviewer` | approve / request_changes | kanban, github, file (чтение) | реализовывать |
| `feedback` | разбор обращений, карты на дефекты | read-only к прод-БД, `scripts/feedback_queue.py` | писать в прод |

До фазы 1 исполнителем выступает `default` — это позволяет проверить механику,
не создавая профилей.

## 4. Классы работ

| Класс | Что входит | Кто берёт |
|---|---|---|
| `safe` | доки, тесты, мёртвый код, тексты интерфейса, UI-полировка по чеклисту, хардненинг CI | воркеры, свободно |
| `careful` | новые эндпоинты, поведение Mini App, n8n-воркфлоу, конфиг линтеров | воркер + обязательное ревью |
| `manual-only` | миграции `db/init`, деньги и доли, права и роли, деплой на прод, `.env`, токены | только Виктор |

Правило: класс пишется в тело карты первой строкой. Ревьюер блокирует карту
класса `manual-only`, если её взял воркер.

## 5. Шаблон карты

Заголовок: `<ID из бэклога>. <что сделать>` (ID из `72`, `74`, `79` или номер
обращения).

Тело карты:

```text
Класс: safe | careful | manual-only
Область: services/tool-api | bot | docs | deploy | tests
Источник: docs/reports/72 (Ш-NN) | обращение №NN | V-NNN

Зачем: одна-две строки.

Критерии приёмки (Given/When/Then):
- Given ..., when ..., then ...

Проверки (обязательны все):
- env -u PYTHONPATH .venv/bin/python -m pytest -p no:warnings -o addopts="" -q
- .venv/bin/ruff check .
- env -u PYTHONPATH .venv/bin/python scripts/check_invariants.py
- env -u PYTHONPATH .venv/bin/python scripts/check_registers.py

Границы: что менять нельзя (миграции, деньги, .env). Коммит — один на карту,
сообщение с ID.

Отчёт: комментарий в карте — что сделано, хеш коммита, номера тестов.
```

Команды создания:

```bash
hermes kanban create "<ID>. <заголовок>" \
  --body-file card.md --priority high \
  --workspace worktree --branch wt/<id>-<slug> \
  --completion-contract local-only \
  --max-runtime 45m --max-retries 2
```

`local-only` — потому что required checks GitHub на приватном репозитории
бесплатного плана недоступны (проверено: `403 Upgrade to GitHub Pro`). Пока
контракт локальный, ревьюер обязан сам вызвать `gh pr checks`. После перехода на
GitHub Pro/Team контракт меняется на `OWNER/REPO`.

## 8. Ограничения и риски

1. **Один репозиторий.** Worktree спасает файлы, но не семантические конфликты.
   `db/init`, `docs/` (сквозная нумерация), общие роутеры — не более одной карты
   в этих областях одновременно.
2. **Приватный репозиторий без branch protection.** Required checks недоступны,
   контракт локальный, проверку PR делает ревьюер.
3. **Токены.** Воркеры наследуют модель профиля-родителя (тот же ключ OpenRouter,
   лимит уже упирался в `402`). Дорогие модели — только на картах с явным
   `--model`.
4. **Ревью-ёмкость.** Больше двух карт в работе = очередь к владельцу, а не
   ускорение.
5. **Прод.** Воркеры не получают доступ к прод-БД на запись и к `.env` с
   прод-токеном; локальный запуск — только с dev-ботом (инцидент 30.10,
   «После релиза»).

## 9. Что не делаем

- Не запускаем двух воркеров в одном worktree.
- Не даём воркерам merge в `main` — только PR.
- Не создаём 6–8 профилей «на будущее».
- Не ставим рутины чаще 30 минут: работа событийная, воркер спавнится под карту.
- Не включаем `swarm` до фазы 3.
