# 44. Что даёт Google Calendar, а что придётся держать у себя

> **n8n выведен из контура (V-026, 01.11.2026).** Где ниже n8n назван частью контура или
> источником разбора свободного текста, читать: `POST /tools/route` в tool-api
> (`services/tool-api/app/router_llm.py`); воркфлоу, публичный вебхук и переменные `N8N_*`
> удалены из деплоя. История контрактов — `docs/archive/29-n8n-scenarios.md`.

Дата: 27.10.2026. Анализ возможностей Calendar API применительно к нашей задаче:
какие правила можно жить в календаре, а какие обязаны быть в коде и настройках бота.

Короткий вывод: **календарь — это события и занятость зала, но не люди и не правила.**
Люди, роли, время в пути и строгость поиска остаются в нашей базе.

---

## 1. Что календарь умеет

| Возможность | Что даёт | Годится нам |
|---|---|---|
| Создание и правка событий (`events.insert/patch`) | полный CRUD | да, запись — только в черновой календарь |
| `colorId` события (11 цветов) | визуальный тип события | да, это наша палитра |
| `summary` / `description` | текст, маска «Тип - Название» | да, но это текст, а не данные |
| `extendedProperties.private/shared` | до 50 пар «ключ-значение» на событие | да, единственный способ хранить машинные данные |
| `attendees` | участники по email | **нет**: у нас люди из Telegram, email нет |
| `reminders.overrides` | напоминания на событие | частично: дублирует нашу очередь |
| `recurrence` (RRULE) | повторяющиеся серии | да, но читать нужно мастер-события |
| `transparency` (busy/free) | влияет на занятость | да, для зала |
| `freebusy` API | занятые интервалы календаря | да, для проверки зала |
| `watch` + push-каналы | уведомления об изменениях | позже: нужен HTTPS и продление канала |
| `calendarList` | список календарей и их цвета | ограниченно: у service account пуст |
| Квоты | ~1 млн запросов в день, 600 в минуту на пользователя | нам хватает с запасом |

### Чего календарь не умеет принципиально

1. **Занятость по часам на человека** — нет такого объекта. `attendees` — только email,
   а «свободен с 19:00» в календарь не записать.
2. **Несколько ролей у человека** — нет понятия роли.
3. **Состояние «не уверен»** — событие либо есть, либо нет.
4. **Время в пути** — нет и не будет.
5. **Строгость события** — обязательные/факультативные участники не различаются.
6. **Цена ошибки** — календарь не знает, что для показа нельзя опаздывать.

## 2. Что переносим в календарь

| Данные | Как хранить |
|---|---|
| Событие: репетиция, показ, тренинг, аренда | обычное событие, `summary` по маске «Тип - Название» |
| Тип события | `colorId` по палитре + тип в начале `summary` |
| Название и проект | `summary` (текст для людей) |
| Машинные данные (id людей, проект, тип) | `extendedProperties.private` |
| Занятость зала | само событие + `transparency='opaque'` |
| Повторяемость | `recurrence` (RRULE), читать мастер-события |

Правила записи (уже действуют, `config/calendar-rules.yaml`):

- маска `"Тип - Название"`, типы: Аренда, Репетиция, Тренинг, Показ, Служебное;
- события до полуночи ставить до `23:55`;
- локации и описания не заполнять — они не используются;
- запись только в `CALENDAR_ID_DRAFT`, чтение из `CALENDAR_ID_READ`.

Дополнить правилами: в `extendedProperties` писать `svoi_kind`, `svoi_project_id`,
`svoi_participant_ids`. Тогда бот читает событие и сразу знает, кого оно блокирует,
не разбирая текст.

## 3. Что остаётся в коде и настройках

| Что | Где | Почему не в календаре |
|---|---|---|
| Занятость по часам | `availability_hour` (БД) | календарь не умеет «свободен с 19:00» |
| Время в пути | `participant.travel_minutes` | свойство человека, не события |
| Роли и псевдонимы | `person_alias` | в календаре нет людей |
| Строгость поиска | `app/window_policy.py` | правило алгоритма, а не данные |
| Палитра | `config/calendar-palette.yaml` | отображение, а не смысл |
| Маска названий | `config/calendar-rules.yaml` | соглашение, живёт рядом с парсером |
| Тихие часы | `.env` / `notification_pref` | настройки эксплуатации |

Принцип: **календарь хранит «что и когда», наша база — «кто и как».**

## 4. Что можно реализовать через календарь

### 4.1. Блокировка занятости событиями (следующий шаг)

```
событие в календаре с extendedProperties.svoi_participant_ids
        │
        ▼
при поиске окон: часы события вычитаются из свободного времени этих людей
```

Это закрывает дыру: сейчас показ 5 декабря не мешает боту предлагать репетицию
на этот вечер.

### 4.2. Проверка зала

`freebusy` для календаря зала даёт занятые интервалы. Для аренды это и есть
главный фильтр: «зал свободен 5 декабря с 18 до 22».

Ограничение: у service account нет своего `calendarList`, поэтому запрос
делается по конкретному `calendarId`, который у нас уже есть в `.env`.

### 4.3. Запись занятости на неделю

После того как человек отметил занятость, можно создавать в черновом календаре
не события, а **служебные блоки** «занят» — но это спорно: 7 дней × N людей
дают сотни событий. Пока не делаем; вместо этого занятость живёт в БД.

### 4.4. Уведомления об изменениях (позже)

`watch`-канал на боевой календарь → n8n получает пуш «событие изменилось» →
tool-api пересчитывает затронутые дни. Требует: HTTPS-домен, продление канала
каждые ~7 дней, обработка `sync`-токенов. Отложено до прода.

## 5. Ограничения, о которых нужно помнить

1. **Service account не создаёт файлы** Google Sheets/Docs и не загружает файлы
   (квота 0). Создавать события в календаре может — это отдельное право.
2. **`singleEvents=true` теряет регулярность**: серия разворачивается в экземпляры,
   у них нет `recurrence`. Для анализа правил читать с `singleEvents=false`.
3. **Цвет календаря** (не события) service account не видит: `calendarList` пуст.
   Красить можно только события через `colorId`.
4. **Приглашения участникам** уходят с email — у нас их нет, поэтому `attendees`
   не используем: люди узнают о событии через бота.
5. **Квоты на запись**: пачка событий в цикле может упереться в лимит.
   Писать батчами и с задержкой, ошибки складывать в `import_row`.
6. **Часовой пояс**: события создаём в `Europe/Samara` (UTC+4); не полагаться
   на часовой пояс сервера.

## 6. Итоговая схема ответственности

```
GOOGLE CALENDAR          наша БД                 код и настройки
─────────────────        ─────────────────       ──────────────────────
события                  люди и роли             правила поиска окон
тип (colorId)            занятость по часам      строгость по типу события
повторяемость            время в пути            дорога и сдвиги
extendedProperties       сверка, аудит           тихие часы, настройки
занятость зала           бюджет                  маска названий, палитра
```

Правило на будущее: **если данные нужны алгоритму — они живут в базе;
если людям для просмотра — можно в календаре.** Дублировать одно и то же
в двух местах нельзя: разойдётся, и мы снова будем сверять вручную.

## 7. Что сделать в ближайшее время

| Шаг | Зачем | Оценка |
|---|---|---|
| Писать `extendedProperties` при создании событий | чтобы события знали своих участников | 2 часа |
| Читать события из `CALENDAR_ID_READ` при поиске окон | блокировать занятых в показе | 1 день |
| `freebusy` для проверки зала в аренде | аренда перестанет быть «слепой» | полдня |
| Разбор `RRULE` для регулярных репетиций | не разворачивать серии вручную | 2 часа |
| Watch-канал на боевой календарь | реакция на правки в календаре | после прода |
