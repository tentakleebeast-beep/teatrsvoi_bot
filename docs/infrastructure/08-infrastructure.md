## 0. Поправка к предыдущему обсуждению

Ранее я написал, что Telegram Trigger в n8n удобнее, потому что «не нужен публичный HTTPS». **Это неверно как аргумент**: aiogram тоже умеет long polling и тоже не требует HTTPS. Публичный HTTPS нужен только для **webhook**-режима — и это отдельная ось, не связанная с выбором «aiogram или n8n».

Три независимых вопроса, которые я ранее смешал в один:

| Ось | Варианты | Что требуется |
|---|---|---|
| Кто потребляет апдейты Telegram | aiogram **или** Telegram Trigger в n8n | ровно один потребитель на bot token |
| Способ доставки апдейтов | long polling / webhook | polling — ничего; webhook — публичный HTTPS |
| Кто исполняет сценарии | n8n (всегда) | внутренний HTTP между сервисами |

Комбинации: `aiogram+polling` (локально), `aiogram+webhook` (VPS), `n8n Trigger+polling` (тоже работает везде). Выбор — не про HTTPS, а про то, где живёт логика бота.

## 1. Решение по транспорту (ADR-8)

**Принято: aiogram как транспорт, long polling локально → webhook на VPS. n8n — только сценарии, вызываемые по внутреннему HTTP.**

Почему не Telegram Trigger в n8n:

1. **Деградация.** n8n лёг — бот мёртв целиком, включая `/start`, регистрацию и простые команды. С aiogram бот отвечает без n8n (режим из `docs/architecture/05` §5).
2. **Версионирование.** Логику в git можно ревьюить и тестировать; воркфлоу n8n — только визуально и вручную.
3. **Состояние и файлы.** FSM регистрации, приём `.docx` с ролями, выдача файлов — в aiogram это десяток строк, в нодах — набор HTTP-костылей.
4. **Один бот = один поток исполнений.** При Telegram Trigger каждое сообщение — исполнение воркфлоу; при 20 активных людях это шум в истории n8n и лишняя нагрузка на единственную точку.
5. Переезд не усложняется: см. §4, меняется одна переменная окружения.

Плата за решение: ещё один сервис (≈200 строк) и необходимость дисциплины «бот не ходит в Google и Postgres».

### Правило, которое нельзя нарушать
**Один bot token — один потребитель.** Если где-то уже запущен поллер на боевой токен (старый бот, чужой сервис, второй n8n), наш aiogram получит `409 Conflict` и апдейты будут теряться у обоих. Перед первым запуском это надо проверить (см. §6, вопрос 1).

## 1a. Две среды: dev и prod (01.11.2026)

Почему появилось: 30.10.2026 локальный гейтвей поднялся на **боевом** токене из `.env`,
перехватил `getUpdates` у сервера, выдал 1457 ошибок `TelegramConflictError` — и бот
молчал четыре часа. Причина не в коде бота, а в окружении: локальный запуск и прод
читали один и тот же файл. Теперь среда — явный параметр, и dev физически не видит
прод-токен.

| Что | dev (мак разработчика) | prod (сервер) |
|---|---|---|
| Файл окружения | `.env.dev` (в git не попадает) | `/opt/svoi/.env` |
| Токен бота | `DEV_BOT_TOKEN` — отдельный бот «СВОИ dev» | `TELEGRAM_TOKEN` — боевой бот |
| `TELEGRAM_TOKEN` в dev-процессе | подставляется из `DEV_BOT_TOKEN` | берётся из боевого конфига |
| База | локальный `postgres:16` (127.0.0.1:5433) | Postgres на сервере |
| Google-файлы | нет вовсе (в `.env.dev` нет `GOOGLE_SA_*`, `DRIVE_*`, `*_SPREADSHEET_ID`, `CALENDAR_ID_*`) | боевые файлы театра |
| Запуск | `scripts/run_service.py <сервис>` — `--env dev` по умолчанию | юнит systemd (`EnvironmentFile=/opt/svoi/.env`) |
| launchd-агенты | `com.svoi.gateway`, `com.svoi.tool-api` с `--env dev`, сторож `com.svoi.conflicts` (раз в 5 минут) | не используются |

`deploy/svoi.env` — **не** файл окружения сервиса: это настройки выката (`SVOI_DOMAIN`,
`SVOI_ROOT`, …), токенов в нём нет и быть не должно (docs/infrastructure/75 §5.5).

### Команды

```bash
cp .env.dev.example .env.dev && chmod 600 .env.dev   # один раз; вписать DEV_BOT_TOKEN
.venv/bin/python scripts/run_service.py gateway --check   # среда, маска бота, БД — без запуска
.venv/bin/python scripts/run_service.py gateway           # dev, по умолчанию
.venv/bin/python scripts/run_service.py gateway --env prod   # только на сервере
python scripts/install_launchd.py --doctor                     # агенты совпадают с шаблонами
```

Каждый запуск печатает строку вида
`run_service: среда=dev файл=.../.env.dev бот=***9216 бд=127.0.0.1:5433/svoi` — по логу
видно, на каком боте и какой базе поднялся сервис. Полного токена в логе нет.

### Guard-ы (проверяются кодом, а не дисциплиной)

1. **Нет `DEV_BOT_TOKEN`** → запуск не начинается: «среда разработки не настроена».
   Прод-токен не подставляется никогда, даже если он лежит рядом в `.env`.
2. **Основной `.env` в dev-режиме не читается вообще** — ни гейтвеем, ни tool-api.
3. **БД должна быть локальной.** `DATABASE_URL` на удалённый хост в dev-режиме —
   отказ: прогон на боевой базе это запись в живые данные театра.
4. **Прод-токен читается только в ветке `--env prod`** — статическая проверка
   `scripts/check_invariants.py` (§ «Среды») падает, если `TELEGRAM_TOKEN` появится в
   локальном коде или если launchd-агент поднимет сервис не с `--env dev`.
   Тесты: `tests/unit/test_run_service_env.py`, `tests/unit/test_dev_env_isolation.py`.

### Один замок на машину

Замок одиночного экземпляра (`~/.local/state/svoi/tg-gateway.lock`, Ш-28) общий для
сред: на одной машине одновременно живёт один поллер. Если локальный боевой гейтвей
ещё работает, dev-гейтвей откажется стартовать — это защита, а не ошибка. Для отладки
рядом с боевым поллером замок переопределяется явно:

```bash
SVOI_GATEWAY_LOCK=$TMPDIR/dev-gateway.lock .venv/bin/python scripts/run_service.py gateway
```

Разные токены дают разные боты (`getMe`: dev — `@teatrsvoi_testbot`, prod —
`@teartsvoi_bot`), поэтому два поллера на одной машине не конфликтуют: 409 бывает
только на одном и том же токене.

### Прогоны тестов и скриптов

`pytest` поднимает отдельную базу `svoi_test_<pid>` от `DATABASE_URL` (по умолчанию —
локальный 5433) и удаляет её после прогона (`tests/conftest.py`). Боевые данные не
читаются и не пишутся: в dev-окружении на них просто нет ни строки подключения, ни
идентификаторов файлов. Скрипты, которым нужен бот (`scripts/notify_admin.py`), шлют
через dev-бота.

### Данные: dev — стенд, prod — боевые

Решение владельца (05.11.2026, комментарий к карте `t_9c33a525`): «оставь чистое
состояние для тестирования, данные будем обслуживать на проде».

**Правило.** dev-база — стенд. Факты театра (деньги, люди, обращения, журналы) в dev
не переносятся и не восстанавливаются; источник боевых данных — прод. Чего в dev
нет — это не очередь на починку, а состояние стенда; «чинить» пустые факты подгонкой
сумм или правкой вьюх нельзя.

**Следствие.** Числа в dev не обязаны совпадать с прод. На 05.11.2026 `v_balance` в dev
даёт −479 509 ₽, в прод-зеркале было −167 509 ₽ — расхождение ожидаемое, а не дефект.

Что на dev есть и чего намеренно нет:

| Что | Состояние |
|---|---|
| Словари из `db/init` | есть |
| `budget_period` (5), `category`, `project` (5) | есть — восстановлены картой `t_03cc04e9` |
| `participant` (25), `budget_tx` (95) | есть — факты, перенесённые той же картой |
| `dues_charge`, `person_alias`, `slot_proposal`, `notification`, `invite_code`, `invite_attempt`, `feedback`, `feedback_answer`, `audit_event`, `participant_discipline`, `article_map`, `participant_capability_override`, `approval_request`, `category_candidate`, `llm_usage`, `intent_log` — 16 таблиц | намеренно пусто: заполняется только прогонами dev-бота, API и Mini App |

Отдельной строкой: ненулевые сейчас `audit_event` (22), `llm_usage` (12), `intent_log` (13)
и `person_alias` (1) — это следы dev-прогонов, а не история театра. `dues_charge` пуст,
поэтому взносы в dev нулевые и баланс уходит в −479 509 ₽.

Когда нужный факт на dev всё же нужен для проверки, его создают тем же путём, что в
проде: dev-бот, Mini App, API. Для кода регистрации это `POST /admin/invite` (право
`registration.code.issue`, `services/tool-api/app/api/admin.py`). Копирование строк из
дампа — не способ: словари собираются заново и получают другие суррогатные `id`, ссылки
рвутся (разбор — `docs/reports/135-dev-transfer-data-loss.md`).

Дамп `~/.hermes/cache/scratch/dev-db-before-wave-20261105.dump` — архив среза dev-базы
05.11.2026 03:32. Разворачивать его можно только в отдельную базу для сравнения, не в
рабочую dev. Любая заливка в dev — новое решение владельца, а не техническая мелочь.

Что именно потерялось при переносе и чем это чинилось — `docs/reports/135-dev-transfer-data-loss.md`.

### Если бот всё же замолчал: конфликт поллеров

`409 Conflict` виден только в логе, поэтому его сторожит `scripts/conflict_watch.py`:
на сервере — таймер `svoi-conflicts.timer` каждые 5 минут (`--source journal`), на маке —
агент launchd `com.svoi.conflicts` с `StartInterval` 300 (`--source files`, файлы
`~/Library/Logs/svoi/gateway*.log*`, `--env dev` — алерт уходит через dev-бота). Агент
ставит `scripts/install_launchd.py` вместе с сервисными, отдельных шагов не нужно;
проверить вживую: `launchctl print gui/$(id -u)/com.svoi.conflicts` и
`python scripts/conflict_watch.py --source files` (без `--apply` — только посмотреть).
Маркеры — `TelegramConflictError` и `Conflict: terminated by other getUpdates`; админу
уходит один алерт на эпизод (повтор в пределах 6 часов не отправляется) с указанием
хоста, числа строк и первой/последней метки времени.

Окно свежести у обоих источников одно — последние 30 минут (`JOURNAL_MINUTES`): на
сервере его задаёт `journalctl --since -30min`, на маке сторож сам отбирает строки по
метке времени в строке. Хвост файла «последние N строк» окном не считается:
`gateway.log` ротируется только по 5 МБ, поэтому строки старого эпизода (30.10–01.11)
лежат в нём неделями, и 05.11.2026 сторож прислал ложный «конфликт поллеров»
при единственном живом поллере. Строка без метки времени отбрасывается — свежесть
доказать нечем; если в хвосте файла нет ни одной метки моложе окна, файл не читается
вовсе.

Условие доставки, которое легко забыть: **админ должен хоть раз написать dev-боту
`/start`**. Telegram не даёт боту писать первым — без этого `sendMessage` отвечает
`chat not found`, сторож пишет в лог «Telegram не принял сообщение» и код 1.
Проверка одной командой: `python scripts/conflict_watch.py --source files --env dev`
(без `--apply`) печатает текст алерта и не отправляет.

## 2. Текущий этап: локальная машина

```
macOS
├── docker: n8n (localhost:5678)          → сценарии, LLM (OpenRouter)
├── .venv: tool-api (127.0.0.1:8000)      → данные, RBAC, аудит
├── .venv: tg-gateway (polling)           → Telegram, режим MODE=polling
├── SQLite / локальный Postgres           → состояние
└── Google: боевой аккаунт театра         → боевые файлы (опасно, см. §3)
```

Никаких входящих соединений извне. Telegram опрашиваем сами (`getUpdates`), n8n вызываем по `http://127.0.0.1:5678/webhook/...`.

### Что это значит на практике
- Публичный домен не нужен.
- ngrok/cloudflared не нужен.
- Всё, что описано в документах (кроме `docs/architecture/02` §9 и §7), работает без изменений.

## 3. Изоляция от боевых данных (обязательно на текущем этапе)

У тебя боевой bot token и боевой Google Drive. Разработка «в бою» закончится испорченным бюджетом и сообщениями живым актёрам. Поэтому:

| Ресурс | Dev (локально) | Prod (VPS) |
|---|---|---|
| Telegram-бот | **отдельный тестовый бот** из BotFather (`svoi_dev_bot`) | боевой бот |
| Google Sheets бюджета | **копия файла** `Бюджет (dev)` в папке `_dev` | боевой файл |
| Файл занятости | копия в `_dev` | боевой |
| Drive-папки | `_dev/TG_<chat_id>`, `_dev/_shared` | `TG_<chat_id>`, `_shared` |
| Календарь | отдельный `SVOI dev` | боевой |
| n8n | локальный инстанс (уже есть) | отдельный инстанс/контейнер |

Service account один и тот же — он расшарен на `_dev` и на боевые папки, но `dev`-окружение смотрит только в `_dev` через переменные `BUDGET_SPREADSHEET_ID`, `SCHEDULE_SPREADSHEET_ID`, `DRIVE_ROOT_ID`, `CALENDAR_ID`. Смена контура = смена этих четырёх переменных, код не меняется.

Проверка «я не в проде»: при старте `tool-api` пишет в лог `ENV=dev|prod` и `BUDGET_SPREADSHEET_ID`. Если `ENV=dev` и spreadsheet совпадает с боевым — отказ стартовать. Это дешёвая защита от самой дорогой ошибки.

## 4. Целевой контур: VPS

```
Интернет
   │ HTTPS (443, nginx/caddy + Let's Encrypt)
   ▼
┌──────────────────────────────────────────────────┐
│ VPS (docker compose)                             │
│                                                  │
│  tg-gateway  ── webhook /tg/<secret>  ◄──────────┼── Telegram (push)
│      │                                           │
│      ├──► tool-api (внутренняя сеть)  ──► Google │
│      │         │                                 │
│      │         └──► Postgres                     │
│      │                                           │
│      └──► n8n /webhook/tg-inbound (внутренний)   │
│                  │                               │
│                  └──► OpenRouter (LLM)           │
│                                                  │
│  scheduler (напоминания, реконсиляция)           │
└──────────────────────────────────────────────────┘
```

Что появляется на VPS и чего нет локально:
- домен + TLS (для webhook Telegram и для UI n8n);
- Postgres вместо SQLite;
- scheduler как отдельный процесс (cron внутри контейнера);
- бэкапы (см. §5);
- ограничение доступа к n8n UI (basic auth + allowlist IP), потому что теперь он в интернете.

## 5. Что конкретно меняется при переезде

> Ниже — проект webhook-переезда. На 28.10.2026 он **не реализован**: `MODE` в коде
> не читается, gateway всегда работает на polling. Действующая инструкция — `35` §5b.

Код не переписывается. Меняются только переменные окружения и одна ветка запуска:

```env
# dev → prod
ENV=prod                          # было dev (включает защиту от записи в боевые файлы)
MODE=webhook                      # было polling
PUBLIC_BASE_URL=https://svoi.example   # новый
TELEGRAM_TOKEN=<боевой токен>     # было dev-бот
BUDGET_SPREADSHEET_ID=<боевой>    # было dev-копия
SCHEDULE_SPREADSHEET_ID=<боевой>
DRIVE_ROOT_ID=<боевой>
CALENDAR_ID=<боевой>
DATABASE_URL=postgresql://…       # было sqlite
N8N_BASE_URL=http://n8n:5678      # сам URL не меняется, меняется сеть
```

В `tg-gateway` — единственная развилка:

```python
if MODE == "webhook":
    await bot.set_webhook(f"{PUBLIC_BASE_URL}/tg/{WEBHOOK_SECRET}")
    # aiohttp/FastAPI-приложение отдаёт POST /tg/<secret> в dp.feed_update
else:
    await dp.start_polling(bot)      # локально
```

**n8n-воркфлоу при переезде не меняются вообще** — это и есть причина, по которой транспорт отделён от сценариев. Меняется только адрес, по которому бот их дёргает, и он приходит из окружения.

### Чек-лист переезда
1. `docker compose up` на VPS, домен, сертификат.
2. Импорт воркфлоу из `n8n/workflows/*.json` (файлы в git — источник истины).
3. Секреты: `TELEGRAM_TOKEN`, `TOOL_API_TOKEN`, `N8N_SHARED_SECRET`, `OPENROUTER_API_KEY`, `GOOGLE_SA_JSON` — заново, не копировать dev-значения.
4. `MODE=webhook`, `set_webhook` с `secret_token`, Telegram будет слать `X-Telegram-Bot-Api-Secret-Token` — проверять его в gateway.
5. Прогнать smoke: `/start` → регистрация по коду → «расход 3000 на реквизит» → строка в боевом Sheets → аудит.
6. Включить бэкап Postgres (ежедневно, 14 дней) и выгрузку Sheets (Google сам версионирует, но раз в неделю — экспорт в Drive).
7. Мониторинг: `/health` + алерт в личку админу при 5xx или очереди > 50 задач.

### Бэкапы и восстановление
- Postgres: `pg_dump` ежедневно в S3/локально, ротация 14 дней.
- `audit_event` — не бэкапить отдельно, он в дампе.
- Google Sheets — источник истины, но перед миграцией схемы листа делать `Файл → Создать копию`.

## 5.1 Ревизия v1.2 — единый контур (после уточнений)

Отдельный dev-бот и dev-копии файлов **не нужны**: бот только что зарегистрирован, поллеров на токене нет, а Drive-дерево, таблицы и календарь создаются пустыми под проект (`docs/infrastructure/09-google-setup.md`). Изнашивать два набора ресурсов на этапе, когда данных ещё нет, — лишняя работа.

| Вопрос | Dev (сейчас) | Prod (VPS) |
|---|---|---|
| Telegram | **боевой бот**, polling | тот же бот, webhook |
| Google | то же дерево `SVOI/_shared/*` | то же дерево |
| БД | `postgres:16` в Docker (порт 5433) | `postgres:16` в Docker (внутренняя сеть) |
| n8n | локальный `n8n-dev` | отдельный контейнер |
| MODE | `polling` | `webhook` |

Что меняется при переезде: `MODE`, `DATABASE_URL`, `PUBLIC_BASE_URL`, доступность n8n по внутреннему адресу, TLS. Код и воркфлоу — без изменений.

**Правило**: как только в боевых файлах появятся реальные данные, dev переключается на копию (`ENV=dev` + `BUDGET_SPREADSHEET_ID` копии), иначе один эксперимент перепишет настоящий бюджет.

## 6. Открытые вопросы по инфраструктуре

1. **Кто сейчас потребляет боевой bot token?** Если бот уже где-то работает (VPS, чужой сервис, старый код) — наш локальный поллер конфликтует. Нужно либо остановить тот сервис на время разработки, либо (рекомендую) завести отдельного dev-бота.
2. Есть ли у тебя VPS/домен сейчас, или выбираем позже? От этого зависит, нужен ли `MODE=webhook` вообще в этом году — polling на VPS работает нормально, HTTPS для бота не обязателен.
3. Куда кладём медиа: в боевой Drive аккаунта театра (лимит 15 ГБ у SA, если файл создаёт бот) или медиа загружают люди, а бот только читает? От этого зависит, нужен ли Shared Drive (Workspace).
4. Нужен ли доступ к n8n UI снаружи после переезда, или только через SSH-туннель? Второе безопаснее и проще.

## 7. Матрица «где какие секреты»

| Секрет | Где живёт | Кто использует |
|---|---|---|
| `TELEGRAM_TOKEN` | `/opt/svoi/.env` на сервере (локально — `.env`, но локальные запуски его не читают) | только `tg-gateway`, `scripts/send_notifications.py` |
| `DEV_BOT_TOKEN` | `.env.dev` на маке (в git не попадает) | локальный `tg-gateway`, `tool-api`, `scripts/notify_admin.py` (§1a) |
| `TOOL_API_TOKEN` | `.env` | `tg-gateway`, `n8n`, `scheduler` |
| `N8N_SHARED_SECRET` | `.env` | `tg-gateway` ↔ `n8n` (HMAC) |
| `OPENROUTER_API_KEY` | n8n credentials | только n8n |
| `GOOGLE_SA_JSON` | файл `secrets/google-sa.json`, `chmod 600` | только `tool-api` |
| Google OAuth (n8n) | n8n credentials | оставить для ручных экспериментов, в боевых воркфлоу не использовать |

Правило: n8n не имеет ни Google-ключа, ни доступа к Postgres. Всё, что ему нужно знать о мире, он спрашивает у `tool-api`.
