## 1. Что работает сейчас

| Тип | Когда отправляется | Кому |
|---|---|---|
| `dues` — взнос за месяц | 10:00 первого рабочего дня, если остался долг | участнику с привязанным Telegram |
| `availability` — заполнить занятость | пятница 12:00, если на следующую неделю отмечено меньше 5 дней | активным участникам |

Оба типа идемпотентны: ключ `dedup_key + recipient_id` не даёт создать напоминание
дважды за один период. Повторный запуск планировщика в тот же день ничего не добавляет.

**Проверено на живой базе:**

```
поставлено в очередь: 2 (дубли отсечены dedupe_key)
повторный запуск:      поставлено 0
```

## 2. Модель данных

Таблицы уже были в миграции `001`, дублировать их не стали:

```
notification      recipient_id → participant, kind, payload jsonb,
                  dedupe_key, scheduled_at, status, attempts, last_error, sent_at
notification_pref participant_id, kinds_muted text[], quiet_from, quiet_to, digest_enabled
app_setting       notify_quiet_from, notify_quiet_to, notify_kinds_muted — общие по студии (FR-G17)
```

Статусы: `scheduled` → `sent` | `failed` (после 3 попыток) | `skipped` (лимит) | `cancelled`.

Важное решение: **очередь, а не прямая отправка**. Планирование и отправка — разные процессы.
Планировщик можно гонять сколько угодно часто (идемпотентно), отправка работает по расписанию
и не зависит от того, жив ли gateway.

## 3. Правила

| Правило | Значение | Где настраивается |
|---|---|---|
| Тихие часы | 20:00–08:00 (Самара) | частные — `notification_pref` человека, общие — `app_setting` (админ-панель Mini App), по умолчанию в коде |
| Что не присылать | `kinds_muted` — список типов | так же: частные важнее общих (FR-G17) |
| Лимит в час | 3 сообщения одному человеку (счёт по `recipient_id`, запасной признак — `payload.chat_id`), остальные переносятся на час | `NOTIFY_MAX_PER_HOUR` |
| Повторы при ошибке | 3 попытки, потом `failed` | `MAX_ATTEMPTS` в коде |
| Разбор `failed` | `--retry-failed`: свежая ошибка настройки возвращается в очередь, остальные — `skipped` с причиной | `NOTIFY_RETRY_MAX_AGE_HOURS` |
| Крайний срок занятости | пятница 18:00, напоминание в 12:00 | `availability_deadline()` |
| Повтор при тихих часах | переносится на 08:00 | `next_allowed()` |
| Просроченные записи | ждали дольше 24 ч — не отправляются, `skipped` с причиной | `NOTIFY_STALE_HOURS` |

Тихие часы применяются **дважды**: при планировании (сдвигаем `scheduled_at`) и перед отправкой
(проверяем ещё раз, потому что человек мог изменить настройки).

Какие настройки действуют, решает одно правило — `resolve_settings` (`app/notifications.py`,
FR-G17, П-8): есть запись `notification_pref` у человека — берём её целиком, нет — общие
значения студии из `app_setting`, нет и их — 20:00–08:00 из кода. Правило читают и очередь
(`scripts/send_notifications.py`), и планировщик (`scripts/plan_reminders.py`), поэтому
«тихие часы» не могут означать разное в двух местах (это уже случалось, `docs/90` П-7).
Общие значения задаёт администратор в Mini App: «Управление → Уведомления».

Лимит считается **по адресату** (`notification.recipient_id`), а не по `payload.chat_id`:
ключа `chat_id` в payload у уведомлений об обращениях нет, и до 28.10.2026 счётчик для них
всегда был нулевым — за один прогон ушло 27 сообщений двум людям вместо трёх (Ш-34).
`payload->>'chat_id'` остаётся вторым признаком: у старых записей `recipient_id` может быть пустым.

Записи `failed` сами в очередь не возвращаются: `attempts` исчерпан. Их разбирает
`python scripts/send_notifications.py --retry-failed --apply` (Ш-35). Ошибка настройки
(нет токена, 401/404 от Bot API) и запись не старше `NOTIFY_RETRY_MAX_AGE_HOURS` (24 ч)
возвращается в очередь: `attempts = 0`, `scheduled_at` = момент разбора, `last_error`
остаётся как история. Остальные `failed` переводятся в `skipped` с причиной — сообщение
потеряло смысл или повторить его нельзя, и очередь не должна выглядеть сломанной.
Так разобраны семь уведомлений 27.10, упавших на `TELEGRAM_TOKEN не задан`: причина
устранена, но сами они в выборку отправки уже не попадали.

## 4. Скрипты

```bash
# планирование (идемпотентно)
python scripts/plan_reminders.py            # показать
python scripts/plan_reminders.py --apply    # поставить в очередь

# отправка
python scripts/send_notifications.py           # показать готовое
python scripts/send_notifications.py --apply   # отправить
python scripts/send_notifications.py --retry-failed --apply   # разобрать failed
```

Оба работают как самостоятельные процессы: не требуют запущенного gateway и не зависят от n8n. Переменные берутся из `.env` проекта (`load_dotenv`), поэтому скрипт
годится и для запуска из cron, где окружение не наследуется.

## 5. Расписание

**Локально (macOS)** — через Hermes-cron: напоминания каждые 10 минут, чистка
журнала интентов раз в сутки в 04:00.

### 5a. Где лежат скрипты заданий

Hermes-cron принимает только имя скрипта внутри `~/.hermes/scripts/`; абсолютный путь
и `~` он отклоняет ещё при создании задания. Поэтому схема двухуровневая:

| Задание | Логика (git) | Лаунчер дома | Расписание |
|---|---|---|---|
| напоминания | `scripts/cron/notify.py` | `~/.hermes/scripts/svoi_notify.py` | `*/10 * * * *` |
| чистка журнала | `scripts/cron/purge_intent.py` | `~/.hermes/scripts/svoi_purge_intent.py` | `0 4 * * *` |
| недельная сводка канбана | `scripts/cron/kanban_digest.py` | `~/.hermes/scripts/kanban-digest.sh` | `0 9 * * 1` |
| ежедневный отчёт «требует вас» | `scripts/cron/kanban_daily.py` | `~/.hermes/scripts/kanban-daily.sh` | `30 9 * * *` |

Логика — в репозитории: попадает в коммиты, проверяется `ruff` и тестами, ревьюится
вместе с остальным кодом. Домашний лаунчер — шесть строк: путь к проекту и
`runpy.run_path` нужного файла. Правки заданий делаются в репозитории, лаунчер не трогают.

Путь к проекту лаунчер берёт из переменной `SVOI_PROJECT`, по умолчанию
`~/repos/Projects/teatrsvoi_bot Project` (переезд из `~/Documents` — 28.10.2026).
Скрипты репозитория определяют путь сами — от собственного файла
(`Path(__file__).resolve().parents[2]`), поэтому `SVOI_PROJECT` нужен только лаунчеру.

`scripts/cron/notify.py` запускает планировщик и отправку, молчит, когда отправлять
нечего. `scripts/cron/purge_intent.py` читает `.env` (комментарий в значении режется
по ` #`, как в shell) и зовёт `scripts/intent_report.py --purge`, молчит, когда чистить
нечего. Ошибки обоих уходят в stderr: сломанное задание не должно «молчать».

### 5b. Недельная сводка канбана

По понедельникам в 09:00 (Самара) владельцу приходит короткий текст из пяти блоков:
выполнено за неделю, цикл (медиана), доводки ревью, аварии (таймаут/падение),
в очереди / блокировано. Источник цифр — `scripts/kanban_metrics.py --json`
(своей логики сбора нет), доставка — `scripts/notify_admin.py` в чат `123456789`,
формат — без эмодзи, одна экранная страница.

```bash
env -u PYTHONPATH .venv/bin/python scripts/cron/kanban_digest.py --dry-run   # показать текст
env -u PYTHONPATH .venv/bin/python scripts/cron/kanban_digest.py             # отправить
```

Ошибка сбора не глотается: если доски нет, БД недоступна или карт на доске не
осталось, в чат уходит сообщение с причиной и командой проверки, а задание
завершается кодом 1 — неделя тишины не должна выглядеть как «всё хорошо».

Отдельная ловушка: **`HERMES_HOME`**. У профиля воркера канбана свой `HERMES_HOME`,
и `kanban_metrics.py` тогда ищет доску в `<профиль>/kanban/boards`, не находит её и
молча отдаёт `{}`. Поэтому сводка снимает переменную перед вызовом метрики (явный
каталог задаётся `--hermes-home`), и лаунчер тоже запускает её с `env -u HERMES_HOME`.

### 5c. Ежедневный отчёт «требует вас»

Каждый день в 09:30 (Самара) владельцу приходит короткий текст о том, что требует
человека. Недельная сводка (§5b) отвечает на вопрос «стало ли лучше», этот отчёт —
на вопрос «что от меня нужно сейчас»; цифры производительности здесь не повторяются.

1. **Требует вас** — блокировки старше 6 часов и любые «нужен ответ» (`needs_input`
   независимо от возраста): карта, вид (нужен ответ / нужна ручная работа / ждёт
   другую карту / временный сбой), сколько ждёт, вопрос. Блокировка без причины в
   событии и без комментария после неё показывается сразу, без ожидания шести
   часов, с пометкой «нет причины» — это сигнал, что карту завели неправильно.
2. **Мёртвые** — карты без исполнителя и карты без класса приоритета (`priority`
   вне набора 1..5, то есть P4..P0), по строке на вид, с числом и именами карт.
3. **Очередь** — три первые карты в порядке диспетчера: `priority DESC,
   created_at ASC` по `ready`/`todo`.
4. **Итог** — сделано за сутки, в работе, в ревью.

Пустая доска — не повод молчать: приходит строка «Требующих человека нет.»
Пропуск бывает только при сломанном сборе, и тогда в чат уходит причина и команда
проверки, а задание завершается кодом 1.

```bash
env -u PYTHONPATH .venv/bin/python scripts/cron/kanban_daily.py --dry-run   # напечатать
env -u PYTHONPATH .venv/bin/python scripts/cron/kanban_daily.py             # отправить
```

`--dry-run` печатает ровно тот текст, что уходит в чат, и в Telegram не обращается:
ручная проверка не должна зависеть от наличия токена. Отчёт открывает базу доски в
режиме `mode=ro` и статусы карт не меняет — он только читает. Токен и адресат те
же, что у остальных сводок: `scripts/notify_admin.py`, чат `123456789`.

**На сервере** — systemd timers из `deploy/systemd` (`docs/infrastructure/35` §5a):

| Юнит | Что запускает | Когда |
|---|---|---|
| `svoi-notify-plan.timer` | `plan_reminders.py --apply` | раз в сутки в 09:00 |
| `svoi-notify-send.timer` | `send_notifications.py --apply --limit 50` | каждые 5 минут |

Планирование отделено от отправки: очередь наполняется утром, а отправка идёт часто
и короткими пачками, чтобы тихие часы и лимит `NOTIFY_MAX_PER_HOUR` считались на момент
отправки, а не на момент постановки. Наличие и корректность юнитов проверяет
`scripts/check_services.py`.

## 6. Тесты

`tests/unit/test_notifications.py` — 14 тестов на чистые правила:

- тихие часы: вечер, ночь, границы 20:00 и 08:00, день;
- перенос на утро, включая случай «желаемое время уже прошло»;
- ключ дедупликации: одинаковый период, разные люди, разные периоды;
- начало недели (понедельник и середина недели) и расчёт дедлайна;
- просрочка очереди (`is_stale`): граница суток, 23 и 25 часов, свой порог;
- тексты: долг, закрытый взнос, неполная неделя, заполненная неделя;
- отключение типов через `kinds_muted` и отдельный флаг дайджеста.

`tests/integration/test_notifications_limit.py` — 3 теста на лимит и очередь:
пять записей одному человеку (три уходят, две переносятся на час), старые записи с `chat_id`
только в payload тоже занимают лимит, отправленное больше часа назад лимит не занимает.
Сам `deliver()` проверяется на живой БД с подменённым отправителем.

`tests/integration/test_notifications_retry_failed.py` — 5 тестов на разбор `failed`:
свежая ошибка настройки возвращается в очередь и уходит следующим прогоном (`attempts = 0`,
`last_error` сохранён), ошибка настройки старше суток помечается `skipped` с причиной,
ошибка API (не настройки) тоже `skipped` с сохранённым текстом ошибки, сухой прогон
ничего не меняет, `is_config_error()` отличает токен-ошибки от ошибок сообщения.

`tests/unit/test_kanban_daily.py` — 23 теста на ежедневный отчёт (§5c): фикстура
настоящей базы доски (блокировка с вопросом, блокировка без причины, молодая
блокировка, карты без исполнителя и без класса, три карты очереди) собирается в
ожидаемые строки; пустая доска даёт «Требующих человека нет.», `--dry-run` печатает
побайтно тот же текст, что уходит в чат, ошибка сбора уходит в чат и даёт код 1,
повторный сбор не меняет ни одной карты.

`tests/unit/test_cron_wrappers.py` — 10 тестов на обёртки заданий:

- оба файла лежат в `scripts/cron/` (не в домашнем каталоге) и не держат старый путь
  проекта, а путь берут из `SVOI_PROJECT`;
- без переменной окружения проект определяется от файла обёртки;
- `purge_intent` разбирает `.env` с инлайн-комментарием;
- `notify` зовёт планировщик и отправку по порядку, молчит при пустой отправке, останавливается
  и пишет в stderr при падении планировщика;
- `purge_intent` пишет ошибку в stderr и возвращает 1, молчит, когда чистить нечего.

Проверяются только файлы репозитория: мягкого `pytest.skip` для CI без домашних скриптов
больше нет.

Собственно вызов Telegram API тестами не покрыт: он требует живого токена. Проверяется вручную
через `--apply` на одном chat_id.

## 8. Как это устроено концептуально

Уведомление — это **запись в очереди с намерением**, а не вызов API. Из этого следуют
три свойства, которые важны в эксплуатации:

1. **Ничего не теряется при сбое.** Если Telegram недоступен, запись остаётся `scheduled`
   и уйдёт при следующей попытке.
2. **Ничего не дублируется при повторе.** Планировщик можно запускать каждую минуту —
   дедупликация по ключу не даст двух одинаковых сообщений.
3. **Тихие часы соблюдаются даже при сбое расписания.** Проверка стоит и в планировании,
   и в отправке, поэтому сдвиг часового пояса или ручной запуск ночью не разбудят людей.
