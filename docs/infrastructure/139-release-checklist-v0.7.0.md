## 1. Почему шаги вынесены отдельно

Оба предмета лежат вне кода и вне гейта, и оба деградируют молча — без ошибки в логах,
без красного `/health`:

| Что | Как выглядит, если пропустить | Когда выяснится |
|---|---|---|
| `config/participant-names.yaml` | сопоставление имён листов работает на алиасах БД: на копии боевой БД находится **8 листов из 9** (нет «дарья»), на dev-базе — 0 из 9 | при первом импорте расписания, и то если читать вывод, а не только код возврата |
| `docker-compose.yml` (`gardata` без `external: true`) | том `s3-storage_gardata` перестаёт быть «внешним»: `docker compose up` создаёт его сам, если его нет | при первом `docker compose up` после выката |

Правило файла имён — не украшение, оно уже записано в `docs/development/26` §1; здесь только
место в порядке выката. Правило тома — комментарий в самом `docker-compose.yml`:
`external: true` сломал бы первый запуск на чистой машине, `name:` решает обе задачи.

## 2. До выката (pre-flight)

Стандартный снимок — 35 §10a и дамп БД, плюс два предметных шага ниже. Оба выполняются
**до** `deploy/release.sh --apply` / workflow `deploy.yml`: после `checkout --force FETCH_HEAD`
сервисы стартуют сразу, паузы «вставить файл между кодом и рестартом» в автоматическом
выкате нет.

### 2.1. Файл имён: положить заранее

Файл не отслеживается git (`.gitignore`), поэтому `checkout --force FETCH_HEAD` его не удаляет
и не перезаписывает — класть его можно и до выката, и он переживёт выкат.

```bash
# с рабочей машины, из локального хранилища (в репозитории только .example)
scp participant-names.yaml svoi-prod:/opt/svoi/config/participant-names.yaml
ssh svoi-prod 'ls -l /opt/svoi/config/participant-names.yaml &&
  git -c safe.directory=/opt/svoi -C /opt/svoi status --porcelain --ignored config/ | grep participant-names'
```

Ожидаемо: файл на месте, `git status --ignored` показывает его как `!!` (игнорируется,
в дерево не входит). Если путь печатается без `!!` — файл попал в индексацию, разбираться
до выката: в публикуемом дереве имён быть не должно (Ш-03a плана 129).

### 2.2. Том `s3-storage_gardata`: сверить, что существует

```bash
cd /opt/svoi
docker volume inspect s3-storage_gardata --format '{{.Name}} {{.Mountpoint}} {{.CreatedAt}}'
```

- печатает строку — том на месте, продолжаем;
- `no such volume` — **стоп**. В старом файле том был `external: true`, то есть его
  существование было обязательным условием. Если его нет, значит Garage на проде не работал
  и вопрос «где лежат данные S3» надо решать до релиза, а не после: новый файл, не найдя том,
  создаст пустой и поднимет пустое объектное хранилище.

## 3. Выкат

```bash
deploy/release.sh 0.7.0                # prepare: гейты, CHANGELOG, локальный тег; прод не трогает
deploy/release.sh v0.7.0 --apply      # по команде владельца: push тега, workflow, сверка версии
```

Состав файлов — из тега, поэтому `docker-compose.yml` на сервере после `checkout` уже новый.
До первого `docker compose up` (и до любого рестарта контейнеров) проверить, что compose
собрал тот же том:

```bash
cd /opt/svoi
docker compose config | sed -n '/^volumes:/,$p'
```

Ожидаемо (`docker compose config` на этом файле, локальная проверка 08.11.2026):

```
volumes:
  gardata:
    name: s3-storage_gardata
```

Если в выводе стоит `external: true` — на сервере остался старый файл (checkout не прошёл);
разбираться, а не запускать.

Предупреждение при первом `up` — `volume "s3-storage_gardata" already exists but was not
created by Docker Compose / for project …` — **не ошибка**: том найден по имени и смонтирован.
Обратная сторона того же изменения: `docker compose down -v` теперь удаляет и этот том
(внешний бы не тронул). В выкате `down -v` не запускать.

## 4. После выката

```bash
cd /opt/svoi
bash scripts/deploy-check.sh --root /opt/svoi --url http://127.0.0.1:8000   # §10a
.venv/bin/python scripts/import_schedule.py --dry-run
```

Проверка файла имён — по выводу импорта, не по коду возврата:

- `прочитано личных листов: 9 → [...]` — файл подхвачен, все листы людей опознаны;
- `прочитано личных листов: 8 → [...]` и строка `!` про неопознанный лист — файл не подхвачен
  или в нём нет нужного никнейма; дальше не импортировать, а дописать конфиг и повторить
  `--dry-run`;
- ошибка чтения YAML (ожидался словарь с разделами `names` и `category_hints`) — файл битый,
  правка на сервере.

Рестарт для файла не нужен: `services/tool-api/app/participant_names.py` читает его на каждый
вызов, кэша нет. Со второго прогона импорт сам заводит алиасы в `person_alias`, и конфиг нужен
только для новых людей и `category_hints` — то есть деградация, если файл забыть, со временем
сглаживается, но первым импортом данные пишутся уже неполными.
