# 75. Найти домик для Бота Театра: от покупки сервера до прода

> **n8n выведен из контура (V-026, 01.11.2026).** Публичного адреса `n8n.<домен>`,
> контейнера n8n и переменных `N8N_*` в деплое больше нет: роутер свободного текста —
> `POST /tools/route` внутри tool-api. Разделы, где n8n ещё описан (замеры памяти,
> инвентаризация переноса), оставлены как история и помечены. Порядок выката:
> база → API → домен/TLS → сервисы и таймеры → поллер.

Практическая инструкция «с нуля до работающего бота»: где взять сервер, как выбрать и
зарегистрировать домен, как выпустить сертификаты, что поправить в проекте перед выездом,
как развернуть компоненты и как переключить поллер так, чтобы никто не потерял сообщения.

Дополняет, а не заменяет: `docs/infrastructure/24` (архитектура прода, почему именно так),
`docs/infrastructure/35` (runbook: команды и проверки), `docs/infrastructure/08` (локальный
контур и решение «polling для релиза»). Здесь — порядок действий и скрипты, в которых все
адреса вынесены в один файл `deploy/svoi.env`.

Ориентир по времени: **2–3 часа** первого проезда, из них 20–40 минут — ожидание DNS,
выпуска сертификата и установки пакетов. Повторный выкат — 5 минут.

Деньги: **1 500–2 000 ₽/мес** за сервер в зарубежной локации (оплата картой РФ),
**1 500–3 000 ₽/год** за домен `.online` (проверьте цену продления), TLS бесплатный.
Почему сервер не в России — §1.1: это не предпочтение, а условие работы Telegram-канала.

## 0. Что должно получиться

```
        Telegram (люди и Mini App)
             │  long polling, исходящее соединение
             ▼
   ┌──────────────────────────────────────────────┐
   │ VPS 2 vCPU / 4 ГБ / 60 ГБ SSD, Ubuntu 24.04  │
   │                                              │
   │  Caddy :443  ── /webapp*  → tool-api:8000    │
   │              ── /api/*    → tool-api:8000    │
   │                                              │
   │  tg-gateway   (systemd, поллер)              │
   │  tool-api     (systemd, 127.0.0.1:8000)      │
   │  Postgres 16  (docker, 127.0.0.1:5432)       │
   │  таймеры: напоминания, инварианты, сторож     │
   └──────────────────────────────────────────────┘
             │
   Google Drive / Sheets / Calendar, LLM-провайдер (из tool-api)
```

Три правила, из которых следует всё остальное:

1. **Наружу смотрит только Caddy.** tool-api и Postgres слушают `127.0.0.1`.
2. **Домен нужен не боту, а Mini App.** Telegram требует HTTPS для `web_app`;
   polling работает без входящего порта вообще (`docs/infrastructure/35` §5b).
3. **Один bot token — один поллер.** Пока живы два, Telegram отдаёт апдейт случайному,
   второй получает `409 Conflict`, и бот «мигает».

## 1. Решения, которые надо принять до покупки

| Ось | Варианты | Что выбрать для этого проекта |
|---|---|---|
| Страна размещения | РФ / за пределами РФ | **за пределами РФ (Амстердам, Франкфурт, Хельсинки)**: из дата-центров РФ ТСПУ дропает `api.telegram.org`, бот перестаёт получать апдейты (§1.1) |
| Провайдер | Timeweb Cloud, Aeza, Zomro, Hetzner | Timeweb Cloud (EU-локация): рублёвая оплата картой РФ, панель на русском; Hetzner — если есть зарубежная карта |
| Конфигурация | 1–2 vCPU / 2–4 ГБ / 40–60 ГБ | 2 vCPU / 4 ГБ / 60 ГБ: Postgres + n8n + API на одном сервере |
| ОС | Ubuntu 24.04 LTS / Debian 12 | Ubuntu 24.04 LTS — под неё написаны юниты и runbook |
| База | Postgres в контейнере / managed | контейнер на том же сервере; managed — когда данных станет 5–10 ГБ |
| Домен | `.online` / `.ru` / `.com` | `.online`: не подпадает под обязательную идентификацию через ЕСИА (569-ФЗ, только `.ru`/`.рф`/`.su`), зона не привязана к РФ-юрисдикции (§3.4) |
| Прокси и TLS | Caddy / nginx + certbot / Cloudflare | Caddy: сертификат выпускается и продлевается сам; Cloudflare в РФ троттлится — не используем |
| Оплата | карта РФ / зарубежная карта / крипта | карта РФ у провайдера с EU-локацией — самый короткий путь |
| Транспорт Telegram | polling / webhook | polling на релизе; webhook — отдельная задача после (`docs/infrastructure/35` §5b) |

Отдельные независимые вопросы, которые нельзя смешивать: «где живёт сервер», «где живёт
домен», «кто терминирует TLS», «кто читает апдейты». Решение по одному не диктует остальные.

### 1.1 Почему сервер не в России

Первая редакция этой инструкции рекомендовала РФ по 152-ФЗ. Аргумент не выдержал проверки
двумя фактами:

1. **Данные и так не в РФ.** Источник истины — Google Sheets/Drive, доступ через service
   account. Сервер в России не делал хранение локальным, он лишь создавал видимость порядка.
2. **Из дата-центров РФ не работает Telegram API.** С 2026 года ТСПУ распознаёт и дропает
   пакеты к хостам мессенджера: разработчики массово сообщают о недоступности
   `api.telegram.org` с серверов Selectel, Reg.ru и других
   ([vc.ru](https://vc.ru/id5779154/2795944-blokirovka-telegram-api-v-rossii)).
   Официально Telegram заблокирован в РФ с февраля 2026
   ([хронология](https://ru.wikipedia.org/wiki/Блокировка_Telegram_в_России_(2026))).

Практический смысл: RU-хостинг — не «риск на будущее», а неработающий бот сегодня. Плюс
LLM: OpenRouter закрыл РФ-аккаунты и IP с 27.06.2026, оплата РФ-картами перестала
проходить с мая ([разбор](https://proxyapi.ru/openrouter)).

Что остаётся верным для РФ-хостинга: меньше латентность (20–40 мс), рублёвая оплата,
152-ФЗ при будущем оформлении юрлица. Первые два перекрываются EU-провайдером с рублёвой
оплатой; третий — вопрос данных, а не VPS (§14).

Вариант «сервер в РФ + реверс-прокси за рубежом» технически существует, но это второй
сервер, второй сертификат и второй владелец сбоя ради одного бота. Для пустой площадки
дешевле сразу встать туда, где Telegram доступен напрямую.

**Проверяется фактом, а не верой:** `deploy/server-deploy.sh smoke` делает исходящие
запросы к `api.telegram.org`, `api.vk.com` и LLM-провайдеру и падает, если хоть один
недоступен. Из дата-центра в РФ первая проверка вернула бы `000`.

## 2. Сервер: выбор, заказ, проверка после выдачи

### 2.1 Ориентир по ценам

Нужна зарубежная локация с оплатой из РФ. Порядок предпочтения:

| Провайдер | Локация | Ресурсы | Цена/мес | Оплата | Замечание |
|---|---|---|---|---|---|
| **Aeza** | Амстердам, Франкфурт, Хельсинки | 1 / 2 ГБ / 30 ГБ NVMe | **≈ 590–780 ₽** | карта РФ | лучшая цена за нужную конфигурацию; панель проще, чем у Timeweb |
| **Hetzner** | Хельсинки | 2 / 4 ГБ / 80 ГБ (CPX22) | ≈ €8 (~800 ₽) | **только зарубежная карта** | дешевле и ближе всех, но платёжный барьер |
| Zomro | Нидерланды | 2 / 4 ГБ / 60 ГБ | от ≈ €7 (~680 ₽) | карта РФ | запасной |
| Hostkey | Амстердам | 2 / 4 ГБ / 40 ГБ NVMe | 800–1 000 ₽ | карта РФ | запасной |
| **Timeweb Cloud** | Амстердам, Франкфурт | **1 / 2 ГБ / 30 ГБ NVMe** | **2 660 ₽** | карта РФ | удобная панель и поддержка, но в этом регионе доступна только линейка Premium (EPYC 7542 + NVMe) — переплата в 3–4 раза за мощность, которая не нужна (§2.6) |
| Timeweb Cloud | тот же регион | 2 / 2 ГБ / 30 ГБ NVMe | 3 240 ₽ | карта РФ | +580 ₽ за второе ядро; для нашей нагрузки бесполезно (§2.6) |

Фактические цифры Timeweb — из панели на 29.10.2026: линейки Standard/Ultra/High CPU в
выбранном регионе недоступны, NVMe обязателен. Для нашей нагрузки (простой ≈ 1 ГБ RAM,
диск ≈ 9 ГБ) NVMe ничего не даёт: 4 КБ/с записи в простое. Поэтому выбор между «платить
за удобство панели» и «платить в 3–4 раза меньше за те же ресурсы» — решение владельца,
а не техническое.

Для общего ориентира: срез публичных цен на 18.08.2026 (HostMetrics, 20 провайдеров,
порог 2 vCPU / 4 ГБ) давал по РФ минимум 650 ₽ и медиану 1 149 ₽ — но эти тарифы нам
больше не подходят по §1.1.

Латентность (ориентир): Хельсинки 15–30 мс до Петербурга, Амстердам/Франкфурт 30–50 мс до
Москвы. Для бота и Mini App разница неощутима — не выбирайте по ней.

Цены меняются: проверяйте калькулятор провайдера в день покупки, не по этой таблице.

### 2.2 Что именно заказывать

- [ ] 2 vCPU, 4 ГБ RAM, 60 ГБ SSD/NVMe
- [ ] Ubuntu 24.04 LTS, чистый образ (без панелей управления)
- [ ] публичный IPv4 (IPv6 — по желанию, скрипты её не требуют)
- [ ] локальные бэкапы провайдера, если входят в тариф (дополнительно к своим, §7.6)
- [ ] **зарубежная локация:** Амстердам, Франкфурт или Хельсинки (§1.1)
- [ ] доступ по SSH-ключу, пароль root не нужен

### 2.3 Что проверить сразу после выдачи

```bash
ssh root@<IP>
nproc && free -h && df -h / && lsb_release -ds
# ожидание: 2, ~4Gi, диск >= 60G, Ubuntu 24.04.x LTS

ip -4 addr show | grep inet                # совпадает ли IP с панелью

# главная проверка локации: доступны ли внешние API, которые нужны боту
for u in https://api.telegram.org/ https://api.vk.com/method/utils.getServerTime \
         https://openrouter.ai/api/v1/models; do
  printf '%s -> ' "$u"; curl -s -o /dev/null -m 8 -w '%{http_code}\n' "$u"
done
# ожидание: 302 / 200 / 200. Если первая строка 000 — это дата-центр с фильтрацией
# ТСПУ, бот здесь работать не будет (docs/infrastructure/75 §1.1)
```

Если провайдер выдал пароль root, он нужен ровно один раз: чтобы положить ключ.

```bash
ssh-copy-id -p 22 svoi@<IP>     # после создания пользователя (§6.2)
```

### 2.4 Чем платить и что хранить

Карта РФ и автоплатёж: для Timeweb Cloud/Aeza/Zomro этого достаточно, валюта — рубли.
Зарубежная карта нужна только если выберете Hetzner. В менеджере паролей сохранить: логин
панели, IP сервера, дату продления. **Дата продления — отдельное напоминание в календаре**:
просроченный сервер выключают, и бот замолкает без всякой ошибки.

Провайдер за рубежом — не повод расслабляться с чеками: сохраняйте акты/квитанции, это
расход студии.

### 2.5 Заказ в Timeweb Cloud: шаги панели

Порядок шагов сверен с их документацией «Создание облачного сервера». Время — 10 минут
плюс несколько минут на установку.

**До заказа**

1. Аккаунт и баланс: пополнить сразу на 30 дней вперёд — иначе «Заказать» перебрасывает
   в «Баланс и платежи», и сервер не создаётся.
2. Ключ на маке:
   ```bash
   ssh-keygen -t ed25519 -C "svoi-prod" -f ~/.ssh/svoi_prod
   cat ~/.ssh/svoi_prod.pub        # понадобится на шаге 6
   ```

**Панель → «Облачные серверы» → «Добавить» / «Создать»**

| Шаг панели | Что выбрать | Почему |
|---|---|---|
| 1. Программное обеспечение | вкладка «Чистая ОС» → **Ubuntu 24.04 LTS** | маркетплейс-сборки (панели, готовые образы) только мешают: provision и юниты написаны под чистую систему |
| 2. Регион | **Амстердам** или **Франкфурт** | не Санкт-Петербург и не Москва: из РФ-дата-центров `api.telegram.org` не отвечает (§1.1) |
| 3. Конфигурация | линейка **Standard** или «Произвольная»: **2 vCPU / 4 ГБ / 60 ГБ** | Postgres + n8n + tool-api на одном сервере; NVMe приятно, но не обязательно |
| 4. Сеть | **публичный IPv4 — создать новый**; IPv6 — если дадут бесплатно; приватная сеть не нужна; имя хоста `svoi-prod` | IPv4 **оплачивается отдельно** — цену видно на этом шаге, заложите в бюджет |
| 5. Безопасность | **резервное копирование — включить**, **защита от удаления — включить** | бэкап провайдера — страховка от «удалил не то»; наши `pg_dump` остаются основными (§7.6). DDoS-защита и аварийная копия доступны только для СПб/Мск |
| 6. Авторизация | **добавить SSH-ключ** (вставить `svoi_prod.pub`), **выключить** «Доступ по SSH через root-пароль» | вход только по ключу с первого дня; чинить это потом сложнее |
| 7. cloud-init | пропустить | всё делает `deploy/server-deploy.sh provision` — один источник правды, а не два |
| 8. Информация | имя `svoi-prod`, комментарий, проект → проверить сводку справа → **«Заказать»** | |

**Первые 10 минут после выдачи**

Дашборд → IP-адрес и реквизиты подключения. Дальше — обязательная проверка локации (§2.3):
три `curl` к `api.telegram.org`, `api.vk.com` и LLM-провайдеру. Первая строка `000` означает,
что дата-центр фильтрует трафик и бот здесь работать не будет — менять локацию, не начиная
установку.

Ловушка из их документации: если вход по паролю выключен при заказе, вернуть его можно только
удалив `/etc/ssh/sshd_config.d/50-cloud-init.conf`. Держите это в голове, если потеряете ключ.

Дальше — по порядку: `deploy/svoi.env` (IP, домен, e-mail), `deploy/server-deploy.sh check`
на маке, затем §6 (provision) и §7 (развёртывание).

### 2.6 Требования к ресурсам: измерено, а не на глаз

Замеры сняты с локального контура до V-026 (01.11.2026), когда рядом с Postgres работал
n8n; сегодня его в контуре нет, поэтому фактическое потребление ниже таблицы на ≈ 500 МБ.

Замеры сняты с локального контура — он идентичен проду по составу (Postgres + n8n +
tool-api + gateway), отличается только ОС и объёмом данных.

| Компонент | Память (RSS) | Что это |
|---|---|---|
| n8n | **≈ 500 МБ** | самый тяжёлый: Node.js-рантайм, растёт на время исполнения воркфлоу |
| Postgres 16 | ≈ 100 МБ | база 15 МБ, 11 293 строки занятости, 95 операций бюджета |
| tool-api (FastAPI) | ≈ 15 МБ | пул соединений min=1 |
| tg-gateway (aiogram) | ≈ 26 МБ | polling |
| Caddy | ≈ 30 МБ | TLS, прокси |
| ОС + systemd + journald | ≈ 300 МБ | пустая Ubuntu с journald |
| **Простой, итого** | **≈ 1,0 ГБ** | |

Пики, которые надо пережить: `pip install` (+300–500 МБ), первый запуск n8n (+200 МБ),
одновременная отправка пачки напоминаний.

Диск, по факту:

| Что | Объём |
|---|---|
| ОС | 3 ГБ |
| Docker-образы (n8n 1,8 ГБ + postgres 0,66 ГБ) | **2,5 ГБ** |
| venv проекта | 0,26 ГБ |
| код репозитория | 0,02 ГБ |
| база + данные n8n | 0,03 ГБ (растёт медленно: 3,8 МБ на 11 тыс. строк занятости) |
| логи (journald, лимит 1 ГБ) | до 1 ГБ |
| бэкапы (14 дней × 0,2 МБ сейчас) | единицы МБ |
| swap | 2 ГБ |
| **Итого** | **≈ 9 ГБ** + запас на обновления ОС и рост |

Отсюда четыре уровня:

| Уровень | Конфигурация | Что получаете |
|---|---|---|
| **Минимум** | 1 vCPU / **2 ГБ** / 20–25 ГБ SSD + swap 2 ГБ | работает: бот, бюджет, занятость, напоминания, n8n. Тесно на пиках; n8n ограничить кучей (`SVOI_N8N_MEMORY_MB=384`) |
| **Рабочий** | 2 vCPU / 2 ГБ / 30 ГБ | то же, но пики не задевают; CPU с запасом на `pip install` и воркфлоу |
| **Комфорт** | 2 vCPU / 4 ГБ / 40 ГБ | без оглядки на память; место на рост базы и логи |
| **С запасом** | 2 vCPU / 4 ГБ / 60 ГБ | если планируется второе приложение или много медиа |

Что **не** нужно: NVMe (нагрузка на диск ничтожная — 4 КБ/с в простое), выделенные ядра,
DDoS-защита (публичных сервисов, кроме 443, нет). Линейка **Standard** с SSD дешевле
Ultra/Premium и для этой нагрузки не отличается.

Если в панели доступна только NVMe-линейка (как в Амстердаме у Timeweb на 29.10.2026),
выбирать надо по памяти, а не по диску: 1 vCPU / 2 ГБ / 30 ГБ — рабочий минимум (2 660 ₽).
Тише и дешевле, но **не подходит**:

| Вариант из панели | Цена | Почему нет |
|---|---|---|
| 1 vCPU / 1 ГБ / 15 ГБ | 1 620 ₽ | простой уже ≈ 1,0 ГБ — n8n + Postgres + API не оставят запаса; 15 ГБ диска при 9 ГБ занятых не переживут обновлений ОС |
| 1 vCPU / 1 ГБ / 15 ГБ («оптимально для выбранного ПО») | 2 330 ₽ | то же по памяти, но дороже — метка «оптимально» относится к другому ПО, не к нашему стеку |
| 2 vCPU / 2 ГБ / 30 ГБ | 3 240 ₽ | второе ядро нужно только на время `pip install`; в простое CPU занят на 2–3 % |

Как сэкономить, не теряя работоспособность:

1. Взять **Standard**, а не NVMe-линейку.
2. Диск 30–40 ГБ вместо 60: занято ≈ 9 ГБ, остальное — запас.
3. **Годовая оплата** вместо помесячной (у Timeweb скидка за 12 месяцев).
4. При 2 ГБ RAM поставить `SVOI_SWAP_GB=2` и `SVOI_N8N_MEMORY_MB=384` в `deploy/svoi.env` —
   это снимает главный риск «OOM на пике».
5. Сравнить с Aeza/Zomro/4vps (§2.1) — если разница в цене больше 30 %, провайдер не принципиален.
6. Не брать DDoS-защиту и аварийную копию: для нашего профиля это лишние деньги
   (провайдерский бэкап диска — по желанию, он не заменяет `pg_dump`).

## 3. Домен: выбор, регистрация, DNS

### 3.1 Как выбрать имя и зону

- короткое, произносимое по телефону: `teatr-svoi.online` лучше `teatrsvoi-bot-2026.online`;
- зона: **`.online`** — решение этого проекта. Причины в §3.4: требование обязательной
  идентификации через ЕСИА (569-ФЗ, с 01.09.2026) касается только `.ru`, `.рф` и `.su`;
  `.online` — зона Radix, регистрируется у любого аккредитованного регистратора;
- цену смотрите на продление, а не на первый год: у иностранных зон первый год часто идёт
  по промо, продление дороже. Заложите ориентир «дороже `.ru`» и проверьте цифру в панели
  до оплаты;
- **не берите** домен, который совпадает с названием чужого театра или бренда;
- один домен приложения (поддомен для n8n не нужен: V-026 вывел n8n из контура).

Проверка занятости — на сайте регистратора; там же проверьте, нет ли у похожего домена
действующего сайта (иначе люди будут попадать не к вам).

### 3.2 Где регистрировать

| Регистратор | Плюсы | Минусы |
|---|---|---|
| **Reg.ru** | оплата из РФ, `.online` есть, DNS в панели | домен в РФ-юрисдикции: регистратор исполняет требования РКН (§3.4) |
| Timeweb | одна панель с сервером | то же |
| Porkbun / Namecheap | домен вне РФ-юрисдикции | нужна зарубежная карта, продление в валюте |

Для этого проекта — Reg.ru: платить из РФ проще, а «независимость» домена при блокировке
почти ничего не даёт (блокируют IP или SNI, а не запись у регистратора). Домен и сервер
держите у разных провайдеров: при проблеме с хостингом домен не должен уехать вместе с ним.

### 3.3 DNS

Две A-записи (и, если включили IPv6, две AAAA):

| Имя | Тип | Значение | TTL |
|---|---|---|---|
| `@` (teatr-svoi.online) | A | IP сервера | 300 |
| `www` | CNAME | `teatr-svoi.online` | 300 |

**DNS — у регистратора или в Yandex DNS. Cloudflare не используем:** в РФ он троттлится,
и «сертификат не выпускается» будет выглядеть загадкой. Прокси-режим Cloudflare (оранжевое
облако) к тому же ломает ACME-проверку по HTTP — ещё одна причина пройти мимо.

TTL 300 на время переезда: если IP придётся менять, ждать придётся 5 минут, а не сутки.
После стабилизации можно поднять до 3600.

Проверка (делать с локальной машины и с сервера):

```bash
dig +short teatr-svoi.online A
# ожидание: IP сервера
```

Дождитесь, пока запись увидят публичные резолверы:

```bash
dig +short @1.1.1.1 teatr-svoi.online A
dig +short @8.8.8.8 teatr-svoi.online A
```

**Пока DNS не сошёлся, Caddy не выпустит сертификат.** Это самая частая причина
«сертификат не выдался» — не перезапускайте Caddy по кругу, проверьте `dig`.

### 3.4 Что означает домен у РФ-регистратора (юридически)

Короткий ответ на четыре вопроса, которые обычно задают в этот момент.

**1. Влияет ли регистратор на доступ к Telegram API?** Нет. Запросы к `api.telegram.org`
идут с сервера по IP, DNS вашего домена в этом не участвует. Домен и Telegram API — разные
оси: первая отвечает за то, как люди находят Mini App, вторая — за то, доходит ли бот до
Telegram.

**2. Что регистратор обязан делать в отношении меня?**

| Обязанность | Что это значит на практике |
|---|---|
| Идентификация администратора | паспортные данные (для юрлица — ЕГРЮЛ); с 01.09.2026 для `.ru`/`.рф`/`.su` — верификация через ЕСИА ([569-ФЗ от 29.12.2025](https://www.klerk.ru/blogs/fedresurs/704669/)). **На `.online` это требование не распространяется** |
| Хранение и предоставление данных | данные администратора хранятся у регистратора и передаются уполномоченным органам по запросу (РКН, суд, органы ОРД) |
| Исполнение предписаний РКН | приостановка делегирования домена по требованию РКН: реестр запрещённой информации, экстремизм, «фейки», наркотики, суицид; также при недостоверных данных о владельце |
| Ответственность за контент | **на вас, не на регистраторе**: регистратор — держатель записи, а не издатель |

Практический риск один и он не про Telegram: если сайт попадёт в реестр, домен перестанет
открываться **у всех** (не только в РФ), и Mini App умрёт до смены домена. Вероятность для
бота театра-студии — низкая; цена ошибки — один новый домен и повторный деплой (§3.3).

**3. Грозит ли наказание за вызовы «запрещённого приложения»?** Отдельной статьи за факт
обращения к API Telegram нет: блокировка техническая (ТСПУ), а не правовая. Что наказуемо:

| Действие | Ответственность |
|---|---|
| Пользоваться VPN/прокси | для граждан штрафа нет; нормы адресованы сервисам, поисковикам и рекламе |
| Реклама VPN, «способы обхода» | штрафы: граждане 50–80 тыс. ₽, юрлица до 500 тыс. ₽ (ч. 18 ст. 14.3 КоАП) |
| Иностранный мессенджер для общения с клиентами | **41-ФЗ** — только для перечня организаций: госорганы, банки и НФО, операторы связи, маркетплейсы, агрегаторы, владельцы соцсетей; с 01.06.2025 |

Театр-студия в перечень 41-ФЗ не входит, пока не оформлен как организация из списка;
личное использование мессенджеров не ограничено. Следить стоит за расширением перечня —
если он дойдёт до «исполнителей услуг», правило станет вашим, и это аргумент за VK-канал
(§15).

**4. Есть ли риск утечки данных в налоговую?** Автоматического канала «регистратор → ФНС»
нет: регистратор не налоговый агент и не отчитывается о клиентах. Но его данные доступны
уполномоченным органам по запросу, а ФНС — уполномоченный орган: в рамках проверки сведения
могут быть запрошены, как у любого контрагента. Для `.online` WHOIS публичный, но у
большинства регистраторов работает privacy-сервис; для физлиц в `.ru` данные скрыты
по умолчанию.

Что действительно видно налоговой и без домена: платежи (сервер, домен, LLM-подписка) — это
расходы по выписке, а не «утечка». И наоборот: если появятся поступления от студийцев, они
будут видны по эквайрингу/переводам, а не по регистратору. Домен здесь ни при чём.

### 3.5 Что покупать у регистратора, а что не нужно

Регистраторы предлагают десяток допуслуг при покупке домена. Для этого проекта нужны три
вещи, остальное — либо уже входит, либо решается другими инструментами.

**Нужно**

| Что | Почему |
|---|---|
| Регистрация домена на 1 год, на ваше имя | для `.online` (gTLD) ICANN требует реальные данные владельца; подставные данные — риск потери домена |
| DNS-серверы регистратора (`ns1/ns2.reg.ru`) | это и есть наш DNS: две A-записи (§3.3). Переносить в Cloudflare нельзя — он троттлится в РФ и ломает ACME |
| Автопродление + напоминание в календаре | просроченный домен перестаёт резолвиться, и Mini App «исчезает» без ошибки на сервере |
| Двухфакторная аутентификация в аккаунте регистратора | бесплатно и полезнее любого платного «замка»: домен угоняют через аккаунт, а не через WHOIS |

**Можно, но не обязательно**

- **Скрытие данных WHOIS.** Для gTLD персональные данные и так скрываются по требованиям
  ICANN; если регистратор предлагает это как платную опцию — проверьте, что она добавляет
  сверх бесплатного минимума.
- **Продление на 2–3 года** — только если цена фиксируется и выгодна; иначе берите год,
  а цену продления всё равно смотрите до оплаты (§3.1).

**Не нужно**

| Услуга | Почему нет |
|---|---|
| SSL-сертификат | Caddy выпускает и продлевает Let's Encrypt сам (§4) |
| Хостинг, «сайт», конструктор | сервер у Timeweb, статики нет |
| Почта на домене | письма Let's Encrypt приходят на любой ваш ящик; отдельный ящик `admin@` — не задача бота |
| CDN / «ускорение сайта» | трафик мизерный; прокси перед Caddy ломает HTTP-проверку ACME |
| «Домен-замок», «защита от кражи» | при 2FA и автопродлении ценность близка к нулю |
| Парковка, редирект, «резервный домен», брокер, аукцион | у нас свои A-записи и один домен |

Сразу после покупки: добавить A-запись `@` на IP сервера (TTL 300), проверить
`dig +short NS <домен>` (должны быть NS регистратора) и `dig +short @1.1.1.1 <домен>` (IP).
Подробности — §3.3.

## 4. Сертификаты безопасности

### 4.1 Кто их выпускает

Caddy сам получает сертификат Let's Encrypt (ACME) при первом HTTPS-запросе на домен и
продлевает за 30 дней до истечения. Руками ничего делать не нужно; самоподписанные
сертификаты Telegram Mini App не принимает — вариант не рассматриваем.

Что нужно, чтобы это работало:

- [ ] A-запись домена указывает на сервер (проверено `dig`);
- [ ] порт 80 открыт — по нему ACME проверяет владение доменом;
- [ ] порт 443 открыт — по нему отдаётся сайт;
- [ ] `SVOI_ACME_EMAIL` заполнен (иначе писем об истечении не будет);
- [ ] на домене нет чужого CDN-прокси (Cloudflare в режиме «Proxied» ломает HTTP-проверку).

### 4.2 Применение: один Caddyfile на один домен

Шаблон лежит в репозитории — `deploy/templates/Caddyfile.template`, подстановки делает
`deploy/server-deploy.sh proxy`. Что получается:

| Маршрут | Куда | Зачем |
|---|---|---|
| `https://teatr-svoi.online/webapp*` | tool-api:8000 | страницы Mini App |
| `https://teatr-svoi.online/api/*` | tool-api:8000, префикс снимается | API для Mini App и внешних проверок |
| `https://teatr-svoi.online/` | `200 SVOI` | заглушка, чтобы домен не выглядел мёртвым |

Заголовки безопасности (`HSTS`, `X-Content-Type-Options`, `Referrer-Policy`) уже в шаблоне.

Маршрута `https://n8n.<домен>/*` больше нет: V-026 (01.11.2026) вывел n8n из контура,
а вместе с ним — публичный редактор воркфлоу и открытый вебхук роутера. Проверка, что
дороги наружу нет: `curl -fsSI https://<домен>/webhook/router` отвечает 404.

### 4.3 Как проверить, что сертификат настоящий

```bash
# 1. цепочка и срок
echo | openssl s_client -connect teatr-svoi.online:443 -servername teatr-svoi.online 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates
# ожидание: issuer = Let's Encrypt, dates — свежие

# 2. браузерная проверка без предупреждений
curl -fsSI https://teatr-svoi.online | head -3
```

Продление смотреть раз в квартал: `journalctl -u caddy | grep -i "certificate obtained"`.

### 4.4 Если сертификат не выпускается

| Симптом в `journalctl -u caddy` | Причина | Что делать |
|---|---|---|
| `no such host`, `NXDOMAIN` | DNS ещё не сошёлся | ждать, `dig @1.1.1.1` |
| `connection refused :80` | закрыт порт 80 или занят | `sudo ufw status`, `ss -lntp \| grep :80` |
| `too many failed authorizations` | лимит Let's Encrypt (5 неудач/час) | исправить причину и подождать час, не повторять |
| `dns problem: SERVFAIL` | домен без NS или просрочен | проверить статус домена у регистратора |
| сертификат есть, но браузер ругается | прокси Cloudflare/Flexible SSL | выключить прокси или перейти на DNS-01 |

### 5.2 Правки кода, без которых Mini App на проде не откроется

Mini App уже отдаётся tool-api (`/webapp`, `/webapp/admin`, `/webapp/grid` …), но **из бота
на него нет ни одной кнопки**: в `services/tg-gateway/app/main.py` нет ни `web_app`, ни

ссылка нужна абсолютная и на HTTPS.

Шаг M-1. Один адрес вместо хардкода:

- [x] в `.env.example` добавлен `WEBAPP_BASE_URL=` (пусто — Mini App не показываем);
- [x] в гейтвее `WEBAPP_BASE_URL` читается, кнопка собирается только для `https://`

- [x] кнопки: «Открыть анкету» в `/profile`, «Открыть неделю» в помощи и в ответе «окон нет»;

- [x] меню бота: `SetChatMenuButton` с `menu_button.web_app` («Неделя»), если адрес задан;
- [ ] в `tool-api` ничего не меняется: страницы относительные, домен им не нужен.

Правило: **`http://` в проде — ошибка конфигурации, а не «пока сойдёт»**. Telegram не
откроет Mini App по HTTP, а человек увидит пустой экран без объяснений.

- [ ] `ENV=prod` (guard от записи в боевые файлы работает именно по нему);

- [ ] `TOOL_API_URL=http://127.0.0.1:8000` (переменных `N8N_*` больше нет: V-026);

`WEBAPP_SECRET`, `POSTGRES_PASSWORD`) — в вывод они не печатаются.

### 5.4.1 Что где лежит: сервер и мак (01.11.2026)

Разделение сред описано в `docs/infrastructure/08` §1a. Здесь — только карта файлов,
чтобы при выкате не перепутать: сервер и мак больше не делят один `.env`.

| Файл | Где | Что внутри | Кто читает |
|---|---|---|---|
| `.env.dev` | мак, в git не попадает (шаблон — `.env.dev.example`) | `DEV_BOT_TOKEN`, локальная БД, `TOOL_API_*`; боевых Google-идентификаторов нет | `scripts/run_service.py --env dev`, агенты launchd, `scripts/notify_admin.py` |
| `.env` | мак (локальная копия боевого конфига) и сервер | боевой `TELEGRAM_TOKEN`, боевые ID таблиц и календарей | на сервере — юниты systemd; на маке — ничего из локальных запусков |
| `deploy/svoi.env` | мак (из `deploy/svoi.env.example`) и сервер | настройки выката: домен, root, порты, ssh. **Токенов нет** | `deploy/*.sh` |
| `/opt/svoi/.env` | только сервер | то же, что `.env`, с `ENV=prod`, `600`, владелец `svoi` | `EnvironmentFile=` во всех юнитах |

Команды на маке:

```bash
.venv/bin/python scripts/run_service.py gateway --check    # что поднимется: среда, бот, БД
.venv/bin/python scripts/run_service.py gateway            # dev-бот, локальная БД
python scripts/install_launchd.py --doctor                 # агенты с --env dev, пути совпадают
python scripts/conflict_watch.py --apply                   # ловит 409 в логах гейтвея
```

На сервере `run_service.py` не используется: там сервисы поднимает systemd, который сам
читает `/opt/svoi/.env`. Поэтому `--env prod` локально нужен только для диагностики —
без доступа к боевому конфигу он честно откажется стартовать.

### 5.5 Что подготовить на локальной машине

```bash

pg_restore --list svoi-$(date +%F).dump | head   # дамп читается

# 2. тег релиза: на сервере ставим тег, а не «main на момент выката»

# 3. настройки переезда

```

Проверить счётчики, которые должны совпасть после переноса:

## 6. Первичная настройка сервера

Всё, что ниже, делает `deploy/server-deploy.sh` — по одному шагу за раз, чтобы было видно,

### 6.1 Проверка настроек (ничего не меняет)

deploy/server-deploy.sh check

```bash

```

Что происходит: пакеты (`python3-venv`, `git`, `ufw`, `fail2ban`, `rsync`, `curl`),
часовой пояс `Europe/Samara`, пользователь `svoi` с sudo, firewall «только 22/80/443»,
Docker, Caddy. Все действия идемпотентны — повторный запуск ничего не ломает.

```bash

timedatectl | grep "Time zone"  # Europe/Samara
id svoi                         # группы: svoi, sudo, docker, systemd-journal

```

Ключ для деплоя (с локальной машины, один раз):

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub -p 22 svoi@<IP>
ssh -p 22 svoi@<IP> true && echo "ssh без пароля работает"
```

С этого момента root по SSH не нужен: `sudo` через пользователя `svoi`. Рекомендуется
сразу закрыть вход по паролю и root-логин в `/etc/ssh/sshd_config.d/99-svoi.conf`:

```
PermitRootLogin no
PasswordAuthentication no
```

```bash
sudo sshd -t && sudo systemctl reload ssh
```

**Проверьте вход новым окном, не закрывая текущую сессию** — иначе можно остаться без доступа.

## 7. Развёртывание компонент

Порядок важен: база → API → домен/TLS → сервисы и таймеры → поллер последним.
(Шага «n8n» в этом порядке больше нет: V-026.)

### 7.1 База данных

```bash
sudo deploy/server-deploy.sh db --restore /tmp/svoi-2026-10-28.dump
# чистая база без переноса данных:
sudo deploy/server-deploy.sh db
# только миграции на уже существующей базе (обновление версии):
sudo deploy/server-deploy.sh db --migrate
```

Скрипт создаёт сеть `svoi`, контейнер `svoi-postgres` (порт только `127.0.0.1:5432`),
ждёт `pg_isready`, при `--restore` восстанавливает дамп и печатает счётчики.

Схема накатывается Alembic: файлы `db/init/*.sql` остаются единственным описанием
схемы, а учёт применённого живёт в таблице `alembic_version`. Каждая ревизия в
`services/tool-api/migrations/versions/` оборачивает ровно один SQL-файл и хранит его
sha256 — правка применённого файла валит накат, а не меняет историю молча. Поэтому
правило: **применённые файлы `db/init` не правятся**; новая схема — новый файл с новым
номером и новая ревизия (`scripts/gen_alembic_revisions.py`).

- `db` (чистая база) и `db --migrate` — `alembic upgrade head`. Повторный запуск
  ничего не применяет (no-op), одновременный — ждёт advisory lock в `env.py`.
- `db --restore` — после `pg_restore` сверяется **только номер версии**, read-only
  (`deploy/check_schema.py --expect-head`): совпал с головой цепочки — ставится
  `alembic stamp head` (baseline). Структуру флаг не сравнивает. Дамп, снятый до
  перехода на Alembic, версии не имеет и всегда останавливает `--restore` — это
  безопасное поведение, а не ошибка; структуру сверяют отдельно по §7.1.1.
  Не совпало — скрипт останавливается: сначала разбор расхождений,
  потому что `upgrade head` поверх чужой схемы не лечит, а маскирует.
- Миграции после восстановления **вслепую не накатываются**: повторный прогон
  опасных миграций данных мог бы перевернуть занятость (L-001).

Локальный контур (dev) идёт тем же путём и без отдельной команды: `docker compose up -d
postgres migrate` — сервис `migrate` (тот же образ, что у `tool-api`) выполняет
`alembic -c alembic.ini upgrade head` и завершается; `tool-api` стартует только после
`service_completed_successfully`, то есть на накатанной схеме. Mount
`db/init` в `docker-entrypoint-initdb.d` у `postgres` убран: initdb срабатывает лишь на
пустом томе, а на непустом молча пропускается — отсюда и расходилась схема dev и прода.

### 7.1.2 CI: job `images` накатывает схему Alembic

Job `images` в `.github/workflows/tests.yml` поднимает пустой `postgres:16` (mount `db/init`
в job убран), ждёт `pg_isready` и накатывает цепочку тем же образом, который стартует ниже:

```bash
docker run --rm --network svoi-ci \
  -e DATABASE_URL=postgresql://svoi:…@pg-ci:5432/svoi \
  svoi-tool-api:ci alembic -c alembic.ini upgrade head
```

Почему именно так: приложение схемы не накатывает — на старте оно только сверяет
`alembic_version` с головой цепочки и отказывается подниматься при расхождении (код выхода 3,
«схема не применена (version=нет, head=060_…)»). База из mount `db/init` таблицы создавала,
но `alembic_version` не имела, поэтому job `images` был красным по причине схемы, а не кода.
Теперь схема приходит ровно тем путём, что и на проде, и заодно проверяется, что
`alembic.ini`, `services/tool-api/migrations` и `db/init` действительно попали в образ.

Job по-прежнему выключен переменной `CI_GITHUB_RUNNERS=off` (квота минут Actions): правка
workflow его не включает. Удаление переменной — отдельное решение владельца, а не следствие
этой правки.

### 7.1.1 Baseline существующей БД

База, жившая до перехода на Alembic, не имеет `alembic_version`. Baseline ставится
только после сверки структуры — иначе учёт соврёт про применённое.

```bash
# 1. бэкап и точная копия боевой базы (на копии, не на боевой)
pg_dump -Fc svoi > /tmp/svoi-$(date +%F).dump
sudo -u postgres createdb -T svoi svoi_migr   # копия файлов, схема не пересобирается

# 2. эталон: пустая база, накатанная цепочкой
sudo -u postgres createdb svoi_check
DATABASE_URL=postgresql://svoi:***@127.0.0.1:5433/svoi_check \
  .venv/bin/alembic -c alembic.ini upgrade head

# 3. сверка структуры: отличаться должна только таблица alembic_version
pg_dump --schema-only --no-owner --no-privileges svoi_migr  > /tmp/migr.sql
pg_dump --schema-only --no-owner --no-privileges svoi_check > /tmp/check.sql
diff /tmp/migr.sql /tmp/check.sql

# 4. только при пустом diff (кроме alembic_version)
DATABASE_URL=postgresql://svoi:***@127.0.0.1:5433/svoi_migr \
  .venv/bin/alembic -c alembic.ini stamp head
```

`createdb -T` требует, чтобы к базе-источнику не было подключений: иначе
`source database is being accessed by other users`. На проде останавливают сервисы
или берут копию на отдельном хосте; для локальной проверки достаточно закрыть
лишние сессии.

**Ловушка `pg_restore`.** Пересборка копии через `pg_dump | pg_restore` может молча
потерять внешние ключи: ограничения добавляются после данных, и если в данных есть
нарушающие строки, `ALTER TABLE … ADD CONSTRAINT` падает, а `pg_restore` идёт дальше
с предупреждениями. Пустой `diff` такой копии с источником **не доказывает** совпадение
структуры. Поэтому копию делают через `createdb -T` (или проверяют, что `pg_restore`
не выдал ни одного warning, и отдельно сверяют число FK:
`select count(*) from pg_constraint where contype='f' and connamespace='public'::regnamespace`
должно совпасть с источником). Иначе baseline поставят на неполной схеме.

Шум, который в `diff` ожидаем и структурой не является: таблица `alembic_version` и её
первичный ключ (только в эталоне), строка `COMMENT ON SCHEMA public IS ''` (есть в базе,
созданной старым initdb), случайный токен `\restrict`/`\unrestrict` в шапке дампа.

Непустой `diff` — стоп, `stamp head` не ставить: расхождения перечисляются фактом,
затем либо точечный файл, либо `stamp <предыдущая ревизия>` + `upgrade head`.

Приложение на старте схему не создаёт: без накатанной версии `tool-api` отказывается
стартовать с текстом «схема не применена (version=…, head=…); выполните
`alembic upgrade head`», а не падает 500-й на первом запросе.

Проверки:

```bash
docker exec -i svoi-postgres psql -U svoi -d svoi -c "select count(*) from budget_tx;"
# число должно совпасть с локальным снимком (§5.5)
ss -lntp | grep 5432      # только 127.0.0.1:5432, не 0.0.0.0
```

**Дамп может отставать от кода.** Локальная база живёт своей жизнью: миграции в
репозитории появляются, а к ней не применяются. На проде это вылезло 30.10.2026 —
не было `participant.write_gender` и `budget_tx.is_plan`, и Mini App отвечал 500 на
неделе занятости и на записи операции.

```bash
sudo /opt/svoi/deploy/server-deploy.sh schema      # только отчёт, ничего не меняет
```

Отчёт `schema` сверяет и структуру, и версию: `--files` показывает, какому файлу
принадлежит недостающая таблица или колонка, `--expect-head` — совпадает ли
`alembic_version` с головой цепочки.

Основной путь лечения — `db --migrate` (то есть `alembic upgrade head`): он применяет
только недостающие ревизии и останавливается на первой ошибке. Точечный `psql` остался
аварийным путём: им накатывают один файл на базе, которую нельзя вести по цепочке
(часть миграций рассчитана на порядок «от чистой схемы» — 004 упирается в уникальность
алиаса, которую позже ослабили). После точечного наката версия в `alembic_version`
не двигается — её ставят `alembic stamp <ревизия файла>` осознанно.

```bash
# аварийно: один файл, без учёта версии
docker exec -i svoi-postgres psql -U svoi -d svoi -v ON_ERROR_STOP=1 \
  < /opt/svoi/db/init/039_write_gender.sql
```

### Смена LLM-провайдера: одна группа переменных

Адрес, ключ, модель и метка провайдера живут в `.env`, а не в коде (`app/llm.py`):

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `LLM_BASE_URL` | корень API **без** `/chat/completions` | `https://openrouter.ai/api/v1` |
| `LLM_API_KEY` | ключ провайдера | — (без ключа бот живёт на правилах) |
| `LLM_MODEL` | модель | `openai/gpt-4o-mini` |
| `LLM_PROVIDER` | метка в `llm_usage.provider` | выводится из домена: `openrouter`, `proxyapi`, `vsegpt`, иначе хост |
| `LLM_TIMEOUT_SECONDS` | таймаут ассистента | 45 |
| `LLM_MAX_TOKENS` | предел ответа ассистента | 700 |
| `LLM_TEMPERATURE` | температура ассистента | 0.3 |

Старые имена `OPENROUTER_API_KEY` и `ASSISTANT_MODEL` работают как алиасы: их можно
оставить, но при конфликте побеждает новое имя. Мусор в числах (`LLM_TIMEOUT_SECONDS=abc`)
не роняет сервис — берётся значение по умолчанию.

Роутер берёт те же переменные, что и ассистент (`app/llm.py`): отдельных настроек и
отдельного деплоя у него нет, пересобирать нечего. При смене провайдера правится только
`.env` приложения:

```bash
# на сервере: поменять LLM_* в /opt/svoi/.env и перезапустить сервис
sudo systemctl restart svoi-tool-api
```

Итого при смене провайдера правятся: `.env` (адрес, ключ, модель). Бизнес-логика не
меняется ни в одном из мест.

Проверка роутера изнутри сервиса (снаружи дороги нет — 404):

```bash
curl -s -X POST http://127.0.0.1:8000/tools/route \
  -H "Authorization: Bearer $TOOL_API_TOKEN" -H "X-Actor-Chat-Id: $ADMIN_CHAT_ID" \
  -H 'Content-Type: application/json' \
  -d '{"text":"расход 3000 на реквизит","user":{"name":"Тест","roles":["администратор"]}}'
# ожидание: {"ok":true,"intent":"budget","scenario":"budget","category":"Реквизит и костюмы",...}
```

### 7.5 Сервисы и таймеры

```bash
sudo deploy/server-deploy.sh units
```

Рендерит юниты из `deploy/systemd/` под `SVOI_ROOT` и `SVOI_USER`
(`deploy/render_units.py`), включает `svoi-tool-api` и все таймеры:
напоминания (09:00 и каждые 5 минут), инварианты (04:30), сторож (каждые 10 минут),
health-агент (каждые 5 минут), разбор обращений (каждые 10 минут). **Поллер
намеренно не включается** — он включается на шаге переключения (§8), иначе на
сервере и локально окажутся два читателя Telegram.

#### Разбор обращений на сервере: вопросы — ответ, баги — в dev

Правило владельца 02.11.2026: **на сервере баги и пожелания не разбираются** —
сервер не коммитит в git, работа идёт в dev-среде. Таймер
`svoi-feedback-triage` (`scripts/feedback_triage.py --apply`, каждые 10 минут,
`POST /tools/feedback/triage`) делает ровно это:

| Вид обращения | Что делает сервер | Что видит автор |
|---|---|---|
| `question` | ответ модели (тот же ассистент, что у `/tools/route`), журнал `source='server'` | ответ в боте в течение 10 минут |
| `praise` | короткий шаблон, без модели | «Спасибо! Передали команде.» |
| `bug`, `wish` | статус `seen`, журнал `source='server'`, текст «Принято, передано в разработку.» | только эта пометка |
| вопрос без ответа модели | ничего: обращение остаётся в очереди | попадает в дайджест «требует вас» |

Карту по багу или пожеланию заводит **только dev-среда**: `.github/workflows/feedback-watch.yml`
каждые 30 минут выгружает обращения, у которых нет строки журнала с источником
кроме `server`, в `feedback/inbox/`, а `scripts/feedback_inbox.py` на машине
разработчика создаёт из файлов карты. Мост выгружает доставленное сервером и
после выгрузки ставит `source='agent'` — поэтому повторная выгрузка дублей не
делает. Сервер в git не пишет и карт не создаёт.

Очередь неразобранных и ручной разбор остаются доступны человеку:
`GET /tools/feedback/open` и `POST /tools/feedback/decide`. Если серверный таймер
не ответил (нет ключа модели, сбой провайдера, обращение старше 6 часов) — оно
попадает в ежедневный дайджест 11:00 отдельным разделом «требует вас».

Локальный cron-разбор на машине разработчика остаётся резервом и выключается
**только после проверки серверного**: `hermes cron list`, задача
«teatrsvoi: разбор обращений (прод → канбан)».

```bash
systemctl list-timers 'svoi-*' --no-pager
sudo systemctl start svoi-notify-send.service && journalctl -u svoi-notify-send -n 20
```

Гейтвей здесь не запускаем. Его единственный экземпляр — предмет §8.

### 7.6 Бэкапы

```bash
sudo install -m 755 /opt/svoi/scripts/backup.sh /usr/local/bin/svoi-backup
# ежедневно в 03:00, окружение — из .env

  | sudo crontab -u svoi -
sudo -u svoi /usr/local/bin/svoi-backup        # первый бэкап сразу
```

Бэкап без проверки восстановлением — не бэкап. Раз в квартал:

```bash
docker exec -i svoi-postgres psql -U svoi -d postgres -c "create database svoi_check;"
docker exec -i svoi-postgres pg_restore -U svoi -d svoi_check /tmp/svoi_<дата>.dump
docker exec -i svoi-postgres psql -U svoi -d svoi_check -c "select count(*) from budget_tx;"
docker exec -i svoi-postgres psql -U svoi -d postgres -c "drop database svoi_check;"
```

Сторож (`svoi-watchdog.timer`) уже следит за свежестью бэкапа и диском; алерты идут в
Telegram через очередь `notification`, а не напрямую.

### 7.7 Мониторинг снаружи

Минимальный и достаточный набор — три проверки:

| Что | Чем | Порог |
|---|---|---|
| `/api/health` отвечает | Uptime Kuma / healthchecks.io (внешний) | 2 провала подряд |
| инварианты данных | `svoi-invariants.timer` (уже стоит) | любой FAIL |
| бэкап свежий | `svoi-watchdog.timer` (уже стоит) | нет файла моложе 24 ч |

### 7.8 Проверка контура одной командой: smoke

```bash
sudo deploy/server-deploy.sh smoke
```

Что проверяется и почему именно это:

| Проверка | Что ловит |
|---|---|
| исходящие `api.telegram.org`, `api.vk.com`, LLM | сервер в дата-центре с фильтрацией ТСПУ — бот не получит апдейты (§1.1) |

Код выхода 1 и список проблем — если хоть одна проверка красная. Это же запускать после
каждого обновления, вместе с `scripts/deploy-check.sh` (§10).

## 8. Переключение поллера: момент, когда бот меняет дом

Это самая рискованная операция переезда, потому что сообщения живых людей. Порядок
обязателен: **сначала гасим локальный читатель, потом поднимаем серверный**. Не наоборот:
две секунды с двумя поллерами — это потерянные апдейты и `409 Conflict` в логах.

Подготовка (за день):

- [ ] предупредить студийцев: «вечером бот может не отвечать 10 минут»;
- [ ] на сервере `deploy/server-deploy.sh smoke` — API, домен, база, n8n, инварианты зелёные;
- [ ] локально `.env` остаётся как был (dev-контур отдельный: своя база, свой токен — по
  возможности; если токен тот же, локальный поллер обязан оставаться выключенным);
- [ ] выбранное окно: не 09:00 (напоминания) и не 03:00 (бэкап).

Переключение:

```bash
# 0. готовность сервера принять поллер (ничего не меняет)
deploy/poller-switch.sh check

# 1. остановить локальный → запустить серверный → проверить 409 и число процессов
deploy/poller-switch.sh switch
```

Что делает скрипт по шагам: проверяет SSH, `/health` на сервере, наличие юнита, отсутствие
поллеров на сервере и число локальных; выгружает launchd-агент `com.svoi.gateway` и гасит
оставшиеся процессы; включает `svoi-gateway` на сервере; убеждается, что процесс ровно
один и в журнале нет `Conflict`; при любой проблеме **сам возвращает поллер локально** и
падает с кодом 1.

Что нужно для запуска с ноутбука (проверено 30.10.2026):

```bash
# в deploy/svoi.env: системные службы включаются только от root
SVOI_SSH_USER="root"
SVOI_SSH_KEY="~/.ssh/svoi_prod"
```

Скрипт не использует `ssh -t`: псевдотерминал нужен только интерактивному sudo, а без
терминала шаг молча не выполняется. Если вход уже root — sudo не нужен, иначе `sudo -n`.

После переключения — глазами:

- `journalctl -u svoi-gateway -n 20`: `Run polling for bot @…`, ни одного `409 Conflict`;
- `journalctl -u svoi-gateway | grep "меню бота"`: адрес Mini App уже новый домен;
- написать боту «кто я» — ответ должен прийти с сервера (локальный поллер выключен).

Таймеры переезжают отдельно и только после успешного переключения:

```bash
sudo /opt/svoi/deploy/server-deploy.sh units --with-timers   # включить серверные
systemctl start svoi-notify-plan.timer svoi-notify-send.timer \
                svoi-feedback-digest.timer svoi-invariants.timer \
                svoi-watchdog.timer svoi-health.timer \
                svoi-conflicts.timer svoi-cold-rotate.timer
# локальные launchd-агенты выгружены, иначе уведомления придут дважды
```

Проверки сразу после:

```bash
ssh svoi@<IP> 'systemctl status svoi-gateway --no-pager | head -5'
ssh svoi@<IP> 'pgrep -fc services/tg-gateway/app/main.py'      # 1
ssh svoi@<IP> 'journalctl -u svoi-gateway -n 50 --no-pager | grep -ci conflict'  # 0
```

И живая проверка, которую нельзя автоматизировать без второго аккаунта:

- [ ] написать боту «кто я» → отвечает именем и ролями;
- [ ] нажать «Бюджет» → цифры совпадают с локальными;
- [ ] «сколько у нас денег?» → тот же ответ, что на локали;
- [ ] запись расхода → строка появилась в Google Sheets;
- [ ] открыть Mini App из бота (§9.2) — страница грузится по HTTPS.

### 8.1 Если что-то пошло не так

| Симптом | Причина | Действие |
|---|---|---|
| бот молчит, в журнале `409 Conflict` | где-то второй поллер | `poller-switch.sh back`, найти второй процесс (`pgrep -af tg-gateway`) и убить |
| бот отвечает, но данные пустые | не тот `DATABASE_URL` / пустая база | `db --restore`, сверить счётчики |
| «не могу подтвердить» на всё | tool-api недоступен из гейтвея | `curl 127.0.0.1:8000/health`, `TOOL_API_URL` |
| Mini App не открывается | домен/TLS/`WEBAPP_BASE_URL` | `curl -I https://<домен>/webapp`, проверить кнопку в боте |
| LLM-ветка молчит, правила работают | n8n недоступен | `curl 127.0.0.1:5678/healthz`, credential OpenRouter |
| напоминания не идут | таймер не включён / тихие часы | `systemctl list-timers 'svoi-*'`, `journalctl -u svoi-notify-send` |

Аварийный откат поллера — одна команда:

```bash
deploy/poller-switch.sh back
```

Она гасит серверный поллер, проверяет, что на сервере их не осталось, и поднимает локальный.
Люди теряют максимум те апдейты, что пришли за секунды переключения.

### 9.2 Mini App: проверка на живом Telegram

3. поллер на сервере ровно один, локальный — ноль, в журнале нет `Conflict`.

## 10. Обновление версии и откат

### 10.1 Выкат

```bash
cd /opt/svoi
# клон мелкий (--depth 1): историю целиком не тянем, нужен один тег
git fetch --depth 1 origin v0.4.1
git checkout --force FETCH_HEAD
.venv/bin/pip install -r requirements.txt
sudo /opt/svoi/deploy/server-deploy.sh db --migrate
sudo systemctl restart svoi-tool-api svoi-gateway
bash scripts/deploy-check.sh            # /health, версия, поллер, юниты
```

Проще одной командой: `SVOI_REF=v0.4.1 sudo deploy/server-deploy.sh app` — она делает ровно
этот fetch и checkout.

`db --migrate` — это `alembic upgrade head`: применяются только неприменённые ревизии,
повторный запуск ничего не делает, параллельный ждёт advisory lock. Учёт — в
`alembic_version`; схема по-прежнему описана только в `db/init/*.sql`, и применённые
файлы не правятся (правка меняет sha256 и валит накат — так и задумано).

Правило миграций: новая версия сначала **добавляет** колонки, удаляет — через релиз.
Тогда откат кода не требует восстановления базы (`docs/infrastructure/35` §10).

### 10.2 Откат

```bash
sudo /opt/svoi/deploy/server-deploy.sh rollback v0.4.0
```

Скрипт переключает код на тег, ставит зависимости, перезапускает API и проверяет `/health`.
База не откатывается — это осознанно: миграции аддитивные. Обратной миграции в ревизиях
нет вообще: `downgrade` в каждой поднимает `raise NotImplementedError` (решение 518,
`docs/reports/132-db-schema-single-source-plan.md`). Если откат базы всё же нужен, это
восстановление из дампа, снятого до выката, а не `alembic downgrade`; после восстановления
версию ставят по §7.1.1 только после сверки структуры.

## 11. Обслуживание и стоимость

| Что | Как часто | Команда |
|---|---|---|
| обновления ОС | раз в месяц | `sudo apt update && sudo apt upgrade -y` |
| место на диске | еженедельно (и алерт) | `df -h /` |
| срок сертификата | раз в квартал | `openssl s_client … -dates` |
| восстановление бэкапа | раз в квартал | §7.6 |
| ротация журналов | авто (journald) | `SystemMaxUse=1G` |
| обновление зависимостей | раз в квартал | `pip list --outdated`, тесты, выкат |

Стоимость в месяц: сервер 1 500–2 000 ₽ (Timeweb Cloud EU; Hetzner ≈ €8 при зарубежной
карте), домен `.online` — ориентир 100–250 ₽/мес в пересчёте с годовой оплаты (смотрите
цену продления), TLS 0 ₽, внешний монитор 0 ₽ (бесплатный тариф), бэкапы 0 ₽ (диск сервера
+ Google Drive). Итого **1 600–2 300 ₽/мес**. Резерв на «managed Postgres, если данные
вырастут» — от 1 500 ₽/мес.

Скрытая статья, о которой легко забыть: **LLM**. Разбор фраз идёт через модель, и расход
зависит от числа сообщений. Смотрите `llm_usage` в базе (`tokens_in`, `tokens_out`) и
`v_intent_gaps`; квота на человека задаётся в профиле, а не «на глаз».

## 12. Что нельзя делать

1. Запускать два поллера — локальный и серверный (`409 Conflict`, потерянные сообщения).
2. Копировать локальный `.env` на сервер: dev-токен, локальные пути, чужой `TOOL_API_TOKEN`.
3. Открывать Postgres, n8n или tool-api наружу «на минутку, проверить».
4. Передавать секреты через чат, почту или мессенджер.
5. Править воркфлоу только в UI n8n, не выгружая в `n8n/workflows/`.
6. Оставлять `http://` в `WEBAPP_BASE_URL` — Mini App просто не откроется.
7. Ставить на прод самоподписанный сертификат или прокси Cloudflare в режиме Flexible.
8. Считать бэкап сделанным, ни разу его не восстановив.
9. Брать сервер в РФ «потому что дешевле»: из дата-центров РФ Telegram API не отвечает
   (§1.1), и бот не получит ни одного апдейта. Проверка — три `curl` из §2.3.
10. Ставить DNS на Cloudflare: в РФ он троттлится, и сертификат «загадочно» не выпускается.

## 14. Данные, 152-ФЗ и будущее оформление театра

Это не юридическая консультация, а фиксация того, что мы решили и чем платим за решение.

**Что решили (ADR-9).** Сервер — за пределами РФ. Причина: из дата-центров РФ не работает
Telegram API (§1.1), а данные и так находятся вне РФ (Google Drive/Sheets). Размещение
сервера не создаёт и не решает вопрос локализации персональных данных.

**Что это значит по 152-ФЗ.**

| Ситуация | Требование | Наше состояние |
|---|---|---|
| Театр не оформлен как юрлицо | ст. 18 ч. 5 152-ФЗ формально адресована операторам ПД; у физлица без регистрации обязательств по локализации нет | рисков нет, риск принят осознанно |
| Появилось ИП/ООО/НКО | первичная база ПД россиян должна быть в РФ | **нарушено уже сейчас** — имена, телефоны, суммы лежат в Google. Сервер тут ни при чём |
| Появился приём платежей | фискализация, кассы, отчётность | отдельный проект, не связанный с хостингом |

Вывод: переезд в РФ ради 152-ФЗ не имеет смысла, пока источник истины — Google Sheets.
Когда появится юрлицо, придётся решать перенос **данных** (Google → РФ-хранилище), а не
перенос VPS. Это отдельная задача с отдельным бюджетом.

**Что делать сейчас, чтобы будущий перенос был дешёвым:**

- держать персональные данные в одном месте (Postgres) и не дублировать их в логах —
  правило уже соблюдается: `tool-api` пишет id, а не ФИО;
- не смешивать «канал» и «данные»: Telegram/ВК — идентификатор связи, всё остальное — в БД
  (это же требование из разбора Habr: `tg_chat_id` не должен быть ключом человека);
- помнить, что бэкап — тоже копия данных: дампы уезжают на тот же сервер и в Google Drive.

**Риск, который мы принимаем явно:** при оформлении театра придётся либо переносить данные
в РФ (и тогда Telegram-канал на RU-сервере не работает — противоречие архитектуры), либо
оставаться в серой зоне до первого требования. Второй путь дешевле сейчас и дороже потом;
это осознанный выбор владельца, а не недосмотр.

## 15. Будущий VK-канал: что учесть в инфраструктуре сейчас

VK-адаптер в планах. Хорошая новость: он почти не влияет на выбор хостинга, но влияет на
несколько инженерных решений, которые дешево принять заранее и дорого — потом.

### 15.1 Что требует VK и зависит ли это от локации

| Что нужно | Зависит от локации сервера? |
|---|---|
| Callback API: публичный HTTPS, валидный сертификат, ответ < 3 с | нет — домен и TLS у нас есть в любой локации |
| VK должен достучаться до нашего вебхука (серверы VK в РФ) | нет — зарубежный адрес из РФ доступен, блокировки нет |
| Bots Long Poll (исходящий, без входящего порта) | нет — как и Telegram polling |
| Ключ доступа сообщества, приложение, телефон РФ для аккаунта | нет — это про аккаунт VK, не про сервер |

Геоблокировок `api.vk.com` для зарубежных IP в документации нет; проверяется одним
`curl` — эта проверка уже стоит в `smoke` рядом с Telegram и LLM (§7.8).

Реальные риски VK лежат не в сети: платформа ужесточает доступ сторонних приложений и
меняет правила игры. Это аргумент за то, чтобы канал был сменяемым, а не единственным.

### 15.2 Что заложить заранее

1. **Транспортно-нейтральная логика.** Уже так: бизнес-правила в `tool-api`, канал — в
   гейтвее. VK-адаптер — новый сервис `services/vk-gateway`, который ходит в тот же API.
   Ни одной строки бизнес-логики в нём быть не должно.
2. **Быстрый ack вебхука.** VK требует ответа за 3 секунды, иначе повторяет событие.
   Обработчик VK должен подтверждать приём и ставить работу в очередь, а не считать бюджет
   внутри вебхука (в Telegram-polling этой проблемы нет — там обработка синхронная).
3. **Идемпотентность по `event_id`.** VK доставляет повторно так же, как Telegram; для
   действий с деньгами ключ операции обязателен (в проекте это уже правило — `C-10`).
4. **Никакой геоблокировки в `ufw`.** Вебхуки придут с российских адресов VK: фильтр
   «только ЕС» или «только свои IP» убьёт канал.
5. **Один идентификатор человека на все каналы.** `tg_chat_id` и `vk_user_id` — атрибуты
   канала, а не личности; в БД уже есть `participant.id`, к нему и привязываемся.
6. **Mini App под VK** — это VK Bridge и отдельная точка входа, но тот же домен и те же
   страницы. Требование HTTPS совпадает с Telegram, так что переезд ничего не ломает.

### 15.3 Что изменится, если VK станет основным каналом

Тогда впервые появится сценарий «Telegram можно выключить». В этот момент станут
осмысленны и РФ-хостинг, и 152-ФЗ-совместимое хранение — но только вместе с переносом
данных из Google. Пока Telegram остаётся хотя бы вспомогательным каналом, сервер за
пределами РФ — единственная локация, где работают оба канала одновременно.

Переезд в таком будущем не должен быть переписыванием: ровно для этого скрипты `deploy/`
не содержат адресов, а домены и порты живут в `deploy/svoi.env`. Практическая цена
переезда — те же 2–3 часа по этой инструкции.

### 15.4 Сколько стоит VK-фронт прикладной части

Здесь — только инфраструктура. Прикладная оценка (что из страниц и API переносится
целиком, пять разрывов, объём работ по этапам) — `docs/reports/116`. Коротко, чтобы не
искать: VK Mini App как второй вход при живом Telegram — 5–8 рабочих дней агента, полный
второй канал с сообщениями и уведомлениями — ещё 2–4 недели, платежи VK не нужны (деньги
подтверждает человек). Решение по второму адресу при этом не требуется: домен один, он
доступен из РФ (§16).

## 16. Доступность Mini App из РФ: замер, мониторинг и что делать при блокировке

не было. Симптом был такой: с сети владельца `https://svoi-theater-samara.online` не

проверки (Jina, check-host, узел ru1) отвечали `ok`. Ощущение «домен заблокирован в РФ»
не подтвердилось ни одним замером, но и опровергнуть его было нечем: не было ни

делать при каждом вердикте и как узнать о блокировке раньше участников.

### 16.2 Как померить: одна команда

```bash
# с мака или с сервера — источник замера внешний, машина не важна
env -u PYTHONPATH .venv/bin/python scripts/check_availability.py
# домен берётся из SVOI_DOMAIN / deploy/svoi.env / WEBAPP_BASE_URL, если не задан --domain
env -u PYTHONPATH .venv/bin/python scripts/check_availability.py \
  --domain svoi-theater-samara.online --probes 10 --min-ok 5 --json /tmp/availability.json
```

Что делает скрипт:

1. **Прямая проверка** `GET https://<домен>/api/health` с этой машины — жив ли сервер
   и TLS. Это единственное, что можно проверить «изнутри».
2. **Замер с узлов РФ** через Globalping: по умолчанию 8 проб из России плюс адресно
   сети МТС (`AS8359`), Билайна (`AS3216`), Ростелекома (`AS12389`) и МГТС (`AS25513`).
   Замер идёт не с вашей машины, поэтому VPN, локальный DNS и домашний Wi-Fi на
   результат не влияют. Запасной источник — check-host.net (`--provider check-host`,
   два узла в Москве), он же подхватывается сам, если Globalping недоступен.
3. **Вердикт** и код выхода:

| Вердикт | Код | Значение | Что делать |
|---|---|---|---|
| `ok` | 0 | ответили не меньше `--min-ok` узлов | ничего; это и есть «домен доступен» |
| `partial` | 1 | часть узлов не ответила | смотреть, какие сети упали: одна сеть — жалоба оператора, все — смотреть сервер и маршрут |
| `blocked` | 1 | не ответил ни один узел | адрес режут целиком: см. §16.4 |
| `unknown` | 2 | измерить не удалось (оба источника недоступны) | это не провал доступности: проверить связь с API замеров, админа не будить |

Код 2 отдельный намеренно: «не смогли померить» и «адрес не работает» — разные события,
и путать их значит повторять историю 02.11.2026.

Машинный отчёт (`--json`) хранит по каждому узлу город, сеть, ASN, код, TLS и время —
именно его прикладывают к карте, когда спорят «работает или нет».

### 16.3 Что делать при каждом вердикте

| Что видно | Первая проверка | Дальше |
|---|---|---|
| `ok`, но жалуется один человек | его сеть и устройство, а не сервер: открыть `https://<домен>/webapp` в браузере телефона без VPN | если у него не открывается, а у узлов открывается — это его оператор; собрать оператора, сеть, экран |
| `partial`, упала одна сеть | `--probes 12`, чтобы увидеть, все ли узлы этой сети лежат | жалоба оператору связи; параллельно проверить, не менялся ли IP сервера |
| `blocked` | `dig +short <домен> @1.1.1.1` — тот ли IP; `curl -fsS https://<домен>/api/health` с сервера по `127.0.0.1:8000` | сервер жив, а снаружи нет — блокировка маршрута/адреса; §16.4 |
| `unknown` | связь с `api.globalping.io` и `check-host.net` с этой машины | ничего не менять; повторить через 10 минут |
| страница не открылась, а замер `ok` | журнал Caddy за последние 20 минут: есть ли запросы с устройства (`docs/infrastructure/35`) | если запросов нет — проблема до сервера (сеть устройства, WebView); если есть и код не 200 — смотреть API |

Правило: **сначала замер, потом гипотезы.** Любая правка кода Mini App или DNS до
замера — это ставка, а не диагностика.

### 16.4 Если блокировка подтвердилась

Порядок жёсткий: подтверждение → решение владельца → работа. Перенос прода и покупка
нового домена — отдельное решение владельца, а не техническая мелочь.

1. **Подтвердить и записать.** `--provider both --probes 12 --json` — сохранить отчёт
   в карту. Проверить, что дело не в DNS: `dig +short <домен> @1.1.1.1` и `@8.8.8.8`
   должны давать IP сервера.
2. **Отличить блокировку IP от блокировки по имени.** Замер по IP
   (`--domain 203.0.113.10`, сертификат при этом не совпадёт — это ожидаемо) и по
   домену: если по IP открывается, а по имени нет — режут SNI/имя; если не открывается
   ни то, ни другое — режут адрес.
3. **Выбрать решение из таблицы** — это развилка владельца, у вариантов разная цена:

| Вариант | Что даёт | Цена и риск |
|---|---|---|
| второй домен на **другом IP** (тот же или новый сервер) | обход блокировки адреса; старый домен остаётся рабочим для всех остальных | новый домен (1,5–3 тыс. ₽/год), правка Caddy, смена `WEBAPP_BASE_URL`, BotFather |
| CDN/прокси перед сервером (Cloudflare и подобные) | меняет IP на адреса CDN, TLS на краю | бесплатный тариф, но в РФ CDN троттлится и ломает HTTP-проверку ACME (§3.3); нужен режим Full (strict) или DNS-01 |
| реверс-прокси в РФ | адрес в РФ, до сервера — по туннелю | второй сервер (деньги, 152-ФЗ), второй владелец сбоя (§1.1) |
| ничего не менять, только мониторинг | честная картина и раннее предупреждение | блокировка останется; годится, когда жалуется одна сеть |

4. **Не менять код Mini App.** Ни один из вариантов не требует правок страниц: адрес
   живёт в `WEBAPP_BASE_URL` и в Caddy, страницы относительные (§5.2).

### 16.5 Если решение — второй домен: чек-лист

Домен имеет смысл только на **другом IP**: второй домен на тот же адрес не обходит
блокировку адреса, а создаёт иллюзию решения.

- [ ] A-запись нового домена на новый IP (TTL 300), проверено `dig @1.1.1.1`
- [ ] сервер отвечает `https://<новый домен>/api/health` → `ok: true` (Caddy: второй
      site-блок в `/etc/caddy/Caddyfile`, сертификат выпускается сам, §4)
- [ ] `WEBAPP_BASE_URL=https://<новый домен>` в `/opt/svoi/.env`, `systemctl restart svoi-tool-api svoi-gateway`
- [ ] BotFather: `/setdomain` для бота — новый домен (Mini App должен быть привязан к
      домену, иначе Telegram откроет страницу в чужом контексте)
- [ ] кнопка меню бота ведёт на новый адрес: после рестарта гейтвея в журнале
      `journalctl -u svoi-gateway | grep "меню бота"` — новый домен (§5.2)
- [ ] тест обоих адресов: `scripts/check_availability.py --domain <старый>` и
      `--domain <новый>` — оба `ok` по каждому адресу (критерий приёмки «health по
      обоим адресам»)
- [ ] записать в §16.6, какой адрес основной и какой резервный

Старый домен после переезда не выключаем: он работает у всех, у кого не blocked, и
стоит копейки.

### 16.6 Мониторинг: узнать раньше участников

`svoi-geo-check.timer` (каждый час в :20) запускает
`scripts/check_availability.py --apply --probes 8 --min-ok 5`. При `blocked` или
`partial` админам ставится уведомление в очередь `notification` — тот же путь, что у
сторожа и health-агента, с дедупликацией по проблеме и часу. При `unknown` (не смогли
померить) уведомления нет: иначе падение Globalping выглядело бы как падение прода.

```bash
systemctl list-timers 'svoi-geo-check*' --no-pager
journalctl -u svoi-geo-check -n 40 --no-pager          # последние замеры
sudo systemctl start svoi-geo-check.service            # замерить прямо сейчас
```

Чего этот сторож **не** видит и не заменит:

* блокировку у конкретного оператора в одном городе, если другие узлы живы — это
  `partial`, и его видно только при жалобе;
* проблемы WebView на устройстве (кэш, старая версия клиента) — сервер видит только
  отсутствие запросов;
* деградацию скорости (1,2 с у Timeweb в замере — ещё не поломка, но уже повод
  посмотреть).

### 16.7 Что осталось открытым

* **Замер с устройства без VPN на двух операторах** (iPhone + Android) — делается
  руками владельца: замеры с узлов показывают маршрут, а не WebView. Чек-лист — §9.2.
* **Решение по второму адресу принято 03.11.2026: домен остаётся один.** Замер блокировки

## Приложение В. Если бот молчит: одна страница

1. `curl -s http://127.0.0.1:8000/health` — API жив?
   - нет → `systemctl restart svoi-tool-api`, `journalctl -u svoi-tool-api -n 50`.
2. `pgrep -fc services/tg-gateway/app/main.py` — поллер ровно один?
   - 0 → `systemctl start svoi-gateway`, смотреть `journalctl -u svoi-gateway`;
   - 2+ → лишний убить, разобраться, откуда взялся.
3. `journalctl -u svoi-gateway -n 100 | grep -i conflict` — есть `409`?
   - да → значит, где-то второй читатель Telegram (локальный контур, старый процесс).
4. `docker exec svoi-postgres pg_isready -U svoi` — база жива?
   - нет → `docker start svoi-postgres`, дальше `db --migrate`.
5. `curl -s http://127.0.0.1:5678/healthz` — n8n жив?
   - нет → `docker restart n8n-prod`; правила продолжат работать без LLM-ветки.
6. `curl -fsSI https://<домен>/webapp` — Mini App отдаётся?
   - нет → `systemctl status caddy`, сертификат и DNS (§4.4).
7. Всё зелёное, а бот молчит → проверить, что у бота на сервере тот же `TELEGRAM_TOKEN`,
   и написать ему `/start` из другого аккаунта.

## Приложение Г. Короткий прогон: сервер получен, что делать

Сжатая версия §6–§11 — на один экран, когда сервер уже выдан. У каждой команды указано,
что должно быть в ответе.

**0. На маке**

```bash
cp deploy/svoi.env.example deploy/svoi.env && chmod 600 deploy/svoi.env
nano deploy/svoi.env      # SVOI_DOMAIN, SVOI_N8N_DOMAIN, SVOI_ACME_EMAIL, SVOI_REPO, SVOI_SERVER
deploy/server-deploy.sh check                 # «настройки в порядке»
```

**1. Первый вход и проверка локации** — шлюз, дальше идти нельзя, если красно

```bash
ssh -i ~/.ssh/svoi_prod root@<IP>
nproc && free -h && df -h / && lsb_release -ds        # 2 / ~4Gi / >=60G / 24.04
for u in https://api.telegram.org/ https://api.vk.com/method/utils.getServerTime \
         https://openrouter.ai/api/v1/models; do
  printf '%s -> ' "$u"; curl -s -o /dev/null -m 8 -w '%{http_code}\n' "$u"
done                                                  # 302 / 200 / 200
```
`000` у `api.telegram.org` → менять дата-центр, не начиная установку.

**2. Скрипты и подготовка сервера**

Сначала `provision`: он создаёт пользователя `svoi`, firewall, Docker, Caddy и swap.
До этого шага `sudo -u svoi` отвечает `unknown user svoi` — это ожидаемо.

```bash
# на маке
scp -i ~/.ssh/svoi_prod -r deploy root@<IP>:/tmp/svoi-deploy
# на сервере
sudo /tmp/svoi-deploy/server-deploy.sh provision
ufw status | head -6            # 22, 80, 443
timedatectl | grep "Time zone"  # Europe/Samara
id svoi                         # пользователь появился, группы sudo, docker, systemd-journal
```

**3. Ключ деплоя** (репозиторий приватный)

Ключ создаётся **от рабочего пользователя** — он существует после шага 2. Деплой-скрипт
запускает `git` через `runuser -u svoi`, поэтому ключ, положенный в `/root/.ssh`, для него
не существует.

```bash
sudo -u svoi ssh-keygen -t ed25519 -N "" -C "svoi-prod-deploy" \
     -f /home/svoi/.ssh/id_ed25519
sudo cat /home/svoi/.ssh/id_ed25519.pub
```
GitHub → репозиторий → Settings → Deploy keys → Add deploy key (**read-only**) → вставить.
Если ключ лежит по другому пути, укажите его в `deploy/svoi.env`: `SVOI_GIT_KEY=...`.
Проверка от имени svoi:

```bash
sudo -u svoi ssh -i /home/svoi/.ssh/id_ed25519 -o IdentitiesOnly=yes -T git@github.com
# «Hi <аккаунт>/<репозиторий>! You've successfully authenticated...»
```

**4. Код**

```bash
sudo /opt/svoi/deploy/server-deploy.sh app    # клон ≈7 МБ, venv, зависимости
```

`deploy/svoi.env` в git не попадает (`.gitignore`), поэтому в свежем клоне его нет —
скопируйте настройки из каталога, откуда ставили:

```bash
sudo install -m 600 /tmp/svoi-deploy/svoi.env /opt/svoi/deploy/svoi.env
```

Без этого файла любая следующая команда `server-deploy.sh` не найдёт адресов.

**5. Секреты**

```bash
sudo /opt/svoi/deploy/server-deploy.sh env     # .env + 4 случайных секрета, WEBAPP_BASE_URL из домена
sudo -u svoi nano /opt/svoi/.env               # TELEGRAM_TOKEN, ADMIN_CHAT_ID, LLM_API_KEY,
                                               # ID таблиц и календарей
```

Значения, которые уже есть в локальном `.env` на маке, можно перенести, не печатая их в чат:
локальный скрипт отдаёт JSON нужных ключей по ssh, серверный `apply_env.py` вписывает их в
`/opt/svoi/.env` и печатает только имена ключей.

Секретный файл сервисной учётки:

```bash
scp -i ~/.ssh/svoi_prod secrets/google-sa.json root@<IP>:/tmp/
# на сервере:
install -m 600 -o svoi -g svoi /tmp/google-sa.json /opt/svoi/secrets/google-sa.json && rm -f /tmp/google-sa.json
```

**6. База**

```bash
# на маке
pg_dump -h 127.0.0.1 -p 5433 -U svoi -Fc svoi > svoi-$(date +%F).dump
scp -i ~/.ssh/svoi_prod svoi-$(date +%F).dump root@<IP>:/tmp/
# на сервере
sudo -S -p '' /opt/svoi/deploy/server-deploy.sh db --restore /tmp/svoi-$(date +%F).dump
# счётчики операций/часов/людей должны совпасть с локальными
```

**7. TLS** (A-записи уже указывают на IP; проверка `dig +short @1.1.1.1 <домен>`)

```bash
sudo -S -p '' /opt/svoi/deploy/server-deploy.sh proxy  # «TLS в порядке»
```

**8. n8n** — вручную один раз в `https://n8n.<домен>`: владелец, credential LLM, Published

```bash
sudo -S -p '' /opt/svoi/deploy/server-deploy.sh n8n
```

**9. Сервисы и таймеры** (поллер пока не включаем)

```bash
sudo -S -p '' /opt/svoi/deploy/server-deploy.sh units
```

**10. Проверка контура**

```bash
sudo -S -p '' /opt/svoi/deploy/server-deploy.sh smoke   # исходящие API, health, HTTPS, Mini App, база, n8n
```

**11. Переключение поллера** — с мака, одна команда

```bash
deploy/poller-switch.sh check && deploy/poller-switch.sh switch
```

**12. Приёмка**: `/api/health` → `"env":"prod"`; боту «кто я»; «сколько у нас денег?»;
«расход 3000 на реквизит» → строка в Sheets; `/profile` → «Данные записаны».

Ориентир: 1,5–2 часа, из них 20–30 минут — DNS и установка пакетов.
