# 110. Бэкапы БД: где лежат, сколько живут, как восстановить

Решение владельца V-027: **7 ежедневных дампов, глубина хранения — одна неделя, место — на
сервере**. Раньше `scripts/backup.sh` работал только руками, и отсутствие бэкапа ловил сторож
постфактум; теперь дамп снимает таймер, а сторож остаётся вторым контуром.

Карта, из которой вырос документ, ссылалась на `docs/infrastructure/75`; номер 75 занят
(`75-hosting-and-migration.md`), как и 104 (аудит тестов), поэтому по правилу «следующий
свободный номер» документ получил 110.

## 1. Коротко

| Вопрос | Ответ |
|---|---|
| Кто отвечает | Виктор (владелец сервера); агент файлы готовит, но на сервер не выкатывает |
| Где дампы | `/opt/svoi/backups/` (`SVOI_BACKUP_DIR` в `/opt/svoi/.env`), файлы `svoi_ГГГГ-ММ-ДД_ЧЧММ.dump` |
| Формат | `pg_dump -Fc` (custom, сжатый), читается `pg_restore` |
| Когда снимается | каждый день в 03:30 по Самаре, `svoi-backup.timer` |
| Сколько хранится | ровно 7 последних `svoi_*.dump`; более старые удаляет сам `backup.sh` |
| Второй контур | `svoi-watchdog.timer` каждые 10 минут: дамп старше 24 часов → «нет свежего бэкапа» |
| Файлы бота | `/opt/svoi/backups/storage/`, тот же прогон, тот же срок (7 дней, `scripts/storage_backup.py`) |

## 2. Как это устроено

```
svoi-backup.timer  (03:30 Europe/Samara)
        │
        ▼
svoi-backup.service  (oneshot, User=svoi, EnvironmentFile=/opt/svoi/.env)
        │
        ▼
/opt/svoi/scripts/backup.sh
   1. docker exec svoi-postgres pg_dump -U svoi -Fc svoi > svoi_<штамп>.dump
   2. файл не пустой и читается `pg_restore --list` — иначе код 1 (таймер в failed)
   3. ротация: оставить BACKUP_KEEP=7 последних `svoi_*.dump`, старые удалить
   4. `df -h` в журнал: свободное место видно при каждом прогоне
   5. storage_backup.py — копия объектного хранилища, KEEP_DAYS=7
```

Юниты лежат в репозитории: `deploy/systemd/svoi-backup.service` и
`deploy/systemd/svoi-backup.timer`. Установка — `deploy/server-deploy.sh units --with-timers`
(рендер в `/etc/systemd/system`, `daemon-reload`, `enable`).

Проверить, что таймер жив:

```bash
systemctl list-timers svoi-backup.timer
systemctl status svoi-backup.timer svoi-backup.service
journalctl -u svoi-backup.service -n 30 --no-pager
```

Ожидаемо: строка `svoi-backup.timer` с ближайшим запуском и `NEXT` на 03:30, в журнале —
`бэкап готов: /opt/svoi/backups/svoi_...dump (...)`, `дампов в каталоге: 7 (храним 7)`.

Ручной прогон (он же первый прогон после установки):

```bash
sudo systemctl start svoi-backup.service
sudo journalctl -u svoi-backup.service -n 20 --no-pager
ls -lt /opt/svoi/backups/svoi_*.dump | head
```

## 3. Ротация и место

- Хранится ровно 7 файлов `svoi_*.dump`. Восьмой прогон удаляет самый старый; проверка —
  «8 дампов → осталось 7, самого старого нет».
- Единственное правило удаления — число файлов, а не возраст: счёт идёт по имени файла
  (в нём дата и время), `mtime` не участвует. Скопированный или восстановленный из архива
  дамп меняет возраст, но не должен выпадать из окна; и наоборот, дамп с испорченным `mtime`
  не удаляется, пока он входит в семёрку самых новых по имени.
- Из этого следует: если таймер почему-то стоял неделю, в каталоге останутся 7 старых дампов,
  а не пусто. Устаревание в этом случае ловит сторож (дамп старше 24 часов → «нет свежего
  бэкапа»), а не удаление: лучше старый дамп, чем ни одного.
- `KEEP_DAYS=7` (переменная окружения) к дампам БД не применяется — она задаёт срок для копии
  объектного хранилища (`scripts/storage_backup.py`), у него своя ротация по возрасту.
- Свободное место печатается в журнал каждым прогоном. После первой недели посмотреть:

```bash
df -h /opt/svoi/backups
du -sh /opt/svoi/backups /opt/svoi/backups/storage
```

Ориентир: один дамп рабочей базы — единицы-десятки мегабайт; 7 дампов + storage укладываются
в диск 60 ГБ. Если `df` показывает занятость выше 85%, сторож тоже пришлёт «диск занят».

## 4. Восстановление

Восстановление возвращает базу к состоянию на момент дампа: **все данные, появившиеся после
него, пропадут**. Поэтому сначала останавливаем пишущие сервисы.

1. Выбрать дамп и убедиться, что он читается:

```bash
ls -lt /opt/svoi/backups/svoi_*.dump | head
sudo docker exec -i svoi-postgres pg_restore --list < /opt/svoi/backups/svoi_2026-10-31_0826.dump | head
```

2. Остановить бота и API (иначе они пишут в базу во время восстановления):

```bash
sudo systemctl stop svoi-gateway.service svoi-tool-api.service
```

3. Восстановить одной командой — `--clean --if-exists` удаляет объекты текущей схемы и
   создаёт их из дампа, `--no-owner` не требует совпадения ролей:

```bash
sudo docker exec -i svoi-postgres pg_restore -U svoi -d svoi --clean --if-exists --no-owner \
  < /opt/svoi/backups/svoi_2026-10-31_0826.dump
```

`pg_restore` может напечатать предупреждения о уже удалённых объектах — это нормально.
Ненормально: `error:` в выводе или код возврата не 0. Повторить с `--verbose`, если ошибок
много, и не запускать сервисы, пока ошибки не разобраны.

4. Поднять сервисы и проверить, что база отвечает:

```bash
sudo systemctl start svoi-tool-api.service svoi-gateway.service
curl -sf http://127.0.0.1:8000/health
sudo docker exec svoi-postgres psql -U svoi -d svoi -c 'select count(*) from participant;'
```

`/health` должен вернуть `"ok": true`, счётчик участников — число, близкое к ожидаемому.

5. Сразу снять свежий дамп восстановленного состояния, чтобы следующий сбой не откатил
   снова в старую точку:

```bash
sudo systemctl start svoi-backup.service
```

### Если база не поднимается после восстановления

- `database "svoi" does not exist` — контейнер пересоздан без тома: проверьте
  `docker compose ps`, `docker volume ls`, не начинайте восстановление в пустую базу
  без понимания, куда делся том.
- `role "svoi" does not exist` — восстановление шло в другой контейнер/кластер; проверьте
  `docker exec svoi-postgres psql -U postgres -c '\du'`.
- Ошибки расширений (`pg_trgm`, `uuid-ossp`) — расширения ставятся `db/init` при первом
  старте; пересоздайте базу по `docs/infrastructure/35`, затем повторите шаг 3.
- После восстановления схема может отставать от кода: `deploy/server-deploy.sh schema`.

## 5. Границы и что осталось человеку

- Агент готовит файлы в репозитории; установку юнитов, `systemctl enable --now`, проверку
  свободного места после первой недели и первый живой прогон делает Виктор.
- Прод обновляется только по команде владельца; таймер ставится тем же
  `server-deploy.sh units --with-timers`, что и остальные.
- Копии дампов за пределы сервера не уезжают (решение V-027 — размещение на сервере).
  Если сервер потерян целиком, восстановление идёт из последнего дампа на нём же, поэтому
  внешняя копия — отдельное решение владельца, а не молчаливое расширение этого контура.
