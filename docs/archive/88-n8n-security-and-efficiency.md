# 82. n8n: оценка безопасности и эффективности, и нужен ли он вообще

> **Выведено из контура (V-026, 01.11.2026).** Решение заказчика — «убрать целиком»:
> n8n, его публичный адрес и переменные `N8N_*` удалены. Роутер свободного текста —
> `POST /tools/route` в tool-api. Документ оставлен как основание решения: он и был
> оценкой, которая к этому привела.

**Статус:** оценка с фактами, 31.10.2026. Проверялось на живой локальной установке
(n8n 2.44.6, контейнер `n8n-dev`) и по конфигурации прода (`docs/infrastructure/24`, `35`).

---

## 1. Что n8n делает сейчас

| Факт | Значение |
|---|---|
| Воркфлоу в работе | один: `WF-01 router` — webhook → Code (промпт) → HTTP к OpenRouter → Code (разбор) |
| Вход | `POST /webhook/router`, **без аутентификации** (в узле Webhook нет ни `authentication`, ни проверки секрета) |
| Проверено живьём | `curl -X POST http://127.0.0.1:5678/webhook/router -d '{"text":"проверка"}'` → **HTTP 200** |
| Наружу в проде | Caddy проксирует `/webhook/*` → `n8n:5678` (`docs/infrastructure/24` §2), то есть вебхук **публичный** |
| Ключ LLM | лежит в credential `openRouterApi` внутри n8n (в `.env` его нет — это и есть причина, почему `tool-api` не может вызвать модель сам) |
| Данные | `database.sqlite` + WAL, 10,1 МБ: воркфлоу, креды (зашифрованы `N8N_ENCRYPTION_KEY`), история выполнений |
| Память | **531,9 МиБ RSS** (для сравнения: Postgres 104 МиБ, Garage 5,3 МиБ) |
| Порт локально | опубликован как `0.0.0.0:5678`, а не `127.0.0.1` |

## 2. Безопасность

### 2.1 Открытый вебхук — дырка, а не теория

Вебхук принимает запрос от кого угодно и **сам идёт в модель нашим ключом**. В проде это значит:
любой, кто узнал адрес `https://<домен>/webhook/router`, может гонять наш LLM сколько хочет.
Последствия по возрастанию:

1. **Деньги:** расход на нашем ключе OpenRouter, счёт приходит нам.
2. **Квота:** `llm_usage` пишется по людям из `tool-api`, а вызовы через n8n в него **не попадают** —
   значит внешние вызовы ещё и не видны в учёте.
3. **Данные:** в промпт уходит текст запроса и манифест роли; чужой человек может заставить модель
   отвечать от лица бота (тот же промпт), то есть получить «официальный» ответ театра.

В `.env.example` уже есть `N8N_SHARED_SECRET`, но он **не используется**: ни gateway его не шлёт,
ни воркфлоу его не проверяет. Это надо закрыть независимо от решения «оставлять n8n или нет».

### 2.2 Ключ модели живёт в двух местах

Сейчас: ключ в n8n-credential, а `tool-api` без ключа (поэтому агент по файлам не может вызвать
модель). Если ключ положат и в `.env`, появятся два независимых хранилища одного секрета с разной
защитой: `.env` — файл 600 на сервере, credential — зашифрован ключом n8n, который, если
`N8N_ENCRYPTION_KEY` не задан явно, лежит рядом в `config`. При утечке тома утекает всё.

### 2.3 История выполнений = переписка людей

n8n по умолчанию сохраняет данные выполнений. Через роутер идут тексты запросов студийцев —
это персональные данные в третьем месте (Postgres, n8n, логи). Нужно либо отключить сохранение
(`EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`), либо чистить по расписанию. Сейчас не сделано ни то, ни другое.

### 2.4 Интерфейс n8n

UI даёт доступ к креденшелам и к запуску любого воркфлоу. В проде он должен быть либо закрыт
совсем, либо за отдельной аутентификацией и не на том же домене, что Mini App. В `docs/infrastructure/24`
он висит на `n8n.<домен>` — это отдельная поверхность, которую надо помнить.

## 3. Эффективность

| Ось | С n8n | Без n8n (вызов из `tool-api`) |
|---|---|---|
| Память на VPS 4 ГБ | **532 МиБ** постоянно (13% памяти ради одного вебхука) | 0 дополнительно: `tool-api` уже работает |
| Задержка ответа | gateway → n8n → OpenRouter → n8n → gateway: два лишних сетевых круга, +50–150 мс | gateway → tool-api → OpenRouter: один круг |
| Отказоустойчивость | n8n лежит — LLM-ветка мертва целиком (бот деградирует в формы) | меньше компонентов — меньше отказов |
| Учёт квот | **не ведётся** для вызовов через n8n | один учёт в `llm_usage` |
| Тесты | JS-ноды проверяются только смоуком руками | pytest, фейковый провайдер, CI |
| Диффы | воркфлоу в git только генератором (`scripts/build_router_workflow.py`, 409 строк) | обычный код и ревью |
| Скорость правок | визуально, без выката | правка + выкат (5 минут) |
| Что даёт уникального | визуальные сценарии, ретраи, расписания, готовые интеграции | — |

Что из «уникального» мы реально используем: **ничего**. Расписания держат systemd-таймеры
(`svoi-*.timer`), ретраи — код и повторные прогоны, интеграции — прямые HTTP-клиенты
(Google, OpenRouter). Воркфлоу один, и он линейный: три ноды, из них две — JavaScript.

## 4. Вывод

**n8n в текущем виде — это открытый вебхук, который тратит наши деньги и не учитывается в квотах,
ценой половины гигабайта памяти на сервере.** Плюсы платформы (визуальные сценарии, расписания)
не используются; минусы (второй контур, отсутствие тестов и учёта) — используются полностью.

Рекомендация по шагам, в этом порядке:

1. **Сейчас, независимо от решения:** закрыть вебхук. `N8N_SHARED_SECRET` в заголовке
   `X-Svoi-Secret`, проверка в первой Code-ноде, gateway шлёт его же. Без этого адрес в интернете
   — приглашение тратить наш ключ.
2. **Отключить сохранение выполнений** (`EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`) и почистить
   накопленное: там тексты людей.
3. **Перенести роутер в `tool-api`:** правила + вызов модели уже есть (`/tools/assistant/ask`,
   `app/agent.py`), ключ — в `.env`, квоты и аудит — в одном месте. После этого `WF-01` выключается.
4. **Выключить n8n на VPS** и вернуть ~0,5 ГБ памяти. Вернуть его, если появится задача, где
   визуальный сценарий реально экономит время (например, интеграция с билетным сервисом).

Пункт 3 не срочный: пока вебхук закрыт секретом, риск снят. Но два пути к модели — это два учёта
квот, и раньше или позже кто-то спросит «почему у человека лимит не кончается».
