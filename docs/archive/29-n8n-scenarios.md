принимает `tool-api`. Если завтра n8n упадёт, бот потеряет свободный диалог, но продолжит
записывать расходы, считать деньги и показывать расписание.

## 2. Схема WF-01 (как её видно в редакторе)

```
[Webhook]  →  [2. Собрать промпт]  →  [3. Запрос к OpenRouter]  →  [4. Разобрать ответ]
                                              │ (ошибка)
                                              └→ [Ответ при сбое модели] ─┐
                                                                          ▼
[4. Разобрать ответ] → [5. Развилка: сценарий] → ┬→ [→ BUDGET: запись траты] ─→ [6. Ответ клиенту]
                                                  ├→ [→ SCHEDULE: занятость] ──→
                                                  ├→ [→ DUES: взносы] ──────────→
                                                  └→ [→ ASSISTANT: текст] ──────→
```

Что даёт такая схема для аудита:

- **видно все сценарии сразу** — четыре именованные ветки, пятая (сбой) отдельно;
- у каждого узла есть подпись `notes` — что он делает и почему;
- четыре стикера на канвасе: контракт запроса, контракт ответа, карта сценариев,
  инструкция «как менять промпт»;
- развилка не меняет поведение (все ветки сходятся в один ответ), она **документирует**
  маршрутизацию — раньше это было видно только в чужом коде.

## 3. Контракты (текущий адрес — `/tools/route`)

**Запрос** — `POST {TOOL_API_URL}/tools/route` (было `POST /webhook/router` в n8n).
Заголовки — как у любого вызова tool-api из gateway: `Authorization: Bearer <TOOL_API_TOKEN>`,
`X-Actor-Chat-Id`.

```json
{
  "text": "купили ткань 12000",
  "user": { "name": "Иванов Виктор", "roles": ["администратор", "организатор"] },
  "categories": ["Реквизит и костюмы", "Аренда помещения", "..."]
}
```

- `categories` — закрытый список из `GET /tools/intent/categories`; пусто — tool-api берёт
  его сам из базы;
- `user` — контекст, иначе ассистент не знает, кто пишет;
- пустой `text` gateway не отправляет (проверяет сам), а route отвечает `ok:false, error:empty_text`.

**Ответ**

```json
{ "ok": true, "intent": "budget|schedule|dues|assistant", "scenario": "budget",
  "category": "Реквизит и костюмы" | null,
  "answer": "текст для ASSISTANT",
  "confidence": 0.86 | null, "threshold": 0.7,
  "engine": "tool-api-llm" }
```

`scenario` — синоним `intent` (имя поля из карты V-026): gateway читает `intent`, проверки
читают любой из двух.

**Ответ при сбое модели**

```json
{ "ok": false, "intent": null, "scenario": null, "category": null, "answer": "",
  "error": "provider_unavailable", "detail": "…", "engine": "tool-api-fallback" }
```

Это осознанное решение: **HTTP 200 даже при сбое**. Gateway видит `ok:false` и уходит в кнопки,
а человек не получает «сервис недоступен». Повторов внутри tool-api нет намеренно: два
запроса к модели за наши деньги на одну фразу — хуже, чем кнопки.

## 4. Матрица покрытия сценариев

| Фраза | Ожидание | Кто обрабатывает | Проверено |
|---|---|---|---|
| «расход 3000 на реквизит» | `budget` + категория | n8n → правила tool-api | да |
| «купили ткань 12000» | `budget` + «Реквизит и костюмы» | n8n (категория) | да |
| «занят в пятницу после 19» | `schedule` | n8n | да |
| «сколько я должен» | `dues` | n8n | да |
| «что ты умеешь» | `assistant` + текст | n8n | да |
| «кто я» | `assistant` + имя и роли | n8n (контекст) | да |
| «как записать доход» | `assistant`, не `budget` | n8n + правила gateway | да |
| «сколько у нас денег» | `budget` → ответ числами | **gateway, без LLM** | да |
| «что на неделе» | `schedule` → события | **gateway, без LLM** | да |
| «список участников» | список из БД | **gateway, без LLM** | да |
| пустой текст / сбой модели | `ok:false`, кнопки | n8n fallback | да |

Важно: пять строк из одиннадцати вообще не доходят до модели — их перехватывают детерминированные
ветки gateway. Это экономит токены и убирает класс ошибок «модель не поняла простой вопрос».

## 5. Как проверить (аудит за минуту, было 5)

Всё, что раньше смотрели в SQLite n8n, теперь проверяется одним скриптом по «золотому набору»
из 20 фраз (набор ниже в §7 и в `scripts/check_router_scenarios.py`):

```bash
env -u PYTHONPATH .venv/bin/python scripts/check_router_scenarios.py
```

Скрипт ходит в `POST {TOOL_API_URL}/tools/route`, то есть проверяет живой tool-api и живую
модель с тем же промптом. Код 1 — хоть одна фраза ушла не туда, код 2 — tool-api недоступен
или отверг токен.

Раньше здесь были команды `sqlite3 … workflow_entity` и `curl /webhook/router` — они
относились к n8n и выведены из контура (V-026).

## 6. Как менять промпт (и не сломать) — выведено из контура (V-026)

Промпт и разбор ответа живут в коде tool-api, а не в воркфлоу:

```
services/tool-api/app/router_llm.py   ← единственный источник правды
   ├─ system_prompt()  (промпт и правила классификации, дословно из WF-01)
   ├─ parse_answer()   (контракт разбора: первая строка — сценарий, CATEGORY, CONFIDENCE)
   └─ LlmError         (ветка сбоя: gateway уходит в кнопки)
tests/unit/test_router_llm.py         ← контракт разбора и промпта
scripts/check_router_scenarios.py     ← «золотой набор» фраз против живого tool-api
```

Порядок правки: промпт → `tests/unit/test_router_llm.py` → прогон `pytest` →
`scripts/check_router_scenarios.py` на живом контуре → ревью. Сборки JSON и импорта
воркфлоу больше нет: `scripts/build_router_workflow.py` и каталог `n8n/` удалены вместе с n8n.

### Грабли публикации (проверено на 2.44.6)

1. **Узел вебхука должен называться ровно `Webhook`.** При переименовании в «1. Вебхук POST /router»
   n8n отвечал `Cannot read properties of null (reading 'disabled')`: имя в `webhook_entity`
   не находилось среди узлов. Нумерацию шагов держим в остальных узлах, а вебхук не трогаем.
2. **`import:workflow` не включает воркфлоу.** После импорта нужны: `active=1`,
   `activeVersionId=versionId`, строка в `workflow_published_version` и запись в `webhook_entity`.
3. **Credentials не переносятся вместе с логикой.** В JSON нужен блок
   `credentials.openRouterApi` — иначе живой запуск даёт `Credentials not found`,
   хотя импорт проходит успешно.
4. **AI Agent node в 2.44.6** импортируется, но не публикуется (вебхук не регистрируется).
   Поэтому инструменты модели — только через HTTP Request + код, как сейчас.

## 7. Ограничения и техдолг n8n

| Ограничение | Следствие | План |
|---|---|---|
| Развилка — визуальная метка, логика ветвления в gateway | в n8n нельзя «починить» сценарий, меняя схему | осознанно: данные — в tool-api |
| n8n на SQLite | риск потери воркфлоу при сбое | перевести на Postgres при переезде в прод (`docs/infrastructure/24`) |
| Промпт без версионирования | откат только через git | тег на релиз вместе с кодом |
| Нет тестов на промпт | качество классификации проверяется руками | добавить «золотой набор» из 20 фраз и скрипт проверки |
| Квоты LLM не считаются в ветке n8n | расход не привязан к человеку | считать по `intent_log.tokens` в tool-api |

Следующий практический шаг — «золотой набор» фраз: 20 примеров с ожидаемым интентом,
прогон curl-ом после каждого изменения промпта. Это даст регрессию там, где сейчас
только глазная проверка.
