# 17. Бизнес-алгоритмы: как человек передаёт данные и как бот их понимает

> **n8n выведен из контура (V-026, 01.11.2026).** Где ниже n8n назван частью контура или
> источником разбора свободного текста, читать: `POST /tools/route` в tool-api
> (`services/tool-api/app/router_llm.py`); воркфлоу, публичный вебхук и переменные `N8N_*`
> удалены из деплоя. История контрактов — `docs/archive/29-n8n-scenarios.md`.

Документ отвечает на вопрос «что именно делает бот», когда человек пишет ему или правит файл.
Инварианты — `docs/architecture/11`, тесты — `docs/development/16`, маршрутизация — `docs/development/14`.

---

## 0. Три способа передать данные и один результат

| Способ | Когда | Что происходит |
|---|---|---|
| **Кнопка/форма** | человек не хочет формулировать | слоты заполняются по шагам, LLM не участвует |
| **Свободный текст** | «расход 3000 на реквизит», «занят в среду» | router → сценарий → черновик |
| **Ручная правка файла** | человек работает в таблице | сверка при чтении, расхождения → `Проверки` |

Все три пути сходятся в один объект **intent**:

```json
{"intent":"budget.capture",
 "slots":{"amount":3000,"tx_type":"expense","category":"Реквизит и костюмы",
          "tx_date":"2026-10-26","counterparty":null,"project":null},
 "missing":[], "flags":[], "confidence":0.95, "source":"form|text|file"}
```

Правило: **пока `missing` не пуст, запись не создаётся** — бот спрашивает недостающее.
Правило: **`flags` не блокируют запись**, но видны человеку и попадают в черновик.

## 1. Алгоритм: бюджет

### 1.1 Приём и распознавание

```
сообщение
 ├─ router (n8n): intent = budget?
 │    ├─ да → разбор
 │    └─ нет → сценарий schedule / dues / assistant
 ├─ разбор (правила tool-api, затем n8n как второй эшелон):
 │    1) тип: расход / доход (глаголы: расход, оплат, купил, сдал, взнос…)
 │    2) сумма: «12к», «45 000», «350000», «1,5к»
 │    3) дата: явная (26,09 / 29.10) → иначе дата сообщения
 │    4) категория: словарь статей + алиасы + опечатки
 │    5) контрагент: фамилия в конце фразы, «Зайцева», «Крылову»
 │    6) проект: Пурга / Бунин / ЛитРейв / Жизнь насекомых
 └─ черновик → кнопки «Записать / Изменить / Отмена»
```

**Приоритет источников при конфликте:** явная дата в тексте → дата из файла → дата сообщения.
**Приоритет категории:** точное совпадение статьи → синоним → проект → «Прочее» с флагом.

### 1.2 Запись

```
commit → проверка прав (budget.write)
       → проверка суммы (>0) и периода
       → INSERT budget_tx (status=confirmed, origin=bot)
       → audit_event (before/after, source_text, chat_id)
       → append строки в лист «Транзакции» (best effort)
       → позже: пересборка месячного листа
```

Если Google недоступен: **запись в БД остаётся**, ответ честный («в таблицу запишу позже»),
операция попадает в очередь на досылку.

### 1.3 Ошибки и неполные данные

| Ситуация | Поведение | Что видит человек |
|---|---|---|
| Нет суммы | `missing=[amount]` | «Не увидел сумму. Напишите цифрами или выберите кнопкой» |
| Сумма есть, тип неясен | вопрос | «Это расход или доход?» — две кнопки |
| Неясна категория | запись разрешена, `flag=category_ambiguous` | «Категория: выберите или оставьте Прочее» |
| Дата непонятна | конец периода + флаг | «Поставил конец месяца — поправьте, если не так» |
| Похоже на не-трату («созвонимся в 19») | `ok=false` | «Не похоже на трату — записать как расход?» |
| Дубль (та же сумма+категория+дата за 10 мин) | предупреждение | «Похоже, это уже записано. Всё равно записать?» |
| Несколько дат в тексте | первая дата, флаг `multi_date` | «Дат в периоде: 5, поставил первую» |

**Паттерн «не знаю — спроси, не выдумывай»:** любое поле либо заполнено из текста, либо
спрошено кнопками. Бот не подставляет правдоподобные значения молча.

Порога «крупная сумма» нет: строка про `second_approval` убрана 30.10.2026
(`docs/architecture/25` §4) — расход и доход пишутся сразу, любой суммы.

## 2. Алгоритм: занятость

### 2.1 Распознавание

```
текст
 ├─ дата: сегодня / завтра / послезавтра / день недели / dd.mm / dd,mm
 │    └─ нет даты → need_date → переспрос
 ├─ интервал: «с 10 до 18», «после 18», «до 15», «весь день»
 │    └─ нет времени → по умолчанию весь день (с подтверждением)
 ├─ вид: занят (busy) / свободен (free) / удобно (preferred)
 └─ черновик → «Верно?» → запись в availability_hour по часам
```

### 2.2 Правила
1. Часовой пояс — Самара, UTC+4 (Europe/Samara). «Сегодня» считается по времени Самары, не по UTC.
2. Запись почасовая: 18–24 = часы 18…23. Час 24 не существует.
3. Повторная запись перезаписывает (`source='bot'`), прежнее значение — в аудите.
4. Импорт из файла (`source='imported'`) **не перетирает** свежую ручную запись:
   при сверке побеждает более поздняя по времени, конфликт — в `Проверки`.
5. Если человек сообщил «занят весь день», а в календаре есть событие — окно считается занятым.

### 2.3 Ошибки

| Ситуация | Поведение |
|---|---|
| Нет даты | переспрос, ничего не пишем |
| Интервал перевёрнут («с 18 до 10») | трактуем как 10–18? **нет** → переспрос |
| Дата в прошлом | принимаем, но помечаем `flag=backdated` |
| Конфликт «свободен», хотя есть запись «занят» | спрашиваем подтверждение, пишем только после «Верно» |

## 3. Алгоритм: расписание и окна (проектирование)

### 3.1 Источники
```
занятость (БД, availability_hour)  ← основной
календарь READ (только чтение)     ← подтверждённые события
календарь DRAFT                    ← обкатка записи, не влияет на боевую картину
```

### 3.2 Поиск окон
1. Вход: длительность (напр. 2 ч), список участников, диапазон дат, предпочтения
   (день недели, время суток, «не позже 22:00»).
2. Для каждого часа в диапазоне: `свободен_всеми = ∀ участник: is_free ∧ нет события`.
3. Непрерывные блоки ≥ длительности → кандидаты.
4. Скоринг (детерминированный, не LLM): покрытие → предпочтения → близость к вечеру →
   отсутствие переносов у людей.
5. Возврат top-3 с пояснением: «вторник 19:00–21:00: свободны все четверо, нет событий».
6. Если данных по человеку нет → окно помечается «нет данных», а не «свободен».

### 3.3 Ошибки и неполные данные

| Ситуация | Поведение |
|---|---|
| Нет данных по 1 из 4 | предложить окна + список «неизвестно», попросить подтвердить |
| Пересечение с календарём | окно отбрасывается, причина показывается |
| Окна нет | «нет общего окна», ближайшие варианты с заменой участника |
| LLM просит слот, которого нет | ответ запрещён: слоты только из выдачи алгоритма |

## 4. Алгоритм: файл — источник истины (регрессивный пересчёт)

Заказчик: **истина — то, что человек внёс руками в файл.** Бот не спорит, а сверяет и сообщает.

```
1. Прочитать лист(ы) периода (Транзакции / месячный лист).
2. Нормализовать: суммы, даты, категории, контрагенты (по person_alias).
3. Сопоставить с БД по ключу (период, блок, дата, сумма, контрагент).
4. Классифицировать расхождение:
   • в файле есть, в БД нет → добавить в БД (файл прав)
   • в БД есть, в файле нет → помечать rejected, НЕ удалять
   • сумма/категория отличаются → принять значение файла, старое в аудит
   • итог месяца в файле не равен сумме строк → ошибка, ничего не меняем, пишем в «Проверки»
5. Пересчитать: итоги блоков, «Итог месяца», накопительный результат, баланс.
6. Записать отчёт о сверке: сколько принято, отклонено, конфликтов, что требует решения.
```

**Реализовано (26.10.2026):** `scripts/reconcile.py`.
Бюджет — сравнивает лист «Транзакции» с `budget_tx` по `id`, добавляет отсутствующие,
помечает удалённые как `rejected`, принимает значения файла при расхождении сумм/дат/категорий,
сверяет итоги по периодам. Занятость — сравнивает часовую матрицу файла с `availability_hour`
(сейчас только отчёт: 7 208 клеток совпали, 901 относится к архивному участнику).

**Жёсткие правила:**
- Бот **никогда** не перезаписывает файл при сверке — только читает и предлагает.
- Ошибка в файле (итог не сходится) — сигнал человеку, а не «исправление» задним числом.
- Все расхождения видны на листе `Проверки` с типом и периодом.
- Накопительный итог пересчитывается от начала, а не «дельтой» — иначе история поедет.

## 5. Обработка неточных данных: общие паттерны

| Паттерн | Правило |
|---|---|
| **Спросить, а не догадаться** | недостающий слот → вопрос кнопками, а не значение по умолчанию |
| **Флаг, не блокировка** | неоднозначность помечается и пропускается; деньги — исключение: сначала спрашиваем кнопками, порога нет (снят 30.10.2026, `docs/architecture/25` §4) |
| **Один источник для чисел** | любое число в ответе берётся из инструмента, иначе «не могу подтвердить» |
| **Идемпотентность** | повторное подтверждение не создаёт вторую операцию (ключ: `chat_id + message_id`) |
| **Прозрачность** | в ответе — что поняли, что поставили по умолчанию, что требует решения |
| **Обратимость** | отмена записи = `status='reversed'` + аудит, физического удаления нет |
| **Деградация** | нет LLM → формы; нет Google → БД и очередь; нет n8n → правила |
| **Опечатки** | словарь алиасов (`комуналка`, `БУНИН`, «Ивнов») пополняется при каждой находке |
