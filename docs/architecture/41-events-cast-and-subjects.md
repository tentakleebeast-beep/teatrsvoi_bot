# 41. События, роли и разбор субъекта запроса

Дата: 27.10.2026. Развивает `docs/architecture/40` (поиск окон) и `docs/development/21` (каскад разбора).
Отвечает на три вопроса: как учитывать занятость в спектаклях, как понимать
«окна для Наташи и Сэма в Жизни насекомых» и как искать «максимум свободных».

---

## 1. Что не так с текущей моделью

Сейчас занятость — это сетка `availability_hour` (кто свободен в какой час).
Этого достаточно для вопроса «когда все свободны», но не хватает для трёх
реальных сценариев:

| Сценарий | Что мешает |
|---|---|
| «Окна для Наташи и Сэма в Жизни насекомых» | Наташа и Сэм — роли, а не люди; роль существует только внутри спектакля |
| «Когда тренинг, чтобы пришло больше людей» | нужен не общий пересечение, а максимум свободных |
| «У нас показ 5 декабря — кто занят» | событие и его участники живут в календаре, а не в БД |

---

## 2. Что уже есть в схеме (не надо создавать заново)

Проверка показала: половина модели уже существует с миграции `001`.

| Таблица | Что содержит | Используется? |
|---|---|---|
| `project` | спектакли, курсы, тренинги (`kind`, `status`) | да |
| `event_plan` | событие: `title`, `kind`, `project_id`, `starts_at`, `ends_at`, `participant_ids[]`, `status`, `gcal_event_id` | частично |
| `person_alias` | псевдонимы человека: `alias`, `alias_kind` (name/short/tg_username/payee/external), `source` | да |
| `slot_proposal` | сохранённый запрос окон: `request jsonb`, `candidates jsonb`, `chosen_index`, `event_plan_id` | нет |

Вывод: новых сущностей почти не нужно. Не хватало двух вещей — **роли как вида
псевдонима** и **привязки роли к спектаклю**.

---

## 3. Изменение модели (миграция 022)

```sql
alter table person_alias add column project_id bigint references project(id);
alter table person_alias add constraint ... alias_kind in (..., 'role');
alter table event_plan add constraint ... kind in
  ('rehearsal','show','training','rental','meeting','other');
```

Почему роль живёт в `person_alias`, а не в отдельной таблице:

1. Механизм разбора имён один — не нужно два похожих пути («найди человека» и «найди роль»).
2. Роль без проекта запрещена сама собой (`project_id` заполняется для `kind='role'`).
3. Люди меняются ролями между спектаклями — это ровно псевдоним с областью действия.

Пример данных:

```sql
insert into person_alias (participant_id, alias, alias_kind, project_id)
values ((select id from participant where person_key = 'орлова'),
        'Наташа', 'role', (select id from project where name = 'Жизнь насекомых'));
```

## 4. Занятость в событиях: три источника правды

| Источник | Что даёт | Как используется |
|---|---|---|
| `availability_hour` | «могу / не могу» по часам | основной фильтр окон |
| `event_plan` | «уже занят событием» | вычитается из свободного времени |
| календарь READ | подтверждённые события (внешние) | то же, но только чтение |

Правило: **событие блокирует время тех, кто в нём указан** (`participant_ids`),
и только на свой интервал. Событие без участников (аренда зала) не влияет
на занятость людей, но влияет на занятость *зала* — это отдельная сущность,
которую пока не моделируем.

Что нужно сделать в коде (не сделано, записано в план):

1. при поиске окон вычитать из `availability_hour` интервалы `event_plan`
   для выбранных участников;
2. хранить `slot_proposal` — предложенные варианты и выбранный, чтобы понимать,
   какие окна люди реально приняли (обучение правил, не ML).

---

## 5. Режимы поиска

| Режим | Запрос человека | Что считаем |
|---|---|---|
| `subset` | «окна для Наташи и Сэма в Жизни насекомых» | пересечение свободного времени указанных людей |
| `all` | «окна для всех» | пересечение по всей труппе |
| `max_free` | «тренинг, чтобы пришло больше людей» | часы с максимумом свободных, без требования «все» |

Реализовано в `app/slots.py::rank_hours` (режим `max_free`) и `find_windows` (остальные).

## 6. Разбор субъекта запроса

Модуль `app/subject.py`. Логика повторяет каскад категорий (`docs/development/21`):
правила → при неуверенности модель → при неуверенности кнопки.

```
фраза
  │
  ├─ есть «максимум свободных / тренинг / всем составом» → mode = max_free
  │
  ├─ ищем проект: «Жизнь насекомых» (по основе слова, падежи не важны)
  │
  ├─ ищем людей: имя → короткое имя → роль (роли других проектов не берём)
  │
  ├─ нашли ≥1 человека → mode = subset, confidence 0.85–0.95
  │
  └─ никого не нашли → mode = all, confidence 0.2, unresolved = [...]
```

Что проверено тестами (`tests/unit/test_subject.py`, 12 кейсов):

- «Наташи и Сэма в Жизни насекомых» → обе роли, один проект;
- «Сэма» без проекта → роль находится;
- «Саша» / «Алёны» / «Новикова» → короткие имена и фамилии с падежами;
- «Сэм в Чёрной пурге» → роль чужого проекта не подставляется;
- «тренинг для труппы» → `max_free`;
- «для всех» и пустая фраза → `all`;
- «Марата» → `unresolved`, низкая уверенность → бот переспросит.

Сопоставление идёт по началу слова (3–4 буквы), потому что русские окончания
меняются, а основа нет: «Наташи» ≈ «Наташа», «Чёрной пурге» ≈ «Чёрная пурга».

## 7. Зачем здесь модель, и почему не сразу

Модель полезна там, где правила бессильны: «окна для тех, кто занят в детском
спектакле» (роль не названа), «собери тех, кто вчера был на показе».

Но модель не должна решать сама. Схема, как в каскаде категорий:

1. **Правила** разбирают имена, роли, проекты, режим. Это 90 % запросов.
2. Если `unresolved` не пуст и уверенность ниже 0.7 — отдаём модели **закрытый
   список** людей и ролей (id + имя + роли) с просьбой выбрать только из него.
3. Если модель не уверена — показываем кнопки с кандидатами (до 5).
4. Выбор человека логируем (`intent_log`), чтобы через месяц видеть,
   какие формулировки не разбираются.

Что для этого нужно передавать модели: список людей с ролями и проектами,
сегодняшнюю дату, диапазон поиска. Без этого контекста она начнёт выдумывать
имена — а имя, придуманное моделью, в окнах недопустимо.
