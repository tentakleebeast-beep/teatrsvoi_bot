# 11. Бизнес-правила и инварианты логики

Документ — контракт между театром и ботом. Всё, что здесь написано, реализуется кодом и
проверяется автоматически (`scripts/check_invariants.py`). Если правило нельзя проверить —
оно не правило, а пожелание.

Источник истины: Google Sheets (человек) → индекс в Postgres (бот) → ответы с указанием источника.

---

## 1. Учёт денег

### 1.1 Метод учёта — кассовый
Деньги учитываются **на дату фактического движения**. Аванс, полученный в октябре за декабрь, — доход октября.
Поле `service_period` фиксирует, к какому периоду услуга относится, но **не переносит** сумму.

Причина: театр живёт наличными и коротким горизонтом. Accrual-учёт дал бы «красивую» прибыль при пустой кассе — вредная иллюзия.

### 1.2 Обязательство по авансу
Если `is_advance = true`, то:
- сумма входит в доход периода получения;
- в `service_period` фиксируется период, за который заплачено;
- бот обязан по запросу «что у нас с декабрём» показать: получено авансом N, ожидается доплата M;
- при закрытии `service_period` остаток по авансу должен стать 0. Ненулевой остаток после закрытия — **ошибка**, алерт администратору.

### 1.3 Инвариант баланса (главный)
```
Баланс = Σ доходов − Σ расходов по всем периодам
```
Требования:
- пересчёт «с нуля» по операциям обязан совпадать с накопительным итогом последнего периода **до рубля**;
- расхождение > 0 → бот не отвечает на вопросы про деньги, пока не покажет расхождение;
- удаление периода запрещено; исправление — компенсирующая запись (`replaces`), не удаление.

### 1.4 Что является доходом, а что расходом

| Блок (`block`) | Тип | Примеры |
|---|---|---|
| `dues` | доход | взносы студийцев |
| `show_income` | доход | выручка показов, курсы, возвраты долгов |
| `sublease` | доход | субаренда, авансы арендаторов |
| `expense` | расход | аренда, коммуналка, ремонт, тренинги, реклама, расходники |
| `show_cost` | **расход** | закупки к спектаклю, доли (21%/30%), гонорары актёрам, программки, свет, съёмка |

**Вложения в показы — расходы, не доход.** «21% Крылову» — расход театра. «Выплата ОВ» (Семёнов О.В.) — расход театра.

### 1.5 Доли от сборов
Если у выплаты задан `rate_pct`:
```
ожидаемая выплата = round(сборы_показа × rate_pct / 100)
```
где сборы — сумма `show_income` по тому же проекту и периоду.
- расхождение ≤ 1% от сборов (округление) — норма;
- больше — бот помечает расхождение и просит подтвердить, но не исправляет сам.

### 1.6 Планируемые операции
`status = 'expected'` — операция известна, но денег ещё не было (например, «ЛитРейв 29.10» без суммы).
- **не входит** в баланс и в фактические итоги;
- **входит** в прогноз и в напоминания;
- при появлении суммы переводится в `confirmed`.

Плановые суммы периода хранятся в `budget_plan` (план по блоку и категории), отдельно от факта.

### 1.7 Взносы
- Начисление — `dues_charge` (человек × период), тариф — `dues_plan` (может отличаться: льгота, неполный месяц).
- Взносы **не дублируются** в `budget_tx`. Если человек платит через бота — создаётся `dues_charge.amount_paid` и, при необходимости, одна `budget_tx` на всю кассу дня, но не по человеку.
- Долг = `Σ начислено − Σ оплачено`. Не хранится как число, только вычисляется.

### 1.8 Человек в операции
Если в операции есть человек (взнос, доля, гонорар, возврат) — он обязан быть привязан к `participant`, а не существовать только текстом.
Сопоставление имён идёт через `person_alias` (полное имя, никнейм, «ОВ», «Света», «Крылов»). Несопоставленное имя — не «прочее», а `import_row.issue = 'unknown_person'` и очередь ревью.
Соответствие «имя в файле → человек» в коде не хранится (Ш-03a плана 129): скрипты и сервис ищут человека по `person_alias`, `person_key` и `display_name` из БД, а никнеймы, которых в БД ещё нет, берут из локального `config/participant-names.yaml` (в git только пример). Подсказки категории по фамилии получателя (`category_hints`) — оттуда же.

## 2. Занятость и расписание

### 2.1 Занятость
- Гранулярность — час, `0/1` по смыслу файла (`1 = свободен`).
- Отсутствие данных ≠ свободен. `known_cnt` показывается всегда рядом с `free_cnt`.
- Данные старше 28 дней считаются устаревшими и помечаются в ответе.
- Занятость, полученная из чата («занят в среду после 18»), имеет приоритет над импортированной.
- Сводка (сколько свободно) **вычисляется**, никогда не хранится.

### 2.2 Окна для событий
- Алгоритм детерминированный (пересечение интервалов + скоринг), LLM не выбирает слоты.
- Бот предлагает только те окна, где у всех обязательных участников есть данные **или** явно помечено «нет данных».
- Событие создаётся только после подтверждения; повторное создание по одному запросу запрещено (idempotency key).

## 3. Данные и их качество

### 3.1 Качество периода
`budget_period.quality`:
- `draft` (июль–август 2026) — смешанные форматы, ошибки, используются только для истории и примеров;
- `clean` (сентябрь–октябрь 2026) — основа для аналитики и обучения промптов.
Бот обязан помечать ответы по `draft`-периодам: «данные черновые».

### 3.2 Импорт
- Перезаливка допускается только для `origin = 'import'` и только в пределах периода.
- Повторный импорт того же файла не меняет суммы (идемпотентность).
- Неизвестное не теряется: `import_row.issue` + ревью.

### 3.3 Ручные правки
Файл — главнее бота. Человек исправил сумму → бот принимает его версию при следующем чтении, фиксируя расхождение в `budget_recon`. Свою правку не «возвращает».

### 3.4 Опечатки и синонимы
`article_alias` хранит: `комуналка → Коммунальные платежи`, `Тренинги Крылов → Тренинги и занятия`, `низ афиши → Реклама и полиграфия`.
Правило: словоформы и опечатки нормализуются, при двух равнозначных совпадениях — вопрос пользователю, а не догадка.

## 4. Инварианты, проверяемые автоматически

| Код | Инвариант | Что значит нарушение |
|---|---|---|
| **I1** | `Σ доходов − Σ расходов` = накопительный итог последнего периода | расхождение в своде |
| **I2** | Нет дублей: одна и та же операция (период, блок, дата, сумма, статья) не встречается дважды | двойной импорт |
| **I3** | `tx_type` соответствует `direction` категории (доход ↔ income, расход ↔ expense) | категория из чужого блока |
| **I4** | Взносы не задвоены: `dues_charge` и `budget_tx` не содержат одну и ту же сумму взноса | двойной учёт |
| **I5** | `rate_pct` задан → `|выплата − сборы×rate| ≤ 1% сборов` | неверная доля |
| **I6** | `is_advance` → `service_period` заполнен | аванс без периода услуги |
| **I7** | Каждая операция имеет `block`, `category_id`, `tx_date` | неполная запись |
| **I8** | `expected`-операции не входят в баланс | план попал в факт |
| **I9** | Архивные участники не попадают в активные расчёты долгов | считаем по бывшим |
| **I10** | Любой ответ бота с числом содержит `source` (файл/лист/строки/время чтения) | факт без источника |

Проверка: `python scripts/check_invariants.py` — печатает таблицу и код выхода 1 при нарушении.

## 4.1 Календарь и доход

1. Два класса событий:
   - **свои** — репетиции, тренинги, спектакли студии;
   - **арендаторы** — аренда зала и показы арендаторов (оплата студии за помещение и организацию).
2. Любое событие типа `Аренда` или `Показ` арендатора — **доход студии**, даже если стоит
   внутри арендного блока по времени.
3. Название: «Тип - Название». Типы: `Аренда`, `Показ`, `Репетиция`, `Тренинг`, `Служебное`.
4. Цвет — атрибут события из `config/calendar-palette.yaml`, не свойство календаря.
5. Событие, уходящее за полночь, заканчивается 23:55.
6. Регулярные аренды живут сериями `RRULE:FREQ=WEEKLY`; бот разворачивает их в конкретные
   даты и не создаёт дублей поверх существующих инстансов.

## 4.2 Ушедшие из театра

1. Человек, который больше не в театре, переводится в статус `archived`, **не удаляется**:
   история взносов и операций остаётся для отчётов.
2. Архивный участник не попадает в списки, счётчики занятости, подбор окон и рассылки.
3. Его занятость (`availability_hour`) удаляется — она искажает покрытие и не нужна.
4. Финансовые записи (взносы, выплаты, доли) сохраняются: это факты прошлого.
5. Вернуть человека можно сменой статуса на `active` — данные на месте.

## 5. Запреты для бота

1. Не удалять строки — только помечать (`rejected`, `reversed`).
2. Не менять лист `Свод` в Google Sheets (там формулы человека).
3. Не писать в чужие личные папки и не отдавать чужие данные (изоляция через `participant_id`).
4. Не придумывать суммы, даты и имена. Нет данных → «нет проверенных данных».
5. Не считать доли и итоги «на глаз» — только формулами из §1.3 и §1.5.
6. Не требовать второго подтверждения и не заводить очередь согласования: расход и доход пишутся сразу, любой суммы (убрано 30.10.2026, `docs/architecture/25` §4).
7. Не отправлять уведомления в тихие часы 20:00–08:00 по Самаре (кроме срочных изменений расписания).

## 6. Ответы бота про деньги: формат

Любой числовой ответ содержит три части:

```
Короткий ответ: «В сентябре потратили 266 104 ₽ — больше, чем заработали на 7 803 ₽».
Разбивка: расходы студии 187 412 / затраты показов 78 692.
Источник: «Бюджет» · лист «Свод» · прочитано 25.10.2026 19:40 · период помечен clean.
```

Без третьей части ответ не отправляется. Это реализация требования «не галлюцинировать» на уровне формата, а не намерения.

## 7. Известные ограничения текущих данных

- 90 операций за 4 месяца — мало для ML, достаточно для правил и few-shot промптов.
- Июль–август содержат опечатки в датах и заголовках («АВГУСТ 2025»), суммы сверены, даты частично восстановлены.
- В файле встречаются незакрытые операции (показ без выручки) — учитываются как `expected`.
- Персональные данные: телефоны и дни рождения студийцев в файле есть; бот их не показывает другим ролям.

## Рабочий день студии (решение заказчика 28.10.2026)

Рабочий день — **08:00–23:00**. Правило одно для всех каналов:

- чат: разбор «занят в среду», «с 10 до 14» обрезается границами 08:00–23:00;
  «весь день» = 08:00–23:00, а не 00:00–24:00;
- назначение события: `08 <= from_hour < to_hour <= 24`, иначе отказ с текстом
  «Рабочий день 08:00–23:00, время вне него не назначаем»;
- запись занятости через API: те же границы, иначе `400 bad_hours`;
- Mini App: сетка рисует ровно 08–23, часы 0–7 не принимаются и не показываются.

Причина: занятость вне рабочего дня никто не заполняет, а «пустые» часы 0–7
создавали впечатление свободного времени ночью и ломали поиск окон.
