# Часть 1. Уведомления

## 1. Типы

| kind | Кому | Когда | Канал |
|---|---|---|---|
| `rehearsal_reminder` | участники события | T−24 ч и T−2 ч | личный чат |
| `schedule_change` | участники события | сразу при изменении/отмене | личный чат |
| `payment_due` | должник + org | за 3 дня до срока, в день срока, далее раз в неделю | личный чат |
| `payment_received` | плательщик + org | при записи оплаты | личный чат |
| `availability_stale` | участник | если данных нет > 14 дней | личный чат |
| `weekly_digest` | org, admin | пн 10:00 | личный чат |
| `budget_conflict` | admin | при расхождении реконсиляции | личный чат |
| `registration_event` | admin | новый участник / отказ доступа | личный чат |
| `system_alert` | admin | падение n8n, Google, очередь > N ошибок | личный чат |

## 2. Модель

Таблица `notification` (см. `docs/architecture/01` §6). Жизненный цикл:

```
scheduled → (quiet hours? → сдвиг на 09:00) → sent
                                   ↘ failed (retry ×3, backoff 1/5/30 мин) → failed → system_alert
        ↘ cancelled (событие отменено, долг закрыт)
```

Правила:
1. **`dedupe_key`** — обязателен: `payment_due:{participant_id}:{period}`, `rehearsal:{plan_id}:T-24`. Гарантирует отсутствие дублей при перезапусках.
2. **Тихие часы** 20:00–08:00 следующего дня по Самаре (GMT+3, `TZ_OFFSET_HOURS=3`), поля `notification_pref.quiet_from/to`: несрочное переносится на утро, срочное (`schedule_change` в день события) — приходит как есть, но с пометкой.
3. **Лимит** — не более 5 уведомлений в сутки на человека; сверх лимита копится в дайджест.
4. **Отмена при инвалидации**: должник оплатил → все будущие `payment_due` по этому периоду `cancelled`. Событие отменено → `rehearsal_reminder` отменены.
5. **Каждое уведомление уходит через `tool-api /notify`** → запись в `audit_event(action='notification.send')`, чтобы потом можно было ответить на вопрос «мне точно присылали?».

## 3. Шаблоны (черновики)

- Репетиция: «Завтра, 28.10, 19:00–21:00 — репетиция «Гамлет», прачечная. Подтвердите: [Буду] [Не смогу]»
- Взнос: «Взнос за октябрь — 5 000 ₽, срок 30.10. Сейчас числится задолженность 5 000 ₽. [Оплатил] [Напомнить позже]»
- Дайджест org: «Неделя: 3 репетиции, 2 занятия; бюджет −12 400 ₽; должников 4 на 20 000 ₽; занятость заполнена у 14/18.»

Кнопки в уведомлениях — единственный быстрый путь. «Не смогу» → сразу создаёт `busy` на этот интервал и уведомляет орг.состав: это дешёвый способ поднять покрытие занятости.

## 4. Настройки пользователя

`/settings` → отключение категорий, свои тихие часы, вкл/выкл дайджеста. Орг-состав не может
отключить `schedule_change`. Уведомления `budget_approval` нет: механизм второго
подтверждения крупных сумм снят 30.10.2026 (`docs/architecture/25` §4).

# Часть 2. Аудит

## 1. Принципы

- Append-only: `UPDATE`/`DELETE` на `audit_event` запрещены грантами БД.
- Пишется всё, что меняет состояние **или** даёт доступ к данным: создание/изменение транзакций, правки занятости, события календаря, смена ролей, регистрация, выдача кодов, доступ к чужим файлам, отправка уведомлений, отказы доступа.
- Один диалог = один `correlation_id`: по нему видно всю цепочку «сообщение → интент → два tool-вызова → запись в Sheets».
- Ужесточение: `hash = sha256(prev_hash || canonical_json(event))` — цепочка. `/audit verify` проверяет целостность и показывает первое расхождение.

## 2. Что именно фиксируется по бюджету

На каждое изменение — `before` и `after` полной строки:

```json
{
  "action": "budget.tx.create",
  "entity_type": "budget_tx",
  "entity_id": "1730000000123",
  "before": null,
  "after": {"tx_date":"2026-10-25","amount":3000,"category":"Фото/видео","purpose":"Фотосъёмка Зайцев"},
  "source": {"chat_id": 123, "message_id": 991, "tool_call_id": 8871},
  "actor_type": "human", "actor_id": 5, "correlation_id": "…"
}
```

Плюс зеркальная запись в самом листе: колонки `Кто внёс` и `Основание` — так даже человек, открывший файл без бота, видит происхождение строки. Аудит в БД и след в файле должны сходиться; расхождение — сигнал.

## 3. Реконсиляция как часть аудита

`budget_recon` (см. `docs/architecture/01` §4) — ежедневная сверка «файл ↔ зеркало»:
- `row_only_in_sheet` — ручная правка, индексируем;
- `row_only_in_db` — строку удалили, помечаем `rejected`;
- `value_mismatch` — человек исправил, принимаем его версию;
- `header_mismatch` — контракт листа сломан, стоп, алерт.

Отчёт — одна строка админу. Молчание бота здесь недопустимо: именно реконсиляция отвечает на вопрос «почему в боте цифры другие».

## 4. Сроки хранения

| Данные | Срок |
|---|---|
| `audit_event` (деньги) | 5 лет |
| `audit_event` (прочее) | 24 месяца |
| `message_event` | 90 дней |
| `tool_call_log` | 90 дней |

# Часть 3. Защита от галлюцинаций (реализация требования «не выдумывать»)

Требование из `IDEA.md` §4: бот не имеет права выдумывать факты, цифры, даты, имена; обязан помечать предположения.

## 1. Контракт источника

Каждый tool-ответ обязан содержать `source`:

```json
{
  "ok": true,
  "data": {"amount": 184000, "period": "2026-Q3"},
  "source": {"file": "Бюджет театра", "sheet": "Транзакции", "rows": [180, 214],
             "fetched_at": "2026-10-25T14:02:11+03:00"}
}
```

Нет `source` → ответ считается невалидным и не попадает в LLM.

## 2. Пост-валидатор ответа (в n8n, перед отправкой)

Проверяет автоматически:
1. Все числа в тексте ответа присутствуют в `data` хотя бы одного tool-вызова этого диалога (с точностью до форматирования).
2. Все даты — из tool-ответов, не из «сегодня ±».
3. Все имена — из результата поиска по участникам/контрагентам.
4. Если в тексте есть `≈`, `примерно`, `судя по` — в ответе обязан быть дисклеймер «оценка, а не факт из файла».
5. Провал любой проверки → ответ заменяется на: «Не могу подтвердить эти данные по файлам театра. Уточните вопрос или посмотрите лист {название}». Инцидент логируется (`action='answer.fact_mismatch'`) — это метрика качества.

## 3. Пустой результат

Отсутствие данных — это валидный ответ, а не повод додумать:
- «В файле бюджета нет записи о платеже Зайцеву за фотосъёмку.» ✅
- «Скорее всего, оплата прошла в сентябре.» ❌ (если в источнике нет даты)

## 4. Роли в промпте, а не в данных

LLM получает только разрешённый срез: `role`, `allowed_tools`, результат их вызовов. Данные чужих людей не попадают в контекст вообще — не «нельзя говорить», а физически отсутствуют. Это единственная надёжная изоляция.

## 5. Режим деградации

n8n недоступен → простые команды (`/notes`, `/schedule`, `/balance`, `/mydues`) отвечают напрямую из `tool-api`, без LLM. Формулировки фиксированные, факты — из тех же tool-ответов с `source`. Полноценный диалог при этом недоступен, и бот это честно говорит.
