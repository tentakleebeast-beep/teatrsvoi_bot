# 04. Занятость, сводное расписание, окна, календарь

Исходное состояние: расписание существует «в голове» заказчика, вносится в Google Calendar вручную; занятость участников ведётся каждым вручную в общем файле. Задача — собирать занятость из чата, читать файл, строить сводную картину и предлагать окна.

---

## 0. Календари и часовой пояс (обновлено 26.10.2026)

- Часовой пояс всей системы — **Самара, UTC+4** (`TZ_OFFSET_HOURS=4`, Europe/Samara).
  Внимание: Самара — UTC+4, Москва — UTC+3. Календари студии живут в Europe/Samara.
- Два календаря в `.env`:
  - `CALENDAR_ID_READ` — боевой «Театр-студия СВОИ», **только чтение**;
  - `CALENDAR_ID_DRAFT` — «SVOI CALENDAR», черновой для обкатки: сюда пишет бот,
    боевой не трогаем.
- Именование: маска **«Тип - Название»** — «Аренда - Валерий», «Репетиция - Чёрная пурга»,
  «Тренинг - Музыка», «Показ - Добряки».
  Типы: `Аренда`, `Показ`, `Репетиция`, `Тренинг`, `Служебное`.
- Доход студии: события арендаторов (`Аренда - …`) и показы арендаторов (`Показ - …`) —
  это оплата за помещение и организацию. Свои события (репетиции, тренинги, спектакли
  студии) доходом не являются.
- Цвета — `config/calendar-palette.yaml`, задаются **на событии** (`colorId` 1–11):
  Аренда 10 (зелёный, как «Авокадо» сейчас), Показ 11, Репетиция 9, Тренинг 5, Служебное 8.
  Цвет календаря целиком — личная настройка пользователя, сервисной учётке недоступен.
- События, уходящие в ночь, заканчиваются **23:55**, не 00:00.
- Регулярные аренды — еженедельные серии (`RRULE:FREQ=WEEKLY` по дням недели). В API их
  видно только при `singleEvents=false` у мастер-событий; инстансы несут `recurringEventId`.
- Правила оформления событий выведены из 381 события боевого календаря и лежат в
  `config/calendar-rules.yaml`:
  - название короткое, без даты и времени внутри («Валерий Аренда», «Репа ЖН Наташа», «КУРС»);
  - локация, описание, участники и повторения не заполняются;
  - аренда 1–1,5 ч, репетиции 2–4 ч, показы 1–5 ч;
  - типовые старты: 08:00, 09:00, 10:00, 12:00, 16:00, 18:00, 20:00;
  - «аренда» встречается и первым, и вторым словом — бот нормализует к «Валерий Аренда».
- Проверка доступа: `GET /tools/calendar/health`, чтение: `GET /tools/calendar/events?days=7`,
  тот же вызов с `draft=true` — черновой.
- Заполнение чернового неделей: `python scripts/calendar_fill_draft.py` (идемпотентно).

## 1. Два независимых артефакта

| Артефакт | Что содержит | Кто главный |
|---|---|---|
| Файл занятости (Google Sheets) | «когда человек **может**» — доступность | человек (в т.ч. через бота) |
| Google Calendar | «что **уже стоит**» — события | орг.состав через бота |

Сводное расписание = доступность ∪ события. Это разные вещи, и смешивать их в одну таблицу нельзя: доступность устаревает, события — нет.

## 2. Каноническая схема доступности

Адаптер читает существующий файл и приводит его к виду:

| Поле | Тип | Пример |
|---|---|---|
| `participant_id` | через `person_alias` | 12 |
| `avail_date` | date | 2026-10-28 |
| `start_time` / `end_time` | time | 18:00 / 22:00 |
| `kind` | `free` \| `busy` \| `preferred` | busy |
| `raw_text` | исходная фраза | «в среду после 18 не могу» |
| `valid_until` | date | 2026-11-25 |

Правила:
- `busy` — «не могу», «занят», «на работе до 19».
- `free` — «могу», «свободен».
- `preferred` — «удобно», «лучше в это время».
- Нет данных о человеке ≠ свободен. Отсутствие записей = **неизвестно** (`unavailable_reason='no_data'`), и это явно показывается в предложении окон.
- Строка истекает через 28 дней (`valid_until`) — иначе через полгода поиск окон будет опираться на прах. Джоба `availability.expire` чистит просроченные и раз в 2 недели просит участника обновить («Ваша занятость устарела, актуальна?» + кнопки).

### Формат хранения в файле
Лист `Занятость`:

| Дата | Участник | С | По | Тип | Источник | Обновлено |
|---|---|---|---|---|---|---|
| 28.10.2026 | Зайцев | 18:00 | 22:00 | занят | бот | 25.10 14:02 |

Бот пишет только эти 7 колонок и только в конец листа; сортировкой и оформлением занимается человек.

## 3. Сбор занятости из чата

```
"я занят в среду после 18"           → busy, 2026-10-28, 18:00–23:59
"в пятницу могу только до 15"        → busy, 2026-10-30, 00:00–15:00 (или free после 15)
"28-29 октября на гастролях"         → busy, две даты, весь день
"свободен в выходные, лучше в субботу"→ free 31.10–01.11 + preferred 31.10
"снимаюсь 3 ноября с 10 до 18"       → busy, 03.11, 10:00–18:00
```

Конвейер:
1. Парсер дат/времени (Python, `dateparser` + правила для «среда», «выходные», «после 18»), не LLM. LLM — только чтобы выделить фразу про занятость и «понять» опечатки.
2. Черновик ответа:

```
Записал занятость:
  ср 28.10, 18:00–23:59 — занят
[Верно] [Исправить] [Отменить]
```
3. Подтверждение → `tool-api /availability` → строки в БД + `values.append` в лист → audit.
4. Нечёткая дата («в среду» при двух средах в горизонте) → уточняющий вопрос с кнопками дат.
5. Нет `participant_id` привязки → «не знаю, кто вы в файле, напишите организатору» (кейс из открытых вопросов).

Тот же путь используется, когда орг.состав вносит занятость **за другого** («Зайцев занят 28-го») — с пометкой `source='admin'` и уведомлением человеку.

## 4. Сводное расписание

`GET /schedule/summary?from&to&project` возвращает:

- события из Calendar (заголовок, время, участники, место);
- агрегированную доступность по дням: сколько человек `free`, `busy`, `нет данных`;
- «горячие» дни: пересечение занятости > 60% состава;
- покрытие: доля участников с актуальными данными (`coverage_pct`) — ключевая метрика доверия к расписанию.

Ответ орг-составу — компактная структура + текст: «На 28.10 данных по 14 из 18 (78%). Свободны 6, заняты 5, неизвестно 3».

## 5. Алгоритм поиска окон (детерминированный)

Вход:
```json
{
  "duration_min": 120,
  "participants": [12, 15, 18, 21],
  "window": {"from": "2026-10-27", "to": "2026-11-02"},
  "required_free": "all",
  "constraints": {"location": "прачечная", "not_before": "17:00", "not_after": "23:00",
                  "weekdays_only": false, "avoid_days": ["2026-10-31"]}
}
```

Шаги:
1. Сетка слотов по 30 мин в окне, шаг сдвига 30 мин, TZ Europe/Moscow.
2. Удалить пересечения с Calendar (события участников и площадки) — с буфером 30 мин на дорогу.
3. Удалить `busy`-интервалы.
4. Отсеять слоты, где `no_data` у кого-то из обязательных участников — либо пометить, но не отбрасывать (флаг `unknown_participants`).
5. Скоринг: база 100; −15 за каждого `no_data`; +10 если все `preferred`; −20 за слот после 21:30; −10 за ранний (<10:00); +5 за день, где у большинства уже есть репетиция (меньше выездов).
6. Вернуть top-3 с объяснением на человеческом языке: «ср 28.10 19:00–21:00 — свободны все 4; у Зайцева помечено „удобно“; минус: двое под вопросом».

Важно: скоринг и пересечения считает **код**, LLM только переводит результат в текст. LLM не имеет права предлагать слот, которого нет в `candidates`.

Сохранение: `slot_proposal` + выбор `chosen_index` → `event_plan(status='proposed')` → подтверждение → создание события в Google Calendar.

## 6. Календарь

- Один общий календарь театра (`CALENDAR_ID` в окружении), service account с правами записи.
- Создание только после подтверждения: показываем «Что / Когда / Где / Кто приглашён» → [Создать] [Правка] [Отмена].
- Тема события по шаблону: `Репетиция · {проект} · {группа}`, тип в описании: `kind=rehearsal; plan_id=42`.
- `gcal_event_id` сохраняется в `event_plan`; повторное создание не допускается (проверка по `plan_id` в описании).
- Изменение/отмена через бота — с уведомлением всем участникам (`schedule_change`).
- Recrudescence-кейс: событие удалили руками в календаре → реконсиляция помечает `event_plan.cancelled`, не восстанавливает.
- Повторяющиеся события (регулярные тренинги) — поддержать `RRULE`, но в MVP только через ручное создание в календаре; бот их читает.

---

## 7. Чего не делаем в MVP

- Автоматическое назначение репетиций без человека (только предложения).
- Учёт дороги/пробок, приоритетов ролей в спектакле, доступности зала по договору.
- Групповые чаты как источник занятости.
- Опрос «кто когда может» через массовую рассылку с кнопками — фаза 2 (сильно снижает ручной ввод, но требует отдельного диалогового дизайна).

---

## 8. Нужно от заказчика

Образец текущего файла занятости (колонки и формат) → адаптер `sheet_import`. Без него сводное расписание работает только на данных, собранных ботом.
