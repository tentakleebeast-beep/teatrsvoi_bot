# 51. Назначение события: что сделано

Дата: 27.10.2026. Реализация `docs/architecture/50` — шаг, который замыкал процесс.
Два входа: текст в чате и (дальше) форма поиска окон.

---

## 1. Два входа — один результат

| Вход | Кто | Состояние |
|---|---|---|
| Текст: «назначь репетицию с Витей и Людой в четверг в 20:00» | организатор | готово |
| Форма поиска окон → выбор окна → назначение | организатор | следующий шаг |

Оба ведут к одному API: `preview` → `assign`. Разница только в том, откуда
берутся участники и время.

---

## 2. Как работает текст

```
«назначь репетицию с Витей и Людой в четверг в 20:00»
        │
        ├── тип: репетиция
        ├── день: четверг (ближайший)
        ├── время: 20:00, длительность по умолчанию 2 часа
        ├── кто: «Витей», «Людой» → Новиков Виктор, Волкова Людмила
        └── помещение: сцена (по умолчанию)
        │
        ▼
   проверка занятости людей → предупреждение
   проверка занятости помещения → ошибка
        │
        ▼
   карточка с кнопками [Назначить] [Отмена]
```

### Имена, а не роли

Заказчик подчеркнул: «Витя и Люда — имена актёров, а не ролей». Реализовано так:
сопоставление идёт по псевдонимам (полное имя, короткое имя, фамилия), а роли
(`alias_kind='role'`) отодвигаются в конец списка кандидатов.

Падежи обрабатываются отсечением окончаний: «Витей» → `вит`, «Витя» → `вит`,
«Людой» → `люд`, «Люда» → `люд`. Без этого «с Витей и Людой» не находило никого.

### Что блокирует, а что предупреждает

| Проверка | Поведение | Почему |
|---|---|---|
| люди заняты по своим отметкам | предупреждение | человек рядом, он может решить иначе |
| помещение занято | **ошибка** | зал физически один, обойти нельзя |
| имена не найдены | предупреждение | можно назначить без них |
| тип/день/время не распознаны | ошибка с подсказкой | без этого событие бессмысленно |

Это ровно то, что заказчик сформулировал: «участники — предупреждение,
помещение — ошибка».

### Диалог уточнений: бот помнит, о чём спросил (t_ebce081e)

Живой разговор 05.11.2026 показал, что одного разбора мало: человек сказал
«поставь встречу с Марком и Машей», бот спросил день, на «завтра» ответил
расписанием, а на «с 15-00 до 18-00» показал расход на 15 ₽. Причина — состояния
не было, каждая реплика шла как новая фраза.

Теперь у назначения есть состояние `AssignDraft` (`states.py`) с шагами
`await_kind` / `await_date` / `await_time`:

* что уже сказано, хранится в `state.update_data` (поле `ad.text`) и **дописывается**
  следующей репликой — сказанное не теряется;
* какого поля не хватает, решает **сервер**: коды `no_kind`, `bad_date`, `no_date`,
  `no_time` в ответе `/tools/events/preview` — единственный источник, gateway разбор
  не повторяет (иначе два разбора разойдутся);
* спрашивается только недостающее; после третьей реплики показывается карточка;
* выход из диалога: кнопка «Отмена» (`evdraft:no`), слово «отмена», `/menu`, `/start`,
  кнопка меню и любое явно другое намерение («сколько денег», «запиши расход») —
  черновик снимается, реплика идёт обычным путём;
* запись по-прежнему только по кнопке «Назначить»: у модели нет пишущих инструментов.

Формы времени, которые понимает разбор (модуль `app/assign.py`, функция
`normalize_hours`):

| Написано | Разобрано |
|---|---|
| «с 15-00 до 18-00» | 15:00–18:00 (дефис в часах = двоеточие) |
| «15-18» | 15:00–18:00 (правая часть больше 9 — тоже час) |
| «19-30» | 19:30 (правая часть больше 23 — минуты) |
| «с трёх до шести» | 03:00–06:00 (часы словами; рабочий день проверяет сервер) |
| «5.11», «31.12.2027» | явная дата (иначе спрашиваем день); она сильнее «завтра» |
| «1.5 часа» | половина часа, а не 1 мая: дробь рядом с «час» датой не считается |
| «в 19:00» | 19:00–21:00 (прежняя форма, длительность 2 часа) |

**Защита бюджета.** Строка без денежного признака (нет `₽`, «руб», «потратил»,
«заплатил» и т.п.), но с интервалом часов — это время, а не сумма: `text_to_draft`
возвращает `None`, черновик расхода не появляется. Фраза с суммой («3000 на
реквизит») остаётся операцией, как и раньше (docs/82 §4.1).

## 3. API

### Предпросмотр

```
POST /tools/events/preview
{"text": "назначь репетицию с Витей и Людой в четверг в 20:00"}
```

или структурно:

```json
{"kind": "rehearsal", "title": "Жизнь насекомых", "date": "2026-12-19",
 "from_hour": 18, "to_hour": 21, "participants": [15, 23], "venue": "stage"}
```

Ответ: `proposal_id`, `card` (тип, название, дата, часы, помещение, участники),
`warnings`, `errors`, `can_assign`. Предпросмотр сохраняется в `slot_proposal` —
поэтому подтверждение идёт по `proposal_id`, а не по повторному разбору текста.

#### Контракт «мягкого» предпросмотра (S-8)

Предпросмотр — это разговор с человеком, а не запись. Поэтому непонятный ввод
не является сбоем API: HTTP-статус всегда **200** (кроме грубых нарушений схемы,
`422` от валидации тела: NaN, NUL, слишком длинный текст, нулевая длительность).
Непонимание фразы возвращается в теле:

```json
{"ok": false, "input_error": true, "can_assign": false, "proposal_id": null,
 "card": null, "warnings": [],
 "errors": [{"code": "no_time", "text": "Не понял время начала."}]}
```

Правила контракта:

| Поле | Значение |
|---|---|
| `ok` | `true` — карточку можно назначать; `false` — есть блокирующие ошибки |
| `input_error` | `true` — причина в самом вводе (`no_kind`, `bad_date`, `no_date`, `no_time`, `bad_time`): надо переспросить человека, а не сообщать о сбое |
| `card` | `null`, если разбор не дошёл до карточки |
| `proposal_id` | `null`, если заявка не сохранялась |
| `errors` | список `{code, text}`; `text` — готовая фраза для человека |

`input_error: false` при `ok: false` означает, что ввод понят, но назначить нельзя
(например `venue_busy` — помещение занято). Это не ошибка ввода: боту нужно
предложить другое время, а не переспрашивать состав.

Клиенты обязаны смотреть на `ok` и `input_error`, а не на HTTP-статус.
Это же поведение у обёртки `/webapp/preview` из Mini App.

### Назначение

```
POST /tools/events/assign {"proposal_id": 42}
```

Порядок: повторная проверка помещения → событие в календарь (черновой) →
запись в `event_plan` → уведомления участникам → аудит.

Повторное назначение той же заявки → `400 already_assigned`.
Заняли помещение между предпросмотром и подтверждением → `409 slot_taken`.

## 4. Что записывается

| Куда | Что |
|---|---|
| Google Calendar (черновой) | событие с `svoi_kind`, `svoi_venue`, `svoi_participant_ids`, цвет по палитре |
| `event_plan` | `status='confirmed'`, `gcal_event_id`, участники, помещение |
| `notification` | по записи на каждого участника, `dedupe_key = event:<id>:assigned` |
| `audit_event` | кто назначил, что, кому, попал ли в календарь |

Если календарь недоступен, событие всё равно создаётся в расписании,
а в карточке честно пишется: «Календарь недоступен — событие только в расписании».

## 6. Проверено на живой системе

```
«назначь репетицию с Витей и Людой в четверг в 20:00»
→ Репетиция, четверг 29.10, 20:00–22:00
→ участники: Новиков Виктор, Волкова Людмила
→ нельзя: «Сцена занято в это время» (в календаре идёт показ)

«назначь тренинг с Витей в воскресенье в 12:00»
→ Тренинг, воскресенье 01.11, 12:00–14:00, Новиков Виктор
→ внимание: «По отметкам заняты: Новиков Виктор» → назначать можно

«назначь репетицию с Сашей в субботу в 15:00 на 3 часа»
→ Репетиция, суббота 31.10, 15:00–18:00, Орлова Александра
→ без замечаний
```

## 8. Что осталось

| Задача | Почему не сейчас |
|---|---|
| Форма поиска окон (тип, участники, проект, длительность) перед запуском | отдельный экран Mini App; текстовый вход уже закрывает потребность |
| Кнопка «Назначить» под найденными окнами | полдня, после формы: окна уже содержат состав и время |
| Отрисовка результата поиска на сетке | визуализация, не влияет на запись |
| Уведомление «через 2 дня» | сейчас ставится только уведомление о назначении |
| Отмена и перенос события | нужен `POST /tools/events/cancel` и правило прав |
