# 47. Пространства: сцена, гримёрка, подсобки

Дата: 27.10.2026. Развивает `docs/architecture/46`: зал был один, а мероприятий, которые
не мешают друг другу, — несколько.

---

## 1. Зачем

Репетиция на сцене и разбор роли в гримёрке идут одновременно, и это нормально.
Аренда на сцене не блокирует хоз.работы в подсобках. Пока зал был один,
бот считал студию единым помещением и запрещал параллельную работу.

Теперь занятость считается **по пространству**, а не по студии целиком.

---

## 2. Модель

Таблица `venue` (миграция `025`):

| Поле | Смысл |
|---|---|
| `code` | `stage`, `dressing`, `backstage` |
| `name` | «Сцена», «Гримёрка», «Подсобки» |
| `kind` | `stage` / `room` / `outdoor` |
| `calendar_id` | свой календарь, если есть |
| `is_active` | скрыть, не удаляя |
| `sort_order` | порядок в списках |

Заведены три пространства. Основное — `stage`, хранится в `app_setting`
(`default_venue_code`).

---

## 3. Решение 27.10.2026: пока считаем студию одним помещением

Модель пространств готова, но **в расчёте по умолчанию студия — единое помещение**:
занятие в гримёрке занимает студию так же, как занятие на сцене.

Почему так:

- параллельные занятия требуют отдельной автоматизации (кто в каком помещении,
  сколько людей, можно ли одновременно) — это отдельная задача;
- пока ботом пользуются два человека, ошибиться в «какой зал» дороже, чем
  перестраховаться и не предложить зал;
- данных о том, какие занятия действительно параллельны, ещё нет.

Что это значит практически:

| Запрос | Расчёт |
|---|---|
| `{"policy": "rental"}` (без `venue`) | занятость всей студии: все события периода |
| `{"policy": "rental", "venue": "dressing"}` | только это пространство |

То есть помещение можно указать явно — механизм рабочий, — но по умолчанию
бот считает студию целиком и не предложит зал, занятый хоть чем-то.

---

## 4. Два источника занятости

| Источник | Когда используется | Плюс | Минус |
|---|---|---|---|
| **Свой календарь** (`venue.calendar_id`) | если у зала отдельный календарь | `freebusy` одним запросом, видно всем | нужно заводить календарь на зал |
| **События общего календаря** | по умолчанию | один календарь, различие — свойство события | читаем все события периода |

Второй вариант выбран по умолчанию: заводить три календаря ради трёх помещений
избыточно, а свойство `svoi_venue` в событии решает ту же задачу.

**Событие без `svoi_venue` считается событием сцены.** Так старые события
не теряются и не начинают вдруг блокировать гримёрку.

## 5. Что изменилось в API

### Создание события

```json
POST /tools/events/assign
{"card": {"kind": "rehearsal", "title": "Разбор роли", "date": "2026-12-25",
          "from_hour": 18, "to_hour": 20, "venue": "dressing"}}
```

`venue` необязателен: без него — сцена (`default_venue_code`).

### Поиск окон аренды

```json
POST /tools/schedule/slots
{"policy": "rental", "venue": "dressing",
 "date_from": "2026-12-28", "date_to": "2026-12-28", "min_hours": 2}
```

`venue` необязателен, по умолчанию — сцена. В ответе:

```json
{"mode": "venue", "policy_title": "аренда (Гримёрка)",
 "venue": {"venue": "dressing", "name": "Гримёрка",
           "source": "events", "applied": true, "busy": 0}}
```

### Список пространств

```
GET /tools/venues
→ {"ok": true, "default": "stage",
   "venues": [{"code": "stage", "name": "Сцена"}, ...]}
```

## 6. Проверка: параллельные мероприятия

```
сцена:    показ 18:00–22:00
гримёрка: пусто

аренда на сцене  → окна 08:00–18:00
аренда в гримёрке → окна 08:00–24:00
```

Оба запроса — на один и тот же день. Раньше второй был бы невозможен:
занятость считалась общей.

---

## 7. Буферы не вводим

Заказчик: «уборка и подготовка зачастую включаются во время аренды».
Значит, отдельного буфера между арендами нет — арендатор сам закладывает время.

Если однажды понадобится, это будет поле `venue.buffer_minutes` (по умолчанию 0),
и применяться будет только к аренде, не к репетициям.

## 8. Тесты

`tests/unit/test_venue_spaces.py` — 6 тестов: сцена и гримёрка не мешают друг другу,
событие без зала считается сценой, свободные окна по пространству, склейка двух
событий на сцене, чужое пространство не учитывается.

`tests/integration/test_venues_api.py` — 5 тестов: список пространств, пометка
события пространством, сцена по умолчанию, аренда по разным пространствам
не пересекается.

`tests/integration/test_venue_api.py` — 3 теста (обновлены под новую модель):
аренда без персонала = окна зала, с персоналом = зал и люди, без данных зала —
честное предупреждение.

Всего 15 тестов по пространствам, включая проверку «студия как одно помещение».

## 9. Что осталось

| Задача | Почему не сейчас |
|---|---|
| Второй зал с отдельным календарём | модель готова (`calendar_id`), нужен сам календарь |
| Автоматизация параллельных занятий | отдельная задача: правила «что с чем совместимо» |
| Пересечение пространств (аренда сцены + гримёрки одной командой) | нужен запрос «несколько залов» |
| Занятость по времени, а не по часам | сейчас шаг — час, для аренды достаточно |
| Цена аренды по пространству | бюджет умеет, связки «пространство → статья» нет |
