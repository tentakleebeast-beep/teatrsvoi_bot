# 10. Модель данных v2: что нашли в файлах и как учёт устроен теперь

Основание: разобраны реальные файлы из `sources_example/Инфа СВОИ/Админ/` (8 xlsx, 19 docx, 270 файлов всего). Схема: `db/init/001_schema.sql` (применяется на живом Postgres — проверено).

---

## 1. Что реально лежит в файлах

### Занятость — `Расписание СВОИ.xlsx`

18 листов:
- `Свод СВОИ`, `Свод СВОИ ЖН`, `Свод СВОИ Пурга`, `Свод СВОИ Бунин` — сводки;
- `Жизнь насекомых`, `Пурга`, `Бунин`, `Тренинг`, `Курс` — сетки по проектам;
- `Олег Викторов`, `Дарья`, `Витя М`, `Витя Т`, `Маша`, `Алена`, `Саша`, `Марк`, `Люда` — личные листы (9 человек).

Формат — **часовая матрица**, а не список интервалов:

```
        │ 08:00 09:00 10:00 11:00 …
пн 10.08│   0     0     1     1   …
вт 11.08│   0     0     1     1   …
```

Строк 53 (≈7,5 недель), колонок 20 (08:00 → далее). Значения строго `0/1`.

Проверил арифметику: `Свод СВОИ` = построчная сумма личных листов (2,2,3,3,4…). Значит **1 = свободен, 0 = занят**, а свод — производная величина.

Отсюда три вывода:
1. Единица хранения — **час**, не интервал. Мой прежний `availability(start_time, end_time)` был бы компромиссом с потерями.
2. Свод хранить нельзя — он вычисляется (иначе разъедется с личными листами).
3. Люди в личных листах — **никнеймы** («Витя М»), а в финансах — фамилии («Иванов Виктор»). Это две разные системы имён на одних людей.

### Бюджет — `СВОИ 2025.xlsx`

Листы: `Финансы 2026 до 06`, `Финансы 2026 от 07`, `Финансы 2025`, `Финансы 2025 (Титова Ольга + С…)`, `Финансы 2024 (Титова Ольга)`, `Приглашать`, `Студийцы`, `Репертуарный план`, `Список дел`.

Внутри финансового листа — **не таблица, а четыре блока в ряд на каждый месяц** (177 строк, 17 колонок):

| Блок | Колонки | Пример данных |
|---|---|---|
| Ежемесячная жизнь студии → Взносы студийцев | Фамилия Имя / Дата / Сумма | `Иванов Виктор … 10000` |
| Расходы студии | Статья / Дата / Факт | `Аренда Прачки 07.06.2026 −100000` |
| Показы | Источник / Сумма · Вложения: Статья (студиец) / Сумма / Возврат | — |
| Субаренда | Арендатель / … / Прибыль | — |

Статья расхода — **свободный текст**: `Аренда Прачки`, `Коммуналка`, `Крылов Виктор` (фамилия = гонорар!), `Съемки Бунин (долг)`, `Ремонт уборная`, `Раковина,кран`, `Замки`, `Установка замков`. Третий и четвёртый — фактически одна категория «Ремонт», но человек писал как удобно.

Итоги — формулами внизу блока (строка 19: `65000`, `−187000`).

### Что это значит для схемы

Прежний `budget_tx` (плоский журнал) остаётся верным, но:
- нужен `block`, чтобы различать взносы / расходы / показы / вложения / субаренду — иначе «Сумма» в разных блоках означает разное;
- нужен `period` (`YYYY-MM`), потому что месяц — единица планирования и закрытия;
- нужна **таблица `article_map`**: сырой текст статьи → категория + проект + контрагент. Без неё «Раковина,кран» и «Замки» никогда не сойдутся в статью «Ремонт»;
- `counterparty`-человек («Крылов Виктор» как статья) должен связываться с `participant` через `person_alias(alias_kind='payee')`.

## 2. Проблема, которую нашли на живых данных

В боте ты зарегистрирован как **«Иванов Виктор»** → `person_key='иванов-виктор'`.
В файле финансов — **«Иванов Виктор»** (через «ю»), в расписании — **«Витя М»**.

При миграции первые вставки дали `INSERT 0 0`: очереди не сошлись, и занятость «потерялась» — без ошибки, просто ноль строк. Это самый опасный класс баг в импорте: **тихая потеря данных**.

Лечение — `person_alias` (в схеме v2):

```sql
insert into person_alias (participant_id, alias, alias_kind, source)
values (<id>, 'иванов', 'name', 'import'),
       (<id>, 'витя м',   'short','import');
```

Проверено: после алиасов занятость и взносы легли на нужного человека, `v_availability_summary` и `v_dues_balance` отдают корректные цифры.

Правило на будущее: любой импорт, где не удалось сопоставить имя, **не молчит** — пишет строку в `import_row` с `issue='unknown_person'` и попадает в очередь ревью.

## 3. Разделение «пользовательские» / «ботовские» данные

| Слой | Где живёт | Кто хозяин | Что содержит |
|---|---|---|---|
| Пользовательский | Google Sheets | человек | блоки финансов по месяцам, часовая матрица занятости |
| Ботовский | Postgres | бот | нормализованный журнал, справочники, привязки, аудит, состояние |
| Общий контент | Drive `_shared` | человек | пьесы, партитуры, медиа, афиши |

Три таблицы связывают слои:

**`sheet_binding`** — где в листе живёт блок. Бот никогда не угадывает адреса:
```json
{ "key":"budget.finance", "spreadsheet_id":"…", "sheet_title":"Финансы 2026 до 06",
  "layout":"monthly_blocks", "header_row":3, "meta":{"blocks":["dues","expense","show"]} }
```

**`row_map`** — соответствие строки/ячейки листа сущности БД (`entity_type='budget_tx'`, `entity_id=…`, `sheet_row=5`, `cell_key='2026-08-10T19'`). Строки в листе двигаются — id не двигается. Здесь же `content_hash`, чтобы ловить ручные правки.

**`import_batch` / `import_row`** — журнал миграции: что прочитано, как разобрано, с какой уверенностью, что осталось на ревью.

## 4. Как идёт миграция (идемпотентно)

```
1. import_batch(kind='budget', source=…, source_hash=sha256 файла)
2. для каждого листа по sheet_binding:
     читаем блок → строки → import_row(raw=jsonb)
3. резолв:
     «Фамилия Имя»  → person_alias → participant      (нет → issue='unknown_person')
     «Статья»       → article_map  → category/project (нет → issue='unknown_article')
     месяц/дата     → period, tx_date
4. запись:
     взносы      → dues_charge(participant, period, amount_due)
     расходы     → budget_tx(block='expense', amount=abs(Факт), …)
     показы      → budget_tx(block='show_income'/'show_invest')
     субаренда   → budget_tx(block='sublease')
     занятость   → availability_hour(participant, day, hour, is_free)
5. row_map: запоминаем строку листа ↔ id сущности
6. import_batch.status = 'needs_review' | 'applied', stats в jsonb
```

Свойства:
- **повторный запуск не дублирует** — уникальные ключи (`unique(person,period)`, `unique(participant,day,hour)`, `(source_chat_id, source_message_id)`);
- **неизвестное не теряется** — `import_row.issue` и очередь ревью;
- **файл приходит после людей** — сначала `participant` + `person_alias`, потом финансовые строки; иначе всё упадёт в `unknown_person`.

Отдельно: `article_map` наполняется полуавтоматически — импорт складывает новые статьи в очередь, ты подтверждаешь категорию один раз, дальше распознаётся само.

## 5. Запись обратно в лист (бот → Sheets)

Пишем только то, что человек и так вносит руками, и только по `sheet_binding`:

| Что | Куда | Как |
|---|---|---|
| Взнос оплачен | `dues_charge` + строка в блоке взносов | `values.update` в найденную `row_map` строку, колонка «Сумма/Дата» |
| Расход из чата | блок «Расходы студии» текущего месяца | `values.append` в конец блока + `row_map` |
| Занятость из чата | личный лист человека, ячейка `[day, hour]` | `values.update` по `cell_key` |
| Свод | **никогда** | формулы человека не трогаем |

Перед любой записью — проверка свежести (`properties.lastEditTime` vs `sheet_binding.last_read_at`, ADR-3). Файл новее индекса → перечитать, обновить, потом писать.

## 6. Последствия для остального дизайна

**Заметки переезжают в БД.** Проверено опытом: `storageQuota.limit = 0` у сервис-аккаунта, файлы он создавать не может (подробности в `docs/infrastructure/09`). Значит `.md` в Drive от имени бота невозможны. `note.drive_file_id` остаётся `null`; текст живёт в Postgres, поиск — `to_tsvector`/`pg_trgm`. Выгрузка в Drive — только в файл, созданный человеком, либо после подключения Shared Drive.

**Медиа грузят люди.** `_shared/media` наполняется вручную (или через Telegram — но тогда файл пишет бот, а он не может). Вариант на будущее: человек пересылает файл боту, бот складывает в БД/локально, а человек раз в месяц переносит в Drive. Либо Shared Drive, если появится Workspace.

**Сводные листы — производные.** `v_availability_summary` и `v_dues_balance` считают то же, что формулы человека. Если расхождение — прав человек, бот перечитывает.
