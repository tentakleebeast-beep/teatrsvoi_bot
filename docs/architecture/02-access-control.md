# 02. Роли, матрица доступа, регистрация

> **n8n выведен из контура (V-026, 01.11.2026).** Где ниже n8n назван частью контура или
> источником разбора свободного текста, читать: `POST /tools/route` в tool-api

> удалены из деплоя. История контрактов — `docs/archive/29-n8n-scenarios.md`.

## 1. Роли

| Роль | Кол-во | Кто | Смысл |
|---|---|---|---|
| `admin` | 1 | заказчик (chat_id в `ADMIN_CHAT_ID`) | всё, включая управление идентичностями и просмотр аудита |
| `org` | 3–6 | костяк труппы, организаторы | все пользовательские функции: бюджет, расписание, участники (без управления ролями) |
| `troupe` | ~10 | актёры | своя занятость, свои заметки, уведомления, просмотр своего расписания и своих взносов |
| `master` | 1–3 | педагоги по дисциплинам | сводная занятость и состав труппы, свои отметки, поиск окон, назначение событий, заметки и файлы; без денег, рассылки и управления людьми. Модель и матрица — `docs/architecture/140-master-role.md` |
| `student` | 10–20 | курсы (взрослые, позже подростки) | роль снята миграцией `017`; строка оставлена как след истории |

Правило: **роль — свойство идентичности, а не заявление пользователя**. Пользователь не выбирает роль ни на одном шаге.

## 1.1 RBAC + capabilities (актуальная модель)

Одна роль на человека — упрощение, которое не выдержало реальности: владелец театра
одновременно админ, организатор, студиец и иногда педагог.

Модель: **роли — множественные, доступ — по возможностям (capability)**.

```
participant ──< participant_role >── rbac_role_capability ──> rbac_capability
     └────────< participant_capability_override (выдать/отобрать лично)
```

Итоговый набор = объединение возможностей всех ролей + личные выдачи − личные запреты.
Вычисляется представлением `v_participant_capabilities`, проверяется на каждом запросе
в `tool-api` (`require("budget.write")`), а не в UI.

| Роль | Возможностей |
|---|---:|
| admin | 24 (все) |
| org | 16 |
| master | 7 (расписание, окна, события, заметки, файлы, состав; без денег и управления) |
| troupe | 5 |
| student | роль снята (`017_drop_student_role.sql`) |

Числа — по `db/init/*.sql` после всех миграций: возможности добавляли `admin.panel`,
`feedback.send`, `participants.contact`, `schedule.write`, `budget.import` и другие.
Роль `student` удалена миграцией `017`; строка с ней в матрице §2 оставлена как след
истории, а не действующая роль.

Возможности (сценарии): `registration.code.issue`, `registration.approve`,
`participants.view`, `participants.manage`, `budget.read`, `budget.read.self`,
`budget.write`, `budget.import`, `schedule.read.all`, `schedule.availability.self`,
`schedule.slots`, `calendar.write`, `notes.write`, `files.access`, `notify.send`,
`audit.view`, `quota.manage`, `system.health`.

Управление: `POST /admin/grant` — выдать роль или включить/отключить одну возможность
с указанием причины. Всё пишется в аудит (`rbac.role.grant`, `rbac.capability.grant`).
Проверить свои права в боте: `/caps`.

## 2. Матрица прав

> Матрица отвечает на вопрос «у какой роли есть возможность». Что именно делает каждое действие,
> каким правом закрыто и каким единственным путём пишется — в едином реестре действий:
> `docs/architecture/25-architecture-evolution.md` §9.4 (ADR-13, 04.11.2026). При расхождении
> матрицы и реестра прав реестр — потому что он сверен с кодом на дату, а матрица описывает роли.

Обозначения: ✅ полный доступ · 🟡 только свои данные · 🟢 только чтение · ➖ нет

| Функция | admin | org | troupe | student |
|---|:--:|:--:|:--:|:--:|
| `/start`, регистрация | ✅ | ✅ | ✅ | ✅ |
| Свои заметки (CRUD) | ✅ | ✅ | 🟡 | 🟡 |
| Свои файлы (загрузка/чтение/выдача) | ✅ | ✅ | ➖ | ➖ |
| Общие файлы (пьесы, медиа) | ✅ | ✅ | ➖ | ➖ |
| Файлы студии: экран `/webapp/files` (`files.access`; ✅ ещё у `master` — 140 §4) | ✅ | ✅ | ➖ | ➖ |
| Файлы студии: команды чата (`admin.panel`) | ✅ | ➖ | ➖ | ➖ |
| Сообщить о своей занятости | ✅ | ✅ | ✅ | ✅ |
| Своё расписание (репетиции, занятия) | ✅ | ✅ | 🟡 | 🟡 |
| Сводное расписание по труппе | ✅ | ✅ | ➖ | ➖ |
| Предложить окна для события | ✅ | ✅ | ➖ | ➖ |
| Создать/изменить событие в календаре | ✅ | ✅ | ➖ | ➖ |
| Записать транзакцию (расход/доход) | ✅ | ✅ | ➖ | ➖ |
| Читать бюджет: свод, категории, проекты | ✅ | ✅ | ➖ | ➖ |
| Читать свои взносы/задолженность | ✅ | ✅ | 🟡 | 🟡 |
| Видеть долги других | ✅ | ✅ | ➖ | ➖ |
| Рассылка уведомлений вручную (`notify.send`, только админ) | ✅ | ➖ | ➖ | ➖ |
| Управление участниками (роль, блокировка) | ✅ | ➖ | ➖ | ➖ |
| Выпуск инвайт-кодов | ✅ | ➖ | ➖ | ➖ |
| Просмотр аудита | ✅ | ➖ | ➖ | ➖ |
| Реконсиляция/диагностика | ✅ | ➖ | ➖ | ➖ |

Реализация: `tool-api` держит `POLICY: dict[role, set[scope]]`; каждый эндпоинт объявляет нужный scope (`budget:write`, `schedule:read_all`, …). Проверка — в декораторе доступа, до вызова n8n и внутри tool-эндпоинта (двойная). Отказ → 403 + `audit_event(action='access.denied')`.

Отдельно: `🟡 свои` — определяется только по `participant_id` из подписанного контекста, никогда из тела запроса от n8n.

## 3. Сценарий регистрации

### Триггеры
- `/start` от неизвестного `chat_id` → `status='pending'`.
- `/start` от `admin` при пустой БД → bootstrap: создаётся `admin`, предлагается `/invite org`.

### Шаги

```
[1] /start, chat_id не найден
    → "Это бот театра-студии СВОИ. Вы пока не зарегистрированы.
       Введите код приглашения (8 символов), который дал организатор."
    state = AWAIT_INVITE

[2] Введён код
    ├─ не существует            → "Код не найден. Проверьте или спросите организатора."  (счётчик: 3 попытки → тишина 1 час)
    ├─ истёк (TTL 7 дней)       → "Код устарел, попросите новый."
    ├─ исчерпан (uses/max)      → "Код уже использован."
    ├─ роль admin в коде        → отказ (admin только через ADMIN_CHAT_ID / команду admin)
    └─ валиден ↓

[3] Код принят
    → создаётся participant(status=pending → active), invite_code.uses += 1
    → создаётся Drive-папка /TG_<chat_id>/ + подпапки (Заметки, Файлы)
    → "Как вас зовут? Так, как вы указаны в документах театра (Фамилия Имя)."
    state = AWAIT_NAME

[4] Ввод имени
    → display_name, person_key = normalize(name)
    → если person_key уже занят → "Такой человек уже зарегистрирован. Напишите организатору."
    → создаётся /_shared/ подписка, notification_pref(дефолты)
    → audit_event: participant.register {code, role}
    → "Готово, {Имя}. Вам доступно: …" (список по роли)
    → уведомление admin: "Новый участник: {Имя}, роль {role}, человек {person_key}"

[5] admin может дополнить
    /setkey <Имя> <person_key>     привязка к имени в файлах (если не совпало автоматически)
    /role <Имя> <role>             смена роли (с аудитом и уведомлением участнику)
    /block <Имя> / /unblock <Имя>  блокировка
```

### Краевые случаи регистрации
| Ситуация | Поведение |
|---|---|
| Уже зарегистрирован | повторно код не спрашиваем, показываем меню роли |
| Двойная регистрация (второй аккаунт) | запрет: `person_key` уникален; разбор через admin |
| Код введён в состоянии AWAIT_NAME | игнорируется, повтор вопроса |
| Флуд неверными кодами | 3 попытки / час / chat_id, потом тишина; лог в audit |
| Бот перезапущен посреди регистрации | состояние в `session.state`, шаг продолжается |
| Регистрация не завершена 24 ч | `pending` помечается `archived` cron-джобой |
| Код нужно отозвать | `/revoke <code>` — `expires_at = now()` |

### Команды управления (admin)
`/invite <role> [кол-во] [дней]` — выпуск кодов, ответ списком. Орг.состав получает код с ролью `org` и регистрируется им сам — отдельного назначения роли администратором не требуется; доступ к функциям всё равно проверяется по RBAC на каждом запросе.
`/participants` — таблица: имя, роль, статус, person_key, дата.
`/audit [N]` — последние N записей.
`/health` — состояние n8n, Google, очереди, ошибок за 24 ч.

## 4. Изменение роли

1. `/role <Имя> <org|troupe|student>` — доступно только admin.
2. Запись `audit_event(action='participant.role.change', before, after)`.
3. Участнику уходит уведомление: «Ваш доступ изменён: {роль}. Теперь доступно: …».
4. Кэш контекста в n8n не используется — роль читается из `tool-api` на каждом сообщении, поэтому изменение действует сразу.

---

## 5. Аудит доступа

Логируются все отказы (`access.denied`) с указанием запрошенного scope. Это позволяет поймать две вещи: попытки лезть в чужие данные и ошибки в самой матрице прав.
