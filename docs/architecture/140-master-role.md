# 140. Роль «Педагог» (master): модель, дисциплины, права

Дата: 08.11.2026. Карта `t_6e65cbde` (Э1). Решение владельца в комментарии к карте:
отдельная роль `master` в `participant_role`, связь с дисциплиной — через
`participant_discipline`; педагог может вести несколько дисциплин.

Документ отвечает только на вопрос «как устроено». Код, миграции и экраны правит
`worker-feature` отдельными картами; здесь — границы и цена решений.

---

## 1. Решение

| Вопрос | Решение | Почему |
|---|---|---|
| Где живёт роль | `participant_role.role = 'master'` | Роль — это пакет доступа, её выдают и отзывают строкой с `revoked_at` (как `060`). Выводить роль из связи с дисциплиной — значит потерять отзыв доступа без удаления самой связи |
| Где живёт дисциплина | `participant_discipline` (`relation='teacher'`) | Дисциплина — предметная связь «человек преподаёт музыку», а не право. Она many-to-many и не мешает роли |
| Сколько дисциплин | 1 и более, верхней границы нет | Первичный ключ `(participant_id, discipline_id)` уже это допускает. Тренинг выбирает одну дисциплину, человек может вести несколько |
| Кто выдаёт | администратор, `POST /admin/grant` (роль) + отдельное действие «Дисциплины» в карточке человека | Мастер не появляется по инвайт-коду: у кода нет дисциплины, а мастер без дисциплины — ошибка состояния |
| Инвайт-коды | роли кодов остаются `admin`, `org`, `troupe` | Мастер выдаётся поверх существующей учётной записи: сначала человек регистрируется как труппа/организатор, затем админ добавляет `master` и дисциплину |
| `student` | не возвращаем | Решение `017`/`030` остаётся в силе |

### Почему не «роль выводится из `participant_discipline.relation='teacher'`»

Это выглядит дешевле, но смешивает два разных вопроса:

1. **Доступ к боту.** Роль можно отозвать, не удаляя человека из дисциплины
   (например, педагог временно не ведёт бота, но продолжает преподавать).
2. **Предметная связь.** `relation='teacher'` отвечает на вопрос «кого добавлять
   в тренинг по музыке», а не «кому показывать сводную занятость».

Если роль выводить из связи, то снятие доступа = удаление дисциплины, а удаление
дисциплины = потеря истории «кто что вёл». Кроме того, один человек может быть
`teacher` в музыке и `student` в актёрском — выводить из этого одну роль нельзя.

`participant.is_teacher` и `participant.specialty` (`027`) остаются как исторические
поля и запасной признак для старых данных. Новый источник — `participant_discipline`;
`is_teacher` для мастеров выставляется в миграции, чтобы правило состава тренинга
(`_staff_by_rules`) не расходилось с новой моделью.

## 2. Схема и миграция

### 2.1. Изменения

Файл: `db/init/061_master_role.sql` (следующий свободный номер после `060`; `059`
остаётся задокументированным буфером в `scripts/arch_drift.py`). Ревизия Alembic —
`services/tool-api/migrations/versions/061_master_role.py`, генерируется
`scripts/gen_alembic_revisions.py` и накатывает SQL целиком.

| Объект | Изменение | Обратная совместимость |
|---|---|---|
| `participant_role` | `CHECK (role in ('admin','org','troupe','master'))` | старые строки не меняются; добавляется только новое значение |
| `participant` | `CHECK (role in ('admin','org','troupe','master'))` | `role` — витрина «основная роль», права по-прежнему считает `participant_role` |
| `invite_code` | без изменений (`admin`,`org`,`troupe`) | мастер не выдаётся кодом; это сохраняет инвариант «у мастера есть дисциплина» |
| `participant_discipline` | без изменения структуры; `relation` остаётся `teacher`/`student` | связь уже many-to-many; несколько дисциплин поддерживаются ключом |
| `rbac_role_capability` | 7 строк для `master` | остальные роли не трогаются |
| `v_participant_disciplines` | новый view: `participant_id`, `display_name`, `teacher_disciplines`, `student_disciplines` | только чтение; не меняет существующие view |
| `v_participant_roles` | без изменения | `master` появится в массиве автоматически |
| `v_participant_capabilities` | без изменения | права `master` появятся через `rbac_role_capability` |
| `v_master_without_discipline` | новый view для проверки инварианта | только чтение; используется тестом/инвариантом |

### 2.2. CHECK и инвариант «мастер без дисциплины»

`CHECK` на `participant_role` ловит только недопустимое значение роли. Проверить
наличие хотя бы одной связи с дисциплиной через `CHECK` нельзя: это другая таблица.
Поэтому:

* `POST /admin/grant` при `role='master'` и `enabled=true` требует
  `discipline_id` (или непустой `discipline_ids`) и проверяет, что дисциплина
  существует и у человека появляется `participant_discipline.relation='teacher'`;
* `POST /admin/participant/discipline` не даёт удалить последнюю `teacher`-связь
  у человека с действующей ролью `master` (ошибка `master_without_discipline`);
* `v_master_without_discipline` перечисляет нарушителей; `scripts/check_invariants.py`
  и тест падают, если view не пуст.

Это не «мягкое» правило: роль без дисциплины не должна попадать в прод, иначе
мастер не сможет выбрать дисциплину при создании тренинга.

### 2.3. Что миграция НЕ делает

* Не добавляет `discipline_id` в `participant_role`: одна строка роли не должна
  дублироваться по дисциплинам.
* Не меняет `participant_discipline.relation`: `teacher` уже означает «преподаёт».
* Не удаляет `is_teacher`/`specialty`: старые данные и `_staff_by_rules` продолжают
  работать; новые записи ведём через `participant_discipline`.
* Не выдаёт мастеру доступ к деньгам, рассылке, управлению людьми и админ-панели.
* Не возвращает `student`.

## 3. Матрица прав: capability → master

Права считаются только по `v_participant_capabilities`; `master` — такая же роль,
как `admin`/`org`/`troupe`. Ниже — полный набор, который даём, и явные запреты.

| Capability | master | Обоснование |
|---|:--:|---|
| `schedule.read.all` | да | видеть сводную занятость труппы и чужие отметки — прямая задача педагога |
| `schedule.availability.self` | да | заполнять свою занятость; без этого поиск окон врёт |
| `schedule.slots` | да | искать окна под свои занятия и репетиции |
| `schedule.write` | да | назначать события; это фактическое право записи в календарь (`events.py` проверяет `schedule.write`, а не `calendar.write`) |
| `notes.write` | да | личные и общие заметки |
| `files.access` | да | доступ к «Файлам студии»: экран и данные открыты этим правом с 08.11.2026 (решение V-039 (в), см. §6.2) |
| `participants.view` | да | видеть состав труппы; телефон и управление людьми не входят |
| `calendar.write` | нет | в `rbac_capability` есть, но ни один маршрут его не проверяет; выдавать мёртвое право — обещать то, чего нет. Фактическая запись — `schedule.write` |
| `budget.read` | нет | деньги театра — не задача педагога |
| `budget.read.self` | нет | педагог не участник труппы; если человеку нужны свои взносы, ему добавляют роль `troupe`, а не расширяют `master` |
| `budget.write` | нет | расходы и доходы — не педагог |
| `budget.import` | нет | сверка листов — не педагог |
| `notify.send` | нет | рассылка — только администратор (`057`) |
| `participants.manage` | нет | роли, блокировка, архив — управление людьми |
| `participants.contact` | нет | телефон чужого человека — не для педагога |
| `registration.approve` | нет | заявки — администратор/организатор |
| `registration.code.issue` | нет | коды приглашений — администратор |
| `admin.panel` | нет | панель и файлы студии — администратор |
| `audit.view` | нет | аудит — администратор |
| `quota.manage` | нет | лимиты AI — администратор |
| `system.health` | нет | состояние сервисов — администратор/организатор |
| `feedback.triage` | нет | разбор обращений — администратор |
| `howto.read` | нет | справка пока только администратору (`038`) |

Итог: **7 возможностей**. Для сравнения: `troupe` — 6, `org` — 16, `admin` — все.

### 3.1. Что это даёт на практике

* `GET /tools/schedule/grid`, `/tools/schedule/slots` — читает всю труппу;
* `POST /tools/events/preview`, `/assign`, `/cancel`, `/move` — назначает и отменяет
  события (право `schedule.write`);
* `GET /tools/participants` — видит состав;
* `/tools/notes/*` — заметки;
* `/tools/files/*` — после §6;
* свои отметки занятости — `availability_hour` через `schedule.availability.self`.

### 3.2. Что закрыто и почему

Деньги (`budget.*`), рассылка (`notify.send`), управление людьми
(`participants.manage`, `registration.*`), админ-панель и файловое хозяйство
(`admin.panel`), аудит, лимиты AI, состояние сервисов. Педагог — пользователь
расписания и контента, а не администратор студии.

## 4. Входы: чат и Mini App

### 4.1. Чат

`/start` и «Кто я» берут роли из `v_participant_roles`; для мастера добавляется
подпись **«педагог»** и строка дисциплин:

```
Крылов Виктор
Роли: педагог, режиссёр
Дисциплины: Актёрское мастерство
Возможностей: 7
```

Меню (`keyboards.MENU_GROUPS`) для набора прав мастера:

| Группа | Пункты |
|---|---|
| Занятость | Занятость, Расписание, Поиск окон |
| Профиль | Мой профиль |
| Люди | Участники (по `participants.view`) |
| Помощь | Обратная связь, Что умею |

Группы «Деньги» и «Админ» не рисуются: у мастера нет `budget.write`,
`budget.read`, `registration.approve`, `registration.code.issue`, `admin.panel`.
«Участники» — единственный пункт, который появляется из-за `participants.view`;
это чтение состава, не управление.

Команды и сценарии:

* «найди окно …» → `SLOTS_Q`, право `schedule.slots`;
* «назначь …» → `ASSIGN_Q`, право `schedule.write`; дисциплина тренинга берётся
  из текста или из единственной дисциплины мастера;
* «что у меня завтра» → `SCHEDULE_Q`, право `schedule.availability.self` /
  `schedule.read.all`;
* «кто в труппе» → `LIST_PEOPLE`, право `participants.view`;
* «заметка: …» → `notes.write`.

### 4.2. Mini App

* Главная: `role_label = «педагог»`; блок «Моё» — «Занятость», «Профиль»,
  «Уведомления» (без «Мои взносы»); «Студия» — «Расписание», «Поиск окон»,
  «Обратная связь»; «Люди» — «Участники»; «Ещё/Личное» — «Заметки», «Файлы студии»
  (после §6).
* Вкладка «Время»: «Моя неделя» и «Сводка» (сводка — по `schedule.read.all`).
* Экран «Поиск окон»: форма получает `my_disciplines`; при создании тренинга
  дисциплина выбирается из дисциплин мастера. Если дисциплина одна — она
  подставляется, выбор не показывается. Если несколько — селектор.
* «Мой профиль»: дисциплины только для чтения; правит администратор.
* «Люди → карточка человека»: админ видит и меняет роли и дисциплины; мастер
  видит карточку в режиме чтения (без кнопок управления).
* «Файлы студии»: после §6 — чтение/скачивание; управление доступом остаётся
  у администратора.

### 4.3. Как выбирается дисциплина

| Где | Кто выбирает | Что происходит |
|---|---|---|
| Регистрация по коду | никто | код даёт `troupe`/`org`; `master` не выдаётся кодом |
| «Люди → карточка → Дисциплины» | администратор | отмечает одну или несколько дисциплин; каждая — строка `participant_discipline` с `relation='teacher'` |
| «Назначить тренинг» | мастер | выбирает одну из своих дисциплин; при одной — автоматически; событие получает `event_plan.discipline_id` |
| «Найти окна» для тренинга | мастер | та же дисциплина; правило состава (`_staff_by_rules`) подтягивает педагогов этой дисциплины |

Дисциплина не спрашивается у мастера при регистрации: у кода приглашения нет
дисциплины, а угадывать по имени нельзя. Это решение владельца: сначала человек
в студии, потом админ говорит, что он ведёт.

## 6. Долг, который нельзя замолчать

### 6.1. `calendar.write` — мёртвое право

В `db/init/008` объявлено `calendar.write` («Создавать и отменять события»), но
`grep` по `services/tool-api/app` не находит ни одной проверки этого права. Все
маршруты событий проверяют `schedule.write` (`events.py`: 274, 305, 351, 482,
590, 714). Матрица из карты называет `calendar.write`; фактическое право — `schedule.write`.

Решение: мастеру даём `schedule.write`; `calendar.write` не даём и в матрице
помечаем «нет». Если владелец хочет сохранить `calendar.write` как публичный код,
нужно либо перевести маршруты на него, либо удалить из `rbac_capability`. Это
отдельная карта, не часть роли мастера.

### 6.2. `files.access` — объявлено, но не работает — **закрыто 08.11.2026**

`files.access` есть у `troupe`, `org`, `admin` в `008`, у `master` — в `061`, но файловые
маршруты (`api/files.py`) были закрыты `admin.panel`, поэтому выдача `files.access`
мастеру ничего не давала: он не видел «Файлы студии».

Решение владельца V-039 (в) (`docs/reports/74-questions.md`): раздел видят admin, org и
master. Карта `t_cd0444eb` открыла экран и данные `/webapp/files` и `/webapp/folder`
правом `files.access` (запись `SECTIONS` + проверки в `api/files.py`), а у `troupe`
право снято миграцией `db/init/062_files_studio_access.sql`. Кого пускает конкретное
действие, по-прежнему решает домен: `folders` — admin и org, `tags` и `file_access` —
только admin. Чат бота остаётся под `admin.panel` (П-7).

### 6.3. `participant.is_teacher` и `specialty` — два источника

`_staff_by_rules` (`events.py:113-127`) до сих пор смотрит на `is_teacher` и
`specialty`, а не только на `participant_discipline`. Миграция выставляет
`is_teacher = true` мастерам, но новые данные должны идти через
`participant_discipline`; `specialty` остаётся подписью, не множеством.
Это не блокер, но при следующей правке состава тренинга надо оставить один
источник — `participant_discipline`.

## 8. Что не входит в этот дизайн

* Деньги: бюджет, расходы, доходы, сверка листов, взносы — не мастеру.
* Рассылка: `notify.send` — только администратор.
* Управление людьми: роли, блокировка, архив, инвайт-коды — не мастеру.
* Админ-панель и аудит — не мастеру.
* Замещение педагога (болезнь, отпуск) — отдельная модель, не эта карта.
* Новые дисциплины (речь, пластика, сценическое движение) — добавляются строками
  в `discipline`, модель не меняется.
* Возврат `student` — нет.

## 9. Короткий итог для карты

**Решение.** `master` — отдельная роль в `participant_role`; дисциплины — строки
`participant_discipline.relation='teacher'`, одна или несколько. Роль выдаёт
администратор, инвайт-кодом мастер не появляется. `student` не возвращается.

**Права.** 7: `schedule.read.all`, `schedule.availability.self`, `schedule.slots`,
`schedule.write`, `notes.write`, `files.access`, `participants.view`.
Не даём: `budget.read`, `budget.read.self`, `budget.write`, `budget.import`,
`notify.send`, `participants.manage`, `participants.contact`, `registration.*`,
`admin.panel`, `audit.view`, `quota.manage`, `system.health`, `calendar.write`.

**Файлы.** `db/init/061_master_role.sql` + Alembic-обёртка; `core.py`,
`api/admin.py`, `api/people.py`, `api/events.py`, `api/files.py`,
`api/webapp_api.py`, `webapp.py`; страницы `admin_core.py`, `admin_people.py`,
`admin_rights.py`, `admin_pending.py`, `misc_slots.py`, `person.py`, `home.py`;

`test_disciplines.py`; контракт `contracts/openapi.json`.

**Открытые вопросы.** V-037 (мастер без дисциплины — запрещать или предупреждать),
V-038 (свои взносы мастеру — нет или через роль `troupe`).
