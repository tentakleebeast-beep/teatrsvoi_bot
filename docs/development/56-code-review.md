## 3. Гипотезы улучшения

Отсортировано по «польза / риск».

### 3.1. Разделить `main.py` по доменам (высокая польза, средний риск)

Сейчас 2 632 строки и 55 маршрутов в одном файле: бюджет, занятость, календарь,
события, роли, веб-приложение. Любая правка требует прокрутки через чужие домены.

Предлагаю: `app/routers/{budget,availability,calendar,events,admin,webapp}.py`,
`main.py` — сборка приложения и общие зависимости. Механически: перенос функций
без изменения логики, тесты должны пройти без правок.

Оценка: 3–4 часа. Риск: средний (много импортов), но обнаружение — мгновенное
(421 тест).

### 3.2. Вынести HTML-страницы в пакет (средняя польза, низкий риск)

`webapp_page.py` — 813 строк с четырьмя константами. Читать и править неудобно,
конфликты при параллельной работе неизбежны.

Предлагаю `app/pages/{profile,grid,my,search}.py` + общий `layout.py` (стили, `api()`,
`auth()`). Дубли JS-хелперов (`api`, `pad`, `iso`, `auth`) сейчас скопированы в каждой
странице — при выносе в общий шаблон исчезнут.

Оценка: 2 часа.

### 3.3. Разбить `on_text` в gateway (высокая польза, средний риск)

175 строк и ~40 ветвлений — самое хрупкое место: порядок проверок определяет
поведение, и он не виден из структуры. Часть правил уже вынесена в `routing.py`.

Предлагаю превратить разбор в таблицу маршрутов: список `(условие, обработчик)`,
порядок задаётся списком. Тогда «деньги раньше расписания» станет явным правилом
в одном месте, а не следствием порядка `if`.

Оценка: 3 часа. Риск: средний, но есть 9 тестов на порядок правил
(`test_text_routing.py`), которые сразу покажут регресс.

### 3.4. Линтер и CI (высокая польза, низкий риск)

Линтера в проекте нет: ни `ruff`, ни `flake8`. Это объясняет, почему дубли прожили
так долго — их некому было заметить.

Предлагаю `ruff` с правилами `E,F,W,I,B,UP` + шаг в CI: линт и тесты на каждый push.
В venv нет `pip` (управляется `uv`), поэтому установка: `uv pip install ruff`
или `uvx ruff check .`.

Оценка: 1 час. Первый прогон даст десятки замечаний — вводить постепенно, начав с `F`
(неиспользуемые импорты и переменные).

### 3.5. Изоляция тестовой БД (средняя польза, низкий риск)

Параллельные прогоны падают с `duplicate key pg_database_datname_index`:
`conftest` создаёт одну базу `svoi_test` на всех. Предлагаю имя базы с суффиксом
PID или `pytest-xdist` с базой на воркер.

Оценка: 1–2 часа.

### 3.6. Покрытие: поднять с 28 % до 60 % (средняя польза, средний риск)

Непокрытыми остаются `scripts/*` (импорт, отчёты, сверка) — там ошибки дороже всего,
потому что они пишут в боевые таблицы. Приоритет: `reconcile.py`, `import_finance.py`,
`build_reports.py` — на фикстурах `.xlsx`.

Оценка: 4–6 часов.

### 3.7. Кэш справочников в gateway (низкая польза, низкий риск)

`_user_cache` уже есть, но `form-data` и `venues` дергаются на каждое открытие формы.
Для двух пользователей неважно; для 20 — заметно.

Оценка: 1 час. Делать, когда пользователей станет больше пяти.

## 4. Чего делать не надо

| Идея | Почему нет |
|---|---|
| Микросервисы | два сервиса и так разделены по ответственности; дробление даст сетевые отказы без пользы |
| ORM (SQLAlchemy) | SQL читается, запросы проверены, 55 маршрутов не тот масштаб, где ORM окупается |
| Кэш Redis | нагрузка — единицы запросов в минуту |
| Асинхронный доступ к БД | текущая синхронная модель проще; узкое место — Google API, не Postgres |
| Своя админка | Mini App + кнопки закрывают потребность |
| Переписывание на TypeScript | Python-стек работает, переписывание не даёт бизнес-эффекта |
