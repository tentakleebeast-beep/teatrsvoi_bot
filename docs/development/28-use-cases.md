# 28. Варианты использования (Use Cases) и покрытие тестами

Актуально на 26.10.2026. Формат: **UC-NN · название**, основной поток, альтернативы, ошибки,
критерии приёмки, тесты. Дополняет `docs/development/20` (короткие сценарии) и `docs/development/23` (UX).

Правило проекта: **у каждого UC есть хотя бы один тест** — либо на логику, либо на маршрутизацию.
UC без теста считается неготовым, даже если «вроде работает».

## UC-01 · Записать расход текстом

**Актор:** студиец с правом `budget.write`.
**Триггер:** «купили ткань на костюмы 12к налом».

| Шаг | Что происходит |
|---|---|
| 1 | gateway отправляет текст в каскад `intent/resolve` |
| 2 | правила извлекают сумму 12 000, тип «расход», категорию «Реквизит и костюмы» |
| 3 | бот показывает черновик: сумма · категория · дата |
| 4 | человек жмёт «Записать» |
| 5 | `budget/commit` пишет в БД и строку в Google Sheets |
| 6 | бот отвечает итогом месяца |

**Альтернативы**
- A1: категория не распознана → модель из закрытого списка (порог 0.7).
- A2: модель не уверена → кнопки топ-5 + «Другая категория».
- A3: суммы нет → «Похоже на операцию, но не увидел сумму» + форма.

**Ошибки**
- E1: повторное нажатие «Записать» → `deduped: true`, второй операции нет.
- E2: LLM недоступен → черновик собирается правилами, без сообщения «сервис недоступен».
- E3: Google Sheets недоступен → операция записана в БД, в ответе честно: «в таблицу не попало».

**Приёмка:** одна операция на одно подтверждение; сумма и категория совпадают с фразой;
итог месяца в ответе совпадает с `budget/summary`.

**Тесты:** `unit/test_rules_budget.py` (12), `unit/test_cascade.py` (8),
`integration/test_budget_idempotent.py` (5), `integration/test_intent_log.py` (4).

## UC-02 · Отметить занятость

**Триггер:** кнопка «Занятость» или «занят в среду после 18».

**Основной поток:** день → интервал → запись в `availability_hour` (`kind='declared'`) →
«Записал: среда 28.10, 18:00–23:00 занят».

**Альтернативы**
- A1: «весь день» → 08:00–23:00 одним действием.
- A2: дата названа словами («в среду») → берётся ближайшая среда от текущей даты проекта.
- A3: перезапись существующей отметки → перекрывает, пишет в аудит.

**Ошибки**
- E1: нет даты → «Понял, что про расписание, но не увидел даты» + пример + кнопка.
- E2: нет прав `schedule.availability.self` → отказ с объяснением, не молчание.

**Приёмка:** 16 часовых записей на день; повторная запись не создаёт дублей (upsert).

**Тесты:** `unit/test_rules_availability.py` (8), `unit/test_schedule_grid.py` (13).

## UC-03 · Узнать баланс и итоги

**Триггер:** «сколько у нас денег?», «какой баланс», «сколько потратили на Бунина».

**Основной поток:** gateway ловит запрос регуляркой → `budget/summary` → ответ числами.
Проект определяется по слову в фразе (Бунин, Пурга, ЛитРейв, Жизнь насекомых).

**Ошибки**
- E1: нет права `budget.read` → «Итоги доступны организатору и администратору».
- E2: периода нет в базе → показываем только существующие, без нулей-заглушек.

**Приёмка:** сумма по периодам = `balance`; ответ не содержит текста от модели.

**Тесты:** `integration/test_uc_budget_schedule.py` (5): баланс = доходы − расходы,
фильтр по проекту, отказ труппе; расписание без календаря, пустой календарь, занятость недели.

## UC-04 · Посмотреть расписание недели

**Триггер:** «что на неделе», «расписание», «что в четверг».

**Основной поток:** `calendar/events?days=7` + `availability/summary?days=7` → список событий
и свободных по дням.

**Ошибки**
- E1: календарь недоступен → показываем занятость, честно помечаем «календарь не прочитан».
- E2: событий нет → «в календаре событий нет», не пустое сообщение.

**Приёмка:** даты и время из календаря совпадают с Google; формат `пн 26.10 12:00–16:00`.

**Тесты:** `integration/test_uc_budget_schedule.py` — недоступный календарь, пустой календарь,
отсутствие id календаря, сводка занятости.

## UC-05 · Открыть админ-панель

**Триггер:** кнопка «Админ-панель», `/admin`, `/menu`.

**Основной поток:** проверка `participants.manage` → инлайн-меню: Участники, Заявки, Права,
Бюджет, Аудит, Сервисы.

**Ошибки**
- E1: нет прав → «Панель доступна администратору» (без «к сожалению, у меня нет доступа»).
- E2: кнопка приходит как обычный текст → **обрабатывается отдельным хендлером до свободного текста**.

**Приёмка:** нажатие кнопки не уходит в модель; приходит меню панели.

**Тесты:** `unit/test_gateway_routing.py` (5) — порядок обработчиков, отсутствие дублей,
совпадение набора кнопок клавиатуры и обработчика.

## UC-06 · Посмотреть участников и заявки

**Триггер:** `/participants`, `/pending`, кнопки панели.

**Основной поток:** `/tools/participants` (без архивных) → список с ролями и признаком Telegram;
`/admin/pending` → заявки с кнопками Подтвердить/Отклонить.

**Ошибки**
- E1: нет права `participants.view` / `registration.approve` → отказ с указанием, кто видит.
- E2: заявок нет → «Заявок нет».

**Приёмка:** архивные не показываются; подтверждение меняет статус и пишет аудит.

**Тесты:** `integration/test_uc_admin_flows.py` (4): архивные скрыты, пустые заявки,
подтверждение меняет статус и пишет аудит, заявки с кнопками.

## UC-07 · Выдать код приглашения

**Триггер:** `/invite org`.

**Основной поток:** `admin/invite` создаёт код на 7 дней → бот печатает код и срок.

**Ошибки**
- E1: неизвестная роль → подсказка формата.
- E2: нет права `registration.code.issue` → отказ.
- E3: код использован/просрочен → при регистрации `code_exhausted` / `code_not_found`.

**Приёмка:** код одноразовый; после использования повторная регистрация невозможна.

**Тесты:** `integration/test_uc_admin_flows.py` (4): код с ролью и сроком, админ по коду запрещён,
неизвестная роль отклоняется, просроченный и использованный код не работают.

## UC-08 · Зарегистрироваться по коду

**Триггер:** `/start` → код → выбор себя из списка → готово.

**Альтернативы**
- A1: человека нет в списке → заявка `pending` + уведомление админу.
- A2: chat_id уже привязан к другому человеку → не перезаписываем, зовём админа.

**Ошибки**
- E1: код просрочен → «Код не действует, попросите новый».
- E2: человек уже зарегистрирован → показываем профиль, не начинаем заново.

**Приёмка:** одна запись на chat_id; роли выдаются через `participant_role`.

## UC-09 · Утвердить новую категорию

**Триггер:** модель предложила категорию вне справочника.

**Основной поток:** категория попадает в `category_candidate` → `intent_report.py --candidates`
→ владелец утверждает → появляется в справочнике и в промпте.

**Ошибки**
- E1: категория уже есть под другим названием → отклоняем, добавляем синоним в правила.
- E2: молчаливое создание категории — **запрещено**: `category_final` только из справочника.

**Приёмка:** число категорий не растёт без решения человека.

**Тесты:** `unit/test_cascade.py` (`test_категория_вне_списка_не_принимается`),
`integration/test_intent_log.py` (`test_новая_категория_становится_кандидатом`).

## UC-10 · Сверить файл и базу

**Триггер:** ежедневный cron или ручной запуск `reconcile.py`.

**Основной поток:** читаем «Транзакции» → сравниваем по `id` → добавляем отсутствующие,
помечаем удалённые `rejected`, принимаем значения файла при расхождении → пишем отчёт на лист «Сверка».

**Ошибки**
- E1: дубль `id` в файле → предупреждение, дубль не применяется.
- E2: итоги не сходятся → статус «РАСХОЖДЕНИЕ» на листе, ничего не подкручиваем.

**Приёмка:** после сверки `файл = БД` построчно и по итогам периодов.

**Тесты:** `unit/test_reconcile_helpers.py` (11).

## UC-11 · Заполнить занятость цветом (новый формат)

**Триггер:** человек красит клетки в своей странице месяца.

**Основной поток:** бот читает страницу `MM.YYYY · Ник` → цвет → статус (красный/зелёный/жёлтый)
→ слоты → `availability_hour`.

**Ошибки**
- E1: неизвестный цвет (фиолетовый) → в расчёт не идёт, человеку список клеток на перекраску.
- E2: объединённые ячейки → не ломают чтение.
- E3: пустая клетка → «нет данных», не «свободен».
- E4: `.xlsx` вместо Google Sheets → читаем через openpyxl (Sheets API формат Office не отдаёт).

**Приёмка:** число слотов из файла = число записей в БД; повторное чтение идемпотентно.

**Тесты:** `unit/test_schedule_grid.py` (13).

## UC-12 · Спросить что угодно (ассистент)

**Триггер:** свободный текст, не подходящий под данные.

**Основной поток:** router классифицирует → ASSISTANT → ответ модели с контекстом (имя, роли).
Данных из БД у модели нет, и она это знает.

**Ошибки**
- E1: модель недоступна → детерминированный ответ по сценарию, без «LLM недоступен»,
  если сценарий распознан.
- E2: вопрос требует данных → подсказка команды (`/participants`, кнопки Бюджет и Расписание).
- E3: модель вернула JSON → gateway распаковывает (`clean_answer`).

**Приёмка:** «кто я» отвечает именем и ролями; «что ты умеешь» — текстом без JSON.

## UC-13. Назначение события от окна до уведомления

**Актор:** организатор (`org`, `admin`).
**Триггер:** после поиска окон есть подходящий вариант.
**Цель:** событие в календаре и расписании, участники уведомлены.

### Основной поток

1. Организатор ищет окна: `«окна для Наташи и Сэма в Жизни насекомых»`.
2. Бот отвечает вариантами с составом и пометками «позже подойдут».
3. Под вариантом — кнопка «Назначить».
4. Бот показывает карточку: тип, название, дата, время, участники, помещение.
5. Организатор подтверждает.
6. Бот создаёт запись расписания и событие в календаре одним путём (`POST /tools/events/assign`).
7. Бот ставит уведомления участникам в очередь (`notification`).
8. Отправитель рассылает их с учётом тихих часов и лимита 3/час.

### Альтернативы

| Ситуация | Поведение |
|---|---|
| Окно уже заняли (событие появилось позже) | повторная проверка перед записью, отказ с объяснением |
| Организатор меняет время в карточке | окно пересчитывается, показывается предупреждение о пересечении |
| Участник занят по событию календаря | предупреждение, но запись разрешена (решает человек) |
| Календарь недоступен | событие в расписании создаётся, в календарь — нет, с пометкой |

### Ошибки

| Код | Текст для человека |
|---|---|
| `slot_taken` | «Это время уже занято — покажу свободные рядом» |
| `no_calendar` | «Календарь недоступен, событие записано только в расписание» |
| `notify_failed` | «Событие создано, но уведомления не ушли — проверьте очередь» |

### Критерии приёмки

- событие видно в календаре с `svoi_kind`, `svoi_venue`, `svoi_participant_ids`;
- запись в `event_plan` связана с событием календаря;
- каждому участнику поставлено уведомление, повторное нажатие не дублирует;
- все шаги в аудите.
