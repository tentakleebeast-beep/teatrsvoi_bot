## 0. Что и зачем

Замер в карте: из 15 выпущенных кодов введены 7; знакомство заполнено у 2 из 12
и ни у кого полностью; 3 записи висели в `pending` и не могли войти (на 21.11.2026
подтверждены владельцем, §4.2). То есть люди доходят до бота и отваливаются на девяти
вопросах и на ожидании подтверждения. Меняем три вещи: вход укорачивается до
«код → знакомство из 2–3 вопросов → меню», заявок нет, оба текста (короткая инструкция
и памятка `/help`) говорят правду о шагах.

## 1. Последовательность: что говорит бот на каждом шаге

### 1.1. Веток входа две, «новичка» в боте больше нет

Карта называла три ветки («педагог», «человек уже в базе», «новичок»). После решения
V-116 веток две, потому что запись человека существует **до** кода: код выписан на
конкретного человека (`invite_code.participant_id`), и «выбирать себя из списка»
и «называть себя» больше не нужно никому. «Новичок» как ветка бота исчезает: запись
заводит администратор на экране «Приглашения» (§4.3.2), бот записей не создаёт.

| Ветка | Условие | Что происходит |
|---|---|---|
| человек уже в базе | запись есть, `tg_chat_id is null` | привязка и знакомство сразу (шаги 4–8) |
| педагог без дисциплины | `participant.role = 'master'` и в `participant_discipline` нет строк | реплика о дисциплине, две кнопки, потом привязка |
| повторный `/start` | `tg_chat_id` уже привязан | меню, знакомство не начинается |
| старый код | `invite_code.participant_id is null` | отказ «Этот код больше не действует…» (§1.3) |
| запись уже привязана | у `participant_id` есть `tg_chat_id` | «Этот код уже использован.» |
| запись закрыта | `participant.status in ('blocked', 'archived')` | «Доступ к боту закрыт. Напишите администратору студии.» |

## 2. `intro.py`: три обязательных шага и шесть за кнопкой «Знакомство»

### 2.1. Два плана вместо одного

Сейчас `STEPS` — девять полей (`intro.py:20-21`), `build_plan` (`:137-156`) собирает
из них список «что спросить», и знакомство стартует **после** меню.

```python
#: Знакомство при входе: без этого человек не получает короткого имени.
ENTRY_FIELDS = ("name", "alias", "phone")
#: Дозаполнение по кнопке: всё необязательное.
FILL_FIELDS = ("birthday", "travel", "plays", "roles", "trainings", "manifest")


def build_entry_plan(profile: dict | None) -> list[str]:
    """Имя — если в записи одно слово; короткое имя — всегда; телефон — если пуст."""
    profile = profile or {}
    plan = []
    if len(" ".join(str(profile.get("name") or "").split()).split()) < 2:
        plan.append("name")
    plan.append("alias")
    if not profile.get("phone"):
        plan.append("phone")
    return plan


def build_fill_plan(profile: dict | None) -> list[str]:
    """Только пустые необязательные поля; заполненное не переспрашиваем."""
    profile = profile or {}
    empty = {
        "birthday": not profile.get("birth_date"),
        "travel": profile.get("travel_minutes") in (None, 0),
        "plays": not str(profile.get("plays") or "").strip(),
        "roles": not str(profile.get("roles_note") or "").strip(),
        "trainings": not str(profile.get("interests") or "").strip(),
        "manifest": not str(profile.get("ai_manifest") or "").strip(),
    }
    return [step for step in FILL_FIELDS if empty[step]]
```

Ключи профиля — ответ `GET /tools/profile/me` (`people.py:212-243`): `name`, `phone`
(пустая строка — нет телефона), `birth_date`, `travel_minutes`, `plays`, `roles_note`,
`interests`, `ai_manifest`. `STEPS` и `build_plan` удаляются; `next_step`, `question`,
`parse_step`, `build_patch`, `summary`, `RETRY`, `LABELS`, `FIELD`, `SKIP_WORDS` не меняются.

### 2.2. Короткое имя обязательно только при входе

`alias` в плане входа обязателен (181 §3.2, строка 6): на шаге `Intro.alias` кнопки

Выход из диалога остаётся всегда: любая кнопка меню (`keyboards.MENU_SURFACE`)
снимает состояние (`routers/intro.py:58-62`).

## 3. Два текста, дословно

Оба — константы, реализация их не сочиняет. Ниже — эталон; тест сверяет с ним посимвольно
(§6.2). В текстах нет `{`/`}`, эмодзи и разметки: сборка склеивает части `+`, а не `.format`.

Подписи в текстах — по решению владельца 21.11.2026: кнопка дозаполнения называется
«Знакомство». В 181 §5 в этом месте ещё стоит «Дозаполнить профиль»; реализация берёт

### 4.2. Данные: миграции нет, заявок на проде уже нет

Что остаётся в чек-листе релиза:

1. перед тегом — та же проверка `select count(*) … = 0`; на 21.11.2026 она проходит,
   но между спекой и выкатом может появиться новая запись (бот заявок больше не создаёт,

   привязка переводит её в `active` (`attach` ставит `status='active'`) — это и есть

### 4.3.4. `create_invite`/`list_invites` под персональный код

`api/admin.py`:

```python
class InviteIn(core.ApiIn):
    participant_id: int
    ttl_days: int = core.INVITE_TTL_DAYS
    correlation_id: str | None = None
```

- `max_uses` принудительно 1 (персональный код одноразовый) — поле из тела убирается;
- запись должна существовать, иметь `tg_chat_id is null`, статус не `archived`/`blocked`;
  `role == 'admin'` по записи → `400` `admin не выдаётся кодом: только через ADMIN_CHAT_ID`;
- `insert into invite_code (code, role, participant_id, created_by, expires_at, max_uses)`
  — `role` берётся из записи, `discipline_code` не пишется;
- ответ: `code`, `expires_at`, `participant_id`, `display_name`, `role`;
- аудит `invite.create`: `after={"participant_id": …, "role": …, "expires_at": …}`;
- `list_invites` (`:66-96`) джойнит `participant` и отдаёт `participant_id`,
  `display_name` в каждой строке (экран показывает, на кого выписан код);
- перевыпуск для того же человека разрешён: старый код перестанет действовать сам
  (вход один, `check_code` видит занятый `tg_chat_id` только после привязки; до неё
  два кода на одного человека допустимы и безвредны).

Старые коды (`participant_id is null`): приниматься перестают (`code_not_personal`,
§1.3). Миграция не может выдумать владельца, поэтому в чек-лист релиза входит строка:
`update invite_code set expires_at = now() where participant_id is null and uses < max_uses`
— на замере в карте таких не больше восьми, админ перевыпустит.

### 4.4. Что осталось и названо

- **Утёкший персональный код** по-прежнему даёт вход — но теперь в запись того человека,
  на кого код выписан, а не в пустую запись с вымышленным именем. Чужой видит расписание
  и взносы этого человека. Видно и отзывается: `invite_code.used_by`,
  `participant.invite_code_id` в «Люди» (`admin.py:416-418`), архив/блокировка
  (`core.py:476-481`). Тексты (§3) поэтому не обещают «чужой код не подойдёт», а просят
  не передавать свой.
- **Дисциплина педагога**: если у записи её нет, спрашиваем на входе (шаг 3); если есть —
  не спрашиваем. Админ может поставить её и при создании человека (`person-new`,
  §4.3.2), и позже в карточке. Новых дисциплин не заводим (`keyboards.py:283-295` —
  две кнопки).
- **Два кода на одного человека**: второй выпуск не отменяет первый до привязки. Это
  осознанно: администратор перевыпускает код, когда первый потерян, и ждать, пока
  человек введёт старый, нельзя. После привязки второй код вернёт `code_exhausted`.
