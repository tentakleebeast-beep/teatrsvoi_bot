## 1. Границы ревью

| Входит | Не входит |
|---|---|
| Вид, читаемость, состояния, тексты экранов в четырёх ролях | Контракты API, коды ошибок, права на данные как таковые |
| Согласованность экранов между собой (каркас, компоненты, термины) | Пользовательские сценарии и их полнота (`docs/development/20`) |
| Тёмная и светлая схема, ширины 390/320/430 px | Прод, боевые данные, боевой бот |
| Критерии из `docs/development/91` §1 с пометкой «ревью» | Производительность, безопасность, качество кода |

Почему так: геометрию (шрифт, цели, переполнение, эмодзи, JS-ошибки) уже держат
`tests/webapp/test_miniapp_system.py` на всех 31 экранах. Дизайн-ревью добавляет то, чего
тесты не проверяют: **состояния, тексты и согласованность**. Дублировать тесты в ревью
незачем — совпадение «тест зелёный / ревью чистое» и есть признак, что система работает.

## 3. Роли: четыре, и все четыре видит один и тот же HTML

Роли и права проверены по базе (`rbac_role_capability`, dev-база 08.11.2026): admin — 24
возможности, org — 16, master — 7, troupe — 5 (миграция 062 сняла `files.access`; до неё
на dev-базе было 6). Документ о ролях — `docs/architecture/02`,
о мастере — `docs/architecture/140`.

**Ключевой факт, который определяет методику.** Страницы Mini App — статические константы:
`layout.page` умеет принимать `caps` (`pages/layout.py:126`), но **ни один из 31 экрана его
не передаёт** — подпись четвёртой вкладки правит JS после ответа `/webapp/nav`. Роль меняет
только **данные**: `/webapp/home/data`, сегменты «Денег», список «Управления» из `SECTIONS`,
признаки `/webapp/nav`. Поэтому «ревью в роли» — это ревью **пары «экран + ответ данных под
этой ролью»**, и стенд без API ролей не показывает (см. §5).

| Что меняется по ролям | admin | org | master | troupe |
|---|---|---|---|---|
| Разделы «Управления» (видно / всего 15) | 15 | 5 | 2 | 1 |
| Четвёртая вкладка | Управление | Управление | Управление (Люди, Заметки) | Ещё |
| «Деньги»: сегменты | Операции, Бюджет, Мои взносы | Операции, Бюджет, Мои взносы | нет сегментов | Мои взносы |
| Строка «Сводка занятости» на «Время» | есть | есть | есть | нет |
| «Поиск окон» | есть | есть | есть | нет |
| Заметки | есть | есть | есть | есть |
| Файлы студии (после t_cd0444eb) | есть | есть | есть | нет |

Таблица — снимок dev-базы 08.11.2026 до карты t_cd0444eb; строка «Файлы студии» приведена
к V-039 (в): раздел открыт правом `files.access` у admin, org и master, у troupe право снято
миграцией 062. Поэтому у org и master в первой строке на один видимый раздел больше, чем
в снимке (5 → 6 и 2 → 3).

Отсюда обязательное правило ревью: **каждый экран проверяется в той роли, у которой на него
есть право, и ещё в одной роли, у которой права нет** — состояние «нет права» это часть
дизайна (`docs/development/91` §1, принципы 8–9), а не техническая случайность.

**Первое следствие, известное по коду до ревью.** У master нет ни `budget.read`, ни
`budget.read.self`. «Деньги» у него попадают в ветку `!canRead` (`pages/money_script.py:306`):
сегменты скрыты, показывается блок «Мои взносы», а он тянет `GET /webapp/my/dues`, закрытый
правом `budget.read.self` (`api/finance.py:25`) — 403. Код на 403 рисует
«Не удалось загрузить взносы. Потяните экран вниз, чтобы повторить.» (`money_script.py:332`),
то есть **ложную ошибку вместо «нет права»** — нарушение Б3. Это гипотеза до первого прохода
в роли master; карточка заводится после снимка. Сам вопрос «должен ли мастер видеть свои
взносы» решён — V-038: мастер их не видит; экран обязан говорить «нет права» словами.

### 3.1. Чего в данных сейчас нет

## 4. Критерии

Два слоя, и они не дублируют друг друга.

### 4.1. Слой А — автоматический (Playwright, все 31 экран)

Гоняется на стенде с копией данных, `chromium` (основная, как в карте) и `webkit` (вторая
серия; родитель Э1 уже гонял оба движка). На каждом экране, каждой ширине (390 и 320;
430 — на четырёх вкладках) и каждой схеме (светлая, тёмная):

| № | Критерий | Порог | Как |
|---|---|---|---|
| А1 | Нет переполнения по горизонтали | `scrollWidth − clientWidth ≤ 1 px` | измерить `documentElement` |
| А2 | Нет контейнеров со своей горизонтальной прокруткой | 0 контейнеров `overflow-x: auto/scroll` с `scrollWidth > clientWidth` | обход всех элементов |
| А3 | Нет текста мельче 13 px | минимум по видимым листовым узлам ≥ 13 | `getComputedStyle` |
| А4 | Все цели ≥ 44×44 px | 0 целей меньше | `a, button, input, select, textarea` |
| А5 | Нет эмодзи в видимом тексте | 0 | регулярка по `innerText` |
| А6 | Нет ошибок JS | 0 `pageerror` | слушатель на странице |
| А7 | Контраст текста к фону | ≥ 4.5 (обычный текст), ≥ 3.0 (≥ 18.7 px или 600+) | вычисленные цвета, обе схемы |
| А8 | Нет модальных `alert/confirm/prompt` | 0 вызовов за прогон | перехват `window.alert` и др. |
| А9 | Главных кнопок на экране | больше одной `.ui-btn--primary` — замечание к разбору, не автоматический провал: у старых экранов их может быть две по делу | подсчёт по DOM |
| А10 | Редиректы живые | 301 и цель открывается | 7 адресов из §2.4 |

А1–А6 уже реализованы в `tests/webapp/test_miniapp_system.py` для fixture-стенда; в ревью они
переезжают на стенд с копией данных (другие данные — другие переносы строк, длинные имена,
реальные суммы) и дополняются А7–А10. Контраст сейчас проверяется только на 5 экранах
(`tests/webapp/test_miniapp_visual.py`) — в ревью он на всех 31 и в двух схемах.

### 4.2. Слой Б — ревью человеком: 12 принципов `docs/development/91` §1

Автоматика закрывает принципы 2, 3, 4 и частично 11. Остальные проверяются глазами по
скриншотам и по живым экранам, экран за экраном:

| № | Принцип | Что смотреть на каждом экране |
|---|---|---|
| 1 | Один экран — одна задача | вторая равноправная кнопка — замечание |
| 5 | Состояние словом | «Занят», «Оплачено», «Осталось 3 000 ₽»; цвет не единственный носитель |
| 6 | Действие глаголом | «Записать», «Вернуть»; не «ОК», не «Далее» |
| 7 | Опасное — с названием объекта | лист подтверждения называет объект и число («Отправить 14 людям?») |
| 8 | Ошибка говорит, что делать | причина + действие; без кодов и без «попробуйте позже» |
| 9 | Пусто — не тупик | в пустом состоянии сказано, как его заполнить |
| 9a | Выбранное видно без подписи | заливка/рамка/жирность, без слова «выбрано» |
| 10 | Подсказок минимум | нет служебных фраз («проверяется на сервере»), подсказка — одна строка |
| 11 | Никаких `alert/confirm/prompt` | лист `.ui-sheet`, сообщение `.ui-alert`, результат `.ui-toast` |
| 12 | Сохранение видно | либо сразу + сказано в шапке, либо кнопка; третьего нет |

Плюс три критерия, которых в 91 нет, но они нужны именно при ревью всех экранов:

| № | Критерий | Порог |
|---|---|---|
| Б1 | Один каркас | у всех 31 экрана та же шапка/вкладки/отступы из `layout.page`; свои `<style>` и свои шапки — замечание |
| Б2 | Один словарь | один и тот же объект называется одинаково на всех экранах («Время» / «Занятость» — как в 92 §; «фиксирует», а не «оплачивает») |
| Б3 | Роль видна на экране | человек без права видит словами, чего он не видит и к кому идти, а не пустоту, не «403» и не вечную загрузку |

### 4.3. Приговор экрану

| Приговор | Что это | Куда идёт |
|---|---|---|
| **Дефект** | нарушено правило 91/92 или экран не отвечает на свой вопрос; человек не может сделать то, зачем пришёл | карточка `worker-feature` с классом «дефект», ссылка на снимок и правило |
| **Замечание** | системе не соответствует, но задачу не ломает (отступ, формулировка, лишняя строка) | карточка `worker-feature` с классом «замечание», пачкой по экрану |
| **Идея** | правила не нарушает; «было бы лучше» | список в отчёте, без карточки; приоритет решает владелец |

Правило против шума: **на один экран — не больше трёх строк в отчёте**. Экран без замечаний
пишется одной строкой «чисто», а не пропускается: пропуск читается как «не смотрел».

## 5. Стенд и данные: локальная копия, а не прод

### 5.1. Почему не fixture-стенд `tests/webapp/server.py`

Стенд отдаёт 31 статическую страницу и **один** набор данных: роль переключается только
признаком `participant`/`staff` (`tests/webapp/server.py:124`), `/webapp/home/data` всегда
рисует админа. Четырёх ролей там нет и не будет — стенд проверяет вёрстку, а не права.
Поэтому для ревью нужен настоящий `tool-api`, поднятый локально на копии данных.

### 5.2. Как поднимается

| Шаг | Что делаем | Почему так |
|---|---|---|
| База | отдельная база `svoi_ui` на локальном Postgres (127.0.0.1:5433), восстановленная из дампа | рабочую dev-базу не трогаем: правило 05.11.2026 «dev — стенд» (`docs/infrastructure/08` §1a, V-036) остаётся в силе; ревью — не повод заливать факты в dev |
| Окружение | `.env.ui-review` (в git не попадает) на основе `.env.dev`: `DATABASE_URL` → `svoi_ui`, `DEV_BOT_TOKEN` из dev-бота | `scripts/run_service.py` уже умеет брать другой файл среды (`SVOI_DEV_ENV_FILE`), прод-токен в dev не читается ни при каком флаге |
| Запуск | `SVOI_DEV_ENV_FILE=.env.ui-review .venv/bin/python scripts/run_service.py tool-api --port 8010` | свой порт: рабочий dev-инстанс на 8000 продолжает жить, их не перепутать |
| Вход | токен на человека: `POST /webapp/auth` с `init_data`, подписанным dev-токеном бота, для `tg_chat_id` из копии; открывать `…?dev_token=<токен>` | это тот же путь, что в бою (`webapp.py:110` `issue_token`, `webapp-shell.js:56` `dev_token`); обходного «режима без входа» не заводим |
| Проверка | `GET /health`, `/webapp/nav` и `/webapp/home/data` под каждой из четырёх ролей | если навигация и данные не те, дальше смотреть нечего |

Писать в копию можно (отметка занятости, тестовая операция), но копия после ревью обязана
быть выброшена и восстановлена заново: иначе следующий проход смотрит уже не тот экран.

### 5.3. Чего на копии делать нельзя

| Нельзя | Почему |

### 6.1. Что ревью обязано назвать до начала

- **Сколько экранов:** 31 (§2), а не «все, что найдём».
- **Кто смотрит:** один человек, иначе 31 экран × 4 роли смотрят по-разному.

- **Что не смотрели:** список экранов, выпавших из ревью (например, роль master без
  держателя), отдельным разделом отчёта.
