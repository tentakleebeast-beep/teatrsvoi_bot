ID файлов — в `.env`: `SCHEDULE_XLSX_ID`, `CONTACTS_SPREADSHEET_ID`.

### Правило единственного итога
- Человек может править `Бюджет (вид)` руками — это нормально.
- Бот **перечитывает** лист и сводит к себе (`reconcile`), помечая расхождения.
- Любая цифра в ответе бота берётся из БД, а не из «последнего сообщения» или памяти диалога.
- Если человек поправил вручную, а бот не увидел — при следующем чтении расхождение попадёт в `Проверки`.

## 2. Что выглядит «как раньше»

`Бюджет (вид)` повторяет привычную структуру файла:

```
ИЮЛЬ 2026                                  ← заголовок месяца, тёмная заливка
Дата | Кто / статья | Категория | Сумма | Проект | Источник
Взносы студийцев                           ← зелёная группа
   Иванов Виктор | оплачено | 10 000 ₽
   Итого взносов    |           70 000 ₽
Расходы студии                             ← красная группа
   05.07.2026 | аренда Прачки | Аренда помещения | 100 000 ₽ | файл
   Итого: расходы студии | 189 337 ₽
Показы — доход / Показы — затраты / Субаренда
```

Форматирование: заливка групп, жирные итоги, денежный формат `# ##0 ₽`, закреплённая шапка, ширины колонок.

Сборка: `python scripts/build_reports.py` — пересобирает `Бюджет (вид)`, `Журнал бота`, `Проверки`.

## 3. Маршрутизация запросов бота

```
сообщение
   │
   ├─ 1. кнопка меню            → форма (без LLM)
   ├─ 2. известный сценарий     → правила / n8n (без LLM, если уверены)
   │      • бюджет: «расход 3000 на реквизит»
   │      • занятость: «занят в среду после 18»
   │      • взносы: «сколько я должен»
   │
   └─ 3. всё остальное          → LLM-ассистент
          • «что ты умеешь?»
          • «почему в сентябре минус?»
          • «добавь в бота учёт реквизита по спектаклям»
```

Порядок именно такой: сначала дешёвое и детерминированное, потом модель. LLM **не обходится**, пока он доступен и есть квота — как и просил заказчик. Обход только при:
- `llm_unavailable` — провайдер недоступен;
- `quota_exceeded` — исчерпан лимит человека;
- `llm_error` — модель вернула ошибку.

Тогда бот предлагает формы и не теряет запрос: текст сохраняется в `message_event` для разбора.

### Что уходит в модель
- манифест: `SOUL.md` + `STYLE.md` + роль + личные настройки (`docs/development/12`);
- сам текст запроса;
- **не уходят** данные бюджета и чужие персональные данные.

Если ответ требует цифр, модель должна запросить инструмент; без инструмента она обязана ответить «нет проверенных данных».

## 4. Сценарии n8n (целевое)

| ID | Триггер | Что делает |
|---|---|---|
| WF-01 `intent` | webhook из gateway | определяет сценарий: budget / schedule / dues / assistant |
| WF-02 `budget-capture` | intent=budget | правила + LLM только для неоднозначного, возвращает черновик |
| WF-03 `availability` | intent=schedule | разбор даты/времени, черновик, запись |
| WF-04 `assistant` | intent=assistant | вызов модели с манифестом, ответ по формату STYLE |
| WF-05 `digest` | cron | недельная сводка org |

**Сделано:** `WF-01 · router (intent + assistant)` — вебхук `POST /webhook/router`, id `WFR03router00001`.
Внутри: Code (подготовка промпта) → HTTP Request к OpenRouter с credential `openRouterApi`
(ключ живёт в n8n, в `.env` его нет) → Code (разбор JSON) → Respond.

Ответ роутера: `{"intent":"budget|schedule|dues|assistant","answer":"...","engine":"n8n-openrouter"}`.
Gateway: `budget`/`schedule` — дальше детерминированный разбор; `dues` — свои взносы;
`assistant` — готовый ответ модели.

Важно при переимпорте (n8n 2.44.6): после `import:workflow` нужно выставить
`workflow_entity.active=1`, `activeVersionId=versionId`, запись в `workflow_published_version`
и строку в `webhook_entity` — иначе вебхук не регистрируется (ошибка 404 `not registered`).

WF-02 (разбор бюджета) остаётся как второй эшелон; WF-03 — занятость, WF-04 — сводки.

## 5. Ограничения, о которых надо помнить

1. **LLM-ключ и адрес.** Ветка ассистента и знакомство читают `LLM_API_KEY` и `LLM_BASE_URL` из `.env` (`app/llm.py`); старые имена `OPENROUTER_API_KEY`/`ASSISTANT_MODEL` работают как алиасы. Ключ из n8n-credential недоступен другим сервисам — он зашифрован, поэтому для `tool-api` нужен свой.
2. **Квоты.** Считаются в `llm_usage`, лимиты в `llm_policy`. При исчерпании — формы.
3. **Ручные правки.** Если человек правит `Бюджет (вид)`, а бот — `Транзакции`, расхождение будет видно в `Проверки`. Единый источник — БД; лист для человека помечается как представление.
4. **Заметки.** Живут в БД (сервис-аккаунт не может создавать файлы на Drive, см. `docs/infrastructure/09`).
5. **Файлы (текст, картинки, аудио).** Не Drive: MinIO + Postgres, требования и план шагов — `docs/development/86`.
