# 13. Регистрация: admin, организатор, студиец, педагог

Общее: доступ по `chat_id`, роль — свойство записи в БД, а не заявление человека.
Один `chat_id` — одна запись: повторная регистрация невозможна.

Ролей проекта четыре: `admin`, `org` (организатор), `troupe` (актёр труппы),
`master` (педагог). Роль `student` снята миграциями `017_drop_student_role.sql`
и `030_cleanup_roles_aliases.sql` (решение заказчика 26.10.2026) и не возвращается.

| Роль | Как появляется |
|---|---|
| `admin` | первый `/start` из чата, указанного в `ADMIN_CHAT_ID` (`POST /admin/bootstrap`) |
| `org`, `troupe` | инвайт-код, выпущенный из админ-панели |
| `master` | в карточке человека: админ отмечает дисциплины и выдаёт роль (`POST /admin/grant` с `disciplines`); кодом не выдаётся |

Педагог не появляется по инвайт-коду: у кода нет дисциплины, а мастер без дисциплины
сервер отклоняет (`master_discipline_required`). Сначала человек регистрируется как
`troupe` или `org`, затем админ добавляет `master` и предмет — `docs/architecture/140`, §1 и §2.1.

---

## 0. Точки входа

```
/start
 ├─ chat_id == ADMIN_CHAT_ID, записи нет  → POST /admin/bootstrap → роль admin
 ├─ запись есть, status='active'          → меню роли (/tools/participants/me)
 ├─ запись есть, status='pending'         → /tools/participants/me: 403 participant_inactive,
 │                                          бот снова просит код (доступ появится после подтверждения)
 └─ записи нет                            → ввод кода приглашения
```

Текст, который бот пишет неизвестному чату (`services/tg-gateway/app/routers/menu.py:141`):

```
Это бот театра-студии СВОИ.
Вы пока не зарегистрированы.

Введите код приглашения (8 символов), который дал организатор.
```

Шаги FSM — `Reg.await_code` → `Reg.choose` (выбор себя из списка) → `Reg.await_name`
(`services/tg-gateway/app/states.py`). Состояние живёт в памяти процесса
(`MemoryStorage`, `main.py:72`): после рестарта бота регистрация начинается заново
с `/start`, уже созданная запись остаётся в БД.

## A. Регистрация администратора

Особенность: **нет кода приглашения**. Пароль — сам факт владения Telegram-аккаунтом,
чей `chat_id` указан в `ADMIN_CHAT_ID`.

```
1. Первый /start от chat_id == ADMIN_CHAT_ID
2. Бот зовёт POST /admin/bootstrap: запись создаётся с role='admin',
   status='active', person_key='admin'
3. audit_event: participant.bootstrap_admin
4. Бот показывает главное меню роли admin
```

Защита:

- чужой `chat_id` получает от `POST /admin/bootstrap` ответ 403 `not_an_admin_chat`,
  запись не создаётся;
- `admin` не выдаётся кодом: `POST /admin/invite` с `role='admin'` отвечает
  400 «admin не выдаётся кодом: только через ADMIN_CHAT_ID», а в панели кнопки
  только «Организатор» и «Актёр труппы»;
- второй администратор появляется не кодом, а выдачей роли в карточке человека
  («Роли», `POST /admin/grant`, право `participants.manage`); снять `admin` у себя
  или у последнего администратора нельзя — ответы 400 `self_revoke_admin` и
  `last_admin`.

Восстановление доступа:

```
1. Удалить запись или сменить ADMIN_CHAT_ID в .env
2. docker compose restart tg-gateway
3. /start → снова admin
```

## B. Регистрация организатора (org)

```
1. admin: админ-панель → «Выпустить инвайт-код» (panel:invite,
   право registration.code.issue, keyboards.py:149)
   Бот: «Кому выпустить код? Код одноразовый, действует 7 дней. Человек вводит его
         боту командой /start или в ответ на запрос кода и попадает в систему
         с выбранной ролью.»
   [Организатор] [Актёр труппы]
   └─ нажатие → POST /admin/invite {"role": ..., "ttl_days": 7} → код из 8 символов

2. Человек пишет /start → бот просит код (см. §0)

3. Ввод кода → POST /tools/participants/check_code, проверки:
   ├─ не найден            → «Код не найден. Проверьте написание.»
   ├─ истёк                → «Код устарел — попросите новый.»
   ├─ исчерпан             → «Этот код уже использован.»
   ├─ chat_id уже в базе   → «already_registered»: бот показывает меню, новый код не нужен
   └─ валиден              → шаг 4

4. Бот: «Код принят. Выберите себя из списка — так ваши взносы и занятость
        останутся на одной записи. Начните вводить фамилию или имя: список сузится,
        а кнопки обновятся.»
   [Иванов Виктор] [Лебедева Мария] [Соколов Марк] …
   [Меня нет в списке]
   └─ ввод букв сужает список (GET /tools/participants/search)

5a. Выбор себя → POST /tools/participants/attach:
    chat_id привязывается к существующей записи (не создаётся дубль),
    role — из кода (роль записи не понижается), status='active',
    папка TG_<chat_id>, audit participant.attach
    └─ бот показывает меню и запускает знакомство (docs/development/13 §F)

5b. «Меня нет в списке» или пустой список кандидатов →
    «Напишите фамилию и имя — заявку подтвердит администратор.»
    └─ POST /tools/participants/register {require_approval: true} → status='pending'
       Бот: «Заявка создана: Иванов Виктор. Доступ откроется после подтверждения.»
       ADMIN_CHAT_ID получает: «Заявка: Иванов Виктор — организатор»
       [Подтвердить] [Отклонить]
       audit participant.register {role, chat_id, code}
```

Ошибки регистрации:

- имя занято другой записью → 409 `person_key_taken`, бот пишет
  «Такой человек уже есть. Отправьте /start и выберите себя из списка.»;
- 3 неверных кода за час (`invite_attempt`, `INVITE_MAX_ATTEMPTS = 3`) → 429
  «Слишком много попыток ввода кода. Попробуйте через час.» + audit `registration.reject`.

Текст кода (`texts.invite_text`, HTML — код копируется тапом и кнопкой):

```
Код приглашения для роли «организатор»:

K7M4QP2X

Действует до 2026-11-15, использовать можно один раз.
Скопируйте код кнопкой ниже или нажмите на него в тексте.
Передайте код человеку: он отправляет боту этот код и регистрируется.
```

Особенности роли org:

- приглашать людей сам не может: коды выпускает только носитель `registration.code.issue`
  (у администратора это право есть, у организатора нет — решение заказчика);
- бюджет и сводное расписание доступны сразу после регистрации, без пробного периода.

## C. Регистрация студийца (troupe)

Роль `troupe` — единственная роль для самозаписи актёра через код. Поток тот же, что
в §B: код → проверка → выбор себя из списка (или заявка с именем) → привязка `chat_id`
или `status='pending'`. Отдельных шагов у студийца нет; разница только в наборе прав,
который даёт роль.

Тихие часы при регистрации не создаются: 20:00–08:00 — общие значения по умолчанию
(`notification_store.DEFAULTS_QUIET_FROM/TO`, FR-G3). Свои настройки человек меняет
позже командой `/quiet` или на экране уведомлений в Mini App.

### Что студиец видит сразу после регистрации

```
Главное меню роли «актёр труппы» + знакомство (docs/development/13 §F)
```

Доступно: своя занятость, своё расписание, заметки, взносы.

## D. Общие правила и краевые случаи

| Ситуация | Поведение |
|---|---|
| Уже зарегистрирован, присылает код | `check_code` отвечает `already_registered`, бот показывает меню |
| `pending` пишет `/start` | `/tools/participants/me` отвечает 403 `participant_inactive`; бот снова просит код, доступ откроется после подтверждения |
| 3 неверных кода за час | ответ 429, пауза до окна; запись в аудит `registration.reject` |
| Бот перезапущен посреди регистрации | состояние шага в `MemoryStorage` теряется, регистрация начинается с `/start`; запись в БД остаётся |
| Пришёл по коду, но роль человека выше роли кода | роль не понижается: `attach` оставляет более высокую (`rank`) |
| Блокировка | `status='blocked'`, данные сохраняются, `require` отвечает 403 — доступ закрыт |
| Роль меняется админом | кнопкой «Роли» в карточке человека, audit `rbac.role.grant` / `rbac.role.revoke` |
| Код выпущен, но не использован | виден в «Коды приглашений» (`panel:codes`), отзывается кнопкой «Отозвать» |

Чего в коде нет (проверено 08.11.2026): уведомления участнику о смене роли, автоархивации
незавершённых регистраций по таймеру, отдельных текстов «вы уже зарегистрированы как {роль}».
Не описывайте их как существующие.

## E. Управление в чате

Всё управление — кнопками панели; текстовых команд `/invite`, `/role`, `/block`,
`/approve`, `/quota`, `/settings`, `/participants` в чате нет (`services/tg-gateway/app/commands.py`).
`/revoke` в боте — отзыв доступа к чужому файлу, а не инвайт-кода.

| Кнопка (callback) | Кто | Что делает |
|---|---|---|
| «Выпустить инвайт-код» (`panel:invite`) | `registration.code.issue` | выпуск кода для `org` или `troupe` |
| «Коды приглашений» (`panel:codes`) | `registration.code.issue` | открытые коды и отзыв (`POST /admin/invite/revoke`) |
| «Участники» (`panel:people`) | `participants.view` | список людей, нажатие открывает карточку |
| «Заявки» (`panel:pending`) | `registration.approve` | подтверждение и отклонение `pending` |
| «Роли», «Возможности» в карточке | `participants.manage` | выдача и снятие ролей (`POST /admin/grant`) |
| «Педагог» в карточке | `participants.manage` | дисциплины и роль `master` (140 §4.1–4.3) |
| «Права» (`panel:rights`) | `participants.manage` | роли и число возможностей |
| «Архив», «Заблокировать» в карточке | `participants.manage` | архив и блокировка человека |

## F. Что проверяется автоматически

1. `admin` не может быть выдан кодом: `tests/integration/test_registration.py::test_код_для_admin_запрещён`.
2. Код на снятую роль (см. вводный раздел) не создаётся: `invite_code.role` CHECK
   `('admin','org','troupe')` (`db/init/030`); проверка — в `tests/integration/test_registration.py`
   (набор ролей инвайт-кода).
3. `master` кодом не появляется: CHECK `invite_code` в `061` не менялся,
   `tests/integration/test_master_role.py`.
4. Один `chat_id` — одна запись (unique + тест).
5. Регистрация не создаёт дубль, если человек уже есть в базе: привязка идёт
   через `attach`/`person_key`, а не новой записью.
6. `pending` не имеет доступа: `current`/`require` отвечают 403 (`participant_inactive`).
7. Все шаги регистрации пишутся в `audit_event`: `participant.bootstrap_admin`,
   `participant.attach`, `participant.register`, `registration.reject`.
8. Код одноразовый: второй человек с тем же кодом получает `code_exhausted`.

## G. Знакомство после регистрации (обращение №17, V-009)

Доступ выдан — но бот ещё не знает главного: как человека называть коротко,
сколько ему ехать до студии, какие спектакли и роли у него, что ему интересно.
Спрашивать это анкетой в Mini App на первом же шаге рано, поэтому сразу после
успешной регистрации бот задаёт вопросы в чате, по одному; каждый можно пропустить.

```
регистрация завершена (status='active')
  └─ бот: «Давайте познакомимся — несколько коротких вопросов…»
       ├─ имя (только если в профиле одно слово) → participant.display_name
       ├─ короткое имя        → person_alias (alias_kind='short')
       ├─ телефон (если нет)  → participant.phone, +7XXXXXXXXXX
       ├─ день рождения (если нет) → participant.birth_date
       ├─ дорога до студии    → participant.travel_minutes, 0…240
       ├─ спектакли           → participant.plays
       ├─ роли                → participant.roles_note
       ├─ тренинги            → participant.interests
       ├─ заметка для AI      → participant.ai_manifest, до 600 символов
       └─ сводка «так записать?» → «Записать» / «Отменить»
```

Правила (решение V-009 от 28.10.2026):

- **тариф не спрашивается** — его ставит организатор после договорённости;
- известное не переспрашивается: телефон и день рождения спрашиваются, только если
  их нет в профиле, имя — если в профиле одно слово (короткое имя или ник);
- ответы копятся в состоянии диалога и уходят в профиль **одним**
  `POST /tools/profile/me` только после сводки и кнопки «Записать». «Отменить»
  не пишет ничего; закрыл чат на середине — тоже ничего;
- сводка показывает только заполненные поля; если пропущено всё, записывать нечего;
- разбор ответов — сначала правилами (`services/tg-gateway/app/intro.py`):
  «40», «сорок минут», «полчаса», «половину часа», «час», «1,5 часа», «два часа»,
  телефоны «8 (917)…» и «+7 917…», даты «12.03.1990», «1990-03-12»,
  «12 марта 1990» понимаются одинаково и без сети;
- если правила промолчали (шаги «имя» и «дорога»), слово берёт модель:
  гейтвей зовёт `POST /tools/profile/intro-parse`, а `tool-api`
  (`app/intro_llm.py`) просит у OpenRouter строгий JSON с **одним** полем шага;
  ответ вне схемы, чужое поле и значение вне 0…240 минут отбрасываются —
  модель не может записать в профиль то, чего не спрашивали;
- модель ходит по той же квоте, что ассистент (`v_llm_balance`), и пишет расход
  в `llm_usage` с `intent='intro'`; нет ключа, квота исчерпана или провайдер
  недоступен — бот переспрашивает правилами, знакомство не ломается;
- заметка для помощника (`manifest`) моделью не переписывается: это слова человека,
  их сохраняем как есть;
- непонятный ответ бот переспрашивает и сценарий не двигает; телефон вне 10…15 цифр
  и дата без года или вне 1900…2020 — переспрос, а не запись мусора;
- «нет», «не знаю», «пропустить» и кнопка «Пропустить» — шаг пропускается без записи;
- знакомство не повторяется при каждом `/start`; начать заново — `/intro`;
- `pending` знакомство не получает: до подтверждения у человека нет доступа.

Тесты: `tests/unit/test_intro.py` — разбор ответов и весь сценарий с заглушкой API;
`tests/unit/test_intro_llm.py` — промпт, разбор ответа модели, отказы;
`tests/integration/test_intro_llm_api.py` — endpoint `intro-parse` и закрытое поле шага.
