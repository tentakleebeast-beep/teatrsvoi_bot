# 13. Регистрация: admin, организатор, студиец

Общее: доступ по `chat_id`, роль — свойство записи в БД, а не заявление человека.
Повторная регистрация невозможна: один `chat_id` = одна запись.

---

## 0. Точки входа

```
/start
 ├─ chat_id == ADMIN_CHAT_ID          → сценарий A (admin, без кода)
 ├─ chat_id уже в базе (active)        → меню роли
 ├─ chat_id в базе (pending)           → продолжить регистрацию с текущего шага
 └─ неизвестен                        → ввод кода приглашения
```

Состояние шага хранится в БД (`session.state`), поэтому перезапуск бота не ломает регистрацию.

---

## A. Регистрация администратора

Особенность: **нет кода приглашения**. Пароль — сам факт владения Telegram-аккаунтом,
чей `chat_id` указан в `ADMIN_CHAT_ID`.

```
1. Первый /start от chat_id == ADMIN_CHAT_ID
2. Бот: «Вы администратор. Доступен полный набор функций.
   Сейчас: 0 участников, бюджет не подключён.
   Дальше: [Выдать код организатору] [Проверить Google] [Квоты AI]»
3. admin получает роль немедленно, запись создаётся со status='active'
4. audit_event: participant.bootstrap_admin
```

Защита:
- если `ADMIN_CHAT_ID` пуст → бот не запускается (`SystemExit`), чтобы не отдать права случайному человеку;
- смена владельца = правка `.env` + рестарт; прежний admin переводится в `blocked` вручную;
- второй admin невозможен: `admin` не выдаётся кодом (`/invite admin` → 400).

Восстановление доступа:
```
1. Удалить запись/сменить ADMIN_CHAT_ID в .env
2. docker compose restart tg-gateway
3. /start → снова admin
```

## B. Регистрация организатора (org)

```
1. admin: /invite org  → код вида K7M4QP2X (одноразовый, 7 дней)

2. Студиец пишет /start
   Бот: «Это бот театра-студии СВОИ. Введите код приглашения
         (8 символов, его даёт организатор).»
   [✍️ Ввести код]

3. Ввод кода → проверки:
   ├─ не найден            → «Код не найден» (3 попытки/час, потом тишина)
   ├─ истёк                → «Код устарел, попросите новый»
   ├─ исчерпан             → «Код уже использован»
   └─ валиден              → шаг 4

4. Бот: «Код принят. Как вас зовут? Напишите так, как в документах театра —
        Фамилия Имя.»   [✍️ Написать]

5. Ввод имени → сопоставление с базой (person_alias, нормализация, опечатки):
   ├─ найден ровно один  → «Это вы: Иванов Виктор?» [Да, я] [Нет, другое имя]
   │      └─ «Да» → chat_id привязывается к существующей записи (не создаётся дубль!),
   │               role='org', status='active', папка TG_<chat_id>
   ├─ найдено несколько  → список кнопками (до 4) [Выбрать]
   ├─ не найден          → создаётся новая запись status='pending'
   │      └─ уведомление admin: «Новый участник Имя, роль org, нет в списке.
   │         [Подтвердить] [Отклонить]»
   └─ имя занято другой записью → «Такой человек уже зарегистрирован, напишите организатору»

6. Бот: «Готово, Виктор. Роль: организатор.
   Доступно: бюджет, сводное расписание, окна для событий, уведомления.»
   + audit_event: participant.register {role, code_id}
   + admin получает: «Организатор зарегистрирован: Иванов Виктор»
```

Особенности роли org:
- может сам приглашать людей? **Нет** — коды выдаёт только admin (решение заказчика).
- может менять бюджет и расписание сразу после регистрации, без «试用» периода.

## C. Регистрация студийца / актёра (troupe, student)

Отличается двумя шагами: выбор себя из списка и подтверждение модератором, если не найден.

```
1. admin: /invite troupe  (или /invite student) → код

2. /start → код (как в B)

3. Бот: «Код принят. Выберите себя из списка.»
   [Иванов Виктор] [Лебедева Мария] [Соколов Марк] [Ещё…]
   [✍️ Меня нет в списке]

4a. Выбор из списка → «Подтвердите: Иванов Виктор, актёр труппы»
    [Да] [Нет]
    └─ Да → chat_id привязывается к записи, role='troupe', status='active'
            создаётся папка, notification_pref с тихими часами 20:00–08:00
    └─ Нет → возврат к списку (счётчик попыток)

4b. «Меня нет в списке» → ввод имени
    └─ создаётся запись status='pending', роль из кода
       admin+org получают: «Новый человек Имя, роль student, требует подтверждения»
       [Подтвердить] [Отклонить]
       До подтверждения доступно только: /start, статус заявки
```

Почему так: 12 человек уже импортированы из файлов. Если студиец регистрируется сам
«с нуля», появляется дубль, и его взносы/занятость расходятся на две записи. Выбор из списка
решает это за один тап.

### Что студиец видит сразу после регистрации
```
Готово, Марк. Роль: актёр труппы.
Доступно: своя занятость, своё расписание, заметки, взносы.

Что можно прямо сейчас:
• «занят в среду после 18» — запишу в занятость
• «сколько я должен» — покажу взнос за месяц
• «заметка: идея мизансцены во втором акте» — сохраню
```

## D. Общие правила и краевые случаи

| Ситуация | Поведение |
|---|---|
| Уже зарегистрирован, присылает код | «Вы уже зарегистрированы как {роль}» + меню |
| Код введён в состоянии «ввод имени» | игнорируется, повтор вопроса |
| 3 неверных кода за час | пауза 1 час, запись в аудит `registration.reject` |
| Бот перезапущен посреди регистрации | продолжение с сохранённого шага |
| Незавершённая регистрация 24 ч | `archived` джобой |
| Роль меняется admin'ом | уведомление участнику, роль применяется со следующего сообщения |
| Блокировка | `status='blocked'`, данные сохраняются, доступ закрыт |
| Пришёл по коду, но роль в коде ниже текущей | роль не понижается без явной команды admin |

### Команды управления
| Команда | Кто | Что делает |
|---|---|---|
| `/invite <org\|troupe\|student> [n] [дней]` | admin | выпуск кодов |
| `/revoke <код>` | admin | отзыв кода |
| `/participants` | admin | список: имя, роль, статус, привязка |
| `/role <имя> <роль>` | admin | смена роли |
| `/block <имя>` / `/unblock <имя>` | admin | блокировка |
| `/quota <имя> <токены/мес>` | admin | лимит AI |
| `/approve <имя>` / `/reject <имя>` | admin, org | подтверждение pending |
| `/settings` | все | свои уведомления, тихие часы, обращение |

---

## E. Что проверяется автоматически

1. `admin` не может быть выдан кодом.
2. Один `chat_id` — одна запись (unique + тест).
3. Регистрация не создаёт дубль, если человек уже есть в базе.
4. `pending` не имеет доступа ни к чему, кроме `/start` и статуса заявки.
5. Все шаги регистрации пишутся в `audit_event`.
6. Код одноразовый: второй человек с тем же кодом получает `code_exhausted`.

## D. Знакомство после регистрации (обращение №17, V-009)

Доступ выдан — но бот ещё не знает главного: как человека называть коротко,
сколько ему ехать до студии, какие спектакли и роли у него, что ему интересно.
Спрашивать это анкетой в Mini App на первом же шаге рано, поэтому сразу после
успешной регистрации бот задаёт вопросы в чате, по одному; каждый можно пропустить.

```
регистрация завершена (status='active')
  └─ бот: «Давайте познакомимся — несколько коротких вопросов…»
       ├─ имя (только если в профиле одно слово) → participant.display_name
       ├─ короткое имя        → person_alias (alias_kind='short')
       ├─ телефон (если нет)  → participant.phone, +7XXXXXXXXXX
       ├─ день рождения (если нет) → participant.birth_date
       ├─ дорога до студии    → participant.travel_minutes, 0…240
       ├─ спектакли           → participant.plays
       ├─ роли                → participant.roles_note
       ├─ тренинги            → participant.interests
       ├─ заметка для AI      → participant.ai_manifest, до 600 символов
       └─ сводка «так записать?» → «Записать» / «Отменить»
```

Правила (решение V-009 от 28.10.2026):

- **тариф не спрашивается** — его ставит организатор после договорённости;
- известное не переспрашивается: телефон и день рождения спрашиваются, только если
  их нет в профиле, имя — если в профиле одно слово (короткое имя или ник);
- ответы копятся в состоянии диалога и уходят в профиль **одним**
  `POST /tools/profile/me` только после сводки и кнопки «Записать». «Отменить»
  не пишет ничего; закрыл чат на середине — тоже ничего;
- сводка показывает только заполненные поля; если пропущено всё, записывать нечего;
- разбор ответов — сначала правилами (`services/tg-gateway/app/intro.py`):
  «40», «сорок минут», «полчаса», «половину часа», «час», «1,5 часа», «два часа»,
  телефоны «8 (917)…» и «+7 917…», даты «12.03.1990», «1990-03-12»,
  «12 марта 1990» понимаются одинаково и без сети;
- если правила промолчали (шаги «имя» и «дорога»), слово берёт модель:
  гейтвей зовёт `POST /tools/profile/intro-parse`, а `tool-api`
  (`app/intro_llm.py`) просит у OpenRouter строгий JSON с **одним** полем шага;
  ответ вне схемы, чужое поле и значение вне 0…240 минут отбрасываются —
  модель не может записать в профиль то, чего не спрашивали;
- модель ходит по той же квоте, что ассистент (`v_llm_balance`), и пишет расход
  в `llm_usage` с `intent='intro'`; нет ключа, квота исчерпана или провайдер
  недоступен — бот переспрашивает правилами, знакомство не ломается;
- заметка для помощника (`manifest`) моделью не переписывается: это слова человека,
  их сохраняем как есть;
- непонятный ответ бот переспрашивает и сценарий не двигает; телефон вне 10…15 цифр
  и дата без года или вне 1900…2020 — переспрос, а не запись мусора;
- «нет», «не знаю», «пропустить» и кнопка «Пропустить» — шаг пропускается без записи;
- знакомство не повторяется при каждом `/start`; начать заново — `/intro`;
- `pending` знакомство не получает: до подтверждения у человека нет доступа.

Тесты: `tests/unit/test_intro.py` — разбор ответов и весь сценарий с заглушкой API;
`tests/unit/test_intro_llm.py` — промпт, разбор ответа модели, отказы;
`tests/integration/test_intro_llm_api.py` — endpoint `intro-parse` и закрытое поле шага.
