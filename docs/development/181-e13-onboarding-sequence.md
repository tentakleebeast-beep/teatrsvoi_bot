## 2. Как устроено сейчас

### 2.1. Один вход `Reg.await_code` и четыре развилки

`/start` (`menu.py:120-145`) делает три попытки: своя запись через `/tools/participants/me`
→ меню; bootstrap по `ADMIN_CHAT_ID` → меню; иначе `Reg.await_code` и реплика «Введите код
приглашения (8 символов), который дал организатор».

Код обрабатывает `on_text` (`menu.py:651-685`) через `/tools/participants/check_code`
(`people.py:624-643`), и ответ разводится на четыре ветки:

| Ветка | Условие в коде | Что происходит |
|---|---|---|
| ошибка кода | `code_not_found` / `code_expired` / `code_exhausted` | одна из трёх реплик `menu.py:661-663`, состояние не меняется |
| уже зарегистрирован | `already_registered` | меню, состояние снимается (`menu.py:654-659`) |
| педагог | `needs_discipline` (`role == "master"`) | «Код педагога принят. Какую дисциплину вы преподаёте?» + две кнопки: `acting`, `music` (`menu.py:668-674`, список — `keyboards.py:280`) |
| выбор себя | `candidates` непуст | «Код принят. Выберите себя из списка…» + до 8 кнопок и «Меня нет в списке» (`menu.py:675-681`, `keyboards.py:104-112`) |
| имя | кандидатов нет | «Код принят. Напишите фамилию и имя — „Фамилия Имя“» (`menu.py:682-684`) |

Кандидаты — это **все записи без Telegram** (`people.py:607-620`: фильтр `tg_chat_id is null`),
без фильтра по роли кода. «Меня нет в списке» (`reg:none`, `menu.py:881-885`) переводит
в тот же ввод имени, текст другой: «…заявку подтвердит администратор».

Дальше два разных финала:

- **привязка** (`reg:pick`, `menu.py:857-878` → `attach`, `people.py:682-730`) ставит
  `status = 'active'` сразу и без подтверждения (`people.py:706-710`), затем присылает **меню**
  и только потом начинает знакомство (`menu.py:872-876`);
- **новое имя** (`reg_name`, `menu.py:888-925`) зовёт `register` с `require_approval: True`
  (`menu.py:896`), тот создаёт запись `pending` (`people.py:119`), бот отвечает «Заявка
  создана… Доступ откроется после подтверждения» и шлёт админу карточку с кнопками
  `adm:ok`/`adm:no` (`menu.py:913-921`). Знакомство в этой ветке не начинается вовсе.

## 3. Целевая последовательность

Шаг = одна реплика бота (допустимо два сообщения подряд, если второе — клавиатура) и одно
действие человека. Никаких «на будущее»: всё ниже уже существует в коде, кроме прямой
последовательности вызовов и трёх правок из §2.5.

### 3.1. Схема

```
/start
  └─ реплика 1: «вы не зарегистрированы, введите код» ─→ человек: код
       ├─ код не подошёл ─→ реплика об ошибке, повтор ввода (до 3 раз в час)
       ├─ код педагога ─→ реплика «какую дисциплину» ─→ человек: кнопка (2 варианта)
       └─ код принят ─→ реплика «Код принят: <имя>.» ─→ ничего: запись уже привязана
                        (решение V-116: код несёт участника, веток «выберите себя» и «напишите имя» нет)
  └─ знакомство: имя (если в записи одно слово) → короткое имя → телефон → сводка
       └─ человек: «Записать»
  └─ меню: имя, роль, возможности, кнопки разделов
```

Знакомство — 2–3 вопроса вместо девяти, и заявки в схеме нет ни в одной ветке.

## 4. Решение по `pending`

### 4.1. Четыре обязательных ответа

**1. Код верный, человека в списке нет.** Запись создаётся сразу `active`: `register`
вызывается без `require_approval` (`menu.py:896` → `people.py:27, 119`). Роль — из кода
(`people.py:126`), `invite_code.uses + 1` и `used_by` — на новую запись (`people.py:136-137`),
в аудит уходит `participant.register` (`people.py:140-142`). Админу ничего не приходит:
уведомление существует только ради подтверждения (`menu.py:916-921`), подтверждать больше нечего.

**2. Ветка «меня нет в списке» (`reg:none`).** Остаётся. Она нужна не для заявки, а чтобы
не искать себя в списке, которого нет: кандидаты — это записи без Telegram (`people.py:607-620`),
и у человека, которого в студии ещё не заводили, список пуст. Кнопка ведёт в тот же ввод
имени, меняется только текст: «Напишите фамилию и имя — „Фамилия Имя“.» (без «заявку
подтвердит администратор», `menu.py:884`).

**3. `registration.approve`, экран «Заявки», уведомление админу.** Убираются все три:

| Что | Где | Что с ним |
|---|---|---|
| ветка `pending` в `register` | `people.py:119-128` | только `active`; параметр `require_approval` удалить из `RegisterIn` (`people.py:27`) и из вызова в боте |
| реплика «Заявка создана… Доступ откроется после подтверждения» и карточка `adm:ok/adm:no` | `menu.py:913-921` | удалить |
| пункт панели чата «Заявки» | `keyboards.py:130-131, 177` | удалить; `panel:pending` и `send_pending` (`routers/admin.py:47-61`) — тоже |
| раздел Mini App «Заявки» | `webapp.py:281-283`, действие `approve_pending` (`webapp.py:220`), блок `pending` (`webapp.py:191`) | удалить из реестра; страница `pages/admin_pending.py` уходит вместе с разделом |
| `attention_rows` и счётчик «ждут решения» | `api/webapp_api.py:324`, `core.py:813` | удалить строку |
| право `registration.approve` | `db/init/008_rbac_capabilities.sql:42, 63, 73`; у `org` снято `068` | миграция `069` снимает право у всех ролей; строка в справочнике `rbac_capability` остаётся с пометкой «не выдаётся: заявок нет с E13» — удалять справочник нельзя, на него смотрят старые ревизии |
| строки «ожидают подтверждения» в списке людей | `menu.py:179-186` | удалить: источник перестал существовать |

**4. Риск «код утёк — чужой человек попал в `active`».** Сегодня его закрывает не заявка,
а другое, и это видно по коду:

- код одноразовый и живёт 7 дней (`admin.py:35-36, 50-51`), `uses`/`max_uses` (`db/init/001_schema.sql:50-51`);
- чужое имя взять нельзя: `person_key_taken` (`people.py:114-118`);
- вход по коду виден: `invite_code.used_by` (`people.py:136-137`), у записи `invite_code_id`
  (`people.py:126-127`), админ видит и то и другое в «Люди» (`admin.py:416-418`);
- доступ отзывается мгновенно: `archived` и `blocked` дают 403 (`core.py:476-481`), вернуть
  в архив и заблокировать может админ (`participants.manage`).

Заявка же защищала только один путь из двух: привязка к существующей записи ставит `active`
без подтверждения и **сегодня** (`people.py:706-710`). То есть снятие `pending` убирает
подтверждение там, где оно было, и не добавляет новой дыры в привязке — но и не закрывает
остаток: человек с утёкшим кодом, назвавшийся вымышленным именем, попадёт в `active`
и увидит расписание и свои взносы. Полностью это закрывает только персональный код
(участник в самом коде), это отдельное решение — V-116 (§6.2).

### 4.2. Данные: что делать с тремя заявками на проде

Миграции данных **нет**: перевести `pending` в `active` скопом значит выдать доступ трём
неизвестным записям без проверки. Порядок такой:

1. до выката админ открывает «Заявки» (экран ещё есть) и по каждой записи решает: «Подтвердить»
   → `active` или «Отклонить» → архив. Три записи — три нажатия;
2. перед тегом проверить: `select count(*) from participant where status = 'pending'` = 0;
3. после выката экрана «Заявки» больше нет, а запись `pending` осталась бы без единого способа
   активации — поэтому пункт 2 входит в чек-лист релиза, а не в «потом».

### 4.3. Две дыры, которые заявка не закрывала

Найдены при разборе `attach`; без них решение по `pending` неполное.

1. **Права записи важнее роли кода.** `attach` ставит `participant.role` из кода, но при
   этом сохраняет прежние строки `participant_role` (`core.py:170-177`), а права считаются
   объединением ролей (`db/init/008_rbac_capabilities.sql:154-166`). Код труппы + запись
   администратора: в витрине `troupe`, в правах — админ. Правило `people.py:701-703`
   (`role = person["role"]`, кроме `admin`) от этого не спасает: оно про витрину, не про права.
2. **Список кандидатов не фильтруется по роли кода** (`people.py:607-620`): код труппы
   показывает кнопкой запись педагога и администратора.

Закрывается без новой функциональности — проверкой ранга в `attach` и тем же фильтром
в `check_code`. Ранг приходится задать заново: карта в `people.py:701` считает `master`
и `troupe` равными (`{"troupe": 2, "master": 2, "org": 3, "admin": 4}`), поэтому по ней код
труппы на запись педагога проходит, хотя у педагога прав больше
(`schedule.read.all`, `participants.view` — `db/init/061_master_role.sql:50-56`). Целевой
ранг: `troupe = 1, master = 2, org = 3, admin = 4`; привязываться можно только к записи,
чья роль не выше роли кода. Отказ — реплика «Этот код не для этой записи: попросите код
нужной роли.» Смена роли — отдельно и явно, в «Правах» (`participants.manage`), а не
побочным эффектом входа.
