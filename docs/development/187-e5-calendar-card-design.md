## 2. Два источника события — и почему карточка одна

Календарь студии — текстовый журнал занятости: 446 событий 2026 года созданы человеком прямо
в Google, у них пусты `colorId`, `description`, `attendees`, `location` (`160` §3.4). События
бота живут иначе: строка в `event_plan` плюс событие в черновом календаре с маркером
`svoi_event_id` (`186` §5).

| Источник | Как узнать | Что есть | Чего нет |
|---|---|---|---|
| Бот | `extendedProperties.private.svoi_event_id` → строка `event_plan` | тип, участники, создатель, статус, часы | описания: `event_plan` такой колонки не имеет (`001:197–212`), в Google `description` у старых событий пуст |
| Человек | маркер `[А]`…`[П]` в начале `summary`, строки в `event_plan` нет | дата, время, название | тип (только метка), создатель (только аккаунт Google), описание, цвет: `colorId` пуст у всех 446 (`160` §3.4) |

**Решение D1. Ключ карточки — календарь и `eventId`, а не `event_plan.id`.**
`GET /webapp/events/card?calendar=draft|read&event_id=…` читает событие из Google и, если маркер
`svoi_event_id` есть, добавляет строку `event_plan`. Иначе карточка показывается по данным
календаря, а действия, которым нужна строка базы, не рисуются. Сегодня `GET /tools/events/{id}`
умеет только строку базы (`events.py:765`) — на 446 людских событий он отвечает `event_not_found`,
и это первая причина, по которой карточку нельзя строить на нём.

**Цена.** Один лишний вызов `events.get` на открытие карточки. **Выгода.** Одна карточка на все
события: людские не «исчезают» из календаря Mini App, а показываются с честной пометкой
«создано в Google».

## 3. Карточка события (D2)

Состав — решение владельца (`157` §E5): создатель, дата, время, название, описание; действие
первой версии — перенос. Тип и цвет добавляются как оформление (V-080, V-086), не как поля формы.

```
[С]  Спектакль · синий            <- плашка буквы + слово типа + цвет
«Жизнь насекомых»                <- название без метки
вторник, 24 ноября · 19:00–21:30  <- дата, время, длительность
Сцена                            <- место, если задано
Создал: Мария                    <- created_by; у людского — «создано в Google»
Описание                          <- из Google description; пусто — строки нет
[ Перенести ]                    <- единственное действие первой версии
```

| Поле | Откуда | Если пусто |
|---|---|---|
| Тип | `svoi_kind` → настройка; иначе метка `[X]` в `summary` | «Без типа» |
| Цвет | `colorId` события (V-086: цвет из Google) | нейтральная плашка, слова «цвет не задан» |
| Название | `summary` без метки | `summary` как есть |
| Дата, время | `start`/`end` (`dateTime`, при `date` — весь день) | — |
| Место | `location` или `venue.name` по `event_plan.location` | строки нет |
| Создатель | `event_plan.created_by` → `participant.display_name` | «создано в Google» |
| Описание | `description` события Google | строки нет |
| Состояние | черновое / боевое / отменено (`status=cancelled`) | — |

**Откуда описание.** Колонки `event_plan.description` нет, в `insert` (`events.py:456–467`)
описание не пишется, `events_card` его не отдаёт (`765–800`). **Решение:** описание — поле
события Google, пишется в `description` при создании и при переносе; в базе не дублируется —
иначе появляется второй источник правды, который разъедется с календарём. Для 446 старых
событий описание пусто, и карточка этого не скрывает.

**Создатель.** `events_card` не отдаёт `created_by` вовсе (`765–800`), хотя колонка есть
(`001:209`). Для карточки Mini App нужен новый ответ `GET /webapp/events/card`: тот же набор
полей плюс `created_by.name`, `kind.title`, `letter`, `color_id`, `calendar`, `editable`.
Отдавать `created_by` в существующем `/tools/events/{id}` тоже можно, но контракт чата трогать
незачем.

**Перенос — единственное действие.** Экран: дата, часы «с/до», проверка занятости зала, ответ
409 `slot_taken` — как у `POST /tools/events/move` (`641–670`). Длительность сохраняется.
Для людского события кнопки нет, вместо неё текст «Событие создано в Google — правьте там»
(`186` §8, строка 8). Отмена, состав, замена педагога — вторая версия карточки (`157` §E5),
в этом дизайне не проектируются.

## 4. Экран «Сверить» по календарю (D3)

Фоновой синхронизации нет: ручные правки ловит кнопка (`157` §E5, `186` §7). Уже существует
«Сверка листов» — `/webapp/reconcile`, право `budget.import`, три счётчика по строкам
(`pages/misc_reconcile.py`). Смешивать её с календарём нельзя: у неё другое право (у `master`
нет `budget.import`, но есть `schedule.read.all`) и другой предмет.

**Решение D3. Отдельный экран `/webapp/events/reconcile`, одна кнопка «Сверить», один источник.**
Кнопка зовёт общий `POST /tools/google/refresh` из `186` §7 с телом `{"sources":["calendar.read"]}`;
ответ раскладывается по шести строкам:

| Строка | Что значит | Что можно сделать |
|---|---|---|
| Изменено в Google | событие бота правили руками: часы, название, место | показать «в Google: …, у нас: …»; перенос правки в базу — следующая версия |
| Перенесено в боевой | в боевом нашёлся наш `svoi_event_id`, черновик убран | ничего, строка-отчёт (`186` §5 п.3) |
| Цвет не по типу | `colorId` ≠ цвет типа из настройки | «Вернуть цвет типа»; чужой цвет уходит в отчёт, настройка — источник правды (V-119, решение 22.11.2026) |
| Метка не по типу | `[X]` в заголовке ≠ `svoi_kind` | показать обе; правка заголовка — следующая версия |
| Без типа | ни маркера, ни `svoi_kind` | отчёт: сколько таких (у людских — все 446, пока нет миграции V-081) |
| Не прочитано | календарь недоступен, `error` | текст ошибки, прошлый снимок не подставляется |

**Правила экрана.** Ничего не пишет: ни в базу, ни в календарь — это следствие `185` D2 и
V-072, и первая версия «Сверить» только читает. Показывает честное «данные от 17:20» из
`GET /tools/google/freshness` (`186` §7), при `stale: true` — плашку «данные могли устареть».
Без права вместо кнопки — фраза, кто ведёт сверку (образец: `misc_reconcile.py`, отчёт 142 §3
строка 10). Оба эндпоинта (`refresh`, `freshness`) сегодня есть только в спецификации `186`,
в коде их нет — экран зависит от карты реализации E1-4.

**Цена.** Чтение всего окна календаря: `events.list` отдаёт не больше 100 событий за вызов
(`events.py:854–886`, `maxResults=100`), 446 событий — это минимум 5 вызовов с листанием.
**Выгода.** Видно, что человек сделал в Google руками, без фонов и вебхуков.

## 5. Экран «Типы и цвета событий» (D4)

**Кто видит.** Организатор и администратор — право `calendar.write` (dev-база: `admin`, `org`).
Педагог и труппа экран не видят: у `master` есть `schedule.write`, но нет `calendar.write`.
Новая возможность не заводится: роли те же две, третий ключ в матрице дал бы вторую ось ради
ничего. Название возможности в `rbac_capability` — «Создавать и отменять события» — придётся
дополнить словами «и настраивать типы и цвета»; это одна строка в миграции, а не новый код.

```
Типы и цвета событий
┌──────────────────────────────────────────┐
│ [А]  Аренда        ●──────────  ▾ цвет   │
│ [С]  Спектакль     ●──────────  ▾ цвет   │
│ [Р]  Репетиция     ●──────────  ▾ цвет   │
│ [Т]  Тренинг       ●──────────  ▾ цвет   │
│ [П]  Проект        ●──────────  ▾ цвет   │
└──────────────────────────────────────────┘
[ Добавить тип ]           [ Сохранить ]
```

| Поле | Правило |
|---|---|
| Буква | один кириллический символ, уникален среди типов; задаётся при создании и **не меняется** — иначе метка `[X]` в заголовках разъедется с типом |
| Название | любое, до 40 знаков; попадает в карточку словами |
| Цвет | `colorId` 1…11 календаря Google; тип без цвета не сохраняется |
| Порядок | стрелки «выше/ниже», попадает в список выбора при создании события |
| Удаление | только у типа без событий; иначе — «скрыть» (`is_active=false`), тип остаётся у старых событий |

Стартовые значения — сегодняшняя жёсткая таблица кода `core.py:745` (`rental` 10, `show` 11,
`rehearsal` 9, `training` 5, `meeting` 8, `other` 8). Это засев настройки, а не источник правды:
после миграции таблица в коде удаляется. У типа «проект» цвета в коде нет вовсе — он создаётся
настройкой и без выбранного цвета не сохраняется.

**Диалог перекраски (V-087).** Сохранение всегда спрашивает, режим за человека не запоминается:

```
Сохранить настройку?
Применить цвета к событиям, которые уже есть в календаре?
[ Перекрасить все ]  [ Только новые ]  [ Отмена ]
```

- Оба варианта равноправны, ни один не выбран по умолчанию; закрытие диалога = «Отмена», ничего
  не сохраняется (`tg.showPopup` с тремя кнопками; `showConfirm` не годится — в нём две кнопки).
- «Только новые» — настройка сохраняется, ни одно событие не правится.
- «Перекрасить все» — сохраняется, затем бот правит `colorId` только у событий **изменённых
  типов** и только в своей зоне записи: в переходном режиме — черновой календарь
  (`CALENDAR_ID_DRAFT`), в целевом — боевой: «перекрасить все» — постоянная функция, разрешённая владельцем 22.11.2026 (V-120). События других типов и
  людские события без маркера не трогаются.
- Если перекраска упала на середине: настройка уже сохранена, ответ несёт `recolored: N из M`
  и список ошибок; экран пишет «сохранено, перекрашено N из M» — молчаливого частичного успеха нет.

**Контракт.** `GET /webapp/events/types` (список типов и палитра), `POST /webapp/events/types`
(тело `{"types":[…], "apply":"all"|"new"}`, ответ `{"saved":true,"recolored":N,"failed":[…]}`).
Право `calendar.write` проверяется на сервере; страница только не рисует форму без права —
как у экрана «Уведомления» (`pages/admin_notifications.py`: форма скрыта до 200).

## 6. Правила типов и цветов (D5)

1. **Один источник правды — настройка.** Пять типов названы владельцем 14.11.2026 (V-080),
   цвета и список живут в настройке (V-086). Таблица `core.py:745` и литералы `KIND_TITLES_RU`
   (`core.py:499`) после миграции удаляются: два словаря типов в коде и настройке — это ровно
   тот рассинхрон, из-за которого пять копий `api()` в JS уже стоили времени.
2. **Код типа стабилен, буква и название — оформление.** `event_plan.kind` хранит код
   (`rental`, `show`, `rehearsal`, `training`, `project`), а не букву и не цвет.
3. **Тип узнаётся по маркеру, а не по тексту.** Порядок: `svoi_kind` → метка `[X]` в начале
   `summary` → «без типа». Слова «аренда» в 244 заголовках (`160` §3.4) типом не считаются:
   классификация по тексту — догадка, а `185` §2 требует не угадывать.
4. **Метку `[X]` ставит бот при создании.** Сегодня `summary` собирается как
   `f"{KIND_TITLES_RU[kind]} - {title}"` (`events.py:456–467`) — метки нет ни в одном событии.
   Правило: `summary` = `[П] Название`; слово типа в заголовок не дублируется, оно есть
   плашкой в карточке.
5. **Цвет — `colorId` события Google.** Своей палитры Mini App не держит; при записи цвет
   берётся из настройки по типу, при показе — из события, как решил владелец («цвет из Google»).
   Пустой `colorId` — не ошибка, а «цвет не задан»: так выглядят все 446 события до миграции.
6. **Событие без типа допустимо.** Людское событие в боевом календаре может не иметь метки;
   карточка пишет «Без типа», сверка считает такие строкой отчёта. Заставлять человека
   размечать чужие события бот не может.
7. **В боевой календарь бот не пишет** (`185` D2, V-072) с двумя исключениями по решению
   владельца 22.11.2026: разовая миграция при переключении режима (V-081) и перекраска
   существующих событий по кнопке «Перекрасить все» (V-120, вариант б) — это постоянная функция,
   а не только миграция. Оба случая пишут лишь `colorId` событий бота.

## 8. Модель данных настройки (предложение, не код)

```
create table calendar_event_type (
  code        text primary key,                       -- rental | show | rehearsal | training | project
  letter      text not null unique check (char_length(letter) = 1),
  title       text not null,
  color_id    smallint check (color_id between 1 and 11),
  sort_order  smallint not null default 100,
  is_active   boolean not null default true,
  updated_at  timestamptz not null default now(),
  updated_by  bigint references participant(id)
);
```

`event_plan.kind` перестаёт быть `check`-списком (`022:18–21`) и становится внешним ключом на
`calendar_event_type(code)`. Тогда новый тип — строка в таблице, а не миграция и не правка трёх
словарей. `meeting` и `other` остаются в таблице с `is_active = false` (архивные): так старые
строки не нарушают ключ, а выбрать их при создании нельзя. Перед миграцией считается, сколько
в боевой базе строк с этими двумя типами — число в этом документе назвать нельзя, боевая база
в проходе не читалась.

Почему таблица, а не `app_setting` (`025:34–38`), хотя образец экрана настроек
(`admin_notifications.py`) хранит значения там: типы — словарь, на который ссылаются события.
JSON в `app_setting` не даёт ни уникальности буквы, ни внешнего ключа, ни проверки цвета, а
перезапись строки целиком теряет изменение при двух одновременных сохранениях.

## 9. Три предложения

### 1. Сделать типы словарём базы, а не списком в коде

Заменить `event_plan_kind_check` (`db/init/022:18–21`) внешним ключом на `calendar_event_type`,
перенести туда пять типов владельца и стартовые цвета из `core.py:745`, удалить
`KIND_TITLES_RU` и `EVENT_COLORS` из кода. **Даёт:** новый тип добавляется настройкой, без
миграции; цвет перестаёт быть константой; «проект» появляется штатно. **Цена:** 1 миграция,
3–4 точки чтения (`events.py` создание/карточка/список, `window_policy`), проверка боевых
строк с `meeting`/`other`; риск — забытый словарь в `assign.py:241`, его тоже надо свести к
одному источнику.

### 2. Карточка по ключу календаря, а не по строке базы

Новый ответ `GET /webapp/events/card` читает событие Google, при маркере `svoi_event_id`
добавляет `event_plan`; поля `created_by`, `description`, `color_id`, `kind`/`letter`
добавляются в ответ. **Даёт:** одна карточка на людские и ботовые события, «создатель» и
«описание» из `157` §E5 становятся заполнимыми. **Цена:** 1 новый эндпоинт, 1 вызов
`events.get` на открытие, запись `description` в Google при создании/переносе; риск — для
людских событий поля остаются пустыми, и это надо честно писать, а не прятать.

### 3. «Сверить» по календарю — отдельный экран, общий эндпоинт

`/webapp/events/reconcile` с правом `schedule.read.all` зовёт `POST /tools/google/refresh`
с `{"sources":["calendar.read"]}` из карты E1-4; «Сверка листов» остаётся своей. **Даёт:**
педагог видит, что изменилось в календаре, не получая доступа к бюджетной сверке; один контракт
на два экрана. **Цена:** экран нельзя выпустить раньше E1-4 (эндпоинтов `refresh`/`freshness`
в коде нет), листание окна — 5+ вызовов Google на 446 событий.
