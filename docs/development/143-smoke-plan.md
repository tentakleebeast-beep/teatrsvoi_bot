## 1. Почему нужен отдельный смоук, а не «ещё раз pytest»

Замер по репозиторию на 08.11.2026 (HEAD `main`):

| Файлов `tests/test_*.py` | 281 | файловая система |
| Собрано pytest (с браузерными параметрами) | 2867 | `pytest --collect-only -q` |

| Use case UC-* в `docs/development/28` | 13 | разбор файла |

Отсюда три вывода, на которых стоит весь дизайн.

1. **Требования не трассируются по ID.** У 78 требований ID не проставлен ни в тесте, ни в
   скрипте, ни в коде. Это не значит «не реализовано» — это значит, что связать требование
   с доказательством сейчас можно только руками. Матрица обязана строиться из того, что
   реально исполняется, а не из колонки «статус» в документе 19.
2. **Статусы документа 19 несвежие.** Пример расхождения: FR-A7 «Архив» помечен `готово`,
   при этом сценарий S-05 в документе 20 утверждает, что архивация возможна «только миграцией
   `011` для трёх людей» и способа в боте нет; по факту есть `/admin/archive`, экран «Архив»
   и тест `test_admin_people_actions.py::test_архив_из_чата_и_с_экрана_дают_один_результат`.
   Документ 20 от 26.10, документ 19 от 04.11, код — от 08.11. Сверка по документам
   воспроизводит их расхождения, а не состояние системы.
3. **Сквозного прогона «как человек» нет.** Прошлые смоуки (`docs/reports/54`, `59`, `62`)
   — разовые отчёты без повторяемой матрицы: следующий прогон начинался с нуля и другими
   осями. Браузерный набор (`tests/webapp`, 317 тестов на chromium по отчёту 142) держит
   геометрию и JS, но не проверяет, что человек с ролью `org` действительно запишет расход
   и увидит его в бюджете.

Смоук Э3 закрывает ровно этот разрыв: **требование → доказательство → факт**, с повтором
и с ценой одной строки при следующей правке.

## 2. Три слоя доказательств и что такой «смоук»

| Слой | Что это | Когда исполняется | Что даёт в матрицу |
|---|---|---|---|
| **А. Авто** | Существующие `pytest` (unit, integration, `tests/webapp`) и скрипты-гейты `scripts/check_*.py` | `scripts/check_done.py --full` перед смоуком | pass/fail по каждому тесту, у которого в docstring есть ID требования |
| **Б. Сценарии** | 12 сквозных путей «роль → действие → результат» на стенде с копией боевых данных | во время смоука | шаг сценария с ожидаемым и фактическим, скриншот или строка БД |
| **В. Прод-режим** | Минимальный набор проверок на проде: только чтение плюс четыре разрешённых владельцем вида записи | по команде владельца, перед релизом | отдельная колонка «проверено на проде», не смешивается с Б |

Смоук **не перезапускает** слой А своими руками: результат берётся из `check_done`/pytest.
Слой Б — единственное новое, что появляется в этой карте. Слой В существует потому, что
часть поведения физически не воспроизводится на копии (доставка Telegram, запись в Google
Sheets), и владелец разрешил ограниченную запись на проде.

Правило разделения с Э2: вид, геометрия, контраст, тексты экранов — зона `141`/`142` и
`scripts/ui_review.py`, в смоуке не дублируются. Смоук проверяет **поведение и права**:
форма пишет, право отказывает, результат появляется там, где обещано.

## 3. Матрица требований: схема и правила

Матрица — главный артефакт прогона. Одна строка на каждый из 113 ID, без сокращений
и без переписывания формулировок.

### 3.1. Колонки

| Колонка | Значение | Кто заполняет |
|---|---|---|
| `ID` | `FR-A1` … `FR-I2` как в документе 19 | авто |
| `требование` | первые 60–80 символов формулировки из 19 (полная — по ссылке на строку) | авто |
| `приоритет` | `P0` / `P1` / `P2` / `не задан` (для 25 строк дополнений) | авто из 19, `не задан` не додумывается |
| `статус в 19` | `готово` / `частично` / `не начато` / `отменено` / `убрано` | авто |
| `доказательство` | `тест:<файл>::<имя>`, `скрипт:<файл>`, `сценарий:СМ-N/<шаг>`, `прод:СМ-N/<шаг>`, либо `—` | авто + сценарий |
| `результат` | `пройдено` / `провал` / `не проверено` | авто по факту прогона |
| `причина непроверки` | из закрытого списка §3.3 | сценарий |
| `дефект` | ID карты, если провал | сценарий |

### 3.2. Правила

1. `пройдено` ставится только при доказательстве с датой прогона. Статус `готово` в документе
   19 сам по себе доказательством не является и в колонку `результат` не переносится.
2. `не проверено` — не пустая клетка. Причина обязательна, иначе строка считается ошибкой
   отчёта (проверяется скриптом, а не глазами).
3. Отменённые требования (`отменено`, `убрано`) остаются в матрице со статусом `не проверяется`
   и ссылкой на решение, которое их сняло: исчезнувшая строка выглядит как забытая.
4. Дельта к прошлому прогону считается по JSON, а не пересказом: сменившиеся строки
   перечисляются отдельным разделом отчёта.
5. Приоритет не выдумывается: 25 строк без шкалы идут как `не задан` и исключаются из
   процентного критерия §7 до ответа владельца (V-044).

### 3.3. Закрытый список причин «не проверено»

`нет автотеста` · `нужен живой Telegram` · `нужен Google Sheets/Calendar` · `нужен прод` ·
`нужен LLM (недетерминизм)` · `нет данных в копии` · `снято решением V-NNN`.

Список закрыт намеренно: свободный текст в этой колонке через месяц станет свалкой,
в которой нельзя посчитать ни одну категорию риска.

### 3.4. Где живёт матрица

| Файл | Роль |
|---|---|
| `docs/reports/NNN-smoke-YYYY-MM-DD.md` | человеческое представление: снимок, числа, дельта, дефекты, риск |
| `docs/reports/NNN-smoke-YYYY-MM-DD.json` | источник истины для дельты: `{version, commit, date, env, dump_sha256, layers, requirements[], scenarios[], cleanup, defects[]}` |

Номер `NNN` — следующий свободный по `docs/`; индекс пересобирается
`scripts/build_docs_index.py`. JSON прикладывается к карте как артефакт, чтобы следующий
прогон считал дельту машиной.

## 4. Как получается слой А без ручной сверки

Ничего нового для хранения соответствий не заводим: ID требований уже стоят в docstring
тестов (правило `docs/development/16` §3.5), а `scripts/test_audit.py` уже разбирает тесты
через AST и находит эти ID.

Решение:

1. `scripts/test_audit.py` получает ключ `--matrix`: печатает `FR-… → [файл::тест]` в JSON.
   Парсер и правила поиска ID переиспользуются, второго парсера не появляется.
2. `pytest` запускается штатно с `--junitxml`, результат join'ится с матрицей по `nodeid`.
   Прогон для слоя А — **полный** `tests/`, а не только `tests/smoke`: матрица строится по
   всему каталогу тестов, и junit одного сценария оставляет 57 требований без исхода
   (так отчёт 145 и назвал их «без автотеста» — урок L-031). `--junit` принимает несколько
   файлов и склеивает их: побеждает сильнейшее свидетельство (провал > пройдено > пропуск).
   Никакого нового раннера тестов.
3. `scripts/smoke_report.py` собирает: junit XML + матрицу `test_audit --matrix` + результаты
   сценариев + список гейт-скриптов → Markdown и JSON отчёта §3.4. Три входа, один выход.
   Объём каждого входа печатается числом («источники слоя А»), а требование, у которого
   тест в матрице есть, а исхода в junit нет, валит сборку отчёта: «нет автотеста» при
   наличии теста недопустимо.
4. Скрипты без pytest (`check_invariants.py`, `check_registers.py`, `check_deadcode.py`)
   попадают в матрицу как `скрипт:<файл>` с кодом возврата.

78 требований без ID останутся без доказательства слоя А — это и есть «смоук-долг»,
который закрывается сценариями слоя Б или явной строкой `не проверено`. Ожидание, что
сценарии покроют большую часть из них, проверяется первым прогоном и фиксируется числом.

## 6. Среда и данные

### 6.1. Три режима

| Режим | База | Сервис | Что можно | Что нельзя |
|---|---|---|---|---|
| **Стенд** (основной, слой Б) | `svoi_smoke` — свежий `pg_dump` прода, восстановленный локально | `tool-api :8011`, dev-бот (`DEV_BOT_TOKEN`), Playwright | любые записи в свою копию | трогать `svoi` и `svoi_ui`, прод-токен |
| **Авто** (слой А) | `svoi_test` (как сейчас в `tests/conftest.py`) | pytest, гейт-скрипты | всё | сеть, Google, LLM |
| **Прод-режим** (слой В) | прод | прод `tool-api` и бот | чтение; создание и удаление четырёх видов объектов с маркером (файл, заметка, занятость, расход) | события, начисления, тарифы, миграции, сообщения живым людям |

Стенд пересоздаётся из свежего дампа каждый прогон, а не из рабочей dev-базы: по V-036 dev
объявлен чистым стендом и боевых данных не содержит. В отчёте фиксируются sha256 дампа
и коммит — иначе два прогона с разными данными выглядят как регресс.

Порт `8011` и база `svoi_smoke` выбраны так, чтобы не пересечься со стендом ревью
(`svoi_ui` + `:8010` из отчёта 142): два одновременных прогона не должны делить ни базу,
ни процесс.

### 6.2. Набор тестовых данных

Маркер: `SMOKE-<YYYYMMDD>-<NN>`, где `NN` — номер прогона в этот день. Маркер ставится
в имя/комментарий каждого созданного объекта и является единственным признаком для уборки.

| Объект | Что создаём | Где | Как удаляем | Проверка уборки |
|---|---|---|---|---|
| Люди | «Смоук Актёр» (troupe), «Смоук Организатор» (org), «Смоук Педагог» (master + дисциплина) | только стенд | удаление строк `participant`, `participant_role`, `participant_capability_override`, `participant_discipline` | `count(*)` по маркеру = 0 |
| Файл | `SMOKE-<маркер>.txt`, 1 КБ | стенд; прод — по V-042 | `file_object` + объект в S3 | 0 файлов с префиксом маркера |
| Заметка | `note` с маркером в тексте | стенд; прод — по V-042 | удаление по `note.id` | 0 заметок с маркером |
| Занятость | интервал 03:00–04:00 на дату +60 дней | стенд; прод — по V-042 | удаление часовых строк по `participant_id` и дате | 0 строк на эту дату |
| Расход | 123 ₽, категория «Прочее (расход)», маркер в описании | стенд; прод — по V-042 | удаление `budget_tx` по маркеру | 0 строк, итог месяца вернулся к исходному |
| Событие | площадка «Сцена», дата +60 дней, только смоук-участники | только стенд | отмена + удаление `event_plan` и состава | 0 событий с маркером |
| Обращение | текст с маркером | только стенд | удаление `feedback` и `feedback_answer` | 0 обращений с маркером |

Запрещено всегда: писать в строки реальных людей, создавать событие с реальным составом,
менять тарифы и начисления, накатывать миграции на прод, отправлять сообщение реальному
chat_id. Решение владельца 08.11.2026 разрешает на проде только четыре вида записи из
таблицы и требует удалять их после проверки — это и есть граница слоя В.

Уборка выполняется скриптом (`scripts/smoke_data.py`), а не руками: ручная уборка
не воспроизводима и в отчёте недоказуема. Перед прогоном скрипт проверяет, что остатков
прошлого прогона нет, и падает, если нашёл, — «накопленные» тестовые данные портят
следующие числа.

## 7. Критерии приёмки прогона

| Критерий | Порог | Почему такой |
|---|---|---|
| P0-требования с доказательством или явной причиной | 48 из 48 | P0 — «без этого не эксплуатируется»; молча пропущенный P0 и есть источник релизных сюрпризов |
| P1-требования с доказательством | ≥ 80 % (27 из 34) | остаток допустим, если причина из §3.3 и риск назван |
| Сценарии | все 12 выполнены, пропусков ≤ 3 с причиной | двенадцать путей покрывают все домены; больше пропусков — прогон неполный |
| Блокеры | 0 | блокер = путь человека не работает |
| Уборка | 0 остатков по маркеру, итоги месяца и счётчики вернулись к исходным | иначе следующий прогон считает по грязным данным |
| Сообщения живым людям | 0 | цена ошибки — доверие людей, а не строки в отчёте |
| Записи на проде вне разрешённых четырёх видов | 0 | прямое ограничение владельца |
| Отчёт | матрица, дельта, риск, 3 предложения | иначе это не отчёт, а лог |

Числа-знаменатели не набираются руками — они пересчитываются из документа 19:

```bash
env -u PYTHONPATH .venv/bin/python scripts/test_audit.py --matrix --json > /dev/null
```

## 8. Дефекты и маршрут

1. Провал шага или непустая клетка `провал` в матрице — карта `worker-feature` с указанием:
   требование, шаг, ожидаемое, фактическое, доказательство (команда и её вывод), серьёзность
   (`блокер` / `важно` / `мелко`).
2. Смоук-карта не чинит найденное: у неё нет задачи «сделать», есть «показать».
3. После исправления перезапускаются только затронутые сценарии; в отчёте — новый прогон
   с новым номером и дельтой, а не правка прошлого отчёта.
4. Требование, у которого нет ни теста, ни сценария, — это `не проверено`, а не «наверное,
   работает». 78 таких ID на старте — честная точка отсчёта, а не приговор.
