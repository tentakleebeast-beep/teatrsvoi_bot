## 2. Общая рамка

**Два источника события.** Событие бота — маркер `extendedProperties.private.svoi_event_id`
в событии Google плюс строка `event_plan`. Людское событие — только событие Google, строки в
базе нет; тип у него узнаётся по метке `[X]` в начале `summary`, либо не узнаётся вовсе.

**Ключ карточки — календарь и `eventId`** (решение дизайна D1, принимается без переспроса).
Ключ `event_plan.id` не годится: он есть только у событий бота.

**Зона записи бота — черновой календарь.** В переходном режиме (`app_setting.google.mode =
transitional`, `186` §5 п.4) бот пишет только в `CALENDAR_ID_DRAFT` через ключ реестра
`calendar.draft` (`186` §4.3 п.1). В боевой календарь бот не пишет (`185` D2, V-072), с одним
исключением: перекраска `colorId` событий бота в целевом режиме (V-120 б, ключ реестра
`calendar.live`, I-7). Поэтому все остальные пишущие действия этой спецификации — только
черновой календарь.

**Описание события — поле Google, не база.** Колонки `event_plan.description` нет (`001:197–212`),
и она не заводится: описание живёт в `description` события Google. В базе не дублируется, иначе
появляется второй источник правды, который разъедется с календарём. Для людских и для 446 старых
событий описание пусто — карточка это показывает, а не прячет.

**Типы — таблица, а не `app_setting`** (принимается без переспроса): типы — словарь, на который
ссылаются события, JSON в `app_setting` не даёт ни уникальности буквы, ни внешнего ключа, ни
проверки цвета, а перезапись строки целиком теряет изменение при двух одновременных сохранениях.

## 3. Карточка события

### 3.1. Адрес и параметры

```
GET /webapp/events/card?calendar=draft|read&event_id=<id события Google>
```

| Параметр | Правило | Ошибка |
|---|---|---|
| `calendar` | обязателен, `draft` или `read` | 400 `bad_calendar` |
| `event_id` | обязателен, id события Google (не `event_plan.id`) | 400 `event_id_required` |

Право — `schedule.read.all`: то же, что у существующего `GET /tools/calendar/events`
(`events.py:855`). Расширение на «свои события» педагога не решается здесь: это карта
`t_4d081225`. Форма проверки — как у остальных данных Mini App: `core.webapp_actor` плюс
`core._webapp_require(who, "schedule.read.all", deny_text="Календарь смотрит организатор и педагог.")`.

### 3.2. Ответ

```json
{"ok": true, "event": {
  "calendar": "draft",
  "event_id": "abc123",
  "plan_id": 412,
  "letter": "С", "kind": "show", "kind_title": "Спектакль",
  "title": "Жизнь насекомых", "title_raw": "[С] Жизнь насекомых",
  "color_id": 11,
  "start": "2026-11-24T19:00:00+04:00", "end": "2026-11-24T21:30:00+04:00",
  "all_day": false, "date": "2026-11-24", "weekday": "вторник",
  "time_from": "19:00", "time_to": "21:30",
  "location": "Сцена",
  "creator": {"id": 7, "name": "Мария"},
  "description": "Сбор за час до начала",
  "state": "draft",
  "editable": true,
  "not_editable_reason": null
}}
```

| Поле | Откуда | Если пусто / нет |
|---|---|---|
| `calendar` | параметр запроса | — |
| `event_id` | id события Google | — |
| `plan_id` | строка `event_plan` по маркеру `svoi_event_id` | `null` (людское событие) |
| `letter` | буква типа: `svoi_kind` → строка типа из настройки; иначе метка `[X]` из `summary` → тип по букве | `null`, на экране «Без типа» |
| `kind` | код типа (`calendar_event_type.code`) по тому же порядку | `null` |
| `kind_title` | `calendar_event_type.title` | `"Без типа"` |
| `title` | `summary` без метки `[X]` (снимается один ведущий маркер) | пустая строка → на экране «Без названия» |
| `title_raw` | `summary` как есть | равен `title` |
| `color_id` | `colorId` события Google | `null`, нейтральная плашка и слова «цвет не задан» |
| `start`, `end` | `start.dateTime`/`end.dateTime`; при `date` — границы дня | — |
| `all_day` | `true`, если у события `start.date` | `false` |
| `date`, `weekday` | из `start` в `Europe/Samara` | — |
| `time_from`, `time_to` | из `start`/`end`; при `all_day` — `null` | при `all_day` строки времени нет |
| `location` | `location` события Google; если пусто — `venue.name` по `event_plan.location` | `null`, строки места нет |
| `creator` | `event_plan.created_by` → `participant.display_name` | `null`; на экране «создано в Google» |
| `description` | `description` события Google | `null` или пустая строка — строки описания нет |
| `state` | `cancelled` при `status=cancelled`; иначе `draft` при `calendar=draft`, `live` при `calendar=read` | — |
| `editable` | см. §3.3 | — |
| `not_editable_reason` | `human_event` \| `live_calendar` \| `cancelled` \| `not_your_event` \| `plan_missing` | `null`, когда `editable` истинно |

Правило «пусто — строки нет» относится ко всем необязательным полям одинаково: `null` или пустая
строка в ответе означает, что экран **не рисует строку**, а не рисует подпись с пустым значением.

### 3.3. `editable` и перенос

| Случай | `editable` | Причина | Что на экране |
|---|---|---|---|
| Черновое событие бота, строку базы нашёл `_can_move(plan, who)` | `true` | — | кнопка «Перенести» |
| Событие бота, но переносить не вправе | `false` | `not_your_event` | кнопки нет, текст «Переносит создатель события или администратор» |
| Событие в боевом календаре (`calendar=read`) | `false` | `live_calendar` | текст «Событие в боевом календаре — правьте в Google» (`186` §8, строка 8) |
| Людское событие (`plan_id` = `null`) | `false` | `human_event` | текст «Событие создано в Google — правьте там» |
| Отменённое (`status=cancelled`) | `false` | `cancelled` | текст «Событие отменено» |
| Маркер `svoi_event_id` есть, строки в базе нет | `false` | `plan_missing` | текст «У события метка бота, но строки в расписании нет — сообщите администратору» |

`_can_move(plan, who)` — это существующая проверка переноса `events.py:659–665` («создатель или
администратор»), вынесенная в одну функцию и используемая **и** в карточке, **и** в
`POST /tools/events/move`. Роль-зависимая часть (`t_4d081225`) меняет эту функцию в одном месте —
карточка не может показать кнопку, которая получит 403.

**Перенос — единственное действие первой версии.** Экран: дата, часы «с/до», длительность
сохраняется. Запрос — существующий `POST /tools/events/move` с `{"event_id": plan_id, "date":
"YYYY-MM-DD", "from_hour": 19, "to_hour": 21}` (`events.py:642`). Ответы, которые экран обязан
показать словами:

| Код | HTTP | Текст на экране |
|---|---|---|
| `slot_taken` | 409 | «Зал занят в это время — выберите другое» |
| `not_your_event` | 403 | «Переносит создатель события или администратор» |
| `event_cancelled` | 409 | «Событие отменено — переносить нечего» |
| `outside_working_hours` | 400 | «Вне рабочих часов: с 08:00 до 23:00» |
| `bad_interval` | 400 | «Конец раньше начала» |
| `calendar_unavailable` | 502 | «Календарь недоступен — время изменено в расписании, повторите позже» |

Если перенос прошёл в базе, но не в Google (`in_calendar: false`, `calendar_error` не пуст),
экран пишет «Время изменено в расписании; в календарь записать не удалось» — молчаливого
успеха нет. Отмена, состав, замена педагога — вторая версия карточки (`157` §E5), вне этой карты.

### 3.4. Ошибки карточки

| Код | HTTP | Когда |
|---|---|---|
| `bad_calendar` | 400 | `calendar` не `draft`/`read` |
| `event_id_required` | 400 | нет `event_id` |
| `event_not_found` | 404 | `events.get` в указанном календаре не нашёл событие |
| `calendar_id_missing` | 503 | id календаря не задан в конфигурации |
| `calendar_unavailable` | 502 | `events.get` упал (сеть, 401/403, 5xx) |
| `no_access` | 403 | нет права `schedule.read.all` |

Конверт — `app/errors.py` (`code` + `request_id`), тексты — словами, как в §3.3.

## 4. Список событий окна

Сейчас список календаря у чата — `GET /tools/calendar/events?days=7&draft=false`
(`events.py:855`): `timeMin=now`, `timeMax=now+days`, `maxResults=100`, без `pageToken`.
444–446 событий года так не листаются, а «вперёд от сейчас» не показывает месяц назад.

**Решение: свой эндпоинт для Mini App, контракт чата не меняется.**

```
GET /webapp/events/list?calendar=draft|read&from=YYYY-MM-DD&to=YYYY-MM-DD
                       &page_token=<непрозрачный токен>&limit=50
```

| Параметр | Правило | Ошибка |
|---|---|---|
| `calendar` | обязателен, `draft`/`read` | 400 `bad_calendar` |
| `from`, `to` | обязательны, ISO-даты; `to ≥ from`; окно не больше 92 дней | 400 `bad_window` |
| `page_token` | как его вернул предыдущий ответ; хранится как есть | 400 `bad_page_token` |
| `limit` | 1…100, по умолчанию 50 | 400 `bad_limit` |

Ответ:

```json
{"ok": true, "calendar": "read",
 "from": "2026-11-01", "to": "2026-11-30",
 "count": 50, "total_scanned": 446,
 "next_page_token": "Cg0I...",
 "items": [{"event_id": "abc", "title": "Жизнь насекомых", "title_raw": "[С] Жизнь насекомых",
            "letter": "С", "kind": "show", "color_id": 11,
            "start": "...", "end": "...", "all_day": false,
            "location": "Сцена", "status": "confirmed", "has_plan": true, "plan_id": 412}]}
```

Правила:

1. Листание — по `nextPageToken` Google; сервер не собирает весь месяц в память и не отдаёт
   «всё за один раз». `next_page_token: null` — страниц больше нет.
2. `total_scanned` — сколько событий прочитано за все страницы текущего прохода; при листании
   он не обязан быть точным заранее, поэтому экран показывает «показано N» и не обещает общего числа.
3. `has_plan`/`plan_id` — по маркеру `svoi_event_id`; строки `event_plan` для `plan_id`
   читаются одним запросом на страницу (`where id = any(%s)`), не по одному.
4. Событие без `summary` отдаётся (`title_raw` пуст), потому что «пустое название» — факт,
   а не повод выкинуть строку.
5. Ошибки — те же, что у карточки (`calendar_id_missing`, `calendar_unavailable`, `no_access`).

Окно на экране «Сверить» — **календарный месяц**: `from` = первое число, `to` = последнее.
Стрелки «‹ месяц ›» меняют окно, список и отчёт сверки всегда смотрят на один и тот же месяц —
иначе строки отчёта и список под ними говорят о разных периодах.

## 5. Экран «Сверить» по календарю

### 5.1. Адрес, право, отказ словами

| Что | Значение |
|---|---|
| Экран | `/webapp/events/reconcile` (страница), маршрут — `pages/routes.py` по образцу `/webapp/reconcile` (`routes.py:143`) |
| Право | `schedule.read.all` — как в дизайне §9 п.3; у `master` оно есть, у `troupe` нет |
| Строка реестра | `SECTIONS`: ключ `events_reconcile`, название «Сверка календаря», подпись «что изменили в Google», сразу после `reconcile` («Сверка листов» остаётся своей) |
| Без права | кнопки нет, вместо неё фраза «Сверку календаря ведёт организатор» (образец — `misc_reconcile.py`, отказ 403 ведёт к тому же тексту) |

Смешивать со «Сверкой листов» нельзя: у неё право `budget.import` и другой предмет.

### 5.2. Что делает кнопка

1. При открытии экрана — `GET /tools/google/freshness`; берётся блок `calendar.read`.
   Заголовок показывает «данные от HH:MM» из `as_of`; при `stale: true` — плашка
   «данные могли устареть». Если `error` не пуст — вместо времени текст ошибки, прошлый снимок
   не подставляется.
2. Кнопка «Сверить» — `POST /tools/google/refresh`:

```json
{"sources": ["calendar.read"], "dry_run": true,
 "window": {"from": "2026-11-01", "to": "2026-11-30"}}
```

3. Пока идёт запрос — кнопка неактивна и подписана «Сверяю…»; повторное нажатие не отправляет
   второй запрос.
4. Ответ раскладывается по шести строкам §5.3; список событий окна под отчётом — из
   `GET /webapp/events/list` с тем же окном (§4).

**Правило «ничего не пишет» — и как оно уживается с очисткой черновика.** Дизайн §4 говорит
«ничего не пишет», а `186` §7 и карта E1-4 говорят, что `refresh` находит переносы и удаляет
черновик. Чтобы оба правила выполнялись одновременно, экран всегда посылает `dry_run: true`:
`refresh` в этом режиме **не делает ни одной записи** — не удаляет черновик, не пишет аудит об
изменениях, не правит базу, — а только возвращает найденное. Очистка черновика остаётся
поведением `refresh` без `dry_run` (её вызывает чат/следующая версия), и в отчёте экрана она
названа честно: «найден перенос; черновик не удалён — экран ничего не пишет».

### 5.3. Шесть строк отчёта

Источник всех строк — блок `sources["calendar.read"]` ответа `refresh` (§10, требование к E1-4).
Счётчики — `counts`, элементы — массивы (не больше 50 в каждом, остальное в `*_more`).

| Строка | Ключ | Что значит | Что на экране |
|---|---|---|---|
| Изменено в Google | `changed_in_google` | у события бота часы, название (без метки) или место в Google отличаются от базы | «в Google: 19:00, у нас: 20:00» — по каждому полю, которое разошлось; правку в базу не переносим (следующая версия) |
| Перенесено в боевой | `moved_to_live` | строка базы нашлась маркером в боевом календаре, а черновик ещё в черновом | «найден перенос: N; черновик не удалён — экран ничего не пишет» |
| Цвет не по типу | `color_mismatch` | `colorId` события ≠ цвет его типа из настройки | «цвет 8, у типа «Спектакль» — 11». Действия нет: возврат цвета — отдельная ветвь V-119 (§15) |
| Метка не по типу | `label_mismatch` | у события есть `svoi_kind`, а метка в `summary` отсутствует или указывает на другой тип | «в заголовке `[Р]`, тип — «Спектакль»»; правку заголовка не делаем (следующая версия) |
| Без типа | `untyped` | нет ни метки, ни `svoi_kind` | «событий без типа: N (из них людских — M)». Заставлять человека размечать чужие события бот не может |
| Не прочитано | `error` | календарь недоступен | текст ошибки по §5.4; остальные строки пусты, прошлый снимок не подставляется |

**Седьмая строка не заводится.** Случай «маркер бота есть, строки в базе нет» (`orphan_marker`)
показывается отдельной строкой **внутри** карточки «Изменено в Google»: «с меткой бота, но строки
в расписании нет — N». Это тоже расхождение календаря и базы, но отдельной категорией отчёта оно
не становится: шесть строк — решение дизайна, и раздувать их до семи значит менять решение молча.

Пустые состояния: у каждой строки при нуле — «нет», а не пустое место; «не прочитано» при
успешном чтении не рисуется вовсе.

### 6.2. `GET /webapp/events/types`

```json
{"ok": true, "can_edit": true, "mode": "transitional",
 "palette": [{"color_id": 1, "name": "Лаванда"}, … 11 записей],
 "types": [{"code": "rental", "letter": "А", "title": "Аренда", "color_id": 10,
            "sort_order": 10, "is_active": true}, …]}
```

- `types` — все строки `calendar_event_type`, включая неактивные (`is_active: false`), порядок —
  `sort_order, title`. Экран показывает неактивные отдельным блоком «Скрытые».
- `palette` — 11 цветов Google: `color_id` и русское название (`Лаванда`, `Шалфей`, `Виноград`,
  `Фламинго`, `Банан`, `Мандарин`, `Павлин`, `Графит`, `Голубика`, `Базилик`, `Помидор` —
  те же названия, что в комментарии `config/calendar-palette.yaml`). Шестнадцатеричные значения —
  константа оформления в `static/ui.css` (классы `.ev-color-1…11`), снятая с ответа Google
  `colors.get` при реализации; в спецификации они не фиксируются, чтобы не переписывать
  выдуманные значения.
- `mode` — `app_setting.google.mode`. Перекраска работает в обоих режимах (решение
  владельца V-120 б): в переходном пишет в черновой календарь (`calendar.draft`), в целевом —
  в боевой ключом `calendar.live`. Ключ записи боевого календаря объявлен в реестре
  `google_targets` и действует только при `google.mode == target`; в переходном `resolve`
  на нём отказывает `write_target_mode_refused`. Исключение из V-072 ограничено правкой
  `colorId` событий бота (I-7).

### 6.3. `POST /webapp/events/types`

```json
{"apply": "all" | "new",
 "types": [{"code": "rental", "letter": "А", "title": "Аренда", "color_id": 10,
            "sort_order": 10, "is_active": true},
           {"code": null, "letter": "К", "title": "Концерт", "color_id": 3,
            "sort_order": 60, "is_active": true}]}
```

Клиент присылает **весь список**; отсутствие существующего типа в списке ничего не удаляет
(удаления в первой версии нет, §14). `apply` обязателен: значение выбирает человек в диалоге,
значения по умолчанию у сервера нет.

| Поле | Правило | Ошибка |
|---|---|---|
| `code` | у существующего — как есть; у нового `null` | `code_unknown` 404 |
| `letter` | ровно одна заглавная кириллическая буква; уникальна среди типов | `letter_bad` 400, `letter_taken` 409 |
| `letter` (изменение) | у существующего типа буква **не меняется** | `letter_immutable` 409 |
| `title` | 1…40 знаков после `strip` | `title_bad` 400 |
| `color_id` | 1…11; у активного типа обязателен | `color_bad` 400, `color_required` 400 |
| `sort_order` | целое 0…9999 | `order_bad` 400 |
| `is_active` | `false` — тип скрыт из выбора при создании события, старые события сохраняют тип | — |
| `apply` | `all`/`new` | `apply_required` 400 |

**Код нового типа.** Буква и название — оформление, код — внутренний стабильный ключ. Для нового
типа сервер собирает код сам: латинская транслитерация названия (таблица 33 букв + `ё`
в `app/event_types.py`), нижний регистр, всё кроме `[a-z0-9]` → `_`, повторы `_` сжимаются,
обрезка до 32 знаков; при совпадении — суффикс `_2`, `_3`. Примеры: «Аренда» → `arenda`,
«Репетиция» → `repeticia`, «Проект» → `proekt`. Название можно переименовать — код не меняется.

**Сохранение идёт одной транзакцией.** Сначала проверяется весь список; любая ошибка — ответ
с `field` и `code` элемента, **ничего не сохранено**. Затем строки обновляются/вставляются,
пишется аудит `event_types.save` (`before`/`after` по изменённым кодам, режим `apply`).

### 6.4. Диалог перекраски (V-087, ответ владельца 15.11.2026)

Сохранение всегда спрашивает, режим за человека не запоминается:

```
Сохранить настройку?
Применить цвета к событиям, которые уже есть в календаре?
[ Перекрасить все ]  [ Только новые ]  [ Отмена ]
```

- Оба варианта равноправны, ни один не выбран по умолчанию; закрытие диалога = «Отмена», ничего
  не сохранено. Реализация — `tg.showPopup` с тремя кнопками; `showConfirm` не годится: в нём
  две кнопки (`pages/polls_edit_js.py:271` — пример `showConfirm`, не образец для этого диалога).
- «Только новые» — настройка сохраняется, ни одно событие не правится.
- «Перекрасить все» — настройка сохраняется, затем бот правит `colorId` **только у событий
  изменённых типов** и **только через реестр записи**: в переходном режиме — черновой
  календарь (ключ `calendar.draft`), в целевом — боевой (ключ `calendar.live`, решение
  V-120 б). События других типов и людские события без маркера не трогаются.
- Если перекраска упала на середине: настройка уже сохранена, ответ несёт `recolored` из
  `total`, экран пишет «Сохранено. Перекрашено N из M» и список ошибок; молчаливого частичного
  успеха нет.

### 6.5. Ответ `POST` и тексты

```json
{"ok": true, "saved": true, "recolored": 12, "total": 14,
 "failed": [{"plan_id": 412, "gcal_event_id": "abc", "error": "not_found"}],
 "failed_more": 0}
```

| Случай | Текст на экране |
|---|---|
| `apply=new`, сохранено | «Сохранено. Цвета применятся к новым событиям» |
| `apply=all`, все перекрашены (`recolored == total`) | «Сохранено. Перекрашено N из M» |
| `apply=all`, часть упала | «Сохранено. Перекрашено N из M; не удалось: K — <первая причина>» |
| `apply=all`, `total = 0` | «Сохранено. Событий изменённых типов в календаре нет» |

Отказа 409 `recolor_target_forbidden` больше нет (V-120 б): в целевом режиме тот же ответ
и тот же текст, что в переходном, — меняется только календарь, в который пишет бот.

**Порядок перекраски внутри запроса:**

1. Режим читается, но **не отказывает**: он выбирает календарь — `target` → ключ
   `calendar.live`, иначе → `calendar.draft` (V-120 б, I-7).
2. Проверка и сохранение настройки (транзакция, §6.3).
3. `changed = [code, …]` — коды, у которых изменился `color_id` (буква неизменяема, `title`/порядок
   на цвет не влияют).
4. `candidates` — `select id, gcal_event_id from event_plan where kind = any(%s) and gcal_event_id
   is not null order by starts_at`.
5. По каждому: `events.update(calendarId=<выбранный ключом реестра календарь>,
   eventId=<gcal_event_id>, body={"colorId": str(color)})`; адрес — `google_targets.resolve(...)`
   (`calendar.live` или `calendar.draft`), источника чтения (`read_id`) в адресе записи нет.
   Успех — `recolored +1`, ошибка — в `failed` (не больше 50 элементов, остальное в `failed_more`).
6. Аудит `event_types.recolor` со счётчиками и полем `calendar` (`live`/`draft`); в журнал не
   пишутся персональные данные.

Повторный прогон идемпотентен по результату: цвет тот же, дублей событий нет, настройка не меняется.

## 7. Модель данных

### 7.1. Таблица типов

```sql
create table calendar_event_type (
  code        text primary key check (code ~ '^[a-z][a-z0-9_]{1,31}$'),
  letter      text check (letter ~ '^[А-ЯЁ]$'),
  title       text not null check (char_length(btrim(title)) between 1 and 40),
  color_id    smallint check (color_id between 1 and 11),
  sort_order  smallint not null default 100 check (sort_order between 0 and 9999),
  is_active   boolean not null default true,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now(),
  updated_by  bigint references participant(id),
  -- активный тип обязан быть полным: без буквы его не узнать в заголовке,
  -- без цвета его нечем красить
  constraint calendar_event_type_active_complete
    check (not is_active or (letter is not null and color_id is not null))
);

create unique index ux_calendar_event_type_letter
  on calendar_event_type (letter) where letter is not null;
```

**Отличие от эскиза дизайна §8 и почему.** В дизайне `letter text not null unique` и
`color_id smallint check (...)` при `not null` у буквы. Так архивные `meeting`/`other` и тип
«проект» в таблицу не влезают: букв у них нет (V-080 назвал пять типов, `meeting`/`other`
отменены), а «проект» создаётся без цвета и «без выбранного цвета не сохраняется» (дизайн §5).
Отсюда: буква `null` у неактивного типа, частичный уникальный индекс, обязательность буквы и
цвета только у активного типа. Тип «проект» засевается неактивным — он есть, буква `[П]` за ним
закреплена, но выбрать его при создании события нельзя, пока организатор не назначит цвет.

## 10. Что требуется от карты E1-4 (`t_279e41d2`)

Эти требования записаны комментарием в карту E1-4; при расхождении документ `docs/development/186`
главнее тела карты, но не этой спецификации — здесь сказано, что именно нужно экрану E5.

1. **`POST /tools/google/refresh`** принимает, кроме `sources`, два необязательных поля:
   - `dry_run: bool` (по умолчанию `false`) — при `true` не выполняется **ни одной** записи:
     черновик не удаляется, база не правится, аудит об изменениях не пишется; найденное
     возвращается как отчёт;
   - `window: {"from": "YYYY-MM-DD", "to": "YYYY-MM-DD"}` — окно чтения; по умолчанию текущий
     календарный месяц в `Europe/Samara`.
2. **Блок `sources["calendar.read"]`** в ответе `refresh`: `calendar`, `window`, `as_of`, `stale`,
   `error`, `scanned`, `changed_in_google[]`, `moved_to_live[]`, `color_mismatch[]`,
   `label_mismatch[]`, `orphan_marker[]`, `untyped{total,human}`, `counts{}` — ключи и смысл
   по §5.3. Элементы массивов: `plan_id`, `gcal_event_id`, `title_google`, `title_db`,
   `start_google`, `start_db`, `location_google`, `location_db`, `letter`, `expected_letter`,
   `color_id`, `expected_color_id`, `kind`, `draft_event_id`, `svoi_event_id` (только нужные
   для своей категории; лишние не обязательны).
3. **Листание**: `refresh` читает окно постранично (`nextPageToken`), а не одним `maxResults=500`:
   окно месяца может быть больше одной страницы.
4. **`GET /tools/google/freshness`** отдаёт блок `calendar.read` с `as_of`, `last_edit_time`,
   `stale`, `error` (`186` §7). Форма уже описана, менять не нужно — только гарантировать ключ.
5. **Контракт `GET /tools/calendar/events`** (чат) не меняется: `days`, `draft`, те же поля.

Пока E1-4 не сделана, экран «Сверить» выпустить нельзя: в коде нет ни `refresh`, ни `freshness`.

- **Удаление типа не делаем:** в первой версии есть только `is_active=false` («скрыть»).
  Жёсткое удаление «только у типа без событий» (дизайн §5) — отдельная карта: в макете кнопки
  удаления нет, а правило требует проверки, которая без кнопки недостижима.
- **Перекраска 446 событий и миграция боевого календаря** — V-081, не эта карта.
- **Отмена, состав, замена педагога в карточке** — вторая версия (`157` §E5).
- **Чат-контракты** `/tools/events/{id}`, `/tools/events/move`, `/tools/calendar/events` не
  меняются (кроме `summary` с меткой при создании).
- **Палитра YAML и скрипт заполнения черновика** остаются, продуктовыми модулями не читаются;
  их удаление — после перехода в целевой режим.
