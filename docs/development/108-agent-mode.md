# 108. Агентный режим свободного текста: `/tools/agent/ask`

**Статус:** реализовано в коде и тестах 01.11.2026; живой замер на золотом наборе из 30 вопросов
выполнен: **30/30 = 1.0** при пороге 0.8 (`openai/gpt-4o-mini`), разбор прогонов и правки — в §6.
Порог 0.8 пока предложен, а не утверждён владельцем.
Продолжение `docs/development/87` (агент по файлам) и `docs/archive/88-n8n-security-and-efficiency.md` (вывод n8n).

**Переключателя режима нет (Ш-12, 04.11.2026, решение П-1).** Команды `/agent` и
пользовательского режима больше нет: свободный текст всегда идёт в `POST /tools/agent/ask`,
а честный отказ агента — в каскад `POST /tools/route`. Это один путь с двумя разборами,
а не два режима. Вопрос по файлам задаётся обычной фразой (инструменты `list_files`
и `read_file`); отдельный «агент по файлам» (`POST /tools/agent/files`) остался без
входа из чата: это тонкая оболочка общего цикла — его судьба решается ревизией
маршрутов без потребителя (Ш-14).

## 1. Зачем

Свободный текст уходил в **один** вызов модели без инструментов. Модель отвечала из памяти:
не знала сегодняшнюю дату, не видела расписание, бюджет и файлы, не могла ничего проверить.
Отсюда дефект 01.11.2026 — «27 октября 2023 года» на вопрос «какой сегодня день» — и любые
выдуманные суммы.

Решение по форме (01.11.2026): агент живёт **внутри tool-api**, а не отдельным Hermes-сайдкаром.
Причины: у tool-api уже все инструменты, права и конверт ошибок; второй рантайм — это второй
деплой, 1–2 ГБ памяти на VPS, секунды на старт сессии и агент с терминалом в контуре, который
читает пользовательский текст.

## 2. Контракт `POST /tools/agent/ask`

Запрос:

```json
{"text": "какой сегодня день", "chat_id": 123, "correlation_id": "..."}
```

Ответ (всегда 200; `ok` смотреть явно):

```json
{"ok": true, "engine": "agent", "answer": "Сегодня 01.11.2026, воскресенье, 13:05.",
 "scenario": "assistant",
 "steps": [{"step": 1, "tool": "now", "ok": true, "latency_ms": 12}],
 "step_count": 1, "tokens": 210, "latency_ms": 1400, "model": "openai/gpt-4o-mini",
 "propose": null, "tools_available": ["now", "read_schedule", "..."]}
```

* `propose` — намерение записи: `{tool: "budget.tx", args: {...}, human_text: "..."}`.
  Агент **не пишет** в БД, листы и календарь. Бот показывает карточку с кнопкой,
  запись делает детерминированный эндпоинт после нажатия. Поэтому «предложил» и
  «учтено» — разные события.
* `engine: "rules"` + `degraded: {reason}` — ответ по правилам, модель не участвовала.
* `ok:false` — честный отказ (`empty_text`, `step_limit`): бот уходит на маршрутизатор
  и кнопки.

## 3. Пределы (код, а не просьба в промпте)

| Предел | Значение | Переменная |
|---|---|---|
| Шагов ReAct | 4 (1..6) | `AGENT_MAX_STEPS` |
| Общий таймаут | 15 с (3..60) | `AGENT_TIMEOUT_SECONDS` |
| Бюджет токенов на запрос | 6000 | `AGENT_TOKEN_BUDGET` |
| Модель агентного шага | `LLM_MODEL`, если не задана своя | `AGENT_MODEL` |
| Классификатор сценария | та же модель, но отдельно выбирается | `AGENT_CLASSIFIER_MODEL` |
| Внешний поиск | выключен | `AGENT_WEB_SEARCH`, `AGENT_WEB_SEARCH_URL` |

Классификатор — дешёвый вызов без инструментов: он только подсказывает сценарий
(`budget|schedule|dues|assistant`) и не влияет на факты. Выбор моделей — по замеру, не по цене.

В системный промпт подставлена серверная дата `core.now()` (ДД.ММ.ГГГГ, день недели, год):
так модель не достраивает год из памяти. Это не отменяет правило «дата — из `now`»: вопрос
про сегодня проверяется вызовом инструмента, и в замере такой ответ без `now` считается плохим.

## 4. Реестр инструментов первого этапа

Две части, каждая со своей ответственностью (карта A-2):

* `services/tool-api/app/agently/registry.py` — **политика**: тип `Tool`
  (`name`, `json_schema`, `requires`, `read_only`, `handler`), закрытый список `TOOLS`,
  фильтр `available_tools(who)`, схема `tool_schemas(who)` и `execute` с повторной
  проверкой прав;
* `services/tool-api/app/agently/tools.py` — **чтение данных**: сами обработчики.
  В этом файле нет ни одной записывающей команды и ни одной функции записи.

Путь `app/agent/tools.py` из карты A-2 не создан намеренно: `app/agent.py` — отдельный
модуль агента по файлам (`docs/development/87`), и каталог `app/agent/` с ним не
сосуществует в одном пакете. Реестр агентного режима живёт в `agently/`.

| Инструмент | Что отдаёт | Право |
|---|---|---|
| `now` | дата, время, день недели по Самаре | любому |
| `read_schedule` | ближайшие события (7 дней по умолчанию) | свои; все — `schedule.read.all` |
| `read_availability` | свои часы; сводка «кто свободен» — `schedule.read.all` | свои / `schedule.read.all` |
| `read_budget` | итоги месяца и последние операции | `budget.read` |
| `read_dues` | свои взносы; сводка по студии — `budget.read` | `budget.read.self` / `budget.read` |
| `list_files` | имена, размеры, папки (без содержимого) | свои |
| `propose_budget_tx` | намерение записи, **без записи** | `budget.write` |
| `web_search` | внешний поиск, если включён флагом | любому |

> Раздел ниже (§9) заменяет строку `list_files` и добавляет задачные инструменты:
> актуальный состав — `list_files`, `read_file`, `find_slots`, `propose_event`,
> `propose_note`, `propose_move` (05.11.2026).

Права проверяются дважды: инструмент без права не попадает в схему для модели и
отвергается `execute` на сервере (`forbidden`). «Спрятать в промпте» недостаточно.
Человек без `budget.read` не видит `read_budget` в `tool_schemas(who)` и получает
`forbidden` на прямой вызов — это проверяется без базы, на подставном `who`.

Сетка занятости по часам — это `read_availability` (кто свободен, кто занят), а
`read_schedule` отдаёт события. Внешний xlsx-файл сетки агент не читает: `list_files`
показывает только имя, размер и папку, а `read_file` читает текст скачанного файла
(`docs/development/87`).

Пишущих инструментов нет: все `read_only=True`, и `execute` отказывает
(`write_tool_disabled`) любому инструменту, объявленному пишущим, даже если он попал
в реестр. Отсутствие записи проверяется разбором `tools.py`, а не обещанием:
`tests/unit/test_agent_tools.py` (18 проверок) читает модуль и требует, чтобы каждый
SQL-литерал был командой чтения, а из `files_store` звались только `search` и
`list_files`. Критерий карты «`grep -rn "def .*write\|insert\|update" .../tools.py`
пусто» проверяется тем же тестом.

`web_search` выключен по умолчанию (`AGENT_WEB_SEARCH` не задан): внешние ответы не
подменяют данные студии. Включённый флаг без `AGENT_WEB_SEARCH_URL` даёт честный
`web_search_unavailable`, а не выдуманные ссылки.


## 5. Деградация

Нет ключа, провайдер недоступен, таймаут или исчерпан бюджет токенов → `loop.ModelUnavailable`
→ ответ по правилам (`engine: "rules"`): дата из `core.now()`, сумма и категория — из
детерминированного разбора `rules`, иначе — подсказка кнопками с причиной. Человек не видит
«Думаю…» навсегда и не получает выдуманных чисел.

## 6. Наблюдаемость и замер

* **Журнал разбора (A-5).** Агентный ответ пишет две вещи: `llm_usage` (intent `agent`)
  и строку `intent_log` — вопрос, ответ, шаги (`steps`: инструмент, аргументы, `ok`,
  ошибка, мс), число шагов, токены, латентность и итоговый статус `agent_status`
  (`answer` / `proposal` / `refusal`). Колонки добавлены миграцией
  `db/init/048_agent_observability.sql`; старые поля не переименовывались, каскад
  интентов пишет в ту же таблицу как раньше. Аргументы обезличиваются на записи
  (`services/tool-api/app/masking.py`): токены, пароли, `authorization`, телефоны,
  почты и `participant_id`/`chat_id` уходят под маску, а имя инструмента и обычные
  аргументы (период, сумма, категория) остаются — по ним и виден вызов. На чтении
  маска применяется второй раз: для строк, записанных до её появления.
* **Экран разбора.** `/webapp/admin/t/agent` (`GET /webapp/admin/agent`) — последние
  50 сессий: вопрос, шаги с именами инструментов, ответ, время, токены и мс; нажатие
  на строку открывает сессию целиком с аргументами. Право — `admin.panel` (журнал
  хранит тексты вопросов людей), остальным 403. Выборка идёт по `agent_status is not null`,
  поэтому строки каскада интентов (docs/21) в неё не попадают; `v_intent_gaps` и
  `v_top_unmatched` наоборот исключают агентные строки — иначе «модель разобрала»
  считала бы сессии, которые категорий не выбирают. Тот же фильтр (`agent_status is null`)
  стоит в отчёте `scripts/intent_report.py` (`show_gaps`): без него каждая деградация
  агента к правилам поднимала бы «правила разобрали» и «потеряно» — очередь доработки
  словаря показывала бы неправду.
* **Ретенция.** Общая с журналом интентов: `scripts/intent_report.py --purge` (cron
  `scripts/cron/purge_intent.py`) удаляет строки старше 90 дней целиком, вместе с шагами —
  отдельной таблицы нет, расти безгранично нечему.
* Золотой набор: `tests/fixtures/agent_questions.json` — 30 вопросов из обращений и падений.
* Замер: `scripts/check_agent_questions.py --chat-id <id>` (живой провайдер). Проверки
  детерминированные: ожидаемый инструмент, обязательные подстроки (дата считается на момент
  прогона), запрет выдуманного года, `propose` вместо записи, неизменность `budget_tx`.
* **Состояние замера 01.11.2026 (после добавления `LLM_API_KEY`):** живой прогон
  `openai/gpt-4o-mini` — **30/30 = 1.0** при пороге 0.8 (`agent_live6.json`).
  Более ранние прогоны на той же ветке: 20/30 = 0.667, 25/30 = 0.833, 28/30 = 0.933,
  27/30 = 0.9 — каждый разбор дал конкретный дефект, который исправлен в коде:
  1. формат даты «1 ноября 2026» вместо «01.11.2026» → промпт требует ДД.ММ.ГГГГ,
     проверка принимает равнозначные записи (`_date_forms`), смысл — дата из `now`;
  2. «октябрь 2023 года» вместо «ноябрь 2026» → в промпт добавлена серверная дата
     (`core.now()`), инструменты `read_budget`/`read_dues` отдают `period_human`,
     а ответ с годом, которого нет в данных инструментов, переписывается один раз
     (`_correct_stray_years`) и всё равно ловится проверкой замера;
  3. `step_limit` на повторных вызовах одного инструмента → повтор с теми же
     аргументами отдаётся из кеша шага, а после лимита шагов ответ достраивается
     без инструментов (`_final_answer`);
  4. «не удалось записать, категория не из списка» → модель получает закрытый список
     категорий в промпте, а `propose_budget_tx` возвращает `allowed_categories`;
     если модель всё равно не предложила запись, карточку собирает детерминированный
     разбор `rules` (сумма и направление в тексте есть — предложение обязано быть);
  5. `provider_timeout` под нагрузкой провайдера → в замере одна повторная попытка,
     чтобы сетевой сбой не считался плохим ответом (в продукте это деградация к
     правилам, см. §5).
  Стенд отдельно проверяется `--transport scripted`: **30/30 = 1.0** (не замер модели).
  Порог 0.8 остаётся предложенным: цифра 1.0 его перекрывает, но сам порог —
  решение владельца.

## 7. Что не входит в этап

* Запись агентом: БД, листы, календарь — недоступны; только предложение и кнопка.
* Кнопки, формы и подтверждения остаются интерфейсом бота: агент их не заменяет.
* ML-модели не обучаем.
* Реестр A-2 (`t_92b97d87`) уточнил схемы и права инструментов и вынес политику
  (`registry.py`) и чтение (`tools.py`) врозь; проверки — `tests/unit/test_agent_tools.py`.
  A-5 — журнал и экран разбора.

## 8. Подтверждение записи: агент предлагает, код исполняет (A-3)

Агент не пишет в базу, листы и календарь. Между «модель предложила» и «деньги учтены»
стоят три вещи: карточка в чате, одноразовый токен и обычный эндпоинт записи.

| Шаг | Где | Что происходит |
|---|---|---|
| предложение | `/tools/agent/ask` → `propose: {tool, args, human_text}` | инструмент `propose_budget_tx` проверил категорию, сумму и дату; в БД бюджета ничего нет |
| токен | `POST /tools/agent/propose` | `agent_proposal` получает строку `pending`, ответ — `token`, `ttl_seconds: 300` |
| карточка | `services/tg-gateway/app/texts.py` | «Агент предлагает записать операцию», сумма, категория, дата, статья; кнопки «Подтвердить» / «Отмена» |
| запись | `POST /tools/agent/confirm` → `budget_commit` | тот же код, что у формы, и то же право `budget.write`; ключ идемпотентности `agent:confirm:<token>` |
| отмена | `POST /tools/agent/cancel` | операций нет, отказ в `audit_event` |

Правила, которые держат форму:

1. **Токен — единственный ключ к записи.** Он привязан к чату, к человеку и к уже
   проверенным аргументам; аргументы из чата не принимаются вовсе.
2. **Срок 5 минут.** Позже — `token_expired`, статус `expired`, дубля нет: человек
   просит заново, а не подтверждает устаревшую карточку.
3. **Один раз.** Токен забирается атомарно (`update ... where status = 'pending'`);
   повторное или параллельное нажатие получает `token_used`, а второй операции не
   появляется — даже на уровне базы (`on conflict (idempotency_key) do nothing`).
4. **Права те же, что у формы.** Подтверждение закрыто зависимостью
   `core.require("budget.write")` — той же, что стоит на `/tools/budget/commit`;
   человек без права не получает и карточки (gateway проверяет до запроса токена).
5. **Журнал.** `agent.propose` (кто просил, что предложено, до какого часа),
   `agent.confirm` (кто подтвердил, какая операция записалась), `agent.cancel`
   (отказ человека) и `agent.confirm.refused` (истёкший или уже использованный
   токен) — всё в `audit_event`, append-only.
6. **Никакого второго пути записи.** `/tools/agent/confirm` не вставляет операцию
   сам: он вызывает `budget_commit` — тот же код, что у формы и у Mini App.

Миграция — `db/init/049_agent_confirmation.sql` (номер 049, потому что 048 занят
картой A-5 в отдельной ветке). Проверки: `tests/integration/test_agent_confirm.py`
(токен, одна операция, повтор, истечение, отмена, отсутствие права) и
`tests/unit/test_gateway_agent_confirm.py` (карточка, кнопки, тексты).

Что осталось за границей этапа: подтверждение других действий (перенос события,
занятость) подключается добавлением вида в `PROPOSE_TOOLS` и своего эндпоинта записи;
экран истории предложений в Mini App не делался.


## 9. Полнота предложений: реестр функций (t_09672cea)

Агент знал только свои инструменты, а человек — только кнопки: на вопрос «что можно
записать/посмотреть» ответ собирался из памяти модели и не совпадал с тем, что есть
в приложении и боте. Теперь предложение действия строится из закрытого реестра.

* `config/agent-features.yaml` — **реестр функций**: экран Mini App или кнопка чата →
  `tool` (инструмент из `registry.TOOLS`), `capabilities` (пункт «Что умею») либо
  `not_for_agent` с причиной. Продуктовые подписи кнопок не переписаны: `source` —
  их текущий текст. Поверхности: `webapp` (экраны и старые адреса-редиректы из
  `pages.routes.build_router`), `menu`, `quick`, `panel` (админ-панель) и `chat`
  (кнопки в обычных сообщениях: `/start`, подсказка о вводе, фолбэк).
* `services/tool-api/app/agently/features.py` — загрузка и проверка реестра,
  `features_for(who)` (фильтр по правам через `registry.available_tools`),
  `human_capabilities(who)` (детерминированный список действий),
  `prompt_block(who)` (та же выборка для системного промпта) и
  `answers_capability_question(text)`.
* **Ответ на вопрос о возможностях — детерминированный.** Вопросы «что ты умеешь»,
  «что можно записать», «что можно посмотреть», «какие действия доступны» ловятся
  до вызова модели (`loop.run` и `rules_answer`) и получают `human_capabilities(who)`:
  запись отделена от чтения, запись — только «после вашего подтверждения кнопкой»
  (A-3), выдуманных экранов и кнопок нет. В `intent_log` такая строка пишется
  с `source = rules`, а не «разобрала модель».
* **Системный промпт** получает `prompt_block(who)`: модель видит закрытый список
  действий этого человека и правило «другие не предлагай; если не умеешь — скажи
  „Пока не умею“ и перечисли доступное».
* **Просьба о недоступном действии — тоже детерминированный ответ.** Запрос,
  начинающийся с «перенеси / отмени / удали / измени / поменяй / сдвинь», получает
  честное «Пока не умею: … это делает человек в Mini App» и список доступного
  (`features.asks_unsupported_action` / `unsupported_action_answer`). Без этого
  модель на «перенеси репетицию» читала расписание и отвечала «помогу с переносом» —
  то есть обещала действие, которого нет (замер 02.11.2026 дал 9/10 именно на этом).
* **Тест покрытия.** `tests/unit/test_agent_features.py` собирает экраны из
  настоящего роутера, подписи `MENU_ACTIONS` / `DIALOG_CONTROLS` / `panel_rows(["*"])`
  и кнопки чата из двух списков, которые использует сам бот:
  `keyboards.CHAT_BUTTONS` и `routers.menu.CHAT_ACTION_BUTTONS`.
* **Сторож читает исходники, а не только списки.** `tests/unit/button_scan.py`
  разбирает `services/tg-gateway/app/routers/menu.py` и `keyboards.py` целиком и
  достаёт подписи в любом виде: пару `(подпись, колбэк)` в строке клавиатуры (в том
  числе с вычисляемым колбэком `("Изменить", "form:" + kind)` и внутри спискового
  включения), `InlineKeyboardButton(text=…)`, `KeyboardButton(text=…)`,

  тип операции, общий построитель строк), обязана быть описана в разделе `scenarios`
  реестра с причиной — иначе тест падает. Обе стороны проверяются: кнопка без записи
  и запись без кнопки. Проверено пробами: `("Новый раздел", "sar:new")` в `send_menu`,
  `("Поправить", "form:" + kind)` и `KeyboardButton(text="Новая кнопка")` роняют
  соответствующие тесты; откат — зелено. Так закрыт и прежний пробел: кнопка
  «Изменить» с вычисляемым колбэком раньше сторожу не была видна.
* **Кнопки вне объявленных списков внесены в реестр.** Формы и сценарии в

  «Открыть анкету») получили записи поверхности `chat` — с инструментом или

* **Замер.** `tests/fixtures/agent_features_questions.json` (10 вопросов) и

## 10. Модели, деньги и кэш (A-4)

Замер A-0 (`docs/reports/112`) показал, что модель надо выбирать по цифрам, а не по
цене, и что агентный цикл — это несколько вызовов на одно сообщение. Карта A-4
развела роли и поставила деньги под предел. Подробности и цифры — `docs/reports/113`.

### 10.1 Роли и конфиг

Выбор записан в `config/agent-models.yaml`, а не в коде и не в `.env`:

| Роль | Модель | Почему |
|---|---|---|
| `agent` | `openai/gpt-4o-mini`, `max_steps: 4` | 11/16 на классе `tool` — лучший результат, 13% неверных, p95 5,5 с, 14,59 ₽/1000 |
| `classifier` | `openai/gpt-4.1-nano` | дешёвый одиночный вызов (1,49 ₽/1000), ответ — одно слово сценария, инструменты не нужны |

Приоритет: переменная окружения (`AGENT_MODEL`, `AGENT_CLASSIFIER_MODEL`,
`AGENT_MAX_STEPS`) → файл → умолчание в коде. Файл читается при обращении с кэшем
по времени изменения: правка действует со следующего запроса. Битый или пропавший
файл не роняет сервис — работают умолчания, иначе опечатка в YAML молча уводила бы
агента в деградацию к правилам.

### 10.2 Дневной бюджет чата

`services/tool-api/app/agently/budget.py`. Считается по `intent_log` (A-5):
`sum(tokens)` и `sum(step_count)` по агентным сессиям (`agent_status is not null`)
за текущие сутки по Самаре. Пределы — в конфиге: 60 000 токенов и 100 шагов на чат
в сутки (≈ 55 и ≈ 52 сообщения по цифрам замера).

При исчерпании — ответ по правилам (`engine: "rules"`,
`degraded.reason: chat_tokens|chat_steps`, HTTP 200) и одна строка
«Дальше — по кнопкам.». Это не ошибка и не «Думаю…». Без `chat_id` бюджет считается
по человеку, без обоих — не применяется. Gateway (`menu.visible_answer`) для этих
причин ничего не дописывает: модель доступна, исчерпан дневной лимит разговора,
поэтому ложного «модель недоступна» и внутреннего кода человек не видит.

### 10.3 Кэш повторяющихся ответов

`services/tool-api/app/agently/cache.py`. Группы и TTL — в том же конфиге: дата/время
30 секунд, занятость 60; остальное не кэшируется (`default_ttl_seconds: 0`).
Кэшируются только ответы без `propose` — карточка подтверждения обязана появляться
заново. Ключ — чат (иначе человек) + нормализованный текст. Попадание пишется
в журнал `intent_log` источником `cache` (миграция 052), поэтому по журналу видно,
сколько ответов пришло без модели (экран разбора источник пока не отдаёт — отдельная
карточка Mini App); бюджет оно не тратит (`tokens = 0`, `step_count = 0`).

Что реально доходит до кэша:

* **Время** — «который час», «сколько времени»: идут к агенту и повтор берётся из
  кэша. «Какое сегодня число» отвечает gateway из календаря ещё до агента: ноль
  вызовов модели, поэтому кэш там не нужен и не заявляется.
* **Занятость** — «кто сегодня занят», «кто свободен», «занятость на сегодня»:
  правило `availability_q` в `routing.py` отличает вопрос от ввода своих данных,
  пропускает его к агенту (`read_availability`), и повтор в течение 60 секунд
  берётся из кэша. «Занят 28.10 с 10 до 14» по-прежнему уходит в форму.

### 10.4 Порядок проверок и деградация

`/tools/agent/ask`: кэш → квота человека → бюджет чата → ключ провайдера → цикл.
Причины деградации — закрытый список: `llm_unavailable`, `provider_timeout`,
`llm_error`, `token_budget`, `chat_tokens`, `chat_steps`.

### 10.5 Стоимость 1000 сообщений

`scripts/agent_cost.py` считает цену по сохранённому прогону A-0: измеренные
`tokens_in`/`tokens_out` × цены из конфига × курс ЦБ. Цифры — в `docs/reports/113`
(14,59 ₽ за 1000 сообщений у `gpt-4o-mini` в агентном режиме против 2,38 ₽ у
одиночного вызова). Замер классификатора 04.11.2026 добавил режим `assistant`:
классификатор `gpt-4.1-nano` стоит 0,85 ₽/1000 (90,5 вход / 3,6 выход токена),
поэтому «классификатор + исполнитель» у `gpt-4o-mini` — 15,44 ₽/1000 (+5,8% к
чистому `agent`). `--check` сверяет расчёт с `docs/reports/113-agent-cost.json`,
чтобы цифры отчёта нельзя было переписать руками.

## 9. Задача: план, вход в дом и внешний поиск (05.11.2026)

Режим «Озадачить»: одна просьба, несколько инструментов подряд, итог «что сделал /
что не смог». Ниже — то, что добавлено к §2–§8; прежние правила не отменяются.

### 9.1 Один агент

Второго цикла с инструментами нет. Файловые инструменты (`list_files`, `read_file`
с цитатой и проверкой прав через `file_for_viewer`, `propose_move`) живут в общем
реестре `agently` (`agently/file_tools.py`), а `app/agent.py` — тонкая оболочка над
`agently.loop.run` для маршрута `/tools/agent/files`. Один лимит шагов, один учёт
токенов (`llm_usage`), одна трассировка (`intent_log`). Проверка — `tests/unit/
test_agent_single_loop.py`: `tool_calls` разбирается только в `agently/loop.py`.

### 9.2 Реестр: что добавлено

| Инструмент | Что делает | Право |
|---|---|---|
| `list_files` | имена, размеры, папки; поиск по слову | любому |
| `read_file` | текст файла с именем и цитатой; «в файле этого нет» — честный ответ | свои + общие (`file_for_viewer`) |
| `find_slots` | окна для репетиции/тренинга/аренды через `/tools/schedule/slots` | `schedule.slots` |
| `propose_event` | черновик события через `/tools/events/preview` | `schedule.write` |
| `propose_note` | черновик личной/общей заметки | `notes.write` |
| `propose_move` | черновик перемещения файла | свои файлы |
| `web_search` | SearXNG, только при `AGENT_WEB_SEARCH=1` | любому |

Записи по-прежнему нет: `propose_*` возвращает намерение, исполняет код по кнопке.
`needs_input` вместо догадки: если для действия не хватает даты, времени, участников
или суммы, инструмент возвращает `{error: needs_input, kind, missing}`, а петля
превращает это в `propose: {kind: "open", screen, text}`. Таблица экранов — одна
константа `proposals.OPEN_SCREENS` (`event → /webapp/assign`, `availability →
/webapp/week`, `note → /webapp/notes`, `budget → /webapp/tx`, `files →
`/webapp/files`, `slots → /webapp/slots`, `people → /webapp/people`). Два адреса —
редиректы: `/webapp/people` ведёт в «Управление → Люди» (`/webapp/admin/t/people`),
`/webapp/assign` — POST-эндпоинт назначения, и GET по нему открывает `/webapp/slots`;
`test_agent_task.py` проверяет живой GET каждого экрана, а не совпадение словаря.
Gateway рисует web_app-кнопку «Открыть приложение»; без адреса Mini App остаётся
текст, адрес не выдумывается.

### 9.3 Рамка задачи и план

* `POST /tools/agent/ask` принимает `task: true`: шагов 6–8 (`AGENT_TASK_MAX_STEPS`,
  по умолчанию 8) вместо 4, в системный промпт добавляется требование плана и итога.
  Девятый шаг не начинается: ответ `ok:false, error:step_limit`, «Не разобрался» —
  итог не достраивается (для обычного вопроса прежнее поведение сохранено).
* Несколько предложений в одной задаче — это план: `plan: {steps: [...]}`. Gateway
  показывает одну карточку «Выполнить план» (`/tools/agent/plan` → токен →
  `/tools/agent/plan/confirm`). Шаги исполняются по порядку, на каждый пишется
  `audit_event agent.plan.step`, исполнение останавливается на первой ошибке и
  называет шаг; частичный успех возвращается как есть (`done`, `total`,
  `failed_step`). Удалений в плане нет.
* Отмена: «Обнулить» (и «стоп», «остановись») → `POST /tools/agent/cancel-task`;
  флаг живёт в процессе tool-api (`agently/tasks.py`) и читается между шагами.
  Начало следующего вопроса флаг снимает.

### 9.4 Видимость работы

Одно сообщение «Работаю: смотрю данные…» с `typing`; итог ответа содержит строку
шагов (`step_line`: «календарь → занятость → окна»), построенную по фактическим
вызовам, а не по рассказу модели.

### 9.5 Внешний поиск: SearXNG

  настройки — `config/searxng/settings.yml` (форматы `html` и `json`, `limiter: false`),
  адрес только `127.0.0.1:8080`; в `.env.dev` — `AGENT_WEB_SEARCH=1`,
  `AGENT_WEB_SEARCH_URL=http://127.0.0.1:8080/search`. В compose адрес tool-api —
  `http://searxng:8080/search`, потому что `127.0.0.1` внутри контейнера — он сам.
