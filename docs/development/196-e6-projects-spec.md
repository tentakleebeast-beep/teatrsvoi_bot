## 2. Рамка: шесть решений, на которых держится всё остальное

**S-1. Одна сущность `project`, тип — поле.** Спектакль, мероприятие и арендатор — одна
таблица, один список, одна карточка. Новых таблиц E6 не заводит.

**S-2. Событие — источник дохода, операция — производная.** У доходного события есть
сумма; событие порождает ровно одну операцию (`unique (event_id)`). Ручного помесячного
ввода аренды нет.

**S-3. Сумма события — единственный источник (V-128).** Доплата, переплата и возврат
вносятся отдельными операциями по тому же `project_id` с `event_id = NULL`; они не спорят
с суммой события и не меняют её.

**S-4. Карточку проекта видят только `admin` и `org` по праву `budget.read` (V-127).**
Списка и карточки у `master`/`troupe` нет — ни строки в «Управлении», ни доступа к экрану,
ни данных. Доступ труппы к своим проектам без денег — не в MVP.

**S-5. Доход за помещение называется «Аренда (доход)» (V-126).** «Субаренда» переименована
в справочнике, «Аренда помещения» остаётся расходной статьёй. Старое имя читается как
алиас и не создаёт вторую категорию.

**S-6. Один метр — один ответ.** Числа карточки (план, факт, остаток) не хранятся: это
запросы по `budget_plan` и `budget_tx`. Второго места, где лежит «бюджет проекта», нет.

## 3. Модель данных

### 3.1. `project`: что добавляется

Существующее (`001:65–73`): `id`, `name` (уникально), `kind`, `status`, `starts_on`,
`ends_on`, `created_at`.

| Поле | Тип | Правило | Зачем |
|---|---|---|---|
| `description` | `text` | пусто допустимо; до 500 символов проверяет API | одна-две строки «что это» |
| `counterparty` | `text` | пусто допустимо; до 200 символов | арендатор или заказчик словами: имя, телефон. Он не участник и Telegram-доступа не имеет |
| `lead_participant_id` | `bigint references participant(id)` | `null` допустим: у проекта может не быть ведущего | один ответственный человек |

`kind` получает два новых значения: `event` (Мероприятие) и `rental` (Арендатор). Полный
список: `show`, `event`, `rental`, `course`, `training`, `other`. Три последних не
создаются в интерфейсе и остаются ради импортированных строк (`191` §4 п.2).

Правила типа и статуса (`191` §4):

1. Тип выбирается при создании. Смена типа разрешена только у пустого проекта — у
   которого нет ни одного `event_plan` и ни одной `budget_tx`; иначе `409 project_kind_locked`.
2. `name` уникально; переименование не меняет `id`.
3. `status`: `planned`, `active`, `archive`. Архив убирает проект из списка по умолчанию,
   но не трогает события и операции.
4. Ни одна миграция не угадывает тип существующего проекта — только расширяет допустимые
   значения (§3.6).

### 3.2. `event_plan.revenue_amount`

```sql
alter table event_plan add column if not exists revenue_amount numeric(12,2)
  check (revenue_amount is null or revenue_amount >= 0);
```

| Правило | Значение |
|---|---|
| Заполняется | только у событий проекта `kind='rental'` (аренда зала и показ арендатора) |
| Обязательность | при создании аренды или показа арендатора сумма обязательна: без неё `422 revenue_amount_required` |
| Зеркало в Google | `extendedProperties.private.svoi_revenue_amount` — лучшее усилие, как остальные маркеры (`186` §5) |
| Метка `revenue` | остаётся оформлением для человека и признаком в палитре; источник — тип проекта и `revenue_amount` в базе, а не строка свойства |

Сумма у события других типов допустима технически (колонка не различает тип проекта), но
API её не принимает: тип проверяется до записи (§4.5).

### 3.3. `budget_tx`: связь с событием и происхождение

```sql
alter table budget_tx add column if not exists event_id bigint references event_plan(id);
create unique index if not exists ux_budget_tx_event on budget_tx (event_id)
  where event_id is not null;

alter table budget_tx drop constraint if exists budget_tx_origin_check;
alter table budget_tx add constraint budget_tx_origin_check
  check (origin in ('bot', 'manual', 'import', 'event'));
```

| Правило | Значение |
|---|---|
| `event_id` | ставит только сервис дохода (`app/project_money.py`); клиент его не передаёт |
| `origin='event'` | признак производной операции; по нему операция узнаётся как производная |
| Одна операция на событие | частичный уникальный индекс: повтор не создаёт вторую строку (идемпотентность) |
| Удаление | запрещено (`docs/architecture/11` §5): отмена события переводит операцию в `reversed` |
| Правка руками | запрещена: `409 event_operation` (§7.4) |

### 3.4. `budget_plan.project_id`

```sql
alter table budget_plan add column if not exists project_id bigint references project(id);
alter table budget_plan drop constraint if exists budget_plan_period_block_category_id_key;
create unique index if not exists ux_budget_plan_project
  on budget_plan (period, block, category_id, project_id) nulls not distinct;
```

`project_id is null` — бюджет студии, как сейчас. `NULLS NOT DISTINCT` (PostgreSQL 16)
сохраняет прежнюю уникальность строк без проекта: две строки «студия, ноябрь, гонорары»
по-прежнему невозможны, а два проекта с одной статьёй в одном месяце — возможны.

**Решение: `075_projects_money.sql`, голова — этот файл.** После файла —
`scripts/gen_alembic_revisions.py`; `tests/unit/test_migrations_registry.py:51`:
`70` → `71` (или `72`, если `074` влит раньше — тогда голова `074`, а `075` идёт за ней).

Порядок с `074` не конфликтует: `074` меняет `event_plan.kind` (`check` → внешний ключ на
`calendar_event_type`), `075` добавляет туда только `revenue_amount` и не трогает `kind`.
Обе миграции — только `add column if not exists` и `create index if not exists`, поэтому
накат в любом порядке даёт одну схему.

Состав `075`:

1. `project`: два значения в `kind`, три колонки (§3.1).
2. `event_plan.revenue_amount` (§3.2).
3. `budget_tx.event_id`, уникальный частичный индекс, `origin='event'` (§3.3).
4. `budget_plan.project_id`, новая уникальность (§3.4).
5. Переименование статьи «Субаренда» → «Аренда (доход)» (§9).
6. `create or replace view v_invariant_checks` — I1–I8 **плюс** I11 и I12 (§8). Представление
   пересоздаётся в той же миграции: иначе проверка останется на старом составе, а I11/I12
   будут «объявлены и не проверяются» — ровно дефект I9/I10 (R-1 §10).

### 3.6. Разметка существующих строк (риск 1 из `191` §11)

Ни одна строка не размечается автоматически. Перед накатом на копии боевой базы считаются
три числа и пишутся в отчёт о накате:

| Что | Запрос | Что с этим делает карта E6-2 |
|---|---|---|
| проекты, созданные из операций (`_ensure_project` ставил `kind='show'`) | `select id, name from project order by id` | остаются `show`; тип правит человек в карточке, пока у проекта нет событий и операций |
| арендные доходы без проекта | `select count(*), sum(amount) from budget_tx where block='sublease' and project_id is null` | остаются без проекта; карточка их не считает, свод студии — считает как раньше |
| события аренды без проекта | `select count(*) from event_plan where kind='rental' and project_id is null` | остаются без проекта; I11 их не касается, потому что `revenue_amount` у них `null` |

Правило: миграция расширяет допустимые значения и не переписывает данные. Молчаливая
разметка «всё, что `show`, — спектакль» запрещена: она делает вид, что мы знаем тип проекта,
которого никто не задавал.

## 4. Контракты

Все четыре адреса — новые, в модуле `api/projects.py`. Конверт ответа — `app/errors.py`
(`code` + `request_id`). Форма проверки права — `core.webapp_actor` плюс

### 4.1. `GET /webapp/projects/data`

```
GET /webapp/projects/data?kind=all&status=active&q=<поиск>
```

| Параметр | Правило | Ошибка |
|---|---|---|
| `kind` | `all` (по умолчанию) или код типа: `show`, `event`, `rental`, `course`, `training`, `other` | 400 `bad_kind` |
| `status` | `active` (по умолчанию: `planned` + `active`), `archive`, `all` | 400 `bad_status` |
| `q` | подстрока имени, без регистра, до 100 символов; пусто — без фильтра | — |

Право — `budget.read`.

```json
{"ok": true, "count": 2, "items": [{
  "id": 3, "name": "Жизнь насекомых", "kind": "show", "kind_title": "Спектакль",
  "status": "active", "status_title": "активен",
  "starts_on": "2026-09-12", "ends_on": "2027-05-30",

              "time_to": "21:00", "kind": "rehearsal", "kind_title": "Репетиция"}

```

| Поле | Откуда | Если пусто |
|---|---|---|
| `kind_title` | словарь `191` §4: Спектакль, Мероприятие, Арендатор, Курс, Тренинг, Прочее | — |
| `status_title` | «активен», «запланирован», «в архиве» | — |
| `plan` | `sum(budget_plan.amount_planned)` где `project_id = p.id` и `status='planned'`, по всем периодам | `null` — «план не задан» (не `0`) |
| `fact` | `sum(budget_tx.amount)` где `project_id = p.id`, `status='confirmed'`, `is_plan=false` | `null` — «операций нет» |
| `nearest` | ближайшее `event_plan` по `project_id`, `status <> 'cancelled'`, `ends_at >= now()`, по `starts_at` | `null` — строки нет |

Порядок: активные по дате ближайшего события (без события — в конце), затем по имени;
архив — в конце даже при `status=all`. Числа считаются одним запросом с `group by`, не
по одному проекту (в списке бывает несколько десятков строк).

Право — `budget.read`. `id` обязателен и целый → иначе `400 id_required`;

```json
             "status": "active", "status_title": "активен",

             "description": null, "counterparty": null,
             "lead": {"id": 12, "name": "Мария"}},

   {"id": 412, "date": "2026-11-24", "weekday": "пн", "time_from": "19:00", "time_to": "21:00",

    "revenue_amount": null}]},
 "people": {"roles": [{"alias": "Наташа", "participant_id": 5, "name": "Саша Орлова"}],
            "roles_count": 2, "participants_count": 6},
 "rights": {"can_edit": true, "can_plan": true,
            "can_create_event": true, "can_create_rental_event": true}}
```

| Блок | Поле | Откуда | Если пусто |
|---|---|---|---|
| `project` | `lead` | `project.lead_participant_id` → `participant.display_name`; `null`, если нет | строки «Ведущий» нет |
| `money` | `plan` | `budget_plan` по `project_id`, `status='planned'` | `null`, на экране «План не задан» |
| `money` | `fact` | `budget_tx` `status='confirmed'`, `is_plan=false` | `null`, «Операций нет» |
| `money` | `rest` | `plan − fact` | `null`, если `plan` или `fact` = `null` |
| `money` | `expenses`, `income` | те же `budget_tx` по `tx_type` | `0.0` |
| `money` | `unlinked_income` | только для `kind='rental'`: `sum(amount)` где `block='sublease'`, `event_id is null`, `status='confirmed'` | `null` у других типов; `0.0`, если аренда без таких операций |

руками, остаётся возможной (`191` §6.2 п.3), но не выдаётся за доход события. У проекта
другого типа поле `null`, а не `0`: «не считали» и «ноль» — разные ответы.

### 4.3. `POST /webapp/project/save`

Право — `budget.write`. Создание и правка — одно действие, различие по `id`.

```json
{"id": null, "name": "Валерий", "kind": "rental", "status": "active",
 "description": "Арендатор зала по средам", "counterparty": "Валерий, +7 900 000-00-00",
 "lead_participant_id": 12, "starts_on": "2026-11-01", "ends_on": null}
```

| Поле | Правило | Ошибка |
|---|---|---|
| `id` | `null` — создание; иначе проект должен существовать | 404 `project_not_found` |
| `name` | обязателен, обрезается, 1…120 символов, уникален без учёта регистра | 422 `name_required`, 409 `project_name_taken` |
| `kind` | при создании обязателен, одно из `show`/`event`/`rental`; при правке — только у пустого проекта | 422 `bad_kind`, 409 `project_kind_locked` |
| `status` | `planned`/`active`/`archive`; по умолчанию `active` | 422 `bad_status` |
| `description`, `counterparty` | до 500 и до 200 символов, `null` допустим | 422 `too_long` |
| `lead_participant_id` | существующий активный участник или `null` | 422 `lead_not_found` |
| `starts_on`, `ends_on` | ISO-даты; `ends_on >= starts_on` | 422 `bad_dates` |

Ответ: `{"ok": true, "project": {…как в §4.2…}}`. Пишется аудит `project.save` с «было/стало»
по изменённым полям. `archive` обратимо: возврат в `active` — та же операция.

### 4.4. `POST /webapp/project/plan`

Право — `budget.write`.

```json
{"project_id": 3, "period": "2026-11", "block": "expense",
 "category": "Гонорары и доли", "amount": 120000, "note": ""}
```

| Правило | Ответ |
|---|---|
| `period` — `YYYY-MM` | 422 `bad_period` |
| `block` — `expense`, `show_income`, `show_cost`, `sublease`, `dues` | 422 `bad_block` |
| `category` разрешается через `_ensure_category` (направление сверяется с `block`) | 422 `category_direction` |
| `amount > 0` | 422 `amount_not_positive` |
| период закрыт (`budget_period.status='closed'`) | 409 `period_closed` |
| повтор той же четвёрки (период, блок, статья, проект) | обновляет `amount_planned`, не плодит строку |

Ответ: `{"ok": true, "plan": {"id": 12, "period": "2026-11", "block": "expense",
"amount": 120000.0, "project_id": 3}}`. Аудит `project.plan`.

Бюджет студии этой ручкой не правится: там `project_id` пуст, и для него остаётся прежний
путь (`/webapp/admin/dues`, лист). Иначе экран проекта стал бы вторым входом в общий план.

### 4.5. `POST /webapp/project/event`

Право — `schedule.write`; для проекта `kind='rental'` дополнительно `calendar.write`
(`191` §9.3). Это обёртка над существующим `events_assign` (`api/events.py:406`): карточка
пополняется `project_id` и `revenue_amount`, остальная логика назначения не дублируется.

```json
{"project_id": 3, "kind": "rental", "title": "Валерий", "date": "2026-11-26",
 "from_hour": 18, "to_hour": 21, "venue": "hall",
 "revenue_amount": 15000, "participant_ids": [], "discipline": null}
```

| Правило | Ошибка |
|---|---|
| проект существует и не в архиве | 422 `unknown_project` |
| `kind` допустим для типа проекта (`191` §4): `rental` → `rental`/`show`; `show` → `rehearsal`/`show`/`training`; `event` → любое, кроме `rental` | 422 `event_kind_not_allowed` |
| у проекта `kind='rental'` сумма обязательна и `> 0` | 422 `revenue_amount_required` |
| у проекта другого типа `revenue_amount` не принимается (игнорируется, в базу не пишется) | — |
| зал занят | 409 `slot_taken` |
| окно вне 08:00–23:00 | 400 `outside_working_hours` |

Ответ: `{"ok": true, "event_id": 512, "gcal_event_id": "abc", "in_calendar": true,
"operation_id": 1180, "notified": 2}`.

Порядок записи: строка `event_plan` со `revenue_amount` → событие в черновом календаре с
зеркалом `svoi_revenue_amount` → операция дохода (§7) → уведомления. Если операция не
записалась (ошибка БД), событие откатывается тем же переходом: доходное событие без
операции нарушает I11 и оставлять его нельзя.

## 7. Деньги: событие — источник, операция — производная

### 7.1. Что происходит с операцией

| Момент | Событие | Операция |
|---|---|---|
| Создание аренды или показа арендатора | `event_plan` со `revenue_amount`, `status='confirmed'`, событие в черновом календаре | одна строка `budget_tx` с `event_id`, `origin='event'` |
| Сумма не указана | создание отклоняется `422 revenue_amount_required` | — |
| Перенос на другую дату того же месяца | `starts_at`/`ends_at` меняются | `tx_date` и `period` пересчитываются, `rev+1`, аудит «было/стало» |
| Перенос в другой открытый месяц | то же | `tx_date`/`period` пересчитываются, при отсутствии `budget_period` нового месяца он создаётся |
| Перенос в закрытый месяц | отклоняется `409 period_closed`, `starts_at` не меняется | не меняется |
| Правка суммы события | `revenue_amount` меняется | `amount` той же операции, `rev+1`, аудит |
| Отмена события | `status='cancelled'` | `status='reversed'`; строка остаётся (удаление запрещено) |
| Повторная запись того же события | — | `unique (event_id)` не даёт второй операции |

### 7.2. Поля производной операции

| Поле | Значение |
|---|---|
| `block` | `sublease` для аренды зала, `show_income` для показа арендатора |
| `tx_type` | `income` |
| `amount` | `event_plan.revenue_amount` |
| `tx_date` | `starts_at::date`; `period` = её `YYYY-MM` |
| `category_id` | «Аренда (доход)» для аренды, «Продажа билетов» для показа арендатора |
| `project_id` | проект события (обязателен) |
| `event_id` | `event_plan.id` |
| `origin` | `event` |
| `purpose` | «Аренда — <проект> — <дата>» / «Показ — <проект> — <дата>» |
| `status` | `confirmed`; отмена события переводит в `reversed` |
| `rev` | `1` при создании, `+1` при каждой правке |
| Лист | строка пишется тем же протоколом, что остальные операции (`186` §4.3), best effort: сбой листа не отменяет запись |

### 7.3. Блок операции выводится из статьи

Сегодня блок считается только от `tx_type`: `{"expense": "expense", "income": "show_income"}`
(`api/budget.py:107, 252`). Значит ручной доход со статьёй «Аренда (доход)» попадёт в блок
«Показы — доход», а `v_period_totals` считает «Субаренду» отдельной колонкой
(`005:67–70`). Получились бы два ответа на вопрос «сколько мы получили за зал».

**Решение: одна функция `block_for(tx_type, category_name)` — и для базы, и для листа.**

| `tx_type` | Статья | `block` |
|---|---|---|
| `expense` | любая | `expense` |
| `income` | «Аренда (доход)» и её алиасы | `sublease` |
| `income` | любая другая | `show_income` |
| `transfer` | — | `expense` (как сейчас) |

Функция живёт в `api/budget.py` рядом с `_ensure_category` и используется в трёх местах:
`_write_tx` (107), `_append_tx_sheet` (252) и `_sheet_row`-путь (165). Пока их три, лист и
база не разъедутся — это ровно то расхождение, из-за которого появились пять копий `api()`
в JS.

### 7.4. Чего нельзя

1. **Производную операцию нельзя править руками.** `POST /tools/budget/commit` и
   `/webapp/tx/save` отвечают `409 event_operation`, если пришла попытка изменить операцию
   с непустым `event_id`; клиент `event_id` не передаёт вовсе — поле добавлено только для
   серверных путей.
2. **`scripts/reconcile.py` не правит производные строки.** Сегодня он переписывает
   `amount`, `tx_date`, `period` и ставит `origin='import'` (`reconcile.py:184–190`) — это
   уничтожило бы связь с событием и нарушило I11/I12 молча. Правило: строки с
   `event_id is not null` попадают в отчёт отдельной категорией «производная от события»,
   их сумма сверяется через I11, а не переносится из листа. То же для
   `scripts/read_finance_sheet.py:250–268`.
3. **Одна операция на событие.** Доплата, переплата, возврат — обычные операции по тому же
   `project_id` с `event_id = NULL`; они дополняют доход, а не спорят с ним.
4. **Доход без события остаётся возможным.** Старая практика «получила 15000 от Валерия»
   не ломается: операция не привязана к событию, карточка показывает её строкой «доход вне
   событий».
5. **Календарный черновик — не черновик денег.** Событие сразу `confirmed`, операция
   появляется вместе с ним.

**Следствие, названное честно.** Учёт кассовый (`docs/architecture/11` §1.1), а доход аренды
признаётся на дату события, а не на дату поступления денег. Если арендатор платит заранее,
баланс на дату платежа меньше банка; если позже — больше. Это решение владельца (FR-D17).

### 7.5. Закрытый период

`budget_period.status='closed'` сегодня только хранится: правил, которые бы отказывали в
правке закрытого месяца, в коде нет (`grep period_closed services/` — пусто). Спецификация
вводит правило:

| Действие | Открытый месяц | Закрытый месяц |
|---|---|---|
| перенос события (`/tools/events/move`) с `revenue_amount` | `tx_date`/`period` пересчитываются | `409 period_closed`, событие не двигается |
| план проекта (`/webapp/project/plan`) | строка создаётся или обновляется | `409 period_closed` |
| обычная операция рукой | как сейчас | как сейчас (правило закрытия — отдельная карта, E6 его не расширяет) |

Проверка одна на два пути: `_period_status(conn, period)` в `app/project_money.py`. Отказ
пишется в аудит `budget.period.refuse` — молчаливой правки закрытого свода нет.

### 7.6. Что видит бухгалтерия

Месячный свод не меняется: `v_period_totals`, `v_balance` и лист считают по блокам, проект —
дополнительная ось, а не новый баланс (`191` §7 п.5). Цифры студии после E6 те же, пока
аренды вводятся через события; расхождение покажет I11.

## 8. Инварианты I11 и I12

Добавляются в `v_invariant_checks` тем же переходом, что и таблицы (§3.5 п.6).

| Код | Инвариант | Что значит нарушение |
|---|---|---|
| **I11** | У каждого неотменённого события с `revenue_amount > 0` ровно одна `confirmed` операция `origin='event'` с `amount = revenue_amount` и `tx_date = starts_at::date`; у отменённого — ни одной `confirmed` | доход аренды разошёлся с календарём |
| **I12** | Операция `origin='event'` имеет `event_id`, а её проект — `kind='rental'` | арендатор попал в бюджет спектакля |

```sql
i11 as (
  select 'I11', 'Доход аренды сходится с событием',
         not exists (
           select 1 from event_plan e
            where coalesce(e.revenue_amount, 0) > 0 and e.status <> 'cancelled'
              and (select count(*) from budget_tx t
                    where t.event_id = e.id and t.origin = 'event'
                      and t.status = 'confirmed'
                      and t.amount = e.revenue_amount
                      and t.tx_date = e.starts_at::date) <> 1)
         and not exists (
           select 1 from event_plan e join budget_tx t on t.event_id = e.id
            where e.status = 'cancelled' and t.status = 'confirmed'),
         coalesce((select count(*)::text from event_plan e
                    where coalesce(e.revenue_amount, 0) > 0
                      and (select count(*) from budget_tx t
                            where t.event_id = e.id and t.origin = 'event'
                              and t.status = 'confirmed'
                              and t.amount = e.revenue_amount
                              and t.tx_date = e.starts_at::date) <> 1), '0')
           || ' событий без верной операции'
),
i12 as (
  select 'I12', 'Производная операция принадлежит арендатору',
         not exists (
           select 1 from budget_tx t
             left join project p on p.id = t.project_id
            where t.origin = 'event'
              and (t.event_id is null or p.id is null or p.kind <> 'rental')),
         coalesce((select count(*)::text from budget_tx t
                     left join project p on p.id = t.project_id
                    where t.origin = 'event'
                      and (t.event_id is null or p.id is null or p.kind <> 'rental')), '0')
           || ' операций не у арендатора'
)
```

`v_invariant_checks` пересобирается целиком: I1–I8 из `005:88–150` плюс I11 и I12.
Порядок строк — по коду, иначе `check_invariants.py` печатает таблицу вразнобой.

**Что не добавляется и почему.** I9 и I10 объявлены в `docs/architecture/11` §4, но в
представлении их нет (`191` §3 п.7). Их отсутствие — отдельная находка (R-1 §10), и чинить
её здесь нельзя: I9 — про долги и архивных участников, I10 — про `source` в ответах бота,
обе не относятся к проектам, а «заодно» расширять представление значит смешать две правки
в одной миграции.

## 9. Статья «Аренда (доход)»: переименование и алиасы

Решение V-126: «Субаренда» переименовывается, «Аренда помещения» остаётся расходной.
Переименование — одна строка данных и список мест, которые знают имя строкой.

**Миграция `075`:**

```sql
update category set name = 'Аренда (доход)'
 where name = 'Субаренда'
   and not exists (select 1 from category where name = 'Аренда (доход)');
```

Если «Аренда (доход)» уже есть (кто-то завёл руками), миграция молчит, а отчёт о накате
печатает число строк `category` с обоими именами: слияние двух статей — решение человека,
а не миграции.

**Алиас нужен потому, что имя статьи приходит строкой из трёх мест**: из текста чата
(`services/tg-gateway/app/parsers.py:68` отдаёт `"Субаренда"`), из старого импорта
(`scripts/import_finance.py:224`), из формы, где человек мог написать старое слово. Если
`_ensure_category` (`api/budget.py:71–87`) не узнает старое имя, он **вставит вторую
категорию** «Субаренда» — и I3 продолжит зеленеть, а доход разъедется по двум статьям.

**Решение: один словарь алиасов `app/category_alias.py`.**

```python
CANONICAL = {
    "субаренда": "Аренда (доход)",
    "аренда (доход)": "Аренда (доход)",
}
```

`_ensure_category` нормализует имя (нижний регистр, без ё, сжатые пробелы) и подставляет
каноническое до поиска в базе. Других мест, где имя статьи сравнивается строкой, не
заводится; `webapp_categories` отдаёт имена из базы как есть.

| Место | Что меняется |
|---|---|
| `db/init/015_categories_seed.sql:19`, `db/init/003_categories_v2.sql:31` | остаются как есть: чистая установка засевает «Субаренду», `075` переименовывает. Правка старой миграции запрещена — хэш ревизии (`test_migrations_registry.py`) |
| `db/init/075_projects_money.sql` | `update` выше |
| `services/tool-api/app/category_alias.py` | новый файл: канонические имена и алиасы |
| `services/tool-api/app/api/budget.py` | `_ensure_category` нормализует через алиас; `block_for` (§7.3) узнаёт статью по каноническому имени |
| `services/tg-gateway/app/parsers.py:68` | выдаёт «Аренда (доход)», ключевые слова («субаренд», «аренда») остаются |
| `scripts/import_finance.py:224,259` | новое имя в двух литералах |
| `tests/webapp/server.py:108` | список категорий стенда: «Аренда (доход)» |
| `tests/unit/test_text_to_draft.py:62,106` | ожидание и комментарий: доход за помещение — «Аренда (доход)», не «Аренда» и не «Субаренда» |
| `scripts/fill_budget_sheet.py:36,44` | **не меняется**: «Субаренда» здесь — заголовок колонки листа «Свод», а не имя категории. Правка заголовка сломает `header_checksum` привязки (`186` §4.2) |
| `scripts/build_reports.py:132` | то же: заголовок листа, не категория |
| `docs/architecture/10`, `25`, `30`, `40` | исторические упоминания; новые документы пишут «Аренда (доход)» |

Различие «имя категории» / «заголовок колонки листа» — не педантизм: первое живёт в базе и
меняется решением владельца, второе — в файле, который читает человек, и меняется вместе с
файлом, а не миграцией.
