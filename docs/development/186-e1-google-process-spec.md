## 0. Что и зачем

Дизайн 185 ответил «что читаем и куда пишем», но не ответил «как именно и что делать,
когда не получилось». Без этого реализация снова начнёт вычислять адреса листов сама,
как это уже случилось: `sheet_binding` и `row_map` объявлены в схеме с самого начала
(`db/init/001_schema.sql:258-295`), но **ни один модуль сервиса их не читает** — проверено
`grep` по `services/` (совпадения только в `scripts/reset_for_release.py` и
`scripts/db_schema_snapshot.py`). При этом бот сегодня правит и удаляет события в боевом
календаре (`api/events.py:519-533`, `627-641`), а дизайн D10 это прямо запрещает. То есть
проблема не в отсутствии контракта, а в том, что код живёт по другому контракту.

Эта карта фиксирует один контракт и называет расхождения с ним поимённо, с путями и строками.

### 2.2. Реестр (новое)

Один модуль `services/tool-api/app/google_targets.py`. Он не хранит идентификаторы, а
разрешает их из `Settings` и отвечает на два вопроса: «этот объект можно писать?» и
«каким клиентом его читать?».

```text
WRITE_TARGETS = {
  "budget.transactions":  sheet  ← budget_spreadsheet_id,     «Транзакции», layout flat_table
  "schedule.workload":    sheet  ← schedule_spreadsheet_id,   schedule_sheet_title, layout monthly_blocks
  "schedule.test":        sheet  ← schedule_test_spreadsheet_id, layout hour_matrix, meta hours 08..23
  "calendar.draft":       calendar ← calendar_id_draft
}
READ_SOURCES = {
  "schedule.human":   sheet  ← schedule_human_spreadsheet_id / schedule_human_sheet_title (живой лист)
  "budget.live":      sheet  ← finance_source_id (живой «СВОИ 2025»; адрес появляется с E4/импортом)
  "calendar.read":    calendar ← calendar_id_read
  "drive.root":       drive  ← drive_root_id
}
```

Правила модуля (проверяются тестом §12.1):

1. Ни один модуль сервиса не обращается к Google на запись, минуя `google_targets`: у
   каждой записи есть ключ, ключ обязан быть в `WRITE_TARGETS`, идентификатор берётся
   только из реестра.
2. Ключ, которого нет в реестре, — ошибка `write_target_refused` (403), а не «пустая строка».
3. Пустой идентификатор у ключа — ошибка `write_target_unset` (503) с текстом
   «объект записи не настроен», а не молчаливый пропуск записи.
4. Чтение живых источников идёт **read-only** клиентами (`drive.readonly`,
   `spreadsheets.readonly`, `calendar.readonly`). Пишущие области остаются только у
   клиентов записи.
5. `calendar_id_venue` в реестр не входит (дизайн D5), `google.mode` на реестр не влияет:
   в обоих режимах набор объектов записи одинаков (D7).

Новые поля `Settings`: `schedule_test_spreadsheet_id`, `schedule_test_sheet_pattern`
(по умолчанию `''` — «страница по шаблону `MM.YYYY · Ник`»), `drive_root_id`,
`finance_source_id`. Значение по умолчанию для тестового листа — пустое: **никаких
зашитых идентификаторов в коде**, тест это проверяет (§12.1).

### 2.3. Режим приложения

Ключ `app_setting.google.mode`, значения `transitional` и `target`, по умолчанию
`transitional`. Миграция `db/init/071_google_event_calendar.sql` вставляет строку
`('google.mode','transitional') on conflict do nothing`; код дополнительно считает
отсутствующую строку значением `transitional` (защита от базы, поднятой до миграции).
Читается одной функцией `google_mode()`; пишется эндпоинтом `POST /tools/google/mode`
(право администратора, аудит `google.mode.set`). Переход в `target` требует в теле
`{"mode":"target","backup":"<ссылка или путь выгрузки>"}`; без `backup` — 400
`mode_backup_required`. Выгрузку делает человек, бот её не создаёт (D1).

Общие правила чтения:

1. **Живой лист — никогда не запись.** Чтение живого расписания не пишет ни клеток,
   ни служебной колонки `svoi`, ни форматирования (`149` D2).
2. **Нет доступа — нет данных.** Прошлый снимок возвращается только с явной пометкой
   `stale: true` и `as_of`; выдать его за свежий нельзя (D8, AC-6).
3. **Персональные данные не логируются.** Телефоны, коды двери, суммы по людям не
   попадают в `log`, в ответы и в документы — существующий `app/masking.py` обязателен
   для всех новых путей (§12.6).
4. **Drive: только чтение метаданных.** Индекс файлов для поиска наполняет E4; эта карта
   даёт контракт и клиента, но не фоновую индексацию.

## 4. Контракт записи листов

### 4.1. Привязка (`sheet_binding`)

Структура листа фиксируется записью в `sheet_binding`, а не константой в коде. Поля:

| Поле | Смысл | Значения для наших объектов |
|---|---|---|
| `key` | ключ реестра | `budget.transactions`, `schedule.workload`, `schedule.test` |
| `spreadsheet_id` | id файла из `Settings` | — |
| `sheet_title` | лист; **пустое значение запрещено** | `Транзакции`; `Занятость`; `11.2026 · Ник` — по шаблону |
| `layout` | раскладка | `flat_table`, `monthly_blocks`, `hour_matrix` |
| `header_row` | строка заголовков | 1 |
| `first_data_row` | первая строка данных | 2 |
| `first_col`, `last_col` | границы заголовка; `last_col = null` — до последней заполненной | `1..13` для `Транзакции`; `null` для занятости |
| `header_checksum` | контрольная сумма заголовка (§4.2) | считается при засеве |
| `meta` | раскладка | `{"date_col": 2, "people_from": 4}`; `{"hours": ["08:00"…"23:00"], "dates_row": 1}` |
| `last_read_at`, `last_edit_time` | свежесть | обновляются чтением и записью |

Засев — идемпотентный скрипт `scripts/google_seed_bindings.py`: читает `Settings`,
поднимает шапку каждого объекта, считает сумму, делает `insert … on conflict (key) do
update` (кроме `spreadsheet_id`/`sheet_title`, если они уже заполнены). Режимы `--check`
(ничего не пишет, код 1 при отсутствии или расхождении) и `--apply`. Скрипт запускается
человеком и в E1-4 живым прогоном; автоматического засева при старте сервиса нет.

**Лист без привязки не пишется.** Нет строки в `sheet_binding` → `binding_missing` (409),
текст администратору: «Лист не привязан к боту — запустите `scripts/google_seed_bindings.py --apply`».

### 4.2. Контрольная сумма заголовка

Одна функция на чтение и засев:

```text
norm(v) = " ".join(str(v or "").split())          # схлопнуть пробелы, обрезать края, регистр сохранить
payload = "\x1f".join(norm(cell) for cell in header_row[first_col..last_col])
header_checksum = sha256(payload.encode("utf-8")).hexdigest()
```

Пустые ячейки внутри диапазона дают пустые куски, хвостовые пустые колонки обрезаются до
`last_col`, если он задан. Расхождение суммы — `header_mismatch` (409), запись не
выполняется, администратору уходит сообщение. Переименование колонки человеком — это
изменение контракта: пока `sheet_binding` не обновлён, бот в лист не пишет (цена принята
в D4).

### 4.3. Порядок записи (один протокол на все листы)

| Шаг | Действие | При отказе |
|---|---|---|
| 1 | `google_targets.resolve(key)` — получить id | `write_target_refused` / `write_target_unset` |
| 2 | `google_mode()` — режим известен и допустим для ключа | `write_target_refused` |
| 3 | Чтение `sheet_binding` по ключу | `binding_missing` |
| 4 | `spreadsheets.get(fields="properties.modifiedTime,sheets(properties(sheetId,title))")`, выбор листа **по имени**; несколько совпадений или пустое имя → отказ | `sheet_ambiguous` (409) |
| 5 | `values.get` шапки, сверка `header_checksum` | `header_mismatch` |
| 6 | `modifiedTime` ≤ `last_edit_time`; иначе перечитать и пересчитать план | `sheet_changed_since_read` (409) |
| 7 | План записи: адреса из раскладки, `row_map` для дедупа | `plan_problems` (409, как сейчас в `schedule.py`) |
| 8 | Запись `values.batchUpdate`/`append` | `sheet_unavailable` / `sheet_write_failed` (502) |
| 9 | Перечитать те же адреса (`batchGet`) и сравнить | `sheet_verify_failed` (502) |
| 10 | `row_map` upsert + `content_hash`, `last_read_at = now()`, журнал записи | ошибка БД откатывает пометку «записано» |

Правило дедупа: ключ строки — `(binding_key, entity_type, entity_id, coalesce(cell_key,''))`,
как в существующем индексе `ux_row_map`. Перед записью ищем `row_map`; нашли и
`content_hash` совпал — пропускаем; нашли, хеш другой — правим существующую клетку, не
добавляем новую; не нашли — пишем и сохраняем адрес из ответа (`updates.updatedRange`)
вместе с `content_hash = sha256(json.dumps(values, ensure_ascii=False))`.

Семантика объектов:

| Ключ | `entity_type` | `entity_id` | `cell_key` | Что считается «одной записью» |
|---|---|---|---|---|
| `budget.transactions` | `budget_tx` | `str(tx.id)` | `null` | одна строка `Транзакции` |
| `schedule.workload` | `availability_cell` | `<participant_id>:<YYYY-MM-DD>` | ISO-день | клетка дня человека + снимок в `svoi` |
| `schedule.test` | `color_probe` | `<page>:<YYYY-MM-DD>:<HH>` | `YYYY-MM-DDTHH` | текст клетки и её цвет |

`is_deleted = true` ставится сверкой, когда клетка/строка исчезла из листа. Обратной
вставки нет: исчезнувшую строку бот не восстанавливает, а показывает расхождение.

### 4.4. Что остаётся как есть

Расчёт адресов внутри листа занятости (`plan_week`, `find_names_row`, поиск колонки
человека по шапке) не выбрасывается: он и есть вычисление адресов **после** сверки
контрольной суммы. Меняется только источник разрешения: не «первый лист файла», а
`sheet_binding` + имя листа.

## 5. Контракт записи календаря

1. **Создание** — только `calendar.draft`. В событие обязательно пишутся
   `extendedProperties.private`: `svoi_event_id = str(event_plan.id)`, `svoi_source =
   "tool-api"`, `svoi_kind`, `svoi_people`. `svoi_event_id` — маркер «это событие бота»;
   без него событие считается чужим.
2. **Правка и удаление** — только события, найденные `events.get(calendarId=draft,
   eventId=<id>)` и **не отменённые**: `status = "cancelled"` живостью не считается.
   Google отдаёт удалённое через `events.delete` событие по `id` с этим статусом
   (живой прогон 23.11.2026, `origin/main` `e18c88c`, дефект Д-2), поэтому успешный
   `get` сам по себе не доказывает, что событие есть. Не нашли в черновом или нашли
   отменённым → `not_bot_event` (409), в боевом календаре событие **не трогаем** ни при
   каком статусе. Изменение в БД при этом остаётся (как сейчас: БД важнее календаря),
   ответ несёт `calendar_updated: false` и `calendar_error: "not_bot_event"`.
   `tentative` считается живым: событие существует, человек лишь не подтвердил участие.
3. **Перенос человеком.** Человек переносит черновик в боевой вручную (D5, V-075).
   Бот обнаруживает это при сверке: `events.list(calendarId=read, privateExtendedProperty=
   "svoi_event_id=<id>")`. Нашёл — чистит черновик (`events.delete` в draft), пишет аудит
   `event.draft_cleaned`, событие в боевом не меняет.
4. **Отмена человеком в боевом.** Если событие с нашим `svoi_event_id` в боевом имеет
   `status = "cancelled"`, бот помечает `event_plan.status = "cancelled"` и пишет причину
   в историю. Отсутствие события в боевом **не** считается отменой.
5. **Хранение календаря события.** `event_plan.gcal_calendar_id` (миграция 071) — календарь,
   в котором бот создал событие. Без этой колонки нельзя отличить «своё черновое» от
   «чужое боевое» иначе как лишним запросом; с ней отказ `not_bot_event` решается по базе.
6. **Что запрещено.** `calendarId=calendar_id_read` в вызовах `insert/update/delete/patch/
   move` — запрещён на уровне реестра (§12.1). Перенос всех событий, «миграция» боевого
   календаря в этой карте не реализуются (V-081 — отдельная разовая операция с выгрузкой).

## 6. Права сервисного аккаунта

Целевая матрица — дизайн D6. Проверяется не по памяти, а запросом:

- файлы Drive: `permissions.list(fileId=…, fields="permissions(role,type,emailAddress)")`;
- календари: `acl.list(calendarId=…)` — ищем роль нашего `client_email`;
- любой `type="anyone"` с `role in ("writer","owner")` на живых объектах — строка
  «опасно» в отчёте (V-067 решает, закрывать ли сейчас).

Скрипт `scripts/google_rights.py` (новый): читает `Settings`, печатает таблицу
`объект | id | фактическая роль | требуемая | итог` и отдаёт код 1 при любом расхождении.
`--json` — машинный отчёт для хендоффа. Требуемые роли:

| Объект | Требуется SA |
|---|---|
| живой лист «Расписание студийцы», «СВОИ 2025», «СВОИ админка», «Записная книжка», «СВОИ зрители 2026», папка «Инфа СВОИ» | читатель (`reader`/`commenter`) |
| `Бюджет`, `Занятость`, тестовый лист цветов | редактор (`writer`) |
| боевой календарь | читатель |
| черновой календарь | редактор (владелец) |

Порядок операций при закрытии доступов: **сначала** выдать редактора на объекты записи,
**потом** снимать `anyone with link = writer`. Обратный порядок запрещён (D6).

## 7. Расписание синхронизации

Фоновой синхронизации нет. Это следствие решений, а не упрощение: владелец выбрал
«ручные правки календаря ловим кнопкой „Сверить“ (не фон, не webhook)» (`docs/plans/157`
§E5), а дизайн 185 §2 требует «не угадывать» и «не выдавать прошлый снимок за свежий».

| Триггер | Что происходит | Что не происходит |
|---|---|---|
| Запрос экрана/чата (сводка, «кто свободен», неделя) | чтение живого источника, обновление `last_read_at`/`last_edit_time`, ответ с `as_of`; при недоступности — последний снимок с `stale: true` | таймеров и повторов нет |
| Кнопка «Сверить» (`POST /tools/google/refresh`, тело `{"sources":["schedule.human","calendar.read"]}`) | перечитать перечисленные источники, вернуть расхождения лист↔календарь и список найденных «переносов» черновиков (§5.3) | не пишет в живые файлы и боевой календарь |
| Любая запись (§4.3 шаг 3–6) | свежее чтение непосредственно перед записью, сверка `modifiedTime` | не использует кеш вместо свежего чтения |
| Старт сервиса | ничего | нет чтения Google при импорте приложения |

Ответ `GET /tools/google/freshness` — по каждому источнику `key`, `as_of`,
`last_edit_time`, `stale` (bool), `error` (код или null). Этим экраны E5/E4 показывают
честное «данные от 17:20».

Запреты для ревью: в этой карте не появляются ни `scripts/cron/*`, ни запись в n8n, ни
`threading.Timer`, ни `asyncio.create_task` для Google-чтения. Единственная нить в сервисе
сегодня — кеш агента (`app/agently/cache.py:35`), к Google она отношения не имеет.

- **Ролей нет.** Кто ведёт расписание, кто утверждает перенос — ждёт анкеты `161` (§7
  дизайна); спека говорит «человек», а не «организатор».
- **Миграция боевого календаря** в целевой режим (V-081) — отдельная разовая операция,
  не эта карта.
- **Выгрузка перед переключением** — V-115 (Drive или сервер); спека не выбирает носитель,
  только требует наличие ссылки в теле запроса.
- **«СВОИ админка»** остаётся только для чтения до V-113; в реестре записи её нет.
- **Колонка «Решение»** не становится моделью до V-112; в контракте чтения — текст,
  не интервал.
- **Индекс файлов Drive** (наполнение таблицы для поиска) — E4; здесь только клиент и
  контракт `drive.root`.
- **Экраны и тексты** («Сверить», «правьте в Google», плашка «данные от…») — E5/E4; здесь
  API и коды, по которым экраны строятся.
- **Миграция бюджета/занятости в `_shared`** и перенос файлов — действие владельца,
  не код.

## 15. Что ждёт владельца

Не блокирует эту карту: спека выбрана так, чтобы работа шла по умолчаниям дизайна.

| Вопрос | Что действует сейчас | Что изменится при ответе |
|---|---|---|
| V-112 (колонка «Решение») | текст для показа, не модель | вариант «план дня» добавит правило разбора и отдельную карту |
| V-113 («СВОИ админка») | только чтение | вариант «исключение» добавит объект записи и правку реестра |
| V-115 (где выгрузка) | в теле перехода `backup` — ссылка/путь, носитель не важен | вариант «сервер» уберёт Drive из проверки выгрузки |
| V-067 (закрывать доступы) | `google_rights.py` только показывает `anyone/writer` | «закрыть» — операция владельца по §6 |

## 16. Что осталось за картой

- **E4:** наполнение индекса Drive и поиск по файлам поверх `drive.root`.
- **E5:** экран сверки, кнопка «Сверить», карточка события и текст «правьте в Google»,
  цвета и типы из настройки Mini App.
- **E1-2 догон:** ролевые сценарии после анкеты `161` (дизайн §7).
- **Уборка `calendar_id_venue`** из конфига — отдельная карта, если понадобится.
