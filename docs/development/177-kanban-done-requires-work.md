# 177. Карта без работы в ветке не закрывается как done

Дизайн правила доски Hermes (не проектa `teatrsvoi_bot`). Актуально на 20.11.2026.
Основание — карта `t_b89fe815`, случай `t_bc08af77` (19.11.2026). Документ отвечает на три
вопроса: где именно дыра, как выглядит проверка, чего она стоит. Код по этой карте не
правится — правка живёт в Hermes и выносится отдельной картой (см. §7).

---

## 1. Что случилось: факты, а не пересказ карты

Проверено на доске `teatrsvoi` (`~/.hermes/kanban/boards/teatrsvoi/kanban.db`) и в
репозитории проекта (`~/repos/Projects/teatrsvoi_bot Project`), 20.11.2026.

| Факт | Значение | Чем проверено |
|---|---|---|
| Статус карты `t_bc08af77` | `done`, `completed_at` 19.11.2026 16:19:41 | `tasks` |
| Рабочее пространство | `workspace_kind='scratch'`, путь `…/boards/teatrsvoi/workspaces/t_bc08af77` | `tasks` |
| Ветка карты в записи задачи | пусто (`branch_name` NULL) | `tasks` |
| Коммитов сверх `origin/main` в ветке `wt/t_bc08af77` | **0** (HEAD `0dc0e74` — старый коммит main) | `git rev-list --count origin/main..wt/t_bc08af77` |
| Каталог воркспейса | **удалён**; git помнит его как linked worktree со статусом `prunable` | `git worktree list` |
| Отчёт воркера | прогон `1686` (`completed`), summary 206 знаков: «Обновлено сообщение отказа… тесты… прошли» | `task_runs` |
| `tasks.result` | пусто (0 знаков) | `tasks` |

Механизм потери восстановлен по этим следам: воркспейс карты был `scratch`, но внутри него
воркер поднял **связанный git-worktree** на ветке `wt/t_bc08af77`. Правки (13 файлов по
записи карты) остались незакоммиченными. При закрытии `complete_task` вызвал
`_cleanup_workspace` (`hermes_cli/kanban_db.py:2740`), и для `workspace_kind='scratch'`
сработала ветка `shutil.rmtree` **без проверки на грязное дерево**
(`hermes_cli/kanban_db_workspace.py:404-408`). Для `worktree` такая проверка есть —
`_cleanup_worktree_workspace` (`…:426-454`) сохраняет worktree при грязном дереве или
непушенных коммитах. То есть защита в Hermes **уже написана, но включается по типу
воркспейса**, и карта типа `scratch` её не получает.

Отсюда два независимых дефекта, и второй — причина потери файлов:

- **Д1.** Переход в `done` не спрашивает, зафиксирована ли работа.
- **Д2.** Удаление `scratch`-воркспейса не смотрит на грязное дерево, хотя рядом лежит
  готовый предикат `_worktree_is_dirty` (`hermes_cli/worktree_ops.py:520`).

### Что в карте описано неточно (проверил, чтобы не тиражировать)

- **«`result` пуст» — не признак дыры.** На доске **307 из 333** закрытых карт имеют пустой
  `tasks.result`: доказательство живёт в `task_runs.summary`, так устроен `complete_task`
  (`result=` не обязателен, если передан `summary`). Гейт `EmptyCompletionError`
  (`hermes_cli/kanban_db.py:2777`, коммит `6504b665ba`) эту дыру уже закрыл и по карте
  `t_bc08af77` не сработал правильно — summary был.
- **«ветка пустая» по `git rev-list --count base..branch` — не всегда «работы нет».** На той же
  доске карты `t_7af794fc` и `t_8218a446` имеют тот же след (scratch + prunable worktree), их
  ветки дают 0 коммитов сверх `origin/main`, но их работа **уже в main** (merge-коммиты
  `60866fb`, `d5b9c1a`): голова ветки достижима из транка. Буквальное правило «≥1 коммит сверх
  базы» такие карты отклонит зря.
- **Ретроспективно правило не проверить.** Из 53 закрытых карт с записанной веткой **ни одна
  ветка уже не существует**: `_cleanup_worktree_workspace` удаляет `wt/<id>` после проверки
  (`…:492-494`). Проверка имеет смысл только **до** уборки воркспейса.

## 2. Правило

**Р.** Переход карты в `done` разрешён, только если работа зафиксирована. Фиксацией считается
любое из:

1. **коммит сверх базы** — в рабочем дереве карты есть коммит, не достижимый из базовой ветки
   (`git log --oneline HEAD --not <base>` непуст); или
2. **работа уже в транке** — `HEAD` достижим из удалённой ветки/транка (карту слили до
   закрытия; тогда «сверх базы» пусто, но терять нечего); или
3. **явный признак «без кода»** (`deliverable='answer'`, см. §4) — карта не оставляет
   артефакта в репозитории, её результат — ответ в комментарии/решение владельца.

Дополнительно, независимо от 1–3: **грязное рабочее дерево запрещает `done`.** Именно этот
случай и произошёл: незакоммиченные правки исчезают вместе с воркспейсом.

Отказ — не «молча ничего»: гейт **не меняет статус** (как и соседние гейты), возвращает
воркеру ошибку с точной причиной и командой починки, пишет событие
`completion_blocked_uncaptured_work`. До `blocked` карта доходит существующей механикой:
воркер либо коммитит и закрывается со второй попытки, либо сам вызывает `kanban_block` с
нашим текстом (это и предлагает текст отказа), либо прогон кончается без терминального
вызова — тогда срабатывает `_PROTOCOL_VIOLATION_ERROR`
(`hermes_cli/kanban_db_dispatch.py:973`) и после исчерпания ретраев карта встаёт в `blocked`
с `last_failure_error`, где отказ виден дословно. Молчаливого `done` не остаётся ни в одной
из трёх веток.

| Ситуация | Что видит проверка | Итог |
|---|---|---|
| коммит есть, дерево чистое | `log HEAD --not base` непуст, `status` пуст | `done` |
| коммит есть, дерево грязное | правки поверх коммита | отказ: «в воркспейсе есть изменения без коммита» |
| коммита нет, дерево грязное (случай `t_bc08af77`) | грязное дерево | отказ: то же + «в ветке нет ни одного коммита» |
| коммита нет, дерево чистое, `deliverable=code` | нечего фиксировать | отказ: «работа не зафиксирована в ветке» |
| ветка слита в транк, дерево чистое | `HEAD` достижим из `origin/*` | `done` |
| воркспейса нет / не git | git-фактов нет | отказ, пока нет `deliverable='answer'` |
| `deliverable='answer'`, summary непустой | признак + evidence | `done` |

## 3. Где живёт проверка

Одна точка на все пути закрытия — гейт в `complete_task`, по образцу уже существующих
`_gate_empty_completion` и `_gate_created_cards` (оба стоят **до** транзакции записи, чтобы
отказ ничего не менял; `hermes_cli/kanban_db.py:2668-2669`):

| Что | Файл, место | Работа |
|---|---|---|
| Гейт | `hermes_cli/kanban_db.py`, рядом с `_gate_empty_completion` (2777) | `_gate_work_captured(conn, task_id, *, force)`; вызывается после `_gate_empty_completion` |
| Исключение | там же, рядом с `EmptyCompletionError` (2599) | `UncapturedWorkError(reason, detail)` — `ValueError`, как соседи |
| Событие | `task_events` | `completion_blocked_uncaptured_work` с полями `reason`, `branch`, `dirty_files`, `workspace_path` |
| Инструмент | `tools/kanban_tools.py:780` (рядом с обработкой `EmptyCompletionError`) | текст отказа: что не зафиксировано и что сделать (`git add -A && git commit`), карта остаётся in-flight |
| CLI | `hermes_cli/kanban.py:930` (`_cmd_complete`) | тот же текст; `--force` оператора обходит гейт и пишет событие `completion_forced_uncaptured` |
| Схема | `hermes_cli/kanban_db_connect.py:867` (`_LATER_TASK_COLUMNS`) | `("deliverable", "deliverable TEXT")`, NULL = `code` (старые строки ведут себя как раньше) |
| Поля вывода | `tools/kanban_tools.py:420` (`_TASK_FIELDS`), `hermes_cli/kanban_output.py:21` | добавить `deliverable`, иначе признак не виден в `kanban_show` |
| Создание карты | `hermes_cli/kanban.py:376`, `tools/kanban_tools.py:1147` | проброс `deliverable` рядом с `completion_contract`; значение проверяется (`code|answer`) |

Факты берутся существующими предикатами, новых git-вызовов писать не нужно:

- грязное дерево — `_worktree_is_dirty(path, repo_root)` (`hermes_cli/worktree_ops.py:520`),
  он же игнорирует наши `.worktreeinclude`-симлинки и fail-safe отвечает «грязно»;
- «работа в транке» — `_worktree_has_unpushed_commits(path)` (`…:475`) в обратную сторону:
  `False` = все коммиты достижимы из удалённой ветки/локального транка;
- база сравнения — `_worktree_merge_base_ref(path)` (`…:462`): `origin/HEAD` → `origin/main` →
  `origin/master` → локальный транк; `None` = сравнивать не с чем, и тогда правило считает
  работу зафиксированной (fail-safe, иначе карта без remote закроется навсегда);
- `repo_root` для `_worktree_is_dirty` — `_git_common_dir(path).parent`
  (`hermes_cli/kanban_db_workspace.py:649`), как это уже делает уборка.

Что именно проверять как «рабочее дерево карты» (порядок):

1. `tasks.workspace_path` — если внутри есть `.git` (файл или каталог) и это git-репозиторий,
   меряем там. Так ловится случай `t_bc08af77`: `workspace_kind='scratch'`, а внутри worktree.
2. иначе `tasks.branch_name` — ищем ветку в репозитории доски (`board default_workdir`).
3. иначе git-фактов нет → работает только `deliverable='answer'`.

`force` сознательно оставлен: ручное закрытие живой карты оператором уже существует
(`LiveClaimError`, `…kanban.py:925`), запрещать обход значило бы ломать аварийный путь. Но
обход аудируется событием, а не проходит молча.

## 4. Признак «без кода»: `deliverable`

Одна колонка, два значения; NULL читается как `code`, поэтому 333 уже закрытые карты правило
не трогает (гейт смотрит только на переход).

| Значение | Смысл | Что требует гейт |
|---|---|---|
| `code` (по умолчанию) | карта меняет файлы в репозитории | коммит сверх базы **или** работа уже в транке |
| `answer` | результат — ответ/решение, артефакта в репозитории нет | непустой summary (уже требует `EmptyCompletionError`) |

Дизайн-документ и отчёт **не** получают `answer`: они обязаны лежать файлом в репозитории
(правило владельца), а значит их коммит гейт удовлетворяет сам. `answer` — только для карт,
чей продукт физически не файл: «проверить, что X не сломан», «какое решение принято по V-NNN».

Проброс: `kanban_create(deliverable=...)`, `hermes kanban create --deliverable answer`,
поле в `kanban_show`/`kanban_list`. В тело карты признак не пишем — текстовый маркер
обходится одной строкой в теле, колонка проверяется машинно.

## 5. Тесты

Новый файл `tests/hermes_cli/test_kanban_done_requires_work.py` (фикстура копируется из
`tests/hermes_cli/test_kanban_empty_completion.py`), git-репозиторий — `tmp_path` + `git init`,
`workspace_kind='worktree'`:

1. `scratch`-воркспейс, внутри worktree, правка без коммита → `UncapturedWorkError`,
   `tasks.status` остаётся `running`, событие `completion_blocked_uncaptured_work` есть,
   `completed` — нет (повтор `t_bc08af77`);
2. ветка с одним коммитом, дерево чистое → `done` (регресс: нормальная карта закрывается);
3. ветка слита в транк (`HEAD` достижим из `origin/main`), дерево чистое → `done`
   (не ломаем слияние-до-закрытия; случай `t_7af794fc`);
4. `deliverable='answer'`, summary непустой, git-фактов нет → `done`;
5. `deliverable` не задан, git-фактов нет → `UncapturedWorkError`;
6. `force=True` → `done` + событие `completion_forced_uncaptured`;
7. отказ **не удаляет** воркспейс: каталог и файлы на месте после исключения;
8. `_cleanup_workspace` для `scratch` с грязным деревом не делает `rmtree` (защита Д2,
   отдельный тест рядом с `tests/hermes_cli/test_kanban_worktree_teardown.py`).

Проверка руками после правки — на копии доски: создать карту `scratch`, положить в воркспейс
worktree с правкой без коммита, вызвать `hermes kanban complete` → `blocked`, файлы на месте.

Состояние гейта на этом документе (`scripts/check_done.py --quick`, ветка `wt/t_b89fe815`):
`ruff` чисто, `pytest` 2999 passed / 777 skipped, шаг `invariants` красный по **I1**
(«баланс 0.00» на пустой dev-базе; тот же FAIL в основном checkout, к документации отношения
не имеет), из-за него `registers`/`deadcode`/`settings` не запускались.

## 6. Цена и риски

| Риск | Оценка |
|---|---|
| Ложные отказы у карт, которые только читают | лечатся `deliverable='answer'`; на доске это заметная доля `scratch`-карт (259 из 333 закрытых), поэтому признак нужно ставить при создании, а не вспоминать при закрытии |
| Ложные отказы у слитых карт | снимаются пунктом 2 правила (достижимость из транка); без него правило ложно отклонило бы минимум 2 карты (`t_7af794fc`, `t_8218a446`) |
| Воркер застрянет в цикле «commit → отказ» | текст отказа обязан называть команду; гейт пишет событие, видимое в `kanban_show` |
| Время | гейт `complete_task` + исключение + два вызывающих + тесты — 4–6 ч; защита Д2 в уборке — ~1 ч; колонка и проброс — 2–3 ч |
| Где живёт патч | Hermes установлен из `NousResearch/hermes-agent`, локальный checkout на 984 коммита впереди `origin/main` и уже содержит чужую незакоммиченную правку `hermes_cli/kanban_diagnostics.py` (+4 строки). Патч локальным коммитом в отдельной ветке этого checkout; при обновлении Hermes его надо переносить — это цена, а не недосмотр (см. V-111) |

Что правило **не** ловит и не должно: правку, сделанную воркером **вне** своего воркспейса
(прямо в основном checkout проекта). Такие правки принадлежат не карте, а общему дереву;
контроль там — `git status` основного checkout, а не гейт закрытия.

## 7. Что я не трогал и почему

- **Не правил Hermes.** Роль архитектора — отчёт и решение, не код; правка вынесена дочерней
  картой в `~/.hermes/hermes-agent` (её откроют после ответов на V-109…V-111).
- **Не менял статусы задним числом.** `t_bc08af77` остаётся `done`: правило смотрит только на
  переход, а переоткрытие закрытых карт запрещено границей карты.
- **Не трогал `docs/development/26`** (процесс и git): правило относится к доске Hermes, а не к
  проекту; ссылка на этот документ добавлена только здесь.
- **Не заставлял карты без кода коммитить пустышки:** `deliverable='answer'` — обязательный
  явный признак, иначе гейт отказывает.
