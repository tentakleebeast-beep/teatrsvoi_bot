## 1. Где хранить

| Что | Где | Почему |
|---|---|---|
| Код, миграции, скрипты, деплой | **GitHub, публичный репозиторий** | привычно, бесплатно, CI из коробки, VS Code дружит |
| Документация (`docs/`) | там же, в репозитории | документы меняются вместе с кодом |
| Секреты (`.env`, `secrets/google-sa.json`) | **только на машине/сервере**, `.gitignore` | утечка ключа = чужой доступ к бюджету |
| Дампы БД, выгрузки | не в git; бэкап в отдельное хранилище | бинарный мусор в истории |
| Крупные медиа, макеты | Drive, ссылка в документе | git не для файлов на сотни мегабайт |
| Личные настройки участников (`bot/manifests/participants/<person_key>.md`) | **только на сервере**, вне git; в репозитории — один `_example.md` | в публикуемом дереве не должно быть имён и личных предпочтений (Ш-03 плана 129) |
| Локальное соответствие имён (`config/participant-names.yaml`) | **только на машине/сервере**, вне git; в репозитории — `participant-names.example.yaml` | там настоящие имена и никнеймы участников; в публикуемом дереве их быть не должно (Ш-03a плана 129) |

Личные настройки участника — четвёртый слой промпта (`services/tool-api/app/api/admin.py`,
`compose_prompt`): файл читается по `person_key` из боевой БД, `MANIFEST_DIR` —
`<repo>/bot/manifests`. Прод ставится клоном `main` в `$SVOI_ROOT` (`deploy/server-deploy.sh`),
поэтому боевая копия лежит поверх клона как **неотслеживаемый** файл:
`$SVOI_ROOT/bot/manifests/participants/<person_key>.md`. `git checkout --force FETCH_HEAD`
его не удаляет: такого пути нет в дереве коммита.

Две вещи помнить при выкате:

- релиз, который **удаляет** файл из дерева (как Ш-03), забирает отслеживаемую копию вместе с
  собой — после первого такого выката копию на сервер кладут заново из локального хранилища;
- файла нет — ошибки нет: промпт собирается без четвёртого слоя, личные настройки молча не
  применяются. Поэтому после релиза наличие файла проверяют руками, а не по логам.

Альтернатива GitHub — GitVerse или локальный Gitea, если нужна юрисдикция РФ.
Принципиально ничего не меняется: главное — публичный репозиторий и `.gitignore` до первого коммита.

Соответствие «имя в файле → человек» (`config/participant-names.yaml`) живёт по тем же правилам:
файл в `.gitignore`, в репозитории только `participant-names.example.yaml` с плейсхолдерами,
боевая копия — `$SVOI_ROOT/config/participant-names.yaml` поверх клона. Читают его
`services/tool-api/app/participant_names.py` (сервис) и `scripts/_people.py` (импорт расписания,
сверка). Нет файла — работаем на данных БД: `person_alias`, `person_key`, `display_name`.
Файл нужен только для никнеймов, которых в БД ещё нет, и для подсказок категории
(`category_hints`) — их в БД не вывести (Ш-03a плана 129).

**Это обязательный шаг выпуска, а не украшение.** Пока файла на сервере нет, работают только
алиасы из БД, а их заполнено мало: на копии боевой БД без конфига `reconcile.py --only schedule
--dry-run` находит 8 листов людей из 9 (нет «дарья»), на dev-базе — 0 из 9. Поэтому при выкате
после клонирования положить `$SVOI_ROOT/config/participant-names.yaml` рядом с `.env` и один раз
прогнать `scripts/import_schedule.py --dry-run`: со второго прогона импорт сам заводит алиасы
в `person_alias`, и конфиг нужен только для новых людей и `category_hints`.

## 3. Ветки и коммиты

Простой поток, без GitFlow — проект ведёт один человек с редкими помощниками:

```
main ────●────●────●────────●────●
              \            /
               ●──●──●  feat/slots   (1–3 дня, потом merge)
```

- `main` — всегда рабочее состояние: сервисы запускаются, тесты зелёные;
- ветка на задачу: `feat/slots`, `fix/inverted-availability`, `docs/audit`;
- срок жизни ветки — до трёх дней; дольше — значит задача слишком большая;
- коммит: тип + суть по-русски, тело — «почему», а не «что».

```
fix: перевернуть семантику занятости (1 = занят)

Импорт читал 1 как «свободен», из-за чего все 7217 записей
в availability_hour были зеркальными. Миграция 016 исправляет.
```

Типы: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `infra`.

## 4. Что проверять перед merge в main

Гейт запускается одной командой из корня репозитория:

```bash
env -u PYTHONPATH .venv/bin/python scripts/check_done.py
```

Скрипт проходит проверки по порядку и печатает одну итоговую строку: либо
«ГЕЙТ ЗЕЛЁНЫЙ: ruff чисто, pytest … passed/… skipped, инварианты OK, реестры OK,
deadcode новых 0», либо «ГЕЙТ КРАСНЫЙ: шаг «…» упал» и последние 20 строк вывода.
Падение останавливает прогон, но шаги, которые успели пройти, остаются в отчёте.
Полный прогон включает браузерные тесты Mini App; `--quick` пропускает только их
и пишет в итоге «ГЕЙТ ЗЕЛЁНЫЙ (без браузерных)». Флага «только unit» нет:
integration-тесты входят в шаг `pytest` всегда. `--json` — машинный отчёт
(шаг, код, секунды), `--board <slug>` добавляет проверку карт канбана.
Скрипт не поднимает Postgres и не накатывает миграции: окружение (база, `.env`)
готовится заранее, при недоступной базе гейт говорит об этом прямо.

Пункты ниже остаются объяснением того, что именно гоняет скрипт; руками их
выполнять не нужно — расхождение списка и скрипта считается дефектом процесса.

- [ ] `pytest -q` — зелёный целиком, включая `tests/integration` на реальном Postgres
- [ ] `SVOI_WEBAPP_TESTS=1 .venv/bin/python -m pytest tests/webapp -q --browser chromium` — зелёный,
      если правка касалась страниц Mini App
- [ ] `.venv/bin/ruff check .` — чисто
- [ ] `python scripts/check_deadcode.py` — новых находок мёртвого кода нет
- [ ] `python scripts/check_kanban_cards.py` — у карт в работе есть описание
- [ ] хук установлен: `git config --get core.hooksPath` печатает `.githooks` — иначе ruff
      по staged-файлам и инварианты перед коммитом не проверяются (README, «Хук перед коммитом»)
- [ ] версия Python одна: `.python-version`, `requires-python`, CI, `services/*/Dockerfile`,
      локальный venv и README — **3.12** (держит `tests/unit/test_toolchain_versions.py`)
- [ ] `python scripts/check_invariants.py` — все OK
- [ ] новая миграция — это новый `db/init/NNN_*.sql` **и** ревизия Alembic
      (`scripts/gen_alembic_revisions.py --check` чисто), файл идемпотентен, применённые
      файлы не правились (§5)
- [ ] если менялось поведение — обновлён документ в `docs/`
- [ ] в дифе нет секретов и `.env`
- [ ] если баг из живой работы — добавлен регрессионный тест
- [ ] `python scripts/check_registers.py` — реестры уроков, препятствий и намерений чистые
- [ ] `python scripts/audit_actions.py --check` — отчёт 117 (инвентарь действий) не разошёлся с кодом
      и контрактом; в CI это шаг job `contract`, сети и БД он не требует

Последний пункт — правило проекта: **баг не считается закрытым без теста**, который его ловит.

### 4a. Контракт API: снимок и правило его обновления

Схема API зафиксирована файлом `contracts/openapi.json` — это снимок фактической
`app.openapi()`, руками он не правится (INT-012). Проверка `scripts/openapi_snapshot.py`
сравнивает снимок со схемой и печатает точечный дифф (путь, что было, что стало):

```
env -u PYTHONPATH .venv/bin/python scripts/openapi_snapshot.py           # проверка, код 1 при расхождении
env -u PYTHONPATH .venv/bin/python scripts/openapi_snapshot.py --write   # обновить снимок
```

Правило: **изменение контракта (маршрут, метод, поле, тип, обязательность) = обновление
снимка тем же коммитом + перечень изменений в отчёте карты.** Строка отчёта называет, что
именно поменялось (`добавлен POST /tools/x`, `поле ok переименовано в success`), — внешние
потребители (Mini App, бот, наследник n8n) узнают о правке из отчёта, а не из ошибки в проде.

Что держит правило механизмом:

| Место | Что проверяет |
|---|---|
| `tests/integration/test_openapi_contract.py` | снимок совпадает со схемой; дифф ловит добавление, удаление, смену метода, переименование и удаление поля; в снимке нет секретов и внутренних адресов |
| job `tests` в CI (`.github/workflows/tests.yml`) | шаг `python scripts/openapi_snapshot.py` — красный, если схема изменена без обновления снимка |
| `scripts/openapi_snapshot.py --write` | единственный способ обновить снимок; проверка файл не трогает никогда |

Снимок детерминирован: ключи отсортированы, описания, примеры, `operationId`, `info` и
`servers` выброшены — смена текста справки или адреса запуска тест не роняет. Шум
вырезается **по позиции, а не по имени ключа**: имена полей внутри `properties` остаются
в снимке, даже если поле называется `title`, `description` или `summary` (иначе удаление
такого поля не давало бы ни одной строки диффа).


**Гейт — это весь прогон, а не удобная его часть** (урок аудита 96 от 31.10.2026). Переделка
UI была закрыта прогоном только `tests/unit` (898 passed), а `pytest -q` на `main` падал:
три интеграционных теста проверяли удалённые контракты. Отсюда два следствия:

1. Закрывать шаг можно только по полному прогону; частичный прогон пишется в отчёте
   с явной оговоркой «что именно не гонялось и почему».
2. Пропуски — не зелёный свет. 282 браузерных теста молча скипались без `SVOI_WEBAPP_TESTS`;
   теперь они идут отдельным job `webapp` в CI (`.github/workflows/tests.yml`).
   Если тесты сознательно не запускаются, это должно быть видно в job-списке, а не в `skipped`.
3. Одна версия Python — **3.12**. Она выбрана не «по свежести», а по контуру: и образы
   (`python:3.12-slim`), и CI (`actions/setup-python`), и venv на сервере (системный `python3`
   Ubuntu 24.04, `docs/infrastructure/35`) — уже 3.12, а инструменты разбора (`deadcode`)
   под 3.14 падают. Эталон лежит в `.python-version`, за ним следят `requires-python`,
   `ruff target-version` и `tests/unit/test_toolchain_versions.py`.

## 5. Миграции

Схема описана один раз — файлами `db/init/*.sql`; голову цепочки печатает `alembic heads`,
число файлов — `ls db/init` (в тексте они не фиксируются, чтобы не устаревать).
Применяется не файл сам по себе, а цепочка ревизий Alembic в
`services/tool-api/migrations/versions/`: каждая ревизия оборачивает ровно один SQL-файл,
хранит его sha256 и вызывает `run_sql` (`services/tool-api/migrations/sql.py`). Учёт
применённого живёт в таблице `alembic_version`.

**Накат — всегда `alembic upgrade head`, и только он:**

| Где | Чем накатывается |
|---|---|
| сервер (прод, обновление версии) | `sudo deploy/server-deploy.sh db` (чистая база) и `db --migrate` (существующая) |
| compose | сервис `migrate` — one-shot на том же образе, что `tool-api` (`docker-compose.yml`) |
| тесты | `tests/conftest.py`: `command.upgrade(cfg, "head")` на `svoi_test_*` |
| вручную | `env -u PYTHONPATH .venv/bin/alembic -c alembic.ini upgrade head` |

Новый SQL-файл в `db/init` сам по себе не применяется нигде: без ревизии `upgrade head`
его не видит, и схема на dev и на проде останется прежней. Это ровно та поломка, от
которой уходили 30.10.2026 (`docs/infrastructure/75-hosting-and-migration.md`, §7.1.1).

Правила:

1. Изменение схемы — это **новый файл + новая ревизия**. Файл `db/init/NNN_*.sql` с
   номером строго по порядку (номер занимается по максимуму по всем веткам, не только по
   `main`), затем ревизия генератором:
   `env -u PYTHONPATH .venv/bin/python scripts/gen_alembic_revisions.py` (сверка без
   записи — `--check`, её гоняет CI). Одного SQL-файла мало — см. таблицу наката.
2. Применённый файл никогда не переписывается: его sha256 лежит в ревизии, и правка
   валит накат сообщением «файл изменился после ревизии». Исправление — новый файл с
   новым номером и новая ревизия.
3. Миграция идемпотентна: `if not exists`, `on conflict do nothing`.
4. Изменение данных отдельно от изменения схемы — в одном файле, но разными блоками.
5. Перед применением на боевой базе — прогон на `svoi_test` (это делают integration-тесты)
   и на dev-контуре.
6. `downgrade` не пишется: в каждой ревизии он `raise NotImplementedError` — миграции
   только вперёд (решение 518, `docs/reports/132-db-schema-single-source-plan.md`). Откат
   базы — не обратная миграция, а восстановление из дампа:
   `deploy/server-deploy.sh rollback <тег>` возвращает код, база остаётся на месте
   (`docs/infrastructure/75-hosting-and-migration.md` §10.2); учёт версии после
   восстановления ставится `alembic stamp head` и только после сверки структуры (§7.1.1).

## 6. Версии и релизы

**Прод обновляется только по команде владельца.** Ни CI, ни cron, ни агент не выкатывают
код в прод самостоятельно: до команды версия живёт в репозитории и на dev-контуре.
Запрет держится не на слове: `on:` в `deploy.yml` проверяет `scripts/check_invariants.py`
(строка «деплой»), а автодеплой в `scripts/cron/` ловит отдельная строка «cron».
Сам `deploy.yml` живёт в публичном репозитории (§10), в `.github/workflows/deploy.yml`:
запуск только `workflow_dispatch`, автодеплоя нет. Секрет `DEPLOY_SSH_KEY` и переменная
`DEPLOY_HOST` заданы в настройках того же публичного репозитория.

### Нумерация версий

Тег — `vX.Y.Z`, ставится только на `main` при чистом дереве и совпадении с `origin/main`.
Что менять в номере:

| Часть | Когда | Что нельзя менять |
|---|---|---|
| патч `0.3.X` | исправление | поведение, API и схема БД не меняются |
| минор `0.X.0` | новая функциональность или изменение поведения, обратно совместимое | — |
| мажор `X.0.0` | несовместимое изменение API или схемы | — |

Правило одно: если клиент или прошлая версия кода перестаёт работать с новой — это мажор,
даже если правка выглядит маленькой.

### Состав релиза

- `CHANGELOG.md` в корне — по разделам «добавлено / изменено / исправлено», по-русски, коротко.
  Раздел версии **обязан** существовать до тега: `deploy/release.sh` без него падает с кодом 1.
- Тег аннотированный, сообщение — заголовок и состав из `CHANGELOG.md`.
- Существующий тег переставлять нельзя. Ошибка в релизе исправляется следующим патчем,
  а не переносом тега: иначе у двух людей с одним тегом разный код.

### Выпуск и выкат

```
deploy/release.sh 0.3.3            # prepare: гейты, CHANGELOG, тег; прод не трогает
deploy/release.sh v0.3.3 --apply   # по команде владельца: push тега, workflow, сверка
deploy/release.sh --status         # что в проде, без изменений (dry_run=true)
```

`prepare` прогоняет `ruff check .`, `scripts/test_audit.py --strict` и `pytest -q`,
ставит тег локально и печатает план: тег, `sha`, коммиты от предыдущего тега, что сделает
`--apply`. Сеть не трогает, кроме `git fetch --tags`. Публикация — только вторым шагом
и только по команде владельца.

`--apply` пушит тег, запускает `deploy.yml` руками (`dry_run=false`), ждёт run и записывает
фактическое состояние в `docs/reports/78-release-state.md` (версия, тег, `git_sha`, дата,
`env=prod`). Push отчёта печатается командой, но не выполняется.

### Откат

Откат = предыдущий тег, **база при этом не откатывается**. Поэтому миграции пишутся так,
чтобы код прошлой версии продолжал работать: сначала добавляем колонки, удаляем — через релиз.
`deploy.yml` при провале проверки версии откатывается сам; если откат в логе не виден,
`release.sh --apply` выкатывает предыдущий тег тем же workflow и сообщает админу.

### Ручной путь

SSH-выкат (`docs/infrastructure/35` §10) остаётся резервом: с 08.11.2026 SSH с рабочей
машины до прода проверен и работает, но рабочий путь — GitHub Actions, запущенный руками;
с раннеров GitHub сервер достаётся напрямую.

### 6.1. Публичная история: приватный bundle и публикуемое дерево

Решение владельца от 05.11.2026 (`docs/plans/129` §Ш-00 п.1, вариант **B**): репозиторий
публикуется **сжатым деревом**, история не переписывается. `git filter-repo` не применяется
ни к одной ветке. Следствие: **публичной истории у репозитория нет вовсе** — есть один
коммит с текущим деревом.

Почему так, а не чистка истории: коммит, попавший в публичный репозиторий, считается
раскрытым навсегда, а `filter-repo` меняет все SHA (200+ коммитов), ломает ссылки на коммиты
в документах и оставляет данные доступными в старых клонах. Цена сжатой истории — решения
и переписка коммитов наружу не видны, а файл «из истории» публично восстановить нельзя.

**Приватный архив истории.** Вся внутренняя история лежит только в bundle вне репозитория:

| Что | Где |
|---|---|
| Основная копия | `~/svoi-private-backups/bundles/svoi-private-<дата>.bundle` |
| Зеркало | `~/Library/Mobile Documents/com~apple~CloudDocs/svoi-private-backups/` (iCloud, вне машины) |
| Публикуемое дерево | `~/svoi-private-backups/public/svoi-public-<дата>.bundle` |
| Манифест | `~/svoi-private-backups/MANIFEST-<дата>.txt` — SHA-256 файлов, SHA коммитов, даты |

Сборка и проверка:

```bash
git bundle create ~/svoi-private-backups/bundles/svoi-private-2026-11-06.bundle --all
git bundle verify ~/svoi-private-backups/bundles/svoi-private-2026-11-06.bundle   # «is okay»
shasum -a 256 ...bundle                                                          # сверить с манифестом и зеркалом
```

Восстановление истории из bundle — единственный способ её вернуть:

```bash
git clone ~/svoi-private-backups/bundles/svoi-private-2026-11-06.bundle svoi-history
# или в существующий клон: git fetch <bundle> 'refs/*:refs/private/*'
```

Bundle полный (`--all`): его можно клонировать как обычный репозиторий, но **пушить из него
в публичный репозиторий нельзя** — вернёт историю обратно.

**Публикуемое дерево.** Готовится один раз от текущего `main` (после шагов Ш-02…Ш-04):

```bash
# 1. дерево в отдельном рабочем каталоге, без связи с историей
git worktree add /tmp/svoi-public wt/<карта>
# 2. снять с дерева историю: orphan-ветка, файлы остаются как есть
git -C /tmp/svoi-public switch --orphan public/initial
git -C /tmp/svoi-public add -A
git -C /tmp/svoi-public commit -m "СВОИ: Telegram-бот и Mini App театра-студии (исходное состояние)"
# 3. проверить, что история — один коммит, и упаковать в bundle для нового репозитория
git -C /tmp/svoi-public log --oneline            # одна строка
git bundle create ~/svoi-private-backups/public/svoi-public-<дата>.bundle public/initial
```

Требования к дереву перед публикацией (проверяются до коммита):

- нет дампов и выгрузок (`git grep -l "budget_tx" -- 'docs/reports/*backup*'` — пусто);
- нет реальных идентификаторов: chat_id, имена участников, адрес сервисного аккаунта,
  календарные id, адрес и IP прода — плейсхолдеры (шаги Ш-03, Ш-04);
- `scripts/check_done.py` зелёный **на этом дереве**, а не только на ветке.

**Флип делает новый репозиторий, а не переключатель видимости.** Это главное следствие
решения B: если просто открыть существующий приватный репозиторий, публичными станут
**все** ветки, теги и старые коммиты — то есть ровно то, чего решение B избегает. Порядок:

```bash
# новый пустой репозиторий (публичный), затем в него только orphan-ветку
git -C /tmp/svoi-public remote add public git@github.com:<владелец>/<новое-имя>.git
git -C /tmp/svoi-public push public public/initial:refs/heads/main
```

Старый приватный репозиторий 08.11.2026 переведён в архив GitHub (read-only) и выведен
из работы; история есть в bundle. Удалять его или нет — решение владельца, на текущую
работу это не влияет.

**После флипа клоны пересоздаются, а не чинятся.** `/opt/svoi` на сервере, рабочее дерево
разработчика и рабочие деревья воркеров (`~/.hermes/kanban/.../workspaces`, `.worktrees/`)
клонируются заново из нового репозитория. Старый клон, отправивший push в публичный
репозиторий, вернёт туда прежнюю историю — поэтому push из старых клонов запрещён, а не
«не рекомендуется». Ветки карт в работе переносятся как патчи (`git format-patch` из bundle)
или переделываются в новом клоне.

## 7. Как вести работу с ИИ-агентом (эта практика уже сложилась)

| Что делает человек | Что делает агент |
|---|---|
| ставит задачу словами, проверяет результат на живом боте | пишет код, миграции, тесты, документы |
| принимает продуктовые решения (порог, семантика, цвета) | предлагает варианты с плюсами и минусами |
| говорит «ок» на изменение данных | выполняет и **показывает, что именно изменилось** |

Три правила, которые стоит держать:

1. **Агент не принимает решений о деньгах и данных сам** — только предлагает и ждёт «ок».
2. **Любое изменение данных подтверждается цифрами до и после** (как с занятостью: было 6064/1153,
   стало наоборот).
3. **Расхождение озвучивается, а не подкручивается** — это уже спасло от двух ошибок
   (августовские 10 000 и перевёрнутая занятость).

### Реестры, которые агент ведёт сам

| Реестр | Когда пишет агент |
|---|---|
| `docs/development/69-lessons.md` | ошибка дошла до данных, бота или человека — первопричина, правило и где оно закреплено |
| `docs/development/70-obstacles.md` | правило мешает, окружение не пускает, данные расходятся, нужно решение человека |
| `docs/development/71-intents.md` | до начала заметной работы — зачем и на каком основании; по завершении — артефакты |

Форму записей проверяет `scripts/check_registers.py` (тест `tests/unit/test_registers.py`).
Урок считается закрытым, только когда правило держит механизм вне `docs/`: тест, миграция,
скрипт, код.

## 7a. Правила, которые выросли из буксовки 28.10.2026

Записаны по итогам разбора (`docs/reports/68-state-review.md`, `docs/reports/72-work-plan.md`)
и связаны с уроками `docs/development/69-lessons.md` (L-010…L-014).

1. **Дефект чинится классом, а не точкой** (L-010→L-008). Нашли «кнопка меню съедается
   формой» — проверяем все формы и все пункты меню; нашли «цифра в фразе стала деньгами» —
   проверяем все правила маршрутизации. Исправление в одном месте без проверки соседних
   веток гарантирует второй заход.
2. **Никаких ссылок на будущие артефакты** (L-009). В плане и отчётах пишем «отчёт следующим
   номером документа в `docs/reports`», а не конкретный путь, которого ещё нет: иначе
   `tests/unit/test_docs_links.py` падает на собственных планах.
3. **Тест без обоснования не принимается** (L-010). У каждого теста в имени или docstring
   есть ID требования (`FR-…`, `UC-…`), дефекта (`S-…`, `C-…`, `B-…`), вопроса (`V-…`),
   шага (`Ш-…`) или урока (`L-…`). Инвентаризация — `scripts/test_audit.py`
   (`--file`, `--json`, `--strict`). Разрешён один компромисс: docstring модуля с ID или
   ссылкой на документ закрывает файл целиком — но только до рефакторинга, цель — свои ID.
4. **Сервисы запускаются только через репозиторий** (L-011). `scripts/start_services.py`
   (launchd + проверка живого `/health`). Никаких `sh -c`, `nohup`, heredoc: политика
   одобрений их режет, а ручной обход через другое приложение скрывает, что именно запущено.
5. **Отчёты идут своим каналом** (L-012). Сводки админу — ботом проекта
   (`scripts/notify_admin.py`), задание планировщика доставляется только в `origin`.
   Шлюзы Hermes к проекту отношения не имеют: попытка доставить через них остановила работу
   целиком (`blocked_config`).
6. **Зависимости шагов объявляются явно.** Шаг, которому нужен результат другого шага,
   пишет это в тексте («после Ш-48»). Параллельные тики не должны брать связанные шаги.
7. **Карта без описания не заводится** (правило владельца, 31.10.2026). В каждой карте есть
   `body`: что меняем и зачем, область, критерии приёмки, границы. Пустая карта стоит
   воркеру целого захода: спецификация теряется, задача стартует без контекста.
   Проверка — `scripts/check_kanban_cards.py` (находит карты с пустым описанием на всех бордах).
8. **Мерж сразу публикуется, гейт — зелёный CI** (правило владельца, 01.11.2026). После
   вливания карты в `main` ветка уходит в `origin` в том же тике: `git push origin main`.
   Локальный зелёный прогон доказательством не считается: job'ы `webapp`, `webapp-webkit`,
   `deadcode`, `types`, `images` существуют только в GitHub Actions. Показательный случай —
   `origin/main` отставал на 17 коммитов, то есть ни один из новых job'ов ни разу не
   запускался, а «зелёный на `main`» в отчётах означал «зелёный на ноутбуке».
   Карта закрывается по зелёному run на `main` (`gh run list --branch main --limit 1`);
   при красном заводится отдельная карта на починку, мерж задним числом не «доваливается».
9. **Воркер не коммитит и не пушит в `main`** (01.11.2026). Основную ветку собирает
   `worker-review` (п.8 выше): он вливает карту и публикует `main`. Воркер работает
   в своей ветке `wt/<task-id>` или `card-*` и пушит её. Правило держат хуки
   `.githooks/pre-commit` и `.githooks/pre-push` (включаются один раз на клон:
   `git config core.hooksPath .githooks`, README): в контексте воркера
   (`HERMES_KANBAN_TASK` или `HERMES_PROFILE=worker-*`) коммит и push в `main`/`master`
   отклоняются с кодом 1, сообщение называет это правило и подсказывает ветку.
   Профиль `worker-review` в воркерский контекст не попадает — ему `main` нужен по работе.
   Человеку хуки не запрещают ничего: push в `main` проходит с предупреждением, ветка
   вне схемы — тоже предупреждение. Тесты — `tests/unit/test_git_guards.py`.

## 7b. Один файл в работе — одна карта (01.11.2026, редакция 04.11.2026)

Правило: **в работе одновременно не больше одной карты на один существующий файл.** Две
карты, объявившие один и тот же файл, дают конфликт слияния; карты с разными файлами
в одном каталоге конфликта не дают. Лимит профиля (`max_in_progress`) этого не ловит:
карты разные, а файлы у них одни. 31.10.2026 две webapp-карты, взятые одновременно, дважды
конфликтовали с общей оболочкой (`pages/admin.py`, `misc.py`, `person.py`, `week.py`,
`webapp-shell.js`), и обе работы пришлось переделывать через новые карты.

До 04.11.2026 правило мерило грубо: областью считался первый корень пути (`scripts/`,
`docs/`, `db/`), и пять карт, писавших РАЗНЫЕ отчёты в `docs/reports/`, стояли в очереди
друг за другом без причины. Владелец 04.11.2026 разрешил параллельный запуск, если карты
не пересекаются по файлам и конфликт мёржа исключён, — поэтому правило стало файловым.
Области (`экраны`, `API: <домен>`, `инфраструктура`) остались **ярлыком для отчёта**;
запрет и очередь считаются по точным путям.

### Как считается пересечение

Файлы берутся из раздела «Область» в теле карты, руками метку никто не ставит.
Скрипт `scripts/kanban_areas.py` проверяет путь от корня репозитория, а не от своего
расположения: после разреза `tool-api` на `app/api/` относительные пути уже один раз
указывали в пустоту.

1. **Точный путь.** `docs/reports/95-ux-measurements.md` — файл; `docs/reports/` — каталог, файла
   он не называет. Карта, заявившая каталог, конфликта по файлу не даёт: она говорит
   «здесь появятся новые файлы», а какие именно — из тела не видно.
2. **Существующий файл.** Две карты объявили один и тот же существующий файл — вторая
   в `wait`, в причине её имя: «ждёт: файл «scripts/kanban_areas.py» занят картой t_…».
   Вторая карта того же файла — это не «параллельная работа», а конфликт слияния.
3. **Новый файл.** Путь, которого в репозитории ещё нет (отчёт со своим номером), —
   не конфликт: файла нет, сливать нечего. Одинаковый новый путь у двух карт виден
   в `--plan` в парах как предупреждение, но запуск не блокирует: дубль номера ловит
   ревьюер.
4. **Сгенерированные файлы.** Пересобираются генератором, а не сливаются руками. Их
   пересечение — не запрет, а пометка «решить пересборкой»: обе карты стартуют, в плане
   появляется строка `rebuild`. Список — `GENERATED_FILES` в `scripts/kanban_areas.py`:

   | Файл | Генератор |
   |---|---|
   | `docs/README.md` | `scripts/build_docs_index.py` |
   | `contracts/openapi.json` | `scripts/openapi_snapshot.py` |

5. **`tests/…`** участвует в пересечении по файлу (общий тест — такой же конфликт), но
   область не задаёт: тест едет за тем, что проверяет.

### Область как ярлык (для отчёта)

Область печатается рядом с картой, чтобы человек видел, что происходит на доске:

1. раздел «Область» в теле: `app/pages/…`, `static/…` → **экраны**;
   `app/api/<домен>…`, `app/routers/<домен>…` → **API: <домен>** (`schedule` →
   расписание, `money` → деньги); остальной `app/…` и `services/<сервис>/app/…` →
   **API**; `scripts/`, `deploy/`, `.github/`, `db/`, `config/`, `docs/` →
   **инфраструктура**;
2. если раздела нет — по ключевым словам заголовка (экран, Mini App, webapp → экраны;
   роутер, эндпоинт, API → API);
3. если не вышло — **не определена**, и рядом печатается причина: «раздел «Область» пуст»
   или «раздел «Область» есть, но ни один путь не задаёт область». Молчаливого `null`
   больше нет; при этом сама по себе неопределённая область запуск не блокирует.

Путь `tests/` первым в разделе разбор не обрывает: область берётся по следующему
продуктовому пути. Регресс-случай — карта `t_9ca07ae1`, у которой
`services/tool-api/app/files_store.py` раньше не попадал ни в одну ветку и область
выходила `null`.

### Что делает человек

1. Перед тем как взять карту, посмотреть, чем занята доска:
   `env -u PYTHONPATH .venv/bin/python scripts/kanban_areas.py --board teatrsvoi`.
2. В разделе «Область» перечислять **точные файлы**, а не каталоги: каталог правило
   не защищает.
3. Если в работе уже есть карта с тем же файлом — **не начинать**: карта ждёт, пока файл
   освободится.

### Что делает сторож канбана

`~/.hermes/scripts/kanban-watchdog.sh` перед вызовом диспетчера выполняет
`scripts/kanban_areas.py --apply --held <файл>`:

- ready-карты, чей существующий файл занят картой в `running`, не запускаются — сторож
  переводит их в `scheduled` с причиной «ждёт: файл «…» занят картой t_…»; диспетчер
  такие карты не берёт;
- когда файл освободился, сторож возвращает придержанные карты в `ready` (`unblock`) —
  ждать руками ничего не нужно. Отпускает он только те карты, что придержал по правилу:
  причина в журнале должна начинаться с «ждёт: файл …» или «ждёт: область …». Карта,
  отложенная по времени («ждёт до 12:00 — окно релиза»), сторожем не трогается;
- если в `running` уже оказались две карты с одним файлом, сторож пишет это в сводку,
  а проверка ниже падает.

`--plan` отдаёт, кроме `start/wait/hold/release`, два поля: `pairs` — по каждой паре
«можно вместе / конфликт по файлу X / пересобрать» и `rebuild` — сгенерированные файлы,
объявленные несколько раз.

### Проверки

| Что | Чем |
|---|---|
| карты в работе с файлами и областями, причина «не определена» видна | `scripts/kanban_areas.py` (код 1 при конфликте по файлу) |
| две карты на один существующий файл в `running` | `scripts/check_kanban_cards.py` — печатает файл и обе карты, падает |
| разные файлы одного каталога, новый файл, сгенерированные, разбор карт | `tests/unit/test_kanban_areas.py` (на фикстуре, без спавна) |

Правило не ловит того, чего не объявили: карта, написавшая «Область: `docs/reports/`»
каталогом, файлов не называет, и пересечение с ней не считается. Это видно в отчёте
(«пишет: …» печатает только точные файлы), и лечится телом карты, а не догадкой скрипта.

## 7c. Роли в конвейере (02.11.2026)

Карту двигают четыре профиля Hermes, у каждого своя зона и свои запреты. Правило общее:
**роль не делает работу соседа** — иначе пропадает контроль, ради которого роль заведена.

| Роль | Профиль | Что делает | Чего не делает | Когда подключается |
|---|---|---|---|---|
| воркер | `worker-feature` | пишет код, миграции, тесты и документы по телу карты; ветка `wt/<task-id>`, коммит, push ветки | не коммитит и не пушит в `main` (§7a п.9), не мержит, не закрывает карту сам | карта в `ready` |
| ревьюер | `worker-review` | читает дифф до отчёта исполнителя, гоняет полный гейт, вливает карту в `main`, публикует `main`, закрывает карту | не переписывает работу воркера вместо замечаний, не принимает продуктовых решений | карта в `review` |
| уточнятель | `specifier` | превращает расплывчатую карту в тело с областью, критериями и границами; задаёт вопросы владельцу | не пишет код и не оценивает сроки | карта в `triage` или пустое тело |
| техлид | `architect` | мерит дрейф архитектуры (`scripts/arch_drift.py`), приносит отчёт с числами и предложениями с ценой, ревью границ на картах класса `architecture` | **не мержит карты**, **не принимает продуктовые решения**, не правит код и не закрывает чужие карты | понедельник 10:00 (задание планировщика), карта с меткой архитектуры, сверка перед релизом |

### Техлид: отчёт вместо правки

Техлид — не «ещё один воркер». Его продукт — карта-отчёт и файл в `docs/reports/`
(форма — скилла `architect-drift-review`): снимок, числа «метрика → сейчас → прошлый
замер → порог → статус», дельта, три предложения максимум с ценой каждого и раздел
«что не трогал и почему». Замер — `scripts/arch_drift.py`: размеры файлов сервисов
(>500 — повод, >800 — правка требует ADR), дубли функций внутри сервиса, прямые импорты
между сервисами, чтения окружения вне `settings.py`, номера миграций, публичные маршруты
без пометки в `config/public-routes.txt`, расхождение снимка OpenAPI, тесты без `assert`.
Это отчёт, а не гейт: скрипт всегда возвращает 0, за порогом — предупреждение.

Что решает кто:

- **техлид** называет цену и вариант («разрезать `api/schedule.py` на три роутера — 4–6 ч,
  риск конфликтов с двумя открытыми картами»);
- **владелец** говорит «делаем / не делаем» и выбирает приоритет;
- **воркер** делает выбранное по отдельной карте;
- **ревьюер** вливает и закрывает.

Предложение без цены (часы, риск, что сломается) — лозунг, а не отчёт. Больше пяти
предложений — шум. Появился соблазн «поправить, пока смотрел» — это выход из роли:
техлид не правит код.

### Еженедельный замер

Задание планировщика (понедельник 10:00, после сводки конвейера) запускает
`scripts/cron/arch_drift_weekly.py` (`no_agent`). Если хоть одна метрика за порогом —
на доске `teatrsvoi` появляется карта с assignee `architect`, в теле числа и команда
замера; карта идемпотентна по дате. Если всё в норме — тишина: молчание означает
«дрейфа нет», а сломанный замер печатает причину и отдаёт код 1.

## 9. Приоритеты и порядок очереди

Дата: 01.11.2026. Правило выросло из разбора доски: `priority` был числом без
определения — одна карта получила 5 «за безопасность», другая 5 «потому что важная»,
и очередь каждый раз обсуждалась заново.

**Приоритет ставится по классу, а не «на глаз».** Сначала определяется класс
(что произойдёт, если не сделать), и только он задаёт число. Числа вне набора
`{1,2,3,4,5}` и `0` — не приоритет, а его отсутствие: такая карта попадает в отчёт
`scripts/kanban_queue.py` и должна получить класс.

| Класс | Число | Что это | Примеры из этого репозитория |
|---|---|---|---|
| **P0** | 5 | Безопасность, потеря данных, прод недоступен. Вне очереди: владелец узнаёт сразу | бэкап БД не запланирован (`backup.sh` вручную); открытый вебхук n8n; секреты в git |
| **P1** | 4 | Сломан пользовательский путь: Mini App, отметки занятости, деньги, расписание | экран Mini App отдаёт 500; занятость читается зеркально; сумма в бюджете считается неверно |
| **P2** | 3 | Запланированное развитие: новые возможности, соглашения, инструменты разработки | агентный режим A-1…A-5; ежедневный отчёт «требует вас»; правило WIP по областям |
| **P3** | 2 | Гигиена: документация, рефакторинг, чистка | ревизия `docs/`; перевод `/webapp/person` на общую оболочку; роль техлида |
| **P4** | 1 | «Когда-нибудь»: идеи без критериев | карта без области и критериев приёмки — либо получает критерии, либо архивируется |

Как выбирать класс, если тянет поставить «на глаз»:

1. **Данные или доступ под угрозой?** → P0. Не «важно», а «можно потерять».
2. **Человек не может закончить обычное действие?** (отметить занятость, увидеть
   деньги, открыть Mini App, посмотреть расписание) → P1.
3. **Ничего не сломано, но это запланированная работа?** → P2: новая возможность,
   соглашение, инструмент разработки.
4. **Ничего не сломано и не новое, а навести порядок?** → P3: документация,
   рефакторинг, чистка.
5. **Нельзя сформулировать, что изменится и как это проверить?** → P4, и карта
   получает критерии или уходит в архив. Держать её в P2 нельзя: она занимает
   место в очереди, не двигаясь.

### Порядок очереди

Диспетчер берёт карты так: `priority DESC, created_at ASC` — сначала высший класс,
внутри класса старшая карта. Сроков и дедлайнов нет: класс важности отвечает
на вопрос «что раньше», а не «к какому числу».

Посмотреть очередь одной командой:

```bash
env -u PYTHONPATH .venv/bin/python scripts/kanban_queue.py --board teatrsvoi
env -u PYTHONPATH .venv/bin/python scripts/kanban_queue.py --board teatrsvoi --json
env -u PYTHONPATH .venv/bin/python scripts/kanban_queue.py --board teatrsvoi --strict
```

Скрипт печатает готовые к запуску карты (`ready`) и ждущие родителей (`todo`)
в порядке диспетчера, отдельно — карты вне очереди (`blocked`, `scheduled`,
`running`, `review`), объясняет числами, почему следующая карта именно эта,
и перечисляет карты без класса. `--json` — для машинного чтения, `--strict` —
код 1, если есть карта без класса (для гейта).

Приоритеты карт в `done` и архиве не переписываются: история не меняется.
Правка приоритета живой карты — `hermes kanban edit <id> --priority <число>`,
и каждая такая правка перечисляется в отчёте карты, которая наводила порядок.


## 10. Один публичный репозиторий: история, workflows и доставка на прод

08.11.2026 репозиторий сведён к одному — **публичному** `tentakleebeast-beep/teatrsvoi_bot`.
Приватный `teatrsvoi_bot-private` выведен из работы и переведён в архив GitHub: он больше
не участвует ни в CI, ни в выкате, ни в документах. Полная внутренняя история сохранена
в `git bundle` (`~/svoi-private-backups/bundles/`) и в архиве GitHub.

- **Публичная история — один коммит.** Внутренняя история не переписывалась и наружу
  не вышла. Восстановить файл «из истории» можно только из bundle:
  `git clone ~/svoi-private-backups/bundles/svoi-private-2026-11-06.bundle restore && git -C restore show <sha>:<путь>`.
- **Почему ссылки на коммиты в реестрах без обратных кавычек.** В публичном дереве
  старых SHA нет, и `scripts/check_registers.py` справедливо краснел бы на «коммита
  нет в истории». Поэтому в публичном дереве SHA старых коммитов записаны текстом
  с пометкой «в приватной истории», а не ссылкой в backticks. Новые коммиты
  публичной истории ссылаются как обычно.
- **Обезличивание.** Дерево публикуется после прогона Ш-02…Ш-04 плана 129: дампы
  недопустимы (сторож `tests/unit/test_secrets_not_committed.py`), chat_id, IP и адреса —
  плейсхолдерами; SHA в реестрах — текстом, как описано выше.
- **Self-hosted раннер не возвращается.** На публичном репозитории с триггером
  `pull_request` он — исполнение кода из форка на прод-машине. CI идёт на `ubuntu-latest`,
  минуты для публичных репозиториев не тарифицируются. Раннер снят 08.11.2026 целиком.

### Что из `.github/workflows` живёт в публичном репозитории

В публичном репозитории — `tests.yml` (CI) и пять ручных прод-операций. Все они
запускаются только `workflow_dispatch`, автоматического деплоя нет. Секреты
(`DEPLOY_SSH_KEY`, `LLM_API_KEY`, `TELEGRAM_TOKEN`) и переменная `DEPLOY_HOST` заданы
в настройках этого же публичного репозитория (Actions → Secrets and variables).
Проверка: `gh api repos/{owner}/{repo}/actions/secrets`.

| Workflow | Что делает | Запуск |
|---|---|---|
| `tests.yml` | CI: линтер, тесты, браузерные проверки на `ubuntu-latest` | push / pull_request |
| `deploy.yml` | ручной выкат тега на прод, откат при провале | `workflow_dispatch`, `dry_run` по умолчанию |
| `set-llm-key.yml` | запись `LLM_API_KEY` в `/opt/svoi/.env` | `workflow_dispatch` + `confirm=apply` |
| `set-env-value.yml` | запись несекретной переменной в `.env` | `workflow_dispatch` + `confirm=apply` |
| `repair-schema.yml` | DDL-миграции из репозитория на боевую базу | `workflow_dispatch` + `confirm=apply` |
| `backup-timer.yml` | включает и проверяет `svoi-backup.timer` | `workflow_dispatch` + `confirm=apply` |

Диагностика и разовые выгрузки (`diagnose`, `db-audit`, `answer-feedback`, `notify-owner`,
`check-menu`, `probe-webapp-auth`, `people-map`, `participants-*`) остались локальными
скриптами: с 08.11.2026 SSH с рабочей машины до прода проверен и работает, отдельные
workflow для них не нужны. `feedback-watch` заменён локальным cron.

**Доставка на прод.** Прод `/opt/svoi` берёт код из этого же публичного репозитория:
`origin = https://github.com/tentakleebeast-beep/teatrsvoi_bot.git`. Выкат идёт
`deploy/release.sh <версия> --apply`: он ставит тег, пушит его в публичный репозиторий,
запускает `deploy.yml` там же и ждёт результат. Правило не меняется: прод обновляется
только по команде владельца.

**Правило по триггерам.** Ни один workflow с секретами не должен стартовать по
`pull_request`: единственный такой триггер — у `tests.yml`, секретов у него нет.
Прод-workflow'ы — только `workflow_dispatch`.
