# 53. Дисциплины и форма поиска окон

Дата: 27.10.2026. Уточнения заказчика: педагоги преподают конкретные дисциплины,
режиссёр приходит «по возможности». Плюс форма поиска окон — главный вход
в назначение события.

---

## 1. Дисциплины в профилях

| Человек | Преподаёт | Может посещать |
|---|---|---|
| Крылов Виктор | актёрское мастерство | — |
| Попова Света | музыка | актёрское мастерство (как участник) |

Модель (миграция `029`):

```
discipline            актёрское мастерство, музыка, танец, сценическая речь
participant_discipline  participant_id + discipline_id + relation (teacher | student)
event_plan             + discipline_id
```

Связь «преподаёт / посещает» — главное. Без неё Попова либо всегда обязательна
на всех тренингах, либо нигде: оба варианта неверны.

### Как это влияет на состав

```
тренинг по музыке   → обязательна Попова, Крылов не нужен
тренинг по актёрскому → обязателен Крылов; Попова может прийти участником
тренинг без дисциплины → добавляются все педагоги, с предупреждением
```

Проверено тестами: педагог другой дисциплины в состав не попадает.

---

## 2. Режиссёр: «по возможности», а не «по желанию»

Формулировка заказчика: режиссёр приходит, если может — это **факт**, который
фиксируется, а не опция в интерфейсе.

В карточке так и показывается:

```
Режиссёр: Крылов Виктор — присутствует (по возможности)
Режиссёр: Крылов Виктор — не присутствует (по возможности)
```

Присутствие определяется просто: если режиссёр есть в списке участников — да.
Автоматически он не добавляется: окна ищутся в первую очередь по актёрам.

---

## 3. Форма поиска окон

`/webapp/search` — главный вход для организатора:

| Поле | Значение по умолчанию |
|---|---|
| Что назначаем | репетиция (репетиция / показ / тренинг / аренда) |
| Дисциплина | показывается только для тренинга |
| Сколько нужно часов | 2 |
| С даты / по дату | сегодня … +6 дней |
| Помещение | основное (сцена) |
| Участники | чекбоксы с поиском по имени и роли |

Что происходит после «Найти окна»:

1. `POST /webapp/slots` — расчёт по занятости людей, событиям календаря, дороге
   и занятости помещения;
2. список вариантов: день, часы, сколько участников и событий учтено;
3. под каждым вариантом — «Назначить»;
4. `POST /webapp/preview` — карточка с проверками (люди предупреждают,
   помещение блокирует);
5. подтверждение → `POST /webapp/assign` — календарь, расписание, уведомления.

Форма не придумывает своего API: она использует те же расчёты, что и бот.
Правило `docs/plans/37` §2 — «дом + вход»: дом поиска окон — эта форма, чат распознаёт
намерение и даёт вход (ссылку или карточку); отдельный кнопочный путь в чате для формы
не нужен (П-1).

---

## 4. Чего форма пока не умеет

| Чего нет | Почему |
|---|---|
| Чекбоксы для тёзок внутри формы | сейчас форма показывает всех людей списком; при вводе «Витя» видно трёх — выбор делается галочками в том же списке |
| Проект / спектакль в запросе | поле готово в API (`project_id`), в форме появится вместе с выбором названия события |
| Сохранение последнего выбора | следующий шаг: запомнить «мои обычные участники» |
| Календарная сетка с подсветкой окна | визуализация, отдельная задача |

## 6. Найденный по ходу дефект

Форма не работала вовсе: JS не парсился. Причина — экранирование переводов строк
в шаблонных строках: `lines.join("\n")` попадал в страницу как реальный перевод
строки, и скрипт падал целиком (`boot is not defined`).

Поймано проверкой `node --check` на отданной странице — обычные тесты API этого
не видят, потому что страница отдаётся как текст. Добавлю `node --check`
в проверку страниц как отдельный шаг.
