## 1. Цели тестирования

1. **Деньги не врут.** Ни один ответ про бюджет не должен расходиться с БД; ни одна операция не
   должна задваиваться или теряться.
2. **Права не текут.** Актёр труппы не получает доступ к чужим данным ни через бота, ни через API.
3. **Разбор текста предсказуем.** Набор фраз-эталонов даёт один и тот же результат после любого
   изменения правил, модели или промпта.
4. **Деградация управляемая.** При падении n8n / LLM / Google бот отвечает формами, а не молчит
   и не выдумывает.
5. **Ручная правка файла не ломает бота.** Расхождение фиксируется, а не «подкручивается».

## 3. Требования к тестам (обязательные)

### 3.1 Изоляция
- Отдельная БД `svoi_test`, схема накатывается из `db/init/*.sql` при старте сессии
  (`tests/conftest.py::test_db`).
- Каждый тест очищает таблицы после себя (`TABLES` в `conftest.py`), поэтому порядок не важен.
- Google Sheets и Calendar **не вызываются** в тестах: клиент подменяется через `monkeypatch`
  (`test_calendar_api.py`).
- Секреты не нужны: `TOOL_API_TOKEN=test-token`, Google-клиент замокан.
- Часовой пояс — Самара UTC+4 (`TZ_OFFSET_HOURS=4`); `freezegun` не подключён — даты в тестах
  фиксируются параметрами (`today=date(...)`).

### 3.2 Детерминизм
- Никаких `sleep`; ожидание — только через явные фасады.
- LLM в тестах **не вызывается**: тесты каскада передают `category_llm`/`confidence` явно.
- Отдельного «offline-набора» из 20 запросов и кассет нет — при смене модели прогоняется вручную.
- Порядок тестов не влияет на результат.

### 3.3 Понятность падения
- Имя теста описывает правило (по-русски), например
  `test_повторный_запрос_не_создаёт_вторую_операцию`.
- В сообщении об ошибке — входные данные и ожидаемое/фактическое.

### 3.4 Скорость
- Факт: весь набор — **37.16 с** на локальной машине с поднятым Postgres (интеграционные тесты ходят в БД).
- Цели «unit до 15 с, integration до 90 с, E2E до 5 мин» перевыполнены; E2E-набора нет.

### 3.5 Обоснованность теста

- У каждого нового теста в имени или docstring — ID требования (`FR-…`, `UC-…`), дефекта
  (`S-…`, `C-…`, `B-…`), обращения (`№N`), вопроса (`V-…`), шага (`Ш-…`) или намерения (`INT-…`).
  Без ID тест не принимается: `scripts/test_audit.py --strict` — в проверках релиза.
- Варианты одного правила — параметры одного теста, а не копия функции; слияние не должно
  терять ни одного проверяемого факта.
- Отчёт об аудите и правило — `docs/reports/76-test-audit.md`.

### 3.6 Покрытие
- Цель: `tool-api` ≥ 80 %, парсеры ≥ 95 %, gateway ≥ 60 %.
- **Фактически порог не проверяется**: в CI есть `--cov=services --cov-report=term-missing`,
  но нет `--cov-fail-under`; отчёт по `gateway` не собирается.
- Покрытие — индикатор, а не цель: обязательны тесты на все инварианты `docs/architecture/11` и все
  ветки обработки ошибок из `docs/architecture/17`.

## 4. Сценарии по подсистемам

### 4.1 Регистрация и доступ
1. Незнакомый `chat_id` → «вы не зарегистрированы», доступа к данным нет. — есть (код)
2. Владелец (`ADMIN_CHAT_ID`) → получает `admin` без кода, запись создаётся один раз. — есть (код), автотеста нет
3. Код `org` → выбор себя из списка → `chat_id` привязан к существующей записи, дубля нет. — есть (`test_registration.py`)
4. Код истёк / использован / неверный → три разных сообщения, попытка в аудите. — есть
5. «Меня нет в списке» → `pending`, админ получает уведомление с кнопками. — код есть, тест только на `pending/approve`
6. Повторная регистрация тем же `chat_id` → отклоняется. — есть
7. `person_key` занят → предложение выбрать из списка, а не создать второй аккаунт. — есть

### 4.2 Права (RBAC + capabilities)
8. `troupe` → `/admin/invite` 403, `/tools/participants` 403, свои возможности доступны. — есть
9. `org` → бюджет читает и пишет, чужие заметки не видит. — бюджет есть; заметок нет
10. Личная выдача `budget.read` без роли `org` → работает только эта возможность. — есть (`test_admin_panel.py`)
11. Личный запрет перекрывает роль (override `false` сильнее роли). — проверяется view, отдельного теста нет
12. Множественные роли объединяются, пересечение не дублирует возможности. — есть (view, тест ролей)
13. Аудит фиксирует `access.denied` с указанием capability. — код есть, автотеста нет

### 4.3 Бюджет — разбор
14. Эталонный набор (обязательный, растёт с каждым багом):

| Фраза | Ожидание | Факт |

## 5. Данные для тестов

Фактически отдельного каталога `tests/fixtures/` **нет**. Данные создаются внутри тестов:

- интеграционные тесты вставляют участников, операции и взносы напрямую в `svoi_test`;
- unit-тесты используют параметризацию фразами (`test_rules_budget.py`, `test_rules_availability.py`);
- уменьшенных копий `СВОИ 2025.xlsx` и `Расписание СВОИ.xlsx` в репозитории нет;
- кассет LLM (`tests/fixtures/llm/`) и эталонов листов (`tests/fixtures/sheets/`) нет;
- реальные данные театра в тестах **не используются**.

Это осознанный компромисс на текущем этапе, но он означает: импорт xlsx, отчёты и Sheets
проверяются только руками. Появление `tests/fixtures/` — условие для system-тестов.

## 6. Организация и CI

Фактическая структура:

```
tests/
  conftest.py      тестовая БД svoi_test, чистка таблиц, клиент, auth, маркеры по каталогу
  unit/            34 файла, 300 тестов
  integration/     35 файлов, 237 тестов
  system/          отсутствует
  contract/        отсутствует
```

`pytest.ini` объявляет маркеры `unit`, `integration`, `system`; `conftest.py`
(`pytest_collection_modifyitems`) проставляет `unit`/`integration` по пути файла — поэтому
`pytest -m unit` и `pytest -m integration` работают.

```bash
pytest -q                    # всё: 537
pytest -q -m unit            # 300
pytest -q -m integration     # 237 (нужен Postgres svoi_test)
pytest -q --cov=services --cov-report=term-missing
```

CI (`.github/workflows/tests.yml`) фактически:
1. job `lint`: `ruff check .` и `compileall` по `services`, `scripts`, `tests`;
2. job `types`: `mypy` (строгий режим, пилот из пяти чистых модулей — `pyproject.toml`);
3. job `deadcode`: `scripts/check_deadcode.py` — vulture и deadcode с конфигом из
   `pyproject.toml`; декораторы-обработчики не считаются мёртвым кодом, известные
   находки лежат в `config/deadcode-baseline.txt` (зелёно), новая — красит job;
4. job `tests`: Postgres 16 + `pytest -q` с покрытием `services` и `scripts`;
5. job `webapp`: браузерные тесты Mini App (`SVOI_WEBAPP_TESTS=1`, Chromium);
6. job `images`: `docker build` обоих сервисов, затем запуск `tool-api` с Postgres
   (пустая база, схема накатывается `alembic upgrade head` тем же образом), ожидание
   `/health` и smoke-запрос `/tools/categories`
   с сервисным токеном. Красный job означает, что образ собирается, но не работает.

**Чего в CI нет**:
- нет `mypy` на всём репозитории: строгий режим включён только для пилота
  (R-7, `docs/reports/100`), остальные модули подключаются по мере разбора;
- нет job `pytest -m system` и вообще system-тестов;
- нет `--cov-fail-under`, то есть красный прогон по покрытию невозможен;
- contract-проверок нет;
- образы не публикуются и не выкатываются: `images` только проверяет сборку и запуск.

## 7. Definition of Done для задачи

Задача не закрыта, если:
1. есть тесты на новое поведение и они падают без изменения кода;
2. пройдены все инварианты `scripts/check_invariants.py`;
3. обновлён соответствующий документ (`docs/architecture/11`, `docs/architecture/17` или контракт);
4. для исправленного бага добавлен регрессионный тест;
5. ручной чек-лист приёмки (если затронут Telegram или Google) пройден.

Прогон: `pytest -q` · `pytest -q -m unit` · `pytest -q -m integration`.

**Что тесты уже нашли (и это не гипотезы):**
1. `audit_event.source` на чистой установке — `NOT NULL DEFAULT '{}'`, в работающей базе — nullable.
   Любая запись без `source` падала бы на новой базе. Миграция `013` выровняла схемы, `audit()`
   теперь всегда пишет объект.
2. `ON CONFLICT (idempotency_key)` не работает с частичным индексом — заменили на обычный
   уникальный (NULL в Postgres не конфликтует сам с собой).
3. В фикстуре без строки `participant_role` у человека нет ни одной возможности — тест на запись
   в бюджет падал с 403. Это же объясняет, почему у Маши «панель не открывалась», когда роль
   была только в поле `participant.role`.
4. `016_availability_invert.sql` была не идемпотентна: повторный накат снова инвертировал
   занятость. Тестами не ловилось, потому что схема накатывалась один раз за сессию.
   Исправлено 26.10.2026: инверсия защищена меткой в `migration_marker`, повторный запуск

## 8.2 Каких уровней не хватает

### System / E2E (0 тестов)

Нужны сценарии «сообщение → ответ» с фейковым Telegram и фейковым n8n. Минимум:

1. `/start` незнакомца → просьба кода; `/start` владельца → bootstrap и меню.
2. Код → выбор себя → привязка → меню с правильным числом возможностей.
3. «Меня нет в списке» → pending → кнопка «Подтвердить» → active.
4. «расход 3000 на реквизит» → черновик → «Записать» → строка в БД и сообщение «Записано».
5. Повторное нажатие «Записать» → «Эта операция уже записана».
6. «занят в среду после 18» → «Верно?» → «Записано».
7. «Мои взносы» у актёра и у человека без `budget.read.self`.
8. n8n недоступен → ответ формами, а не молчание.
9. Нет прав на бюджет → отказ, запись не создаётся.

Без этого уровня регрессии диалогов (состояния FSM, callback-данные, порядок хендлеров)
ловятся только вручную. `tests/unit/test_gateway_routing.py` проверяет только регистрацию
и порядок хендлеров, но не диалог.

### Contract (0 тестов)

Нужны golden-файлы и `jsonschema`:

1. `n8n` router: `{intent, answer, category}` — допустимые значения и отсутствие лишних полей.
2. `n8n` parse-budget: `{ok, draft{...}, flags[]}` — совместимость с `tool-api` (сейчас расходятся
   названия категорий: «Реквизит и декорации»/«Костюмы» в JS против «Реквизит и костюмы» в БД).
3. `tool-api`: `/tools/budget/parse`, `/tools/budget/commit`, `/tools/availability/parse`,
   `/tools/intent/resolve` — обязательные поля ответа.
4. Sheets: заголовки листа `Транзакции` (14 колонок) и листа `Сверка`.

### Приёмочный чек-лист

Отдельного файла нет. Минимум перед выкаткой: регистрация по коду, запись расхода и дохода,
отмена черновика, занятость текстом и формой, «Мои взносы», бюджет и расписание, админ-панель,
сверка, отчёты.
